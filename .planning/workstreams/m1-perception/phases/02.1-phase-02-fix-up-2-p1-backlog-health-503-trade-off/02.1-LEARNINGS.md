## Decisions

### D-01: Fail-soft visibility — orchestrator step 7.5 else branch (BUG-7 fix)
撤 Supabase service_key 路径之前完全静默 (Phase 02 Inj 3 暴露). 选择 light-weight else-branch 加 audit log + Sentry breadcrumb, 不引入 settings split, 不动 /healthz semantics.

**Rationale:** 备选 (a) 拆 settings 为 strict/non-strict 增复杂度且改 D-22 trust boundary; (c) 让 /healthz 反映 mirror disabled 会让 IETF probe 语义漂移. else branch 是 surgical fix, 不打破 D-12 fail-soft 主契约.
**Source:** 02.1-CONTEXT.md (D-01) + 02.1-01-PLAN.md frontmatter must_haves

### D-02: chaos Inj 3-v2 是 BUG-7 闭环 gate (不是 unit test)
mock_sentry 在 unit test 里能 assert add_breadcrumb 调用, 但**不能保证** Sentry server 真收到 + UI 真显示. Plan 02.1-01 把 unit test pin 代码 contract, chaos 真在 prod 撤 secret 才算 closure.

**Rationale:** Phase 02 LEARNINGS L7 "SESSION 20 E2E 自我欺骗" 反例 — 这次 plan 阶段就先 codify "chaos 是 closure gate, 不允许只靠 unit test".
**Source:** 02.1-CONTEXT.md (D-02) + 02.1-01-PLAN.md frontmatter

### D-03: 独立 ControlAuthMiddleware (不 import scan.py)
`/control/*` 是 scheduler 状态机控制面, `/scan` 是 scanner 触发面. 两者**关注点不同** (state-machine ownership vs scanner-trigger ownership), 即便 HMAC 算法相同, middleware 各自 inline 实现, 不共享 import.

**Rationale:** Phase 03+ 想给 /control/* 加额外 audit 钩子 (例如 admin-action audit log) 时, 改 control.py 不会污染 scan.py 的 trigger 语义. 02.1-RESEARCH Area 3 推荐 B.
**Source:** 02.1-CONTEXT.md (D-03) + 02.1-02-PLAN.md PATTERNS

### D-04: unpause 清 failure_counter=0 (clean restart 语义)
PAUSED → RUNNING 的状态转换不只翻 state 字段, 也必须把 `_failure_counter` 清零. 否则 daemon 重启后还停在边缘状态, 下次 1 个失败就再次 PAUSED.

**Rationale:** "已知 PAUSED 的根因已修复" 时 ops 期望干净重启. counter 不清会让 ops 的"修完了"心智模型与 daemon 内部状态不一致.
**Source:** 02.1-CONTEXT.md (D-04) + 02.1-02-PLAN.md frontmatter

### D-05: 两 endpoint health pattern — /health (IETF strict) + /healthz (always-200)
不简单"degrade /health → 永远 200" — 那会让 Better Stack 外部探针失能. 也不"换 TCP probe" — 那会让 Fly machine 在 daemon 卡死但 TCP listener 还活时不切流量. 选择 split: `/health` 留 IETF strict 给 Better Stack, `/healthz` 永远 200 给 Fly probe.

**Rationale:** Better Stack 监控用户体验 (Polymarket dashboard 用户看到的是 IETF strict 503). Fly machine probe 决定流量路由 (要尽量保持流量, daemon 内部小问题不该切流量, 让告警链路负责). 两者关注点不同.
**Source:** 02.1-CONTEXT.md (D-05) + 02.1-03-PLAN.md PATTERNS

### D-06: /healthz body 与 /health 共享 schema (full mirror, 不简化)
原选项是 /healthz body 只返 `{"ok": true}`, 但被否定. 决定: /healthz body shape 与 /health 完全一致 (4 checks dict + status + serviceId + version + releaseId), 只 HTTP status code 不同. 这样未来加新 check (e.g. R3 cron 监控) 自动 propagate 到两边.

**Rationale:** 单一 source of truth — `_build_health_checks()` 共享 helper. 否则 schema 分叉, 长期会 drift.
**Source:** 02.1-CONTEXT.md (D-06) + 02.1-03-PLAN.md PATTERNS

### D-07: Phase closure 必含 (a) 教学增量, (b) VALIDATION.md frontmatter flip, (c) 凭证 reflection
Phase 末 Plan 04 不是可选, 是 phase-level closure 的硬要求. 不允许"代码改完就推 next phase". 三件套确保 audit trail 闭环.

**Rationale:** Phase 01.1 / Phase 02 都遵守这个 pattern (07-观察市场.md / 08-生产化部署.md 是 anchor). 这是 plan-code drift 防范纪律的延伸 — closure 留 chain 防止下次 audit 时回不去.
**Source:** 02.1-CONTEXT.md (D-07) + 02.1-04-PLAN.md frontmatter

### D-22 reuse: 复用 POLYARB_SCAN_SHARED_SECRET (不引新 env var)
Plan 02.1-02 的 `/control/*` HMAC 使用同一 SCAN_SHARED_SECRET, 不新建 `POLYARB_CONTROL_SHARED_SECRET`. 14 个 Fly secrets 不增加.

**Rationale:** /scan 和 /control/* 共享同一 trust boundary (都是 prod ops 凭 secret 触发), 双 secret 设计是无价值的复杂度. RESEARCH Area 6 A2 评估 LOW 风险.
**Source:** 02.1-02-PLAN.md frontmatter + 02-LEARNINGS.md D-22 历史

## Lessons

### L1: fail-soft contract 与 Sentry breadcrumb upload 有微妙交互
mirror_enabled=False 路径 fail-soft 不抛 exception → Sentry SDK breadcrumb buffer 里那条 mirror crumb **永不上传** (Sentry 是 event-triggered upload, 没 event 不发 crumb). Plan 02.1-01 truth 2 在 prod 永远不可观测 — design-unreachable.

**Context:** Inj 3-v2 跑完后, 拉 PYTHON-A event 200 breadcrumbs 全扫确认 0 条 category=mirror. plan-checker 阶段应该 catch 到 "truth 在 prod 是否可观测" 这个 lens — 这次漏了. 修法 A (mirror 成功路径也 emit crumb) 入 Phase 02.2 backlog.
**Source:** 02.1-01-SUMMARY.md User Setup Required + 02-SOAK-LOG.md Inj 3-v2 段 "Truth 2 → design-unreachable"

### L2: bug 是依赖图不是孤立点 — cross-bug interaction 必须在 Wave 排序前看依赖
Inj 4 (BUG-8) 触发 daemon PAUSED → /health=fail → BUG-6 让 Fly proxy 切流量 → make unpause-prod 经 prod URL 不可达. **BUG-8 闭环依赖 BUG-6 闭环**.

**Context:** Plan 02.1-02 Inj 4 chaos 中实证 — endpoint code 完全 work, 但 prod 路径阻塞. 必须 ssh container localhost:8080 才能调通. Plan 02.1-03 修 /healthz 后, BUG-8 prod UX 才真闭环. 这种 cross-bug interaction 应该在 Wave 排序前 (plan-phase) 就识别, 不是 chaos verification 时撞上才发现.
**Source:** 02.1-02-SUMMARY.md Decisions Made + 02-SOAK-LOG.md Inj 4 段 "Cross-bug interaction"

### L3: dev .env 在 unit test 里会"渗透" — Settings() 加载 .env.file 默认覆盖测试预期
Plan 01 Task 1 RED 阶段, `Settings(...)` 直接读 `.env`, 让 dev 机器的真 Supabase + R2 keys auto-enable `supabase_mirror_enabled=True` → 测试 precondition 失败.

**Context:** 修法 = `_make_settings` 显式传 `supabase_url=""`, `service_key=SecretStr("")` etc 覆盖 .env 提供的值. 这是测试隔离, 不是 production 行为. pytest fixture 设计时容易忘掉这个 — 凡测试涉及 pydantic-settings 的项目都要 audit fixture 是否显式 nil 真凭证.
**Source:** 02.1-01-SUMMARY.md Deviations from Plan #2 (Rule 3 blocking)

### L4: pytest caplog 看不到 loguru — 项目用 loguru 时必须用 StringIO sink
Plan 01 Task 2 GREEN 阶段, orchestrator log 正确出现在 pytest stdout 但 `caplog.records` 空. 根因: loguru 默认不 propagate 到 stdlib logging, caplog 只看 stdlib handler.

**Context:** 修法 = test 里 `logger.add(StringIO(), ...)` 自建 sink, 跑完用 `getvalue()` assert + finally remove sink. 这个 pattern 对项目所有 loguru-based 模块通用. 已在 PATTERNS.md 中固化 (02.1-01-SUMMARY patterns-established).
**Source:** 02.1-01-SUMMARY.md Deviations from Plan #1 (Rule 1 bug)

### L5: Sentry API 是绕过 UI 翻找的正解 — 必须知道 region 路由 (EU vs US)
默认 `https://sentry.io/api/0/projects/` 返回 EU 账号空数组. Sentry self-hosted/region 路由让 EU org 必须 hit `https://de.sentry.io/api/0/...`. DSN host 的 `ingest.de.sentry.io` 是 region 信号.

**Context:** 拉 Sentry token 后第一次 curl 返空, 浪费了 ~3 分钟 debug. region 是从 DSN parse 出来的 ("de" between "ingest." and ".sentry.io"). 落进 verification-ownership memory: "Sentry API 自主验证必须先 parse DSN 拿 region 前缀".
**Source:** SESSION 23 中段 Sentry API debug + verification-ownership-2026-05.md memory

### L6: chaos cleanup 后 daemon 不会立即 self-heal — /health 滞后 chaos cleanup 几分钟
Inj #6-verification cleanup 后 (Gamma URL 恢复 + scheduler_interval 撤回), /health 仍返 503 一段时间 — `snapshot:last_status=fail` 直到下次 scheduled snapshot tick. 这是 sticky 设计 (snapshot 失败状态持久化在 SQLite, 不会因为 chaos cleanup 自动翻回 pass).

**Context:** 这是 prod 行为, 不是 bug — 但 SESSION 收尾时需要等. 教训: chaos verification 之后留够时间让 prod state 自然 converge (~6h scheduled snapshot interval), 不要立即看 /health 然后误判.
**Source:** SESSION 23 EOD final sanity + 02.1-03-SUMMARY.md (no fix needed)

### L7: Pyright 在 uv venv 项目里所有第三方 import 都 unresolved (false positive)
SESSION 23 每个 plan 都触发 Pyright diagnostics — `starlette`, `pytest`, `polyarb.*` 全 unresolved. 这是 Pyright 没看 `.venv/lib/python3.12/site-packages` 路径的 false positive, 不是真 import error.

**Context:** uv 项目用 `.venv/` 不是 venv (`venv/`), Pyright 默认 venv path 找不到. 修法是 pyproject.toml 加 `[tool.pyright] venvPath="."`, `venv=".venv"`. 但 Phase 02.1 不动 — 已是 Phase 02 期间的已知噪声, 推 Phase 02.2 修.
**Source:** SESSION 23 多次 Pyright diagnostic system-reminder (Plan 01/02/03 都有)

### L8: 在容器内跑 verification 比修复 Fly proxy 路径更快
Inj 4 chaos 撞 BUG-6 后, 用户选 "从 daemon 内部 ssh 调 unpause（绕过 Fly proxy）". 一条 `flyctl ssh sftp shell + flyctl ssh console -C` 30 秒搞定. 比另外两个方案 (手 sqlite3 改状态 / 等修 /healthz 上线) 快很多, 同时把 BUG-6 实证留作 Plan 03 的 input.

**Context:** Phase 02.1 是 fix-up phase, 多个 bug 同时 fix. 这种"绕过被 broken 的依赖, 在更内层验证"的 fallback 路径是 ops 标配, 应该作为 chaos plan 设计时的备选 (RESEARCH 时考虑 "如果 prod 路径阻塞了怎么 verify 这个 plan").
**Source:** SESSION 23 mid 用户选择 + 02.1-02-SUMMARY.md "PASS via fallback path"

## Patterns

### P1: 每个 fail-soft skip 路径都必须 emit (loguru INFO + Sentry breadcrumb) 双锚点
代码层面: skip-due-to-config 路径不抛 exception, 但必须留 audit trail. **双锚点** = loguru 行 (Fly log retention 5 天) + Sentry breadcrumb (跨 event 携带). 任一缺失都让"撤 secret 路径"成为黑洞.

**When to use:** 任何 fail-soft path (例如 mirror disabled / R2 disabled / network blip retry). 凡是"不该影响主流程但应该有 audit"的代码, 这个 pattern 是 default.
**Source:** 02.1-01-SUMMARY.md patterns-established + orchestrator.py step 7.5 else 分支

### P2: breadcrumb category 区分 config-state vs failure
`category="mirror"` (config state — disabled) ≠ `category="storage"` (failure — push 失败). 同一模块, 不同语义, 用不同 category 区分让未来 dashboard filtering 干净.

**When to use:** 同一模块多种 audit 信号时, 用 breadcrumb category 区分语义 (state vs error vs intent), 不要 overloaded 单一 category.
**Source:** 02.1-01-SUMMARY.md patterns-established

### P3: 每个 HTTP auth-protected subsystem 拥有自己的 BaseHTTPMiddleware
不要把多个不同关注点的 HMAC 校验逻辑塞到一个 shared middleware. 例: `/scan` 的 ScanAuthMiddleware 和 `/control/*` 的 ControlAuthMiddleware 各自 inline, 不互相 import.

**When to use:** HTTP 服务有多个 auth-protected subsystem 且未来可能演化时. 关注点分离比代码复用更重要.
**Source:** 02.1-02-SUMMARY.md patterns-established + RESEARCH Area 3 rec B

### P4: ISSUE-04 sentinel — 单元测试必须用 prod 实际发的 bytes
单元测试 `client.post(...)` 默认空 body 走 dict serialize 路径 (`b"{}"`), 但 prod `curl -X POST` (无 `-d`) 发的是 `b""`. HMAC 签名对 `b""` vs `b"{}"` 是不同结果. 必须有一个 sentinel test 直接传 prod 字节验证.

**When to use:** Makefile/CLI/shell 触发的 HTTP 端点, 单元测试需要明确 prod 字节流和 fixture client 字节流的差异并 cover 真 prod 字节.
**Source:** 02.1-02-SUMMARY.md patterns-established + Phase 02 plan 02 ISSUE-04

### P5: Helper-first refactor — handler shrinks to wrapper, logic moves to private helper
`/health` 加 `/healthz` 时不复制 check 逻辑, 而是抽 `_build_health_checks(store, settings, now_s) -> (checks, overall)` + `_build_health_body(...)` helper. 两 handler 都调 helper, 各自决定 HTTP status code.

**When to use:** 两个 endpoint share business logic 但 HTTP wrapping 不同时 (例: status code, body envelope, content-type). 先抽 helper 再加 handler, 避免 logic divergence.
**Source:** 02.1-03-SUMMARY.md patterns-established

### P6: VALIDATION.md frontmatter 是 Nyquist gate ledger
phase 末必须翻 `status: complete` + `nyquist_compliant: true` + `wave_0_complete: true` 三字段, **同时**翻 Sign-Off 全 [x] + Approval 时间戳. 不留半翻状态 (例: frontmatter 翻了但 Sign-Off 没翻 — 这是 plan-code drift 反例).

**When to use:** phase closure plan (一般是最后 plan). 让 Phase 02.1 frontmatter flip 跟 02-SOAK-LOG.md 三段 closure + planning-status zero drift 形成一致状态.
**Source:** 02.1-04-SUMMARY.md patterns-established + feedback_plan-code-drift-2026-05

### P7: 教学文档的 file:line 必须从落地后 src/* grep, 不允许从 RESEARCH.md 复制
RESEARCH.md 阶段写的 file:line 是估算 (e.g. "应该在 scan.py:60 附近"). plan 执行后, 真行号会漂移 (插入/删除新行后). 教学文档 09-生产化运维.md 21 个 file:line 引用全部从落地后的 `grep -n` 拿来, 不允许 RESEARCH 估算复制.

**When to use:** 任何教学文档 / 用户手册 / ops runbook 含 file:line 引用. plan 期间 RESEARCH 估算只用于决策讨论, 不用于 user-facing docs.
**Source:** 02.1-04-SUMMARY.md patterns-established

### S4: GHA 自动 deploy "57 秒"完成是无 code 改 docs commit 的 no-op deploy

**Impact**: 不是 bug, 是 Fly 的 ergonomics. 教训: 看 GHA 时间不要直接判断 "deploy 是否真发生" — 改 fly.toml 或 src/* 才会真 build/push image. 反过来 prod 一直在线说明 image 没变. Phase 02 期间也踩过同样坑.
**Source:** SESSION 23 中段 GHA poll 观察

### S5: macOS 本地 HTTPS_PROXY=http://127.0.0.1:7897 对 fly.dev TLS 行为异常
**Surprise**: SESSION 23 中段多次 curl https://polyarb-l1.fly.dev/... 返回 empty body 让 `python -m json.tool` 解析失败. verbose curl 显示 TLS handshake 在 Client/Server hello 后挂起.

**Impact**: 修法 = `curl --noproxy '*'` 绕开本地代理. 这是开发环境怪癖 (probably Clash/Surge HTTP proxy 处理 TLS handshake 有 bug). 教训: 任何 curl https://... 在本机 debug 时优先加 `--noproxy '*'` 避免代理干扰. Inj 4 阶段一度误判 BUG-6 已修 (其实是代理截断了 200 response). 落到 m1-perception 工具 reference memory 待写.
**Source:** SESSION 23 多次 curl debug + verbose handshake snapshot
