<decisions>
## Implementation Decisions

### #7 Fail-soft Visibility 修法

- **D-01:** **Option (b) — orchestrator audit log + Sentry breadcrumb (轻量)**。不动 settings 语义, 在 `src/polyarb/snapshot/orchestrator.py` step 7.5 入口加显式 audit log + `sentry_sdk.add_breadcrumb(category='mirror', level='info', message='mirror skipped: reason=<config-disabled|secret-missing|invalid-credentials>')`。下次出事时 Sentry event 会自动带这个 breadcrumb 作为 context, 不再黑洞。工作量预估 ~30 行 code + 2 测试。**拒绝 (c) drift check** 因为它与 #6 /health trade-off 决策耦合, 增加 plan 复杂度。**拒绝 (a) settings 拆分** 因为它过度工程, ~80 行改动且需要回归测试 settings 边界。

- **D-02:** **Verification = chaos injection 重跑 Inj 3 (撤 Supabase secret)**, 不允许只走 unit test。占 Phase 02 5-20 Inj 3 同款验证手段 — daemon log 必须真出现 "mirror skipped reason=secret-missing", Sentry breadcrumb 在下一次 capture event 可见。Phase 02 L7 自我欺骗教训贯彻。

### #8 Daemon Unpause Prod Endpoint

- **D-03:** **Option (b) — 新起 `/control/unpause` endpoint (HMAC, 专语义)**。在 `src/polyarb/http/` 新建 `control.py`, POST `/control/unpause` 接 `scheduler.unpause()` (codegraph 验证: `unpause` method 已存在 `scheduler.py:192` 但 0 callers, 这正是 bug 本质 — method 写完没接 HTTP)。HMAC 中间件复用 /scan 同模式。可作 future endpoint 同族基础: /control/pause / /control/status 后续按需加。工作量 ~60 行 code + 3 测试 + Makefile target `make unpause-prod`。**拒绝 (a) /scan action=unpause** 因为 /scan 原语义"见发扫描", action 复载语义脏。**拒绝 (c) dashboard 按钮** 超 fix-up 范围, 推独立 plan。

- **D-04:** **Unpause 后 failure_counter 清零** (Option "清零")。Unpause = 重启动满血, counter 清 0 重新计。路径最直观。如果底层故障未真修, daemon 会快速再次累积到 PAUSED — 这是自我修正机制, 不是 bug。`scheduler.unpause()` 已有逻辑实现时验证 (`scheduler.py:192` 现有 method body), 若不清零下个 plan 加补丁。

### #6 /health 503 Trade-off

- **D-05:** **Option (c) — 拆两 endpoint: `/health` (IETF strict 503) + `/healthz` (Fly-friendly 200)**。`/health` 保持 IETF draft-inadarei-api-health-check-06 strict (Better Stack 外探针读, 503 是语义正确的告警信号, 是好事不是坏事)。新增 `/healthz` 总返 200, status 出现在 body — Fly machine health probe 用它做 wake/auto-restart 决策 (不会因 503 切流量)。`fly.toml` 改 `[http_service.checks]` 指向 `/healthz`。工作量 ~80 行 code + fly.toml 调整 + 4 测试 + 文档说明两 endpoint 语义。

- **D-06:** **/health response schema 保持 Plan 02-05 落地版本不变** (4 checks: snapshot age / status / supabase mirror / r2 upload)。`/healthz` body 是 `/health` 的简化版 + 总 200 包装。两者共享 underlying check 逻辑, 只是 HTTP code 渲染策略不同。

### Phase 02.1 Scope Guard

- **D-07:** **严格 fix-up — 只 3 bug, 不蔓延**。3 pre-existing test failure 走独立 chore commit, Axiom 推 P2, 7-day soak 推 Phase 03 启动期。Phase 02.1 预计 1-2 session 完成, 完成后才能 `/gsd-discuss-phase 03`。这是基于 Phase 02 L6/L7 "alert chain discipline + 不蔓延" 的执行落地。

### the agent's Discretion (planner 决定)

以下交给 planner 在 plan 阶段决定:
- **HMAC middleware 复用 vs 独立中间件** — `/control/*` 是否能直接复用 `scan_auth_middleware` (BaseHTTPMiddleware 类), 还是要新建 `control_auth_middleware`。两者 HMAC 逻辑相同但路径匹配规则可能不同。planner 调研 Starlette middleware 路径 dispatch 后定。
- **breadcrumb level=info vs warning** — D-01 假设 level=info (mirror skipped 不是错误, 是 config 状态), 但若用户期望"任何 skip 都报警"则改 warning。planner 看 Sentry retention/quota 决定。
- **/healthz response body shape** — D-05 锁定 status 出现在 body, 但具体 body 是 `{status: 'pass|warn|fail', checks: {...}}` (与 /health 同 schema) 还是 `{status: 'pass|fail', overall: 'ok|degraded|down'}` (简化版只为 Fly probe 看 alive/dead) — planner 决定, 倾向 simplified 因为 Fly probe 只需要 "machine alive" 信号。
- **/control/* 是否一次性建 3 endpoint** — Phase 02.1 strict scope 只要求 `/control/unpause`, 但 planner 可在不增加工作量前提下顺手定义 router 结构方便后续加 /pause / /status。本 phase 不实现, 但 router 框架可以一次性搭。

### Folded Todos

无 — Phase 02.1 是 deferred backlog 的消化, 不从 todo 池里 fold。
