## Research Area 1: Fly.io Machine Probe Semantics (D-05 关键)

### Question

`[http_service.checks]` 在 503 时的真实行为是什么? 改 path 到 `/healthz` 是否够? 是否有更好的方案?

### Findings

**Check fail 的后果** `[VERIFIED: fly.io/docs/reference/health-checks/]`:
> "If a Machine fails its service check, it will be marked as unhealthy by the proxy, and it won't be routed to until its checks start passing."

503 是 non-2xx → check fail → Fly proxy 停止路由外部流量到此 Machine. 这就是 Inj 2 期间 `curl https://polyarb-l1.fly.dev/health` timeout 的根因 — daemon 在跑但 Fly proxy 不 route 到它了.

**重要: 不会自动 restart** `[VERIFIED: fly.io/docs/reference/health-checks/]`:
> "A failing health check can prevent request routing to your Machine. However your Machines won't automatically restart or stop due to failing their health checks."

所以 503 → proxy 切流量, 但 machine 继续运行, daemon 继续 cron. 这符合我们观察到的 Inj 2 现象 (daemon 内部正常, 外部完全不可达).

**D-05 方案 (改 path 到 `/healthz`) 的正确性**:
将 `[http_service.checks]` 的 `path` 从 `/health` 改为 `/healthz`. `/healthz` 永远返回 HTTP 200 (even when system is degraded/failed — status 在 body 里). 这样 Fly probe 永远看到 2xx → machine 永远保持 routable → `/health` 仍然可以返回 503 给 Better Stack 外探针 (这是告警信号, 是好事). `[VERIFIED: 逻辑推断 + docs confirmed check semantics]`

**备选方案: Fly 顶层 `[checks]` 段** `[VERIFIED: fly.io docs]`:
```toml
[checks.alive]
  type = "tcp"
  port = 8080
  interval = "30s"
  timeout = "10s"
```
顶层 `[checks]` 是纯监控, 不影响路由. 但 CONTEXT.md D-05 已锁定改 path 方案, 且 TCP check 不能验证 HTTP 服务健康, 所以维持 D-05 决策.

**`[[http_service.checks]]` 数组语法** `[VERIFIED: fly.io docs]`:
fly.toml 支持多个 `[[http_service.checks]]` 定义 (TOML 数组表语法). 但本 phase 只需要改现有 check 的 path, 不需要多个.

**fly.toml 当前状态** `[VERIFIED: code read]`:
```toml
[[http_service.checks]]
  grace_period = "120s"
  interval = "30s"
  method = "GET"
  path = "/health"    # ← 改为 "/healthz"
  timeout = "10s"
```

### Implications for Plan

- Plan task: `fly.toml` 一行改动: `path = "/health"` → `path = "/healthz"`
- 同时需要在 `health.py` 里实现 `/healthz` handler (永远返 200, status 在 body)
- D-22 要求 /healthz 也是 public (no HMAC) — 与 /health 同模式, Better Stack 探针可以读
- 验证: 修后 `curl https://polyarb-l1.fly.dev/healthz` 永远 200, `curl .../health` 在 FAILED 时 503

## Research Area 3: Starlette Middleware Path Scoping for HMAC (D-03 Agent's Discretion)

### Question

`/control/*` 是否能直接复用 `ScanAuthMiddleware`, 还是需要新建独立中间件? Starlette BaseHTTPMiddleware path dispatch 机制如何?

### Findings

**现有 `scan_auth_middleware` 的 path check 逻辑** `[VERIFIED: code read, scan.py:108]`:
```python
if request.url.path != "/scan":
    # /health and any other path bypass auth
    return await call_next(request)
```

这是一个精确字符串比较. 只有 `/scan` 会走 HMAC 检查, 其他全部 bypass.

**方案对比**:

| 方案 | 代码改动 | 优点 | 缺点 |
|---|---|---|---|
| A: 修改现有 middleware, path check 改为 `path in ("/scan", "/control/unpause")` | scan.py 1 行改动 | 代码最少 | 两种语义耦合在一个 middleware; /control 扩展时要改 scan.py |
| B: 新建 `ControlAuthMiddleware` in control.py, 独立 path check | control.py + app.py 各加几行 | 关注点分离; /control/* 扩展不影响 scan.py | 两个 middleware 对性能有微小影响 (每次请求多一个 dispatch) |
| C: 共享 HMAC 工具函数, 两个 middleware 各自 path-match | 最 clean | — | 代码量最多 |

**Starlette BaseHTTPMiddleware 行为** `[VERIFIED: Context7 docs]`:
- Middleware 列表按**倒序**应用 (最后加的先执行).
- `call_next` 将请求传给下一层.
- path check 在 dispatch 方法内完全自由 — 没有框架层的 path filtering.
- 两个 middleware 都被每次请求调用, 但各自 path-guard 自己的 endpoint.

**推荐方案: B (独立 ControlAuthMiddleware in control.py)**

理由:
1. D-03 明确 "专语义 endpoint" — middleware 也应当专语义
2. `/control/*` 将来可能有不同 HMAC secret (e.g., admin-only secret vs scan secret) — 独立 middleware 允许这个演化
3. scan.py 保持不变 (P11 模板), 不引入回归风险
4. 工作量差异极小 (~10 行 extra)

**HMAC 共享实现** (方案 B 的推荐细节):
```python
# control.py — 复用相同 HMAC 逻辑, 不 import scan.py
import hashlib, hmac
# scan.py 的 HMAC 逻辑是 3 行代码, 直接 inline 到新 middleware
# 不值得抽成第三方工具函数 (会增加 import 复杂度)
```

### Implications for Plan

- 新建 `src/polyarb/http/control.py` — 包含 `control_auth_middleware` + `ControlAuthMiddleware(BaseHTTPMiddleware)` + `unpause()` handler

## Research Area 4: scheduler.unpause() 当前行为 (D-04)

### Question

scheduler.unpause() 当前 body 实际做什么? counter 清零了吗? 是否需要扩展?

### Findings

**scheduler.py:192-200 完整实现** `[VERIFIED: code read]`:
```python
def unpause(self) -> None:
    """Manually unpause the scheduler (called via /scan or SSH).

    Resets failure counter. Plan 04 exposes this via daemon management endpoint.
    """
    self.state = SchedulerState.RUNNING
    self._failure_counter = 0
    self._persist_counter()
    logger.info("scheduler unpaused manually, failure_counter reset to 0")
```

D-04 决策要求的 3 个操作全部已实现:
- ✅ `state → RUNNING`
- ✅ `failure_counter → 0`
- ✅ `_persist_counter()` — SQLite `scheduler_state` 单行 upsert, 重启不丢

**0 callers 是 bug 本质** `[VERIFIED: grep + CONTEXT.md code_context]`:
method 实现完整, 但 `scheduler.py` 在整个 codebase 里没有任何调用者. HTTP entry point 从未建立.

**方法签名**: `def unpause(self) -> None` — 同步方法 (不是 async). HTTP handler 需要注意直接调用即可, 不需要 `await`.

**`_persist_counter` 实现** (write to SQLite) `[VERIFIED: code read]`:
```python
def _persist_counter(self) -> None:
    try:
        self._sqlite_store.upsert_scheduler_state(
            state=self.state.value,
            failure_counter=self._failure_counter,
        )
    except Exception:
        pass  # scheduler_state is best-effort
```
失败是 silent (pass), 符合 fail-soft 主契约. counter 清零的持久化也是 best-effort.

**状态机验证后 HTTP handler 设计** (推荐):
```python
# control.py
async def unpause(request: Request) -> JSONResponse:
    scheduler = request.app.state.scheduler
    if scheduler.state != SchedulerState.PAUSED:
        return JSONResponse({"status": "already_running", "state": scheduler.state.value}, status_code=200)
    scheduler.unpause()
    return JSONResponse({
        "status": "ok",
        "message": "scheduler unpaused",
        "state": scheduler.state.value,
        "failure_counter": scheduler._failure_counter,
    })
```

**注意**: `scheduler._failure_counter` 是私有属性. 返回给客户端用于调试是可接受的 (内网 HMAC 保护), 但 planner 可选择不暴露.

**`scheduler_state` table schema** (no new fields needed) `[VERIFIED: code read + grep]`:
现有 schema: `state TEXT + failure_counter INTEGER`. D-04 不需要加 `last_unpaused_at_ms` — 简单 log message 已足够 ("scheduler unpaused manually, failure_counter reset to 0"). Inj 4 chaos 验证时从 Fly logs 确认即可.

### Implications for Plan

- `control.py` 只需 call `request.app.state.scheduler.unpause()` — 0 修改 scheduler.py
- 返回 JSON 包含 state + counter 便于 `make unpause-prod` 命令行验证
- 3 个测试: `test_unpause_transitions_to_running`, `test_unpause_clears_counter`, `test_unpause_when_not_paused_returns_200`

## Research Area 5: Sentry Breadcrumb 设计 (D-01)

### Question

level=info 还是 level=warning? LoguruIntegration 当前配置会不会把 info breadcrumb 丢掉?

### Findings

**LoguruIntegration 当前配置** `[VERIFIED: code read, sentry.py:115-118]`:
```python
LoguruIntegration(level="ERROR", event_level="ERROR"),
```
- `level="ERROR"`: 只有 ERROR+ 级别的 loguru 日志才自动转成 Sentry breadcrumb
- `event_level="ERROR"`: 只有 ERROR+ 级别的 loguru 日志才触发 Sentry issue

**关键区别**: `sentry_sdk.add_breadcrumb()` 是 **手动 API**, 不受 LoguruIntegration `level` 过滤. 手动 add_breadcrumb 永远会被记录, 无论 `level` 参数.

因此 D-01 的 `sentry_sdk.add_breadcrumb(level='info', ...)` 完全可行 — LoguruIntegration 配置不影响它. `[VERIFIED: code read + Sentry docs]`

**level=info vs level=warning 的实际影响** `[VERIFIED: Sentry docs]`:
- 两种 level 都会被存储 (breadcrumbs 是 ring buffer, 默认 100 条, 按时间滚动)
- level 只影响 Sentry UI 中的视觉强调程度 (颜色/图标)
- 没有 "info breadcrumb 被丢" 的情况 — level 对 retention 无影响

**D-01 的 breadcrumb 设计** (推荐 level=info):
```python
# orchestrator.py step 7.5 — 在 mirror_enabled=False 分支加
import sentry_sdk
sentry_sdk.add_breadcrumb(
    category="mirror",
    level="info",
    message="mirror skipped: reason=config-disabled",
    data={"supabase_mirror_enabled": False, "snapshot_id": snapshot_id},
)
logger.info(
    f"step 7.5: mirror disabled — config-level skip "
    f"(snapshot_id={snapshot_id}). "
    "Supabase dashboard will not update until secret is restored."
)
```

理由: "mirror skipped" 是 config 状态, 不是错误. level=info 语义正确. 若用 warning, 每次正常"mirror disabled" 配置也会触发高可见度 breadcrumb — 会 noise.

**reason 编码方案**:
- `reason=config-disabled` — 当 `supabase_mirror_enabled=False` (secret 缺失/未配)
- `reason=invalid-snapshot` — 当 F-05 guard (is_valid=False, 已有 log)

**breadcrumb 何时可见**: 下次 `sentry_sdk.capture_message()` 或 logger.error (ERROR+ → Sentry issue) 触发时, 附在事件上. Inj 3 验证: 撤 secret → mirror disabled → 随后的任意 Sentry event 会携带此 breadcrumb.

**现有 Sentry breadcrumb 模式** `[VERIFIED: code read, orchestrator.py:529-540]`:
step 7.5 except 分支已有:
```python
sentry_sdk.add_breadcrumb(
    category="storage",
    message=f"supabase_mirror_failed snapshot_id={snapshot_id}",
    level="warning",
    data={"error": str(e)[:200]},
)
```
D-01 新增 breadcrumb 用 `category="mirror"` 与之区分 (failure vs disabled 不同 category).

### Implications for Plan

- 在 orchestrator.py step 7.5 的 **if block 之前** 加一个 `elif not settings.supabase_mirror_enabled:` branch (或者用 `if not supabase_mirror_enabled` early-return pattern)
- 加一条 logger.info (明确可见日志) + 一条 sentry_sdk.add_breadcrumb
- 2 个测试: `test_mirror_disabled_logs_audit_entry`, `test_mirror_disabled_adds_sentry_breadcrumb`
- 注意: D-12 fail-soft 主契约不变 — snapshot 继续, 只是 mirror 静默跳过变为可见跳过

## Research Area 7: Future /control/* Router Framework (Agent's Discretion)

### Question

是否一次性建 /control/* router 框架? 工作量增加多少?

### Findings

**Starlette Router pattern** `[VERIFIED: Context7 Starlette docs]`:
Starlette 支持 `Mount` 将 sub-app 挂在 prefix 下, 或简单用多个 Route:
```python
# Option A: multiple explicit routes (simple, recommended for 1-3 endpoints)
Route("/control/unpause", unpause, methods=["POST"]),
Route("/control/pause", pause, methods=["POST"]),    # 未来
Route("/control/status", status_handler, methods=["GET"]),  # 未来

# Option B: Mount with sub-Router
from starlette.routing import Router, Mount
control_router = Router(routes=[
    Route("/unpause", unpause, methods=["POST"]),
])
Mount("/control", app=control_router),
```

**推荐**: Option A (多个显式 Route). 理由:
- Starlette `Mount` 有 middleware scope 问题 — `ControlAuthMiddleware` 在 app 级别注册, `Mount` 内部的路由也会被覆盖, 但路径匹配逻辑需要调整
- 3 个 endpoint 用 explicit route 更直观, no magic
- `control.py` 可以是普通 module with 3 handler functions, `app.py` register 3 routes

**本 phase 实际工作量 (只 unpause)**:
```python
# app.py 只加 1 行:
Route("/control/unpause", unpause, methods=["POST"]),
```

**搭 router 框架 (加 pause + status 占位)**: 额外 ~10 行 (导入 + 两个 stub handler). 推荐搭空 stub (raise NotImplementedError), 因为这样 planner 未来加实现只需填 handler body, 不改 app.py.

### Implications for Plan

- 推荐搭空 stub for future `/control/pause` + `/control/status` (在 control.py 里, 不写实现)
- `app.py` 注册所有 3 条 route (未来 2 条 stub 返回 501 Not Implemented)
- 这样 ControlAuthMiddleware 已经覆盖所有 `/control/*`, 后续只需填 handler

## Common Pitfalls

### Pitfall 1: scan_auth_middleware bypass 逻辑影响新 endpoint

**What goes wrong:** 现有 `scan_auth_middleware` 有 `if request.url.path != "/scan": return await call_next(request)`. 如果错误地扩展这个中间件来覆盖 `/control/*`, 修改时容易引入 or 条件逻辑 `path not in ("/scan", "/control/unpause")` — 但这意味着所有非列举 path 都 bypass. 更危险的是: `/healthz` 也应该 bypass (public endpoint), 这要求 middleware 的 bypass 逻辑需要更新.

**How to avoid:** 新建独立 `ControlAuthMiddleware` in `control.py`. `ScanAuthMiddleware` path check 只管 `/scan`, `ControlAuthMiddleware` path check 只管 `/control/*`. 两者分开, 互不影响.

**Warning signs:** 如果在 `scan.py` 里看到 `/control` 字样 — 说明边界被违反.

### Pitfall 2: /healthz 中间件 bypass 遗漏

**What goes wrong:** 新加 ControlAuthMiddleware 时, 如果 path check 写成 `path.startswith("/control")` 而忘记 `else: return await call_next(request)`, 则 `/healthz` 会进入 HMAC 检查 → Better Stack 探针返回 401 → Fly check 失败.

**How to avoid:** 测试 `test_healthz_no_hmac_required` (裸 GET /healthz 应返回 200, 不需要 X-Signature).

**Warning signs:** `flyctl checks list` 显示 check failing 而 daemon 正常运行.

### Pitfall 3: orchestrator step 7.5 改动位置错误

**What goes wrong:** D-01 的 audit log/breadcrumb 应该加在 `mirror_enabled=False` 的分支里 (step 7.5 入口的 config-level skip). 但 step 7.5 有两个 branch: F-05 guard (`is_valid=False`) 和 config disabled. 如果只加在 F-05 guard 分支, 则 Inj 3-v2 (撤 secret → enabled=False) 仍然静默.

**How to avoid:** 看 `orchestrator.py:487-548` 的完整结构:
```python
if settings.supabase_mirror_enabled and not is_valid:   # F-05 guard
    logger.info("step 7.5: skip ... is_valid=False")
elif settings.supabase_mirror_enabled:                   # 真 mirror 路径
    try: ... mirror.push_snapshot() ...
    except: ... breadcrumb ...
# ← D-01 新增: else 分支 (mirror_enabled=False)
else:
    logger.info("step 7.5: mirror disabled — reason=config-disabled ...")
    sentry_sdk.add_breadcrumb(category="mirror", level="info", ...)
```

**Warning signs:** Inj 3-v2 跑完, Fly logs 里没有 "mirror skipped" / "mirror disabled" 字样.

### Pitfall 4: scheduler.unpause() 是同步方法, 不能 await

**What goes wrong:** handler 写 `await request.app.state.scheduler.unpause()` → TypeError (coroutine expected).

**How to avoid:** `unpause()` 定义是 `def unpause(self) -> None` (非 async). 直接调用: `scheduler.unpause()`.

### Pitfall 5: /healthz 缺少 Content-Type 头

**What goes wrong:** /health 返回 `application/health+json`. /healthz 如果随手用 JSONResponse 默认 `application/json`, 与 /health 不一致, 可能误导 API 消费者.

**How to avoid:** /healthz 也用 `media_type=HEALTH_CONTENT_TYPE` (或至少文档说明语义).

| Pattern | STRIDE | Mitigation |

| /healthz information disclosure | Info Disclosure | 只 expose status/overall, 不 expose IPs/secrets/schema |

3. **`make unpause-prod` 如何签名 HMAC?**
   - 推荐: 空 body (POST without body) + HMAC of empty string `""`
   - 或: `{"action": "unpause"}` JSON body + HMAC of body bytes
   - 建议 empty body 方案: `curl -X POST https://polyarb-l1.fly.dev/control/unpause -H "X-Signature: sha256=$(echo -n '' | openssl dgst -sha256 -hmac $SECRET | awk '{print $2}')"` (bash one-liner)

4. **Inj 3-v2 需要加速 scheduler interval 吗?**
   - #7 验证不需要到 PAUSED — 只需要一次 cron tick 就能看到 "mirror disabled" log
   - 如果 prod interval 仍是 1h, 可以临时 `flyctl secrets set POLYARB_SCHEDULER_INTERVAL_S=60` 加速, 验证后 unset
   - 或者直接 `flyctl ssh console -a polyarb-l1 -C 'python -m polyarb.daemon.main --once'` 手动触发一次 (如果 main.py 支持 --once 参数)

5. **#6 验证 harness: 如何观察 "Fly proxy 不切流量"?**
   - 直接方法: 修后 deploy → 让 daemon FAILED → 检查 `curl https://polyarb-l1.fly.dev/healthz` 仍然可达 (因为 /healthz 200)
   - 实际挑战: 要触发 FAILED 状态需要 Inj 2 式注入 (改 Gamma URL). 可以: `flyctl secrets set POLYARB_GAMMA_URL=https://invalid.example.com` → 等 1 tick → curl /healthz (应 200) → curl /health (应 503) → 确认 Fly check 仍 passing → 恢复.
