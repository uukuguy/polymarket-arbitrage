    1. **翻译为什么用独立缓存表（不在 markets 加 question_zh 列）**

       - 真实威胁是"用户从论坛复制陌生 yaml"，不是防本人恶意
       - read-only URI 引擎层防御，0 依赖；sqlglot 5MB 依赖收益不匹配
       - 详见 RESEARCH.md §2 / Code: `src/polyarb/observation/scanner.py:<line>`

    3. **为什么 watchlist alert_when 不用 Python 内置任意代码求值器**

       - 我们走 AST walker（ast.parse + 受限节点白名单），仅算术 + 比较 + 白名单变量
       - "把'配置文件'和'代码文件'重新分开"
       - Code: `src/polyarb/observation/watchlist.py:<line>`

    4. **DuckDB 为什么用 union_by_name=true**
       - Phase 1.1 给 markets 加了 category/tags
       - 老 parquet 没这两列，跨 parquet 查询 union_by_name=true 自动 NULL 填充
       - 未来再加列零迁移成本
       - 不变量：parquet schema **只能加列，不能改类型**（RESEARCH §3.5）

    **G. `## 自检题（CLAUDE.md "对手测试" — 用户必答）`** — 5 题完整问答：

    1. **scan-thick-but-slippery 找出来的市场为什么不能直接套？**
       答：spread > $0.10 意味着 mid 是用 (bid+ask)/2 算的"虚假中位"，
       真实成交时第一笔 fill 已经差 $0.05+，加上后续滑点很容易把任何套利毛利吃光。
       这类市场只在 MM rebate 模式下有戏（M4 智能策略阶段）。

    2. **near-end 市场为什么是套利窗口最密的？**
       答：临近结算时 oracle 解析的概率分布坍缩，但订单簿可能滞后调整，
       产生跨 leg 不平衡（neg-risk）或与现实差距（M2/M4 信号源）。
       72h 是经验值——更短没流动性，更长机会还没到密集期。

    3. **scan-ghost-suspicious 为什么 JOIN validation_issues 而不是 markets.incomplete=1？**
       答：incomplete=1 是 Layer 2 字段缺失（zombie/resolving/unknown），
       ghost_book 是 Layer 4 cross-source 检查（CLOB 报有 token 但订单簿空）。
       两者表示不同问题，混用会找错可疑市场。

    4. **watchlist 的 alert_when 走 AST 白名单而不是 Python 内置任意代码求值器，
        为什么这个区别在生产环境很重要？**
       答：那个内置函数能跑任意代码（动态导入 + 系统调用）。本项目运行时
       load 的 yaml 可能来自 git 同步的其它机器、AI 生成、或论坛复制——交给那个内置
       函数等于把代码执行权外包出去。AST walker 把"能执行的语言"限定到算术 + 比较 +
       白名单变量，是把"配置文件"和"代码文件"重新分开。

    5. **如果未来某 phase 想给 markets 表改列类型（INTEGER → BIGINT），
        为什么必须重写所有历史 parquet？**
       答：DuckDB read_parquet(union_by_name=true) 仅对齐**列名**，不对齐**类型**。
       老 parquet INTEGER + 新 parquet BIGINT 跨 parquet UNION 时报错。
       变更类型必须有迁移脚本：读全部历史 parquet → 转列类型 → 原子重写。
       这就是 RESEARCH §3.5 立的"只能加列不能改类型"不变量。
