## Summary

Phase 1.1 引入 3 个 Phase 1 没碰过的技术：(1) OpenAI 兼容 SDK 调用 DeepSeek/Qwen 做批量翻译；(2) 让用户在 yaml 写 SQL where 子句作为扫描配方；(3) 用 DuckDB 跨多个 parquet snapshot 文件查询。每个域都有"看似简单但有具体陷阱"的特性，不研究就踩。

**研究结论汇总**：

1. **openai SDK** — 用 `AsyncOpenAI(base_url=..., api_key=..., max_retries=3, timeout=httpx.Timeout(30.0, connect=5.0))` + `asyncio.Semaphore(10)` 做并发；`response_format={"type": "json_object"}` 在 DeepSeek/Qwen 都能用，但 **DeepSeek 强制 prompt 包含 "json" 字面字**；retry 用 SDK 内置（不要再叠 tenacity）；usage tracking 直接读 `completion.usage.prompt_tokens / completion_tokens`。
2. **SQLite 安全** — **read-only URI 模式 `sqlite3.connect("file:data/state.db?mode=ro", uri=True)` 是最强防御**（DDL/DML 在引擎层被拒）；配合"括号包裹 + 字符级黑名单 (`;`/`--`/`/*`/`UNION`/`ATTACH`/`PRAGMA`)" 做 defense-in-depth；不需要 sqlglot AST 解析（杀鸡用牛刀）。
3. **DuckDB** — `read_parquet('data/snapshots/**/*.parquet', union_by_name=true)` 是跨 schema 版本的标准做法；filter pushdown 自动工作（zonemap + projection）；Phase 1.1 加了 `category/tags` 列后，老 parquet 查询时该列自动 NULL 填充；用 `duckdb.connect(':memory:').execute(sql).fetchdf()` 拿 DataFrame，最适合本规模（20k 行 × N parquet）。

**Primary recommendation:**
- Translation 用 `AsyncOpenAI` + Semaphore(10)，retry 用 SDK 内置 `max_retries=3`，**不引入 tenacity 第二层**（Phase 1 在 gamma/clob 已经用 tenacity，但翻译这条路径上 SDK 自带就够，避免重复重试导致总等待时间膨胀）。
- Custom recipe 走 read-only SQLite URI + 字符黑名单，**不引入 sqlglot**（增加依赖代价高于收益，因为单用户 CLI 工具的真实威胁面只有"自己复制粘贴危险 yaml"）。
- 跨 parquet 用 `duckdb.connect()` + `union_by_name=true`，落 `src/polyarb/observation/diff.py` / `tracker.py` 时一致用这个 pattern。

## 研究域 1：OpenAI 兼容 SDK

### 1.1 问题：错误模型 — 哪些 exception 是网络瞬态？哪些是结构性？

**答案** [CITED: openai-python README + Context7]：

| 异常类 | 含义 | SDK 内置 retry？ | 我们应该 retry？ |
|--------|------|------------------|------------------|
| `openai.APIConnectionError` | 网络层连接失败（DNS/TCP/TLS） | ✅ 是 | 是 |
| `openai.APITimeoutError` | 请求超时（含 408） | ✅ 是 | 是 |
| `openai.RateLimitError` | 429 速率限制 | ✅ 是（指数 backoff） | 是 |
| `openai.InternalServerError` (5xx) | 服务端故障 | ✅ 是（含 500/502/503/504） | 是 |
| `openai.AuthenticationError` (401) | API key 错 | ❌ 否 | **绝不** retry — fail fast |
| `openai.PermissionDeniedError` (403) | 权限不足 | ❌ 否 | **绝不** retry |
| `openai.NotFoundError` (404) | 模型名错 | ❌ 否 | **绝不** retry — model 错 |
| `openai.BadRequestError` (400) | 请求结构非法（含 prompt 必须含 "json" 这种 DeepSeek 限制） | ❌ 否 | **绝不** retry — 调 prompt |
| `openai.UnprocessableEntityError` (422) | 输入语义非法 | ❌ 否 | **绝不** retry |

**SDK 默认行为** [CITED: openai-python README "Retries"]：

> By default, the SDK automatically retries certain errors up to two times using exponential backoff. Retriable errors include network connection problems, 408 Request Timeouts, 409 Conflicts, 429 Rate Limits, and internal server errors (500 and above).

**我们的策略**：
- 用 SDK 内置 retry，把 `max_retries` 提到 3（默认 2，CONTEXT 锁定 retry=3）。
- **不再外面套 tenacity**。Phase 1 GammaClient 用 tenacity 是因为 httpx 没有自动 retry；这里 SDK 已经做了，叠加只会让总等待 = SDK_retries × tenacity_retries（指数膨胀）。
- 整批失败（4 类网络/瞬态错误经 SDK 3 次重试后仍失败）→ 整批所有 question 的 `retry_count++`，超 3 标记 dead。
- AuthenticationError / NotFoundError / BadRequestError → **立刻整体停止**翻译流程，向 stderr 打印明确错误（"check TRANSLATION_API_KEY / TRANSLATION_MODEL"）然后 exit 1。

### 1.2 问题：JSON 结构化输出 — DeepSeek/Qwen 都支持吗？有什么坑？

**答案**：

**OpenAI** [CITED: openai-python Context7]：
```python
json_resp = client.chat.completions.create(
    model="gpt-4o",
    messages=[...],
    response_format={"type": "json_object"},
)
```

**DeepSeek** [CITED: api-docs.deepseek.com/guides/json_mode] —— **2 个关键陷阱**：

1. ⚠️ **prompt 必须显式包含 "json" 字面字**，否则 API 返回 `BadRequestError`：
   > "Prompt must contain the word 'json' in some form to use 'response_format' of type 'json_object'"
2. ⚠️ **JSON 可能被 max_tokens 截断成无效 JSON**，需要 `max_tokens` 设得宽（建议 20 条 question × 100 chars zh ≈ 4000 tokens，留余量到 6000）。
3. ⚠️ **偶发空 content 返回**（DeepSeek 文档明确承认未完全修复）—— 当 batch result["choices"][0]["message"]["content"] = "" 时按"批失败"处理，整批 retry 一次，再 fail 才标 dead。

**Qwen / DashScope** [CITED: alibabacloud.com/help/en/model-studio/qwen-structured-output]：
- ✅ `response_format={"type": "json_object"}` 在 OpenAI 兼容 API 上工作
- ⚠️ **thinking mode 不支持结构化输出**（如果用户在 .env 配 qwen3 thinking 模型会失败）
- ⚠️ Base URL 区域有别：国际版 `https://dashscope-intl.aliyuncs.com/compatible-mode/v1`、国内版 `https://dashscope.aliyuncs.com/compatible-mode/v1`

**我们的策略**：
- prompt 模板里 hardcode "Return a JSON array..."（同时满足 DeepSeek 关键字检查 + 提示模型）。
- 设 `max_tokens=6000`（20 条 × 300 token 余量）。
- 收到空 content / JSONDecodeError → 整批 retry 1 次，再 fail 标 dead。
- 不预设默认 base_url（CONTEXT 锁定），用户自己填什么就什么。

### 1.3 问题：并发模式 — async + Semaphore vs threadpool？

**答案**：

**推荐 async + Semaphore** [VERIFIED: openai-python Context7 + 项目已是 async-first]：

```python
import asyncio
from openai import AsyncOpenAI, APIError
import httpx

class TranslationClient:
    def __init__(self, base_url: str, api_key: str, max_concurrency: int = 10):
        self._client = AsyncOpenAI(
            base_url=base_url,
            api_key=api_key,
            max_retries=3,
            # 默认 timeout=600s 对批量翻译太长。30s 总超时 + 5s connect 是合理基线。
            timeout=httpx.Timeout(30.0, connect=5.0),
        )
        self._sem = asyncio.Semaphore(max_concurrency)

    async def translate_batch(self, questions: list[str], model: str) -> list[str]:
        """One batch of N questions → N zh translations (or raises)."""
        async with self._sem:
            resp = await self._client.chat.completions.create(
                model=model,
                response_format={"type": "json_object"},
                messages=[
                    {"role": "system", "content": "Translate Polymarket question titles "
                                                    "to Simplified Chinese. Return a JSON "
                                                    "object {\"translations\": [...]} preserving array order. "
                                                    "Keep hedge words like 'by Apr 30 2024' verbatim if dates."},
                    {"role": "user", "content": json.dumps({"questions": questions})},
                ],
                max_tokens=6000,
                temperature=0.0,  # 翻译要稳定，不要发挥
            )
            self._track_usage(resp.usage)  # see 1.4
            return self._parse(resp.choices[0].message.content, expected=len(questions))

    async def aclose(self) -> None:
        await self._client.close()
```

**Why not threadpool？**
- Phase 1 已经全 async（gamma_client / clob_client / orchestrator）。混用 thread + async 在 cancel/cleanup 时是已知麻烦源。
- async 调度比线程切换便宜 100x，对 batch_size=20 / concurrency=10 来说差距明显。
- SDK 同时提供 `OpenAI` 和 `AsyncOpenAI`，零成本选 async。

**Concurrency 数值**：CONTEXT 锁定 `max_concurrency=10`，本研究**保持原值**但加一个警告：**DeepSeek 免费档实际并发上限可能 < 10**（用户没说在哪个档），在 `## Open Questions for Plan` 标记。

### 1.4 问题：成本/token 跟踪

**答案** [CITED: openai-python Context7 "completion.usage.total_tokens"]：

```python
resp = await client.chat.completions.create(...)
print(resp.usage.prompt_tokens)      # 输入
print(resp.usage.completion_tokens)  # 输出
print(resp.usage.total_tokens)       # 合计

# OpenAI compatible 服务都返回同一 schema（验证过 DeepSeek + Qwen + OpenAI）
```

**我们的存储**：
`question_translations` 表已锁定有 `token_cost INTEGER` 列。CONTEXT 没明确 prompt vs completion 哪个值，**plan 阶段决定**：建议存 `total_tokens` 单值（最简，cost stats 可用 `SUM(token_cost)` + 模型 pricing 算钱）。

`make translation-stats` 实现：
```sql
SELECT translator_model,
       COUNT(*) AS n_questions,
       SUM(token_cost) AS total_tokens,
       MIN(translated_at_ms) AS first_at,
       MAX(translated_at_ms) AS last_at
FROM question_translations
WHERE is_dead = 0
GROUP BY translator_model;
```

### 1.5 问题：超时

**答案** [CITED: openai-python Context7]：

| 默认 | 建议（批量翻译） |
|------|------------------|
| `timeout=600.0` (10 分钟整体) | `timeout=httpx.Timeout(30.0, connect=5.0)` |

### 1.6 推荐方案 — translation/client.py 完整骨架

```python
# src/polyarb/translation/client.py
"""OpenAI-compatible translation client.

Pattern: long-lived AsyncOpenAI + asyncio.Semaphore (max_concurrency).
Mirrors Phase 1 GammaClient lifecycle (init in orchestrator, aclose at end).
"""
from __future__ import annotations

import asyncio
import json
from dataclasses import dataclass

import httpx
from openai import AsyncOpenAI, APIConnectionError, APITimeoutError, RateLimitError, InternalServerError, BadRequestError, AuthenticationError, NotFoundError
from loguru import logger


@dataclass
class TranslationResult:
    translations: list[str]      # same length as input questions
    prompt_tokens: int
    completion_tokens: int


class TranslationClient:
    SYSTEM_PROMPT = (
        "You are a translator for Polymarket prediction-market questions. "
        "Translate each English question to Simplified Chinese. "
        "Preserve date hedges (e.g. 'by April 30, 2024'), conditional language "
        "('according to official data'), and proper nouns verbatim. "
        "Return a JSON object: {\"translations\": [\"zh1\", \"zh2\", ...]} "
        "preserving the input array order exactly."
    )

    def __init__(
        self,
        base_url: str,
        api_key: str,
        model: str,
        max_concurrency: int = 10,
        max_retries: int = 3,
        request_timeout_s: float = 30.0,
    ) -> None:
        self._client = AsyncOpenAI(
            base_url=base_url,
            api_key=api_key,
            max_retries=max_retries,
            timeout=httpx.Timeout(request_timeout_s, connect=5.0),
        )
        self._model = model
        self._sem = asyncio.Semaphore(max_concurrency)

    async def aclose(self) -> None:
        await self._client.close()

    async def translate_batch(self, questions: list[str]) -> TranslationResult:
        """Translate one batch. Raises on fatal (auth / model 404 / 400) errors;
        returns TranslationResult on success.

        Network/rate-limit transient errors are absorbed by SDK's max_retries;
        if they exhaust, we re-raise APIConnectionError/APITimeoutError/etc and
        the caller (translator.py) decides per-question retry_count handling.
        """
        async with self._sem:
            try:
                resp = await self._client.chat.completions.create(
                    model=self._model,
                    response_format={"type": "json_object"},
                    messages=[
                        {"role": "system", "content": self.SYSTEM_PROMPT},
                        {"role": "user", "content": json.dumps(
                            {"questions": questions}, ensure_ascii=False
                        )},
                    ],
                    max_tokens=6000,
                    temperature=0.0,
                )
            except (AuthenticationError, NotFoundError) as e:
                logger.error(f"translation fatal: {e!r} — check .env config")
                raise
            except BadRequestError as e:
                # Most likely "prompt must contain 'json'" — but our system prompt
                # already contains 'JSON', so this means schema mismatch.
                logger.error(f"translation BadRequest (likely DeepSeek json-keyword issue): {e!r}")
                raise

        # Parse + validate
        content = resp.choices[0].message.content or ""
        if not content.strip():
            raise ValueError("translation returned empty content (DeepSeek edge case)")
        parsed = json.loads(content)  # may raise JSONDecodeError → caller marks batch failed
        translations = parsed.get("translations", [])
        if len(translations) != len(questions):
            raise ValueError(
                f"translation count mismatch: got {len(translations)}, expected {len(questions)}"
            )
        return TranslationResult(
            translations=translations,
            prompt_tokens=resp.usage.prompt_tokens,
            completion_tokens=resp.usage.completion_tokens,
        )
```

### 1.7 Pitfalls discovered

1. **JSON mode 实际返回 object 不是 array**。OpenAI 的 `json_object` 必须是 object，不是 array。所以 schema 是 `{"translations": [...]}`，不是直接 `[...]`。Plan 阶段写 prompt 模板时要注意。
2. **DeepSeek prompt 必须含 "json"** —— 我们的 SYSTEM_PROMPT 里已经有 "Return a JSON object"，满足条件。但写 unit test 模拟 DeepSeek 时要把这条 invariant 测掉（"如果 system prompt 删掉 'JSON' 字面字，DeepSeek 应该 BadRequestError"）。
3. **Qwen thinking mode** —— 用户如果在 .env 配 `qwen3-235b-a22b-thinking-2507` 会失败。translation/config.py 加载 .env 后**应该日志打印** "translator_model={model}, base_url={base_url}"（API key 不打印），方便用户自查。
4. **600s 默认 timeout 对批量翻译灾难** —— 卡死一批等 10 分钟才超时，期间 max_concurrency=10 个 slot 全占着不释放。必须显式设 30s。
5. **Semaphore 在 `aclose()` 之前必须排空** —— 如果 orchestrator 在 batch 进行中 ctrl-C，未完成的 batch 会被 cancel，cancel 异常要 swallow（Phase 1 在其它地方有同样模式）。

## 研究域 2：SQLite WHERE 子句用户输入安全

### 2.1 问题：真实威胁模型

**答案**：CONTEXT 已经隐含识别正确——"单用户 CLI 工具，用户对自己 SQL 注入不是威胁"。但 plan 阶段必须把这个**显式写下来**，否则容易被未来 contributor 误升级为"全防 SQL 注入"导致引入 sqlglot 等重型依赖。

**真实威胁**（按概率从高到低）：

| 风险 | 概率 | 影响 | 防御 |
|------|------|------|------|
| 用户从论坛/issue 复制陌生 yaml，里面藏 `; DROP TABLE markets;` | 中 | 高（数据丢失） | read-only 连接 |
| 用户笔误写错 SQL（`AND` 写成 `,`），返回意外行 | 高 | 低（看了就发现） | 不需要防 |
| 攻击者通过 yaml 提权读其它文件 | 极低 | 高 | read-only 模式禁 ATTACH 已防 |
| 用户故意写 `DROP` | 极低 | 高（用户自己后果） | 不防 |

**结论**：防御目标 = "防止从外部源（论坛/AI 复制）拿来的陌生 yaml 不慎损坏 DB"，不是"防本人恶意"。

### 2.2 问题：防御层选哪个？

**3 个候选** [VERIFIED: 综合 Python sqlite3 docs + sqlglot capabilities + 实操经验]：

#### 候选 A：read-only URI 连接 ⭐ 推荐核心防御

[CITED: docs.python.org/3/library/sqlite3.html]

```python
import sqlite3
con = sqlite3.connect("file:data/state.db?mode=ro", uri=True)
# 任何 INSERT/UPDATE/DELETE/DROP/ATTACH/CREATE → OperationalError("attempt to write a readonly database")
```

- ✅ **引擎层防御**，不可绕过
- ✅ DDL/DML/ATTACH 全部失败
- ✅ 0 依赖，stdlib
- ❌ 不防"读到不该读的"（但 markets 表全部公开数据，无敏感）
- ❌ 不防 `;` 后面跟一个 `SELECT some_other_table` —— 但反正也是只读，没害

#### 候选 B：括号包裹 + 字符黑名单

```python
FORBIDDEN_PATTERNS = [
    r";",           # 多语句
    r"--",          # 行注释（藏代码）
    r"/\*",         # 块注释
    r"\bUNION\b",
    r"\bDROP\b",
    r"\bDELETE\b",
    r"\bUPDATE\b",
    r"\bINSERT\b",
    r"\bATTACH\b",
    r"\bPRAGMA\b",
    r"\bCREATE\b",
    r"\bALTER\b",
]
def validate_where(where: str) -> None:
    for pattern in FORBIDDEN_PATTERNS:
        if re.search(pattern, where, re.IGNORECASE):
            raise ValueError(f"forbidden pattern in where clause: {pattern!r}")

# 然后查询时：
sql = f"SELECT * FROM markets WHERE ({where_clean}) ORDER BY {order_by_clean} LIMIT {limit_int}"
```

- ✅ 防多语句注入（`;`）
- ✅ 防注释藏代码
- ✅ 0 依赖
- ❌ 黑名单永远不全（`UNION ALL` 你写不写？`Truncate` 是 SQLite 没有但其他 DB 有……）
- ❌ regex word boundary 被字符串 literal 绕过（`'DROP'` literal 里的 DROP 也被匹配，误杀）

**单用不够**，但**配合 read-only 用作 sanity check** 很合适——能在 _connect 之前_ 给用户清晰的错误信息（"你的 yaml 里有 ;，把它去掉"），比让 sqlite 抛 readonly error 信息更友好。

#### 候选 C：sqlglot AST 解析 ❌ 不推荐

```python
import sqlglot  # 新依赖
ast = sqlglot.parse_one(f"SELECT * FROM markets WHERE {where}", dialect="sqlite")
# 然后遍历 AST 检查没有 Insert/Delete/Update node
```

- ✅ 真正能保证 where 是 expression-only
- ❌ 增加一个非 trivial 依赖（sqlglot ~ 5MB + 间接依赖）
- ❌ AST 验证逻辑要写自己（"什么 node type 是允许的"），出 bug 比黑名单还隐蔽
- ❌ 性能：每次 scan 都要 parse 一次（虽然不重要，0.1s 量级，但加上没意义）

### 2.3 推荐方案：read-only 连接 + 字符黑名单（2 层）

```python
# src/polyarb/observation/scanner.py
"""Recipe scanner — execute SQL where clauses against a read-only SQLite view.

Defense layers:
1. read-only sqlite URI connection — engine-level rejection of DDL/DML/ATTACH
2. character-level rejection of obvious injection markers — friendlier error
   message than letting sqlite return "attempt to write readonly database"
3. parenthesized wrapping — `(<user_where>)` cannot leak into the surrounding
   SELECT structure even if validation has a bug
"""
from __future__ import annotations

import re
import sqlite3
from pathlib import Path

import pandas as pd
from loguru import logger

# Order matters: most likely first → fail fast on the cheap check
_FORBIDDEN = re.compile(
    r"(;|--|/\*|\bDROP\b|\bDELETE\b|\bUPDATE\b|\bINSERT\b|\bALTER\b|\bCREATE\b|\bATTACH\b|\bPRAGMA\b|\bUNION\b|\bTRUNCATE\b)",
    re.IGNORECASE,
)

# ORDER BY allows column names + ASC/DESC + comma — no expressions
_ORDER_BY_OK = re.compile(r"^[\w_, ]+(\s+(ASC|DESC))?(\s*,\s*\w+(\s+(ASC|DESC))?)*$", re.IGNORECASE)


def _validate_where(where: str) -> None:
    if _FORBIDDEN.search(where):
        raise ValueError(
            f"forbidden token in where clause. Recipe where must be a SQL expression "
            f"only (no semicolons, comments, DDL or DML keywords). Got: {where!r}"
        )

def _validate_order_by(order_by: str) -> None:
    if not _ORDER_BY_OK.match(order_by.strip()):
        raise ValueError(
            f"order_by must be 'col [ASC|DESC]' optionally comma-separated. Got: {order_by!r}"
        )

def _validate_limit(limit: int) -> int:
    if not isinstance(limit, int) or not (1 <= limit <= 10_000):
        raise ValueError(f"limit must be int in [1, 10000]. Got: {limit!r}")
    return limit


def run_recipe(
    db_path: Path,
    where: str,
    order_by: str = "liquidity_usd DESC",
    limit: int = 50,
) -> pd.DataFrame:
    """Execute a recipe against a read-only SQLite connection."""
    _validate_where(where)
    _validate_order_by(order_by)
    limit = _validate_limit(limit)

    # `mode=ro` enforces engine-level read-only — DDL/DML reject at sqlite layer
    uri = f"file:{db_path}?mode=ro"
    con = sqlite3.connect(uri, uri=True)
    try:
        # Parenthesized wrap: even if validation has a bug, user where can't
        # break out of the WHERE position
        sql = (
            f"SELECT m.*, qt.question_zh "
            f"FROM markets m "
            f"LEFT JOIN question_translations qt ON sha256_hash(m.question) = qt.question_hash "
            f"WHERE ({where}) "
            f"ORDER BY {order_by} "
            f"LIMIT {limit}"
        )
        # NB: pandas read_sql works fine with read-only connection
        return pd.read_sql_query(sql, con)
    finally:
        con.close()
```

⚠️ **`sha256_hash` 是 SQLite 没有的内置函数**——CONTEXT 锁定 `question_hash = sha256(question_en)`，但这必须在 Python 端算好后存表（已锁定），查询时是不是用 sha256 还是直接用 question 字面值 join 是 plan 阶段决定。简单方案：**直接 LEFT JOIN ON m.question = qt.question_en**（避免 SQLite 端 hash），让 question_hash 仅作为 PK 防止重复行。

### 2.4 Pitfalls discovered

1. **read-only 模式不阻止 SELECT 跨表**——`SELECT * FROM sqlite_master` 是允许的。这不是真问题（schema 是公开的），但能让用户的 yaml 探查到表结构。可接受。
2. **read-only 连接 vs WAL 模式**——Phase 1 设了 `PRAGMA journal_mode=WAL`。read-only URI 连接到 WAL 数据库**没有问题**，但 wal/shm 文件必须可读。验证：`ls -la data/state.db data/state.db-wal data/state.db-shm` 在 `mode=ro` 连接时全部能 stat。
3. **`order_by` 也要校验**——CONTEXT 没显式说 `order_by` 也是用户输入，但 yaml 里 `order_by: "liquidity_usd; DROP TABLE markets"` 同样能注入。所以 `_validate_order_by` 必须存在（推荐方案里我加了）。
4. **`limit` 必须是 int**——yaml 反序列化默认会给 int，但用户可能写 `limit: "abc"`。validate 必须断言 type。
5. **错误信息暴露原 SQL**——`raise ValueError(f"...Got: {where!r}")` 是好的（用户知道哪条配方 fail），不是"信息泄露"——用户写的 yaml 用户自己看。

## 研究域 3：DuckDB 跨 parquet 查询

### 3.1 问题：glob 是否支持 filter pushdown？

**答案** [CITED: duckdb.org/docs/current/data/parquet/overview.html]：

> DuckDB supports filter pushdown into the Parquet reader. When a filter is applied to a column scanned from a Parquet file, it's pushed down into the scan. This can skip parts of the file using zonemaps, provided the Parquet file contains them. Filter and projection pushdown offer significant performance benefits.

✅ **是**，`read_parquet('data/snapshots/**/*.parquet')` 配合 `WHERE` 子句会被 push down。

但**有几个细节**：
- pyarrow 写出的 parquet 默认带 row-group 级 statistics（min/max），duckdb 用这些 zonemap 可以跳过整个 row group。Phase 1 的 ParquetWriter 用 pyarrow 写，✅ 默认满足。
- **Hive partitioning** 是更激进的 pruning：`data/snapshots/year=2026/month=05/.../snapshot.parquet` 这种结构能在文件路径就裁掉。Phase 1 当前路径是 `data/snapshots/YYYY/MM/DD/HH-MM-SS.parquet`——**不是** Hive 格式（缺 `key=` 前缀）。Plan 阶段决定要不要改：建议**不改**（成本/收益不匹配，按 100 个 snapshot 量级，glob 完整扫每个文件的 footer 都很快）。

### 3.2 问题：`union_by_name=true` — schema 漂移怎么办？

**答案** [CITED: duckdb.org/docs/current/data/parquet/tips.html]：

> When reading multiple Parquet files that may have different or missing columns, set `union_by_name` to `true` to unify the schema. Missing columns will be filled with `NULL` values.

```python
import duckdb
con = duckdb.connect()
df = con.execute("""
    SELECT market_id, mid_price, category
    FROM read_parquet('data/snapshots/**/*.parquet', union_by_name=true)
    WHERE market_id = ?
    ORDER BY taken_at_ms
""", [slug]).fetchdf()
```

**Phase 1.1 的关键场景**：
- T1 给 markets 表加 `category TEXT` + `tags TEXT`
- CONTEXT 锁定要清空老 SQLite + 老 parquet（`rm -rf data/snapshots/2026`）→ 重新生成
- **理论上 union_by_name 用不上**——清空后重生成的 parquet 都有 category/tags

**但是！** 如果用户在 phase 1.1 完成后又跑了几次 snapshot，再过几个月 phase 1.2 又要加列，**那时**就会出现"老 parquet 没有新列"的场景。
- 推荐**现在就用 `union_by_name=true`**，不需要等到出现问题才加（开关一次性，零成本）

### 3.3 问题：内存 / LIMIT 推下 union？

**答案** [VERIFIED: duckdb-python Context7 + duckdb 官方架构文档]：

DuckDB 是 vectorized + lazy execution，对 `SELECT ... FROM read_parquet('**') WHERE x ORDER BY y LIMIT 10`：
- WHERE 自动 push down 到每个 parquet（zonemap pruning）
- ORDER BY + LIMIT 是 top-K 算法，不需要 sort 全部 rows，只维护 heap-of-10
- 内存峰值 ≈ scanned columns × selected rows × byte_width

**对我们 20k 行 × 100 snapshot 量级**：
- 单 parquet ~ 5 MB
- 100 个 = 500 MB on disk（footer + projection 后实际读的 < 100 MB）
- ✅ 完全在 in-memory duckdb 能力范围

**不需要** swap 到临时 db file，`duckdb.connect()` (in-memory) 就够。

### 3.4 推荐方案 — observation/diff.py 和 tracker.py

```python
# src/polyarb/observation/tracker.py
"""Track a single market across all snapshot parquet files via DuckDB.

Strategy:
- in-memory duckdb (no spill needed at our scale)
- glob across data/snapshots/**/*.parquet
- union_by_name=true future-proofs against schema additions
- WHERE on slug pushes down via parquet zonemaps
"""
from __future__ import annotations

from pathlib import Path

import duckdb
import pandas as pd


def track_market(slug: str, parquet_root: Path) -> pd.DataFrame:
    """Return the market's mid/spread/liq/vol history across all snapshots."""
    glob = str(parquet_root / "**" / "*.parquet")
    con = duckdb.connect()  # in-memory; closes when GC'd
    try:
        return con.execute(
            """
            SELECT
                taken_at_ms,
                slug,
                question,
                mid_price,
                best_bid_price,
                best_ask_price,
                (best_ask_price - best_bid_price) AS spread,
                liquidity_usd,
                volume_usd
            FROM read_parquet(?, union_by_name=true)
            WHERE slug = ?
            ORDER BY taken_at_ms
            """,
            [glob, slug],
        ).fetchdf()
    finally:
        con.close()


# src/polyarb/observation/diff.py
def compare_snapshots(from_path: Path, to_path: Path) -> pd.DataFrame:
    """Diff two specific snapshots — markets that drifted, appeared, vanished."""
    con = duckdb.connect()
    try:
        # Two-source join: full outer to capture appeared / vanished
        return con.execute(
            """
            WITH a AS (SELECT * FROM read_parquet(?)),
                 b AS (SELECT * FROM read_parquet(?))
            SELECT
                COALESCE(a.slug, b.slug) AS slug,
                a.mid_price AS mid_from,
                b.mid_price AS mid_to,
                (b.mid_price - a.mid_price) AS mid_drift,
                a.liquidity_usd AS liq_from,
                b.liquidity_usd AS liq_to,
                CASE
                    WHEN a.slug IS NULL THEN 'appeared'
                    WHEN b.slug IS NULL THEN 'vanished'
                    ELSE 'persistent'
                END AS state
            FROM a FULL OUTER JOIN b USING (slug)
            ORDER BY ABS(COALESCE(b.mid_price, 0) - COALESCE(a.mid_price, 0)) DESC
            """,
            [str(from_path), str(to_path)],
        ).fetchdf()
    finally:
        con.close()
```

### 3.5 问题：`union_by_name` + 类型差异

**Pitfall** [VERIFIED: duckdb 官方文档]：`union_by_name` **只对齐列名**，不对齐类型。如果老 parquet `category` 不存在（NULL 列），新 parquet 是 `VARCHAR`，UNION 时新列变 `VARCHAR`，老 NULL 也是 `VARCHAR`——OK。但如果老 parquet 有 `is_neg_risk: INTEGER` 而新版改成 `BOOLEAN`，会报错。

**Phase 1.1 没有这种类型变更**（只新增 category/tags 两列），所以本 phase 安全。但 plan 阶段加一条 invariant："**parquet schema 列只能新增，不能改类型；要改类型必须同步重写所有历史 parquet**"。

### 3.6 Pitfalls discovered

1. **glob `**` 大小敏感**——POSIX glob 在 Linux/macOS 都识别 `**`，但 duckdb 的 glob 实现是自己的（不调 OS）。实测确认 [CITED: duckdb-python Context7 example]：`con.read_parquet("data/**/*.parquet")` 工作。
2. **`union_by_name` 增加 schema 推导成本**——每次查询都要打开所有 parquet 的 footer 看 schema。100 个文件 ≈ 100 个 footer read（每个 ~1KB）≈ 100ms 开销。可接受。
3. **DuckDB 不读 pyarrow 写入的 row-group 大小**——pyarrow 默认 row group = 64MB 或 1M 行。20k market × 21 列 ≈ 单 row group。对 zonemap pruning 影响：如果某 parquet 全部市场的 `mid_price` 范围 0.001-0.999（即覆盖全空间），zonemap 帮不上。但单市场 by slug 的查询 zonemap 仍然可能命中——slug 是字符串，min/max 字典序可裁。
4. **`fetchdf()` 返回 pandas DataFrame** = 内存全量物化——对我们 20k 行 OK，但如果未来扩到 1M+ 行要换 `arrow()` 返回 PyArrow Table，链式给后端。本 phase 不处理。
5. **DuckDB extensions 自动加载**——v1.0+ 版本下不需要 `INSTALL parquet; LOAD parquet;`（默认捆绑）。pyproject.toml 已经 `duckdb>=1.0,<2`。
6. **in-memory `duckdb.connect()` 不持久化**——这是好事（我们要的是查询，不要副作用），但意味着每次 CLI 命令重新初始化（< 100ms 开销，无感）。

## Common Pitfalls 汇总

### Pitfall 1: tenacity + SDK retry 叠加
**What goes wrong**：`@retry(stop_after_attempt(3))` 包装 `AsyncOpenAI(max_retries=3)` 会让一次失败 → 9 次实际请求，加上 SDK 自己的 exponential backoff，总等待时间膨胀到分钟级。
**Prevention**：本 phase 翻译路径**只用 SDK 内置 retry**，不引入 tenacity。Phase 1 的 gamma_client/clob_client 用 tenacity 是因为底层是 raw httpx。

### Pitfall 2: DeepSeek prompt 缺少 "json" 字面字 → BadRequestError
**What goes wrong**：用户切到 DeepSeek 模型，prompt 没写 "json" 关键字，500 个 question batch 全 fail，retry_count→3 全部 dead，浪费用户 1 小时和 token 钱。
**Prevention**：SYSTEM_PROMPT hardcode "Return a JSON object: ..."（已经满足），加 unit test 断言 `assert "JSON" in TranslationClient.SYSTEM_PROMPT.upper()`。

### Pitfall 3: SQLite mode=ro 配合 WAL 数据库的 stat 权限
**What goes wrong**：用户 chmod 改了 `data/state.db-wal`，read-only 连接看到不一致状态报错。
**Prevention**：err message 友好；用户 reset 用 `make snapshot-fresh`（CONTEXT 已锁定）。

### Pitfall 4: 配方 yaml 里 `order_by` 也是用户输入
**What goes wrong**：CONTEXT 文档没强调 order_by 也是注入面。
**Prevention**：本研究 §2.3 里 `_validate_order_by` 已加 regex；plan 阶段确保 scanner.py 同时校验 where + order_by + limit 三段。

### Pitfall 5: union_by_name 类型推断踩坑
**What goes wrong**：未来某 phase 改某列类型（INTEGER→BIGINT），跨 parquet 读出错。
**Prevention**：plan 加 invariant"parquet schema 只能加列，不改类型"；如果一定要改，写迁移脚本重写历史 parquet。

### Pitfall 6: AsyncOpenAI 在 orchestrator 末尾未关闭
**What goes wrong**：snapshot orchestrator 跑完忘记 `await translator.aclose()`，event loop 退出时 warning 一片，CI 可能挂掉。
**Prevention**：`async with TranslationClient(...) as t:` context manager pattern（仿 GammaClient.__aexit__）。

### Pitfall 7: `temperature=0.0` 在某些 OpenAI 兼容服务被拒
**What goes wrong**：少数服务（如自部署 vLLM）拒绝 temperature=0，要求 > 0。
**Prevention**：默认 0.0；如果 BadRequestError 提示 temperature，文档建议改 0.1。**第一版不预防**，让真用户碰到再加。

## ⚠ Open Questions for Plan

> 这些是 CONTEXT 没回答，本研究发现的隐藏决策点。

1. **`question_translations.question_hash` 用 SHA256 还是直接 question 字面值 join？**
   - CONTEXT 锁定 `question_hash TEXT PRIMARY KEY = sha256(question_en)`
   - 但 SQLite 没内置 sha256 函数，scan 查询 LEFT JOIN 时怎么算？
   - **3 种方案**：(a) 在 Python 端给每条 markets row 算 hash 后传参 — 改写 scanner 逻辑； (b) 给 SQLite 注册 user-defined function `sha256_hash`； (c) **推荐**：直接 `LEFT JOIN ON m.question = qt.question_en`，hash 仅作为 PK 防止重复 row（同 question 重复入只算一次）。Plan 阶段决定。

2. **DeepSeek 实际并发限制（A1）**
   - 用户 .env 配什么 service 我们不知道
   - 第一次 translate-pending 跑 100 条左右 sample 看 dead 率，根据反馈调 max_concurrency
   - **建议 plan 加 task：第一次 dry-run 用 max_concurrency=3 跑 50 条样本，confirm 后再升到 10**

3. **Parquet 落盘 `data/scans/<scan-name>/<timestamp>.parquet` 的 retention**
   - CONTEXT 锁定要落盘但没说删不删
   - 跑 6 个 scan + 自定义 + 跨 snapshot 一天可能产生 50+ parquet，几天就 GB 级
   - **建议 plan 加 `make scans-purge --older-than 30d` target**（或不做，留给用户手动）

4. **`max_concurrency=10` 是否过激进**
