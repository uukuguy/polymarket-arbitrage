# Phase 01.1 Plan 03: Scanner Engine + 6 Builtin Recipes + 4-Layer SQL Defense — Summary

**One-liner:** Trust-split scanner engine — 6 git-controlled builtin recipes
bypass the strict blacklist/whitelist while user-supplied yaml recipes are
forced through the full 4-layer defense (read-only sqlite URI / character
blacklist / ORDER BY whitelist / int range LIMIT). The `by-tag` recipe
replaces the planned `by-category` to align with Amendment 01's event_tags
schema. Output is dual-form: rich.Table to terminal + atomic parquet to
`data/scans/<recipe>/<UTC-timestamp>.parquet`. 8 Makefile targets cover
ergonomic single-recipe runs + generic + housekeeping.

## What was built

### Task 1 — scanner + recipes + trust split

**Recipe dataclass** (`src/polyarb/observation/recipes.py`):
- `Recipe(name, description, where, order_by, limit, group_by, _is_trusted)`
- `Recipe.from_builtin(...)` → `_is_trusted=True` (bypass blacklist/whitelist)
- `Recipe.from_yaml(name, body)` → `_is_trusted=False`, drops group_by

**6 BUILTIN_RECIPES (all _is_trusted=True via from_builtin)**:

| Name | Path | Notes |
|------|------|-------|
| thick-but-slippery | row | uses arithmetic ORDER BY (only allowed for trusted) |
| near-end | row | strftime in WHERE (only allowed for trusted) |
| ghost-suspicious | row | uses SELECT subquery on validation_issues (typo correction; only allowed for trusted) |
| coin-flip | row | mid 0.45-0.55 + 7 day end window |
| neg-risk-incomplete | grouped | `group_by="neg_risk_market_id HAVING ABS(SUM(mid_price)-1.0) > 0.02"` |
| by-tag | grouped | `group_by="tag_label"` — Amendment 01: replaces by-category |

**4-layer scanner defense** (`src/polyarb/observation/scanner.py`):

| Layer | Mechanism | Trust-bypass? |
|-------|-----------|---------------|
| 1 | `sqlite3.connect("file:...?mode=ro", uri=True)` engine-level write reject | NO (universal) |
| 2 | `_FORBIDDEN` regex blacklist (;, --, /*, DDL/DML, UNION, SELECT, ATTACH, PRAGMA…) | YES (trusted=True bypass) |
| 3 | `_ORDER_BY_OK` regex whitelist (bare cols + optional ASC/DESC, no exprs) | YES (trusted=True bypass) |
| 4 | `_validate_limit` int range [1, 10000] (rejects bool subclass) | NO (DoS guard universal) |

**Grouped-path no-bypass invariant (Blocker #3)**: `run_recipe_grouped` calls
`_validate_where` + `_validate_order_by` with `recipe._is_trusted`, identical
to `run_recipe`. Yaml is forbidden from setting `group_by` (load_yaml_recipes
silently drops with warning), but the validator chain is the second line of
defense if a future change ever opens that door.

**YAML loading (T-01.1-10 mitigation)**:
- `yaml.safe_load` only — `yaml.load` not used anywhere in the module
- Fail-fast strict validation at LOAD time (not at first execution)
- Same-name yaml recipe does not override builtin (logger.warning + ignore)
- `group_by` key in yaml is dropped + warning (builtin-only)
- Non-dict body silently skipped + warning

## Threat model — defense layer impact analysis

What if any one defense layer were removed?

| Layer removed | Real-world impact |
|---------------|-------------------|
| 1 (read-only URI) | Yaml WHERE could DROP/INSERT/UPDATE silently if Layers 2/3 had a bypass bug. **Highest impact** — engine-level guard is the floor. |
| 2 (blacklist) | Yaml could embed `; DELETE FROM markets` — Layer 1 still blocks engine-side, but error message becomes "attempt to write a readonly database" instead of friendly "forbidden token" → degrades UX, not security. |
| 3 (ORDER BY whitelist) | Yaml could write `ORDER BY (CASE WHEN x THEN y ELSE z END) DESC` — semantically valid, currently rejected for restraint. Low real impact. |
| 4 (limit cap) | Yaml could `limit: 1_000_000` → in-memory pandas DF pressure (DoS, not data loss). Affects single-user only. |

## Trust-split implementation summary

- All 6 builtins constructed via `Recipe.from_builtin(...)` → `_is_trusted=True`
- Test invariant: `assert all(r._is_trusted for r in BUILTIN_RECIPES.values())`
- Yaml-loaded recipes always `_is_trusted=False` (Recipe.from_yaml hard-codes it)
- Sample yaml attacks the strict path catches at LOAD time:
  - `where: 1=1; DROP TABLE markets` → ValueError (semicolon + DROP)
  - `where: market_id IN (SELECT ...)` → ValueError (SELECT in blacklist)
  - `order_by: liquidity_usd * (best_ask_price - best_bid_price) DESC` → ValueError (whitelist rejects arithmetic)
  - `limit: True` → ValueError (bool rejected)
  - `limit: 1000000` → ValueError (DoS cap)
