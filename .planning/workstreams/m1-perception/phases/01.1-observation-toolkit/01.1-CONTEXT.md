## 起源 — 为什么需要这个 Phase

Phase 1 已经把 Polymarket subset 数据（liquidity > $1k）落进 SQLite + Parquet（20353 markets，3 个 snapshot），但用户**无法实际"观察理解"市场**。

SESSION 12 用 visidata 实战 30 分钟暴露的真实 gap：

1. **没有观察工具，只有原始表** — 21 列直接看眼花
2. **没有跨 snapshot 比较** — 看不到 mid/liq/spread 漂移
3. **ghost_book 32668 条 (72%)** 还没消化分类
4. **question 字段英文** — 用户中文母语，扫描速度被语言摩擦吃掉一半
5. **没有 category 字段** — Phase 1 漏抓 Gamma 已有的 tag/category

**目标**：让用户（中文母语初学者）打开终端，30 秒内能判断一个市场该不该碰；10 分钟内能扫完一份 daily snapshot 圈出 3-5 个值得跟踪的市场。

**这是"为进入市场做准备"的第一步**，不是 demo。

## SESSION 12 visidata 实战发现（CONTEXT 输入）

### 市场结构事实
- subset 模式 20353 markets 中，**4.6% (946) 是 thick-but-slippery**（liq>$100k AND spread>$0.10）
- 体育话题在 thick-but-slippery 中占主导（用户主观印象，待 T1 category 字段后数据验证）
- question 主要句式 "Will the X happen by Y?" — 时间锚点是 Polymarket 市场的核心维度

### TUI 设计教训（留给 Phase 1.9，不在本 phase 实现）
- 终端表格列多 = 信息密度低 → 主列表+详情面板分屏，不要照搬表格视图
- visidata 的 hide vs delete 语义混淆（`-` vs `gd`）→ TUI 撤销机制要明确 + 上屏提示
- 快捷键上下文相关（同一键在 columns sheet 和主表语义不同）= 认知负担 → 全局快捷键应一致
- visidata 对只读 source 的 undo 不可靠 → 我们的 TUI 撤销必须在所有 sheet 类型一致工作

## 锁定决策（Plan 阶段不再讨论）

### T1 — markets 表补 category / tags 字段

- **来源**：Polymarket Gamma API `/markets` 返回里已有的字段
- **scope**：在 Phase 1 现有 `gamma_client.fetch_all_active_markets` 抓取流程里，把 `category` + `tags`（数组）一并抓回；snapshot schema 升级
- **schema 变化**：`markets` 表加 `category TEXT` + `tags TEXT`（JSON 数组字符串，留作后续 normalize）
- **老数据处理**：清空现有 SQLite + parquet（详见"Phase 1.1 收尾动作"），新 snapshot 自然带上字段；不重抓历史
- **安全考虑**：tags 是 Gamma 返回的，无需 sanitize（已有 Phase 1 F-4 fixture sanitization 覆盖）

### T2 — question 中文翻译（独立缓存表）

**API 选择**：
- 用 `openai` 官方 SDK，`base_url` 指向任意 OpenAI 兼容服务
- 用户提供 `.env` 里三个变量：`TRANSLATION_API_BASE` / `TRANSLATION_API_KEY` / `TRANSLATION_MODEL`
- **不绑 Anthropic**，不内置默认 endpoint（避免误用未配置 API 时静默失败）

**数据模型**：
```sql
CREATE TABLE question_translations (
  question_hash    TEXT PRIMARY KEY,    -- sha256 of question_en (de-duped)
  question_en      TEXT NOT NULL,        -- 原文
  question_zh      TEXT NOT NULL,
  translator_model TEXT NOT NULL,        -- e.g. "deepseek-chat"
  translated_at_ms INTEGER NOT NULL,
  token_cost       INTEGER,              -- 累计成本观测用
  retry_count      INTEGER DEFAULT 0,    -- 失败重试 counter
  is_dead          INTEGER DEFAULT 0     -- retry > 3 永久标记
);
-- markets 表不加列，查询时 LEFT JOIN
```

**批量策略**：
- 每批 **20 条** question 给 LLM（balance token cost vs retry 成本）
- 输入 JSON 数组，输出 JSON 数组（强制结构化）
- prompt 模板要求：保留 hedge 词（"by April 30, 2026" / "before market close" / "according to official source"）—— Polymarket question 这些词决定结算逻辑
- 并发 `max_concurrency: 10`（可配，默认温和）

**失败处理**：
- 单条失败 → skip 留 NULL，`retry_count++`
- 整批失败（API 网络错误）→ 整批 retry 一次
- `retry_count > 3` 标记 `is_dead=1`，不再尝试，可手动 reset
- **第一版不做反向翻译质量检测**（节省成本，等出现"翻译离谱"问题再加）

**触发**：
- snapshot 完成后自动跑（在 `polyarb.snapshot` orchestrator 末尾加一步）
- 也支持独立命令 `make translate-pending` 手动触发
- 只翻译 `question_translations` 缺失的 question，已翻译的零成本

**成本观测**：
- `make translation-stats` —— 显示累计翻译条数、token 数、按 model 分组成本估算

### T3 — 配方化扫描命令（SQL where 配方）

**Batch 1 — 第一版必做（6 个）**：

| Name | Where 条件（SQL） | Order | 价值 |
|---|---|---|---|
| `scan-thick-but-slippery` | `liquidity_usd > 100000 AND (best_ask_price - best_bid_price) > 0.10` | `liquidity_usd * (best_ask_price - best_bid_price) DESC` | 陷阱市场 |
| `scan-near-end` | `end_time_ms BETWEEN strftime('%s','now')*1000 AND strftime('%s','now','+72 hours')*1000 AND liquidity_usd > 1000` | `liquidity_usd DESC` | 套利窗口最密 |
| `scan-ghost-suspicious` | `incomplete = 1 AND liquidity_usd > 10000` （ghost_book 在 incomplete 字段或 validation_issues 表里，plan 阶段确认） | `liquidity_usd DESC` | 数据异常调查 |
| `scan-coin-flip` | `mid_price BETWEEN 0.45 AND 0.55 AND end_time_ms < strftime('%s','now','+7 days')*1000 AND liquidity_usd > 5000` | `volume_usd DESC` | 高不确定性套利窗口 |
| `scan-neg-risk-incomplete` | （多腿组合：按 neg_risk_market_id 分组，组内 mid_price 加和 ≠ 1.0 ± 容差） | mismatch DESC | **M2 套利直接信号** |
| `scan-by-category` | `GROUP BY category`，统计市场数 / 总 liq / 平均 spread | 市场数 DESC | 市场结构鸟瞰 |

**Batch 2 — 第二版（推迟，列表存档备用）**：
- `scan-fresh-mover` — 跨 snapshot mid 漂移 > X%
- `scan-extreme-priced` — mid<0.05 OR mid>0.95 + liq>$10k
- `scan-one-sided` — 只有 bid 或只有 ask
- `scan-bid-ask-cross` — best_bid > best_ask（订单簿 broken 信号）
- `scan-just-created` — createdAt 24h 内
- `scan-perpetual` — end_time_ms IS NULL
- `scan-thin-but-active` — volume_24h>$10k AND liq<$5k
- `scan-mid-mismatch` — abs(mid - (bid+ask)/2) > 5c
- `scan-dead-volume` — volume_24h=0 AND liq>$50k

**Batch 3 — 自定义配方机制（必做，用户明确要求）**：

`config/scan_recipes.yaml` 用户可编辑文件，schema：

```yaml
recipes:
  my-watchtower:
    description: 我每天早上看的市场组合
    where: |
      liquidity_usd > 50000
      AND end_time_ms < strftime('%s', 'now', '+7 days') * 1000
      AND category IN ('Politics', 'Crypto')
    order_by: liquidity_usd DESC
    limit: 50
```

- 内置配方写死在代码里（`src/polyarb/observation/recipes.py`）
- 用户配方从 yaml 加载（同名以用户为准，或加 prefix 防冲突——plan 阶段决定）
- `make scan <name>` 通用入口，能跑内置 + 用户自定义
- **安全约束**：where 子句只允许 SELECT 上下文（参数化 query，禁止 DDL/DML）

### T4 — 跨 snapshot 对比命令（duckdb 跨 parquet）

**两种形态都做**：

**A. 固定两 snapshot 对比** `make compare from=<id> to=<id>`：
- 输出：哪些 mid 飘了 / 哪些 liq 涨跌 / 谁消失了 / 谁新出现
- 默认 `from=N-1, to=N`（最近两个），用户可指定任意 ID
- 实现：duckdb 直接 `SELECT ... FROM read_parquet('a.parquet') a JOIN read_parquet('b.parquet') b USING (market_id)`

**B. 单市场时序追踪** `make track-market <slug>`：
- 输出：该 market 在所有 snapshot 中的 mid / spread / liq / vol 历史
- 实现：duckdb glob 跨所有 parquet：`read_parquet('data/snapshots/**/*.parquet')`

### T5 — 单市场详情命令

`make show-market <slug>` —— 输出：

- 完整 question（中英对照）
- 所有原始字段（21 列全部）
- 时间维度信息（距结算还有多久）
- 跨 snapshot 简略时序（mid/spread/liq 最近 5 个 snapshot）
- 如属 neg_risk 组，列出同组其它 market

### T6 — 类别统计命令

涵盖在 T3 的 `scan-by-category`，**不单列**。

### T7 — Watchlist（YAML 文件）

`watchlist.yaml`（项目根，gitignore？plan 阶段决定）：

```yaml
- slug: will-trump-win-2024
  reason: 临近大选，跟踪长尾
  alert_when: spread < 2c
  added: 2026-05-02
- slug: ...
```

- `make watchlist` —— 列出所有 watchlist 市场当前状态
- `make watchlist-alerts` —— 检查 `alert_when` 条件，触发的市场打印高亮
- 用户手编 YAML（git diff 友好，跨设备同步用 git）

### 输出格式

**默认 A + C 同时**：
- A. 终端彩色表格（rich 或类似库渲染）—— 直接看
- C. 自动落 parquet 一份在 `data/scans/<scan-name>/<timestamp>.parquet` —— 追溯/二次分析（用 visidata / harlequin / duckdb）

**不做 B (CSV/TSV stdout pipe)** —— 用户可直接用 visidata 打开 parquet。

### Phase 1.1 收尾动作
