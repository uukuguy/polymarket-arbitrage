# Phase 01.1 Learnings: observation-toolkit

> Phase 01.1 把"原始 Polymarket 表 + 没有观察工具"升级为"6 个 scan 配方 + 跨 snapshot diff + 单市场详情 + watchlist alert + 中英对照"的完整观察能力面。代码层面 6 个 plan 全部 ship，但真正的产出是两份 thread（架构方向 + 部署形态），它们直接驱动 Phase 02 设计。
>
> 11 个 plan，402 m1-perception tests green，11 个 commit + 4 个 acceptance amendment commit（已超出 plan 06 scope，由用户实跑验收触发），1 个工程纪律基础设施补强（pre-commit hook + planning-status drift detector）。

## Decisions

### D1 — Schema 双源融合：events + event_tags 独立表，markets 用 event_id FK
保留 markets 主表 + 新建 events / event_tags 两张表，markets 加 `event_id` 外键。`/markets` endpoint 不返回 category/tags，但 `/events` 全有。

**Rationale:** Wave 1 Step 4 schema 验证发现 Gamma `/markets` 返回 category=None / tags=None。CONTEXT 原设计"markets 表加 category/tags 列"被 Amendment 01 推翻。新设计抓 /events 建独立表，反查映射注入 markets.event_id；同时 events 表的 PK = (id, snapshot_id) 让 event 元数据漂移可跨 snapshot 跟踪。
**Source:** 01.1-CONTEXT-AMENDMENT-01.md / 01.1-01-SUMMARY.md

### D2 — 翻译 sidecar：独立 question_translations 表 + LEFT JOIN，不绑 markets
翻译数据走独立缓存表，questions 通过 sha256 hash + LEFT JOIN 拼回。

**Rationale:** 翻译跨 snapshot 高度可复用（同 question 永远不变），绑 markets 列会重复存储 + 每次 schema 升级都要重处理；独立表 + JOIN 让翻译模块完全旁路于 snapshot 主流程。
**Source:** 01.1-CONTEXT.md (T2) / 01.1-02-SUMMARY.md

### D3 — 4 层 SQL 注入防御（trust-split scanner）
yaml 用户配方走完整 4 层（read-only URI / 黑名单 / 白名单 / int range），内置 6 配方因为是 git 受控走 `_is_trusted=True` 绕过 2/3 层但仍走 1/4 层。

**Rationale:** 内置配方需要算术 ORDER BY (`liquidity_usd * spread DESC`) 这类语义合法但被白名单拒绝的语句；yaml 是不受信任输入，必须严格限制。Trust split 通过 `Recipe._is_trusted` 布尔 + validator 的 `trusted` 参数实现，layer 1（engine-level）和 layer 4（DoS guard）对所有路径强制生效，没有 trust bypass。
**Source:** 01.1-03-SUMMARY.md / 01.1-03-PLAN.md

### D4 — Watchlist 用受限 AST walker，禁 Python 内置 eval/exec
`alert_when` 表达式走 `ast.parse(mode='eval')` + 自写 `_eval_node` 节点白名单遍历。源码中绝不出现 Python 内置 eval/exec 字面量调用，CI grep 测试守门。

**Rationale:** yaml 是用户配置不可信，任何 Python 内置 eval 都允许 `__class__.__bases__` 之类逃逸。AST 白名单（Expression/Constant/Name/UnaryOp/BinOp/Compare/BoolOp 7 类节点）+ 变量白名单（ALLOWED_VARS 11 keys）+ 数值常量限定 + 200 字符长度上限 = 受限 mini DSL。
**Source:** 01.1-05-SUMMARY.md (Decision 1)

### D5 — DuckDB 用 in-memory connect()，跨 parquet glob + union_by_name=true
`duckdb.connect()`（无 db file 路径）扫完即 close；`read_parquet(glob, union_by_name=true)` 应对 schema 漂移。

**Rationale:** in-memory 避免在 data/ 留 .duckdb 文件污染冷存；union_by_name 按列名对齐让"老 parquet 缺 event_id / 更早缺 category"自动 NULL 填充。前提：列名稳定，类型不可变 — 这是 schema 演进的硬约束。
**Source:** 01.1-04-SUMMARY.md / 教学文档 07-观察市场.md §设计取舍 4

### D6 — neg-risk-incomplete 容差 ±0.02
group_by HAVING tail：`HAVING ABS(SUM(mid_price)-1.0) > 0.02`。

**Rationale:** CONTEXT Open Question #2，neg_risk 组内 mid_price 理论上加和=1.0；2¢ 容差既覆盖 Polymarket 一般市场 spread 量级，又能筛出真正"组内未完整"的群。直接编码在 group_by HAVING 而非 Python 后处理 = 走 builtin trusted 路径。
**Source:** 01.1-03-SUMMARY.md / 01.1-CONTEXT.md Open #2

### D7 — `make snapshot-markets` 默认 subset，full 留作周/月审计
L1 "日级全量" 语义锁定 = subset（~23k 高流动性市场，10 分钟）。full（~54k 全市场，15-20 分钟）保留但限定为周/月审计工具，不作策略数据源。

**Rationale:** subset/full 跨模式实测（sid=7 full 15m19s / sid=8 subset 9m42s）。full 多抓 ~31k 个市场全是 liquidity ≤ $1k 的小池子 + 死市场；IMDEA $40M 套利 100% 来自头部市场（subset 完全覆盖）；full 的 15-20min 拖尾窗口翻倍且长尾 31k 市场漂移更不稳。"subset 元数据不全"是字面正确但策略目标 100% 完整，原表述误导。
**Source:** threads/market-observation-architecture.md §0.3#10 + §2.7 / STATE.md SESSION 15

### D8 — Phase 01.1 收尾清空老数据，重建带 event_id 的干净基线
不重抓历史，直接 wipe SQLite + 删 `data/snapshots/2026/`，重跑 `make snapshot-markets-v` 拿带 event_id 的新基线。

**Rationale:** 老 snapshot 没有 event_id 列 / 列布局不一致，强行迁移成本远高于重抓（Polymarket 历史价格在 Subgraph 还能补，不丢）。snapshot_id=1 (10450 events / 56022 event_tags / 20589 markets / 99.81% event_id 覆盖) 作为新基线。
**Source:** 01.1-CONTEXT-AMENDMENT-01.md / 01.1-01-SUMMARY.md

### D9 — Translation 用 OpenAI 兼容 SDK，base_url 指向任意 endpoint
不绑 Anthropic，不内置默认 endpoint；用户填 `.env` 三变量（API_BASE / API_KEY / MODEL）。

**Rationale:** 用户有 OpenAI 兼容服务（DeepSeek / Qwen / OpenAI / 其它），保持 vendor 无关。"不设默认 endpoint" 让未配置时立刻报错而非静默用错服务。SecretStr 包 api_key，max_retries=3 走 SDK 内置 retry（不上 tenacity，CI 测试守门）。
**Source:** 01.1-CONTEXT.md (T2) / 01.1-02-SUMMARY.md (Decision: SDK retry only)

### D10 — Translation 与 snapshot 解耦（amendment 后）
原 CONTEXT 设计 translation 在 snapshot orchestrator step 8/8 sidecar 自动跑；amendment commit `24f52ba` 解耦，translation 走独立 `make translate-pending`。

**Rationale:** acceptance 期间用户洞察"snapshot 把数据抓取与翻译耦合在一起"。decouple 之后：snapshot 不依赖 LLM endpoint 可用，translation 可独立 retry，is_valid 三态（OK/DEGRADED/FAILED）语义更纯净。
**Source:** 01.1-06-SUMMARY.md (Acceptance-driven amendments)

### D11 — Phase 02 部署形态：staging PaaS + prod 后期 DIY 的混合路线
Phase 02 起后端走 PaaS（Fly/Railway/Render 三选一），region 选欧洲（Polymarket AWS eu-west-2 London，主推 Fly AMS / Render Frankfurt），dashboard 走 Vercel + Supabase。

**Rationale:** 用户 §7 四锚点决策（2026-05-11）：PaaS vs DIY 选混合；CN 访问有 VPN 不强求 Cloudflare 友好；DB 先合并到 Supabase 单库撞墙再拆；KMS 延到 M3 实盘前。Phase 02 不动 KMS / 不上 Tiger Cloud 双库 / 不上 Cloudflare 回源。
**Source:** threads/deployment-architecture.md §0.1 + §7

### D12 — CLI 用 single-file typer module，不用 cli/ 包目录
`cli_observation.py` / `cli_translation.py` 是单文件，不开 `cli/` 子包。

**Rationale:** SESSION 11 namespace shadow 教训（package shadow 一个 module name 会 silent fail）。PATTERNS §5.3 已经把这条作为项目约定，本 phase 续用。
**Source:** 01.1-02-SUMMARY.md / 01.1-03-SUMMARY.md (Decision)

### D13 — Plan SUMMARY 是项目"可检索不失忆"的硬契约
任何 plan 的代码 commit 之后立即创建 `{phase}-{plan}-SUMMARY.md`；pre-commit hook 阻断缺 SUMMARY 的 plan-scoped commit；`make planning-status` 检测 DRIFT。

**Rationale:** Phase 01.1 plan 04/05/06 在 2026-05-09 落代码但未写 SUMMARY，2026-05-10 才发现并补 retroactive SUMMARY。retroactive 写法 metrics.duration 丢失 / 不可重建。教训：SUMMARY 不是 nice-to-have，是项目记忆锚点；写 hook + planning-status 把纪律工程化。
**Source:** 01.1-04-SUMMARY.md 顶部 retroactive 警示 / STATE.md / CLAUDE.md "每个 Plan 末"段

### D14 — Acceptance checkpoint 不是固定 Q&A，是动态升格机制
PLAN 06 Task 3 原设计是"5 题对手 Q&A → VERIFICATION.md"；实际用户给的是架构级洞察（"8 分钟全量是模糊影像不是主角"），原框架装不下，升格为 thread。

**Rationale:** "5 题问答收口"是 Phase 1 baseline 形成的范式，但当用户实跑暴露的反馈是架构方向问题时，再压回 Q&A 是把信号噪声化。升格为 thread = 把 architecture-level 反馈作为下一 phase 的 input，而不是当前 phase 的 output。
**Source:** 01.1-06-SUMMARY.md (Decision 1) / threads/market-observation-architecture.md (drafting)

## Lessons

### L1 — "我以为 API 有这个字段" 是 CONTEXT 阶段高频谬误源
SESSION 13 markets.category/tags 不存在 → 杀了 plan 01 第一版。继 SESSION 11 `filterDate` 假设证伪后第二次同型错误。

**Context:** CONTEXT 阶段没有 raw httpx curl 验证就直接写 plan，等到 Wave 1 实施才发现字段全 NULL。
**Source:** 01.1-CONTEXT-AMENDMENT-01.md 末尾 "教训"段

### L2 — fetched_at_ms 是 schema-level 的"误导性时间戳"
`orchestrator.py:340-343` 在 stage 5 (CLOB 完成后) 一次性 stamp 所有 target_markets，同一 snapshot 内 `COUNT(DISTINCT fetched_at_ms) = 1`。

**Context:** 下游消费者无法从 schema 知道某条 row 是 8 分钟里哪一秒抓的，所有"snapshot 内时间一致"的下游分析建立在虚假前提上。框架抽象 A（统一市场状态模型）必须显式分离 "stamp 时间 vs 抓取时间"。
**Source:** threads/market-observation-architecture.md §2.1.a 实证 #1

### L3 — Polymarket 薄市场结构：99% 市场全天无 trade
9 分钟跨 snapshot 实证（n=19,081）：99.15% 市场 mid 漂移恰好 = 0；1% 长尾才显著漂移。2 小时延伸（n=18,509）：97.77% 完全不变。

**Context:** 之前的假设"L1 是 8 分钟模糊影像，所有市场都有漂移"是错的 — 实际是 "99% 清晰 + 1% 严重失真"。漂移集中在少数有内生波动的市场上，恰好这 1% 就是策略目标人群。
**Source:** threads/market-observation-architecture.md §2.1.a 实证 #3 + #4

### L4 — Top movers 多为 0.50 锚价跳出，不是市场剧烈波动
2h 漂移 Top 5 全是 mid_run1=0.50 / mid_run2 偏离的对，0.5 是新开市场无人挂单的盘口默认锚价。

**Context:** 看上去"市场大幅移动"其实是"新流动性进入让默认锚价跳出"。真正的内生价格波动隐藏在 1-5¢ 那 0.93% 区间里。L3 K 线必须区分这两类源。
**Source:** threads/market-observation-architecture.md §2.1.a 实证 #4

### L5 — Gamma /events 翻页 ~4% 重复，必须 batch 内 dedupe
`normalize_events` 加 `seen_event_ids` set 在 batch 内按 event_id 去重，与 markets 翻页 dedupe 同性质。

**Context:** Task 4 跑 orchestrator dup 测试时 `_events_for_markets(duplicated)` 产生同 id 两个 event，触发 events.id+snapshot_id PK 冲突 → 整个事务 ROLLBACK。
**Source:** 01.1-01-SUMMARY.md Deviation #1

### L6 — INSERT OR IGNORE 不覆盖已存在 PK，placeholder 路径必须独立 UPDATE
`_overwrite_placeholders` 助手：先 INSERT OR IGNORE 覆盖 fresh 路径，再 UPDATE WHERE question_zh='' 覆盖 placeholder 路径，成功时重置 retry_count + is_dead。

**Context:** 第一版 translator 用纯 INSERT OR IGNORE，placeholder 行写下后永远不会被真实翻译覆盖；retry 测试发现 retry_count 卡在 1 永远到不了 dead=1。
**Source:** 01.1-02-SUMMARY.md Auto-added Critical #3

### L7 — `cache.list_untranslated` 必须包含 placeholder（is_dead=0 且 zh=空）
SELECT 加 OR 分支：`OR (qt.question_zh = '' AND qt.is_dead = 0)`，让 placeholder 行留在 untranslated pool 里直到 retry_count>3。

**Context:** Plan 02 Task 2 retry 测试发现 placeholder 写入后 list_untranslated 把它排除掉，后续 retry 找不到目标→ retry_count 永远不超过 1 → is_dead=1 永远不发生。
**Source:** 01.1-02-SUMMARY.md Deviation #1

### L8 — DeepSeek 强制结构化输出要求 prompt 含字面 "JSON" 关键字
`SYSTEM_PROMPT` 必须出现 "JSON" 字符串，否则 DeepSeek 不进入 JSON 模式。

**Context:** Translation 用 response_format=json_object 但 prompt 不含 "JSON" 字面 → DeepSeek 返回 markdown 包裹的 JSON / 自然语言混合。
**Source:** 01.1-02-SUMMARY.md (TranslationClient: SYSTEM_PROMPT includes literal "JSON")

### L9 — DuckDB FULL OUTER JOIN 的 ABS(NULL) 排序不稳定
不能直接 `ORDER BY ABS(b.mid - a.mid) DESC` — appeared/vanished 行 ABS 表达式是 NULL，NULL 排序不稳定。

**Context:** Plan 04 PLAN 骨架就是 `ABS(COALESCE(...,0))`，但 `b.mid - 0` 与 `0 - a.mid` 把"凭空 0 价"混入 top 排序。改用 `CASE WHEN NULL THEN 1 ELSE 0 + ABS(COALESCE(...)) DESC` 把单边行强制排末尾再按 drift 降序。
**Source:** 01.1-04-SUMMARY.md Refinement #1

### L10 — load_settings() 优先级 yaml > env，CLI 测试要直接 patch load_settings
`Settings(**yaml_data)` 让 yaml 文件覆盖 env vars；CLI 测试用 monkeypatch env path 会被 yaml 覆盖。

**Context:** Plan 03 Task 2 `test_cli_scan_runs_thick_but_slippery` 跑到了真实 baseline DB (20589 markets) 而不是 1-row 测试 fixture。fix: 直接 patch `polyarb.cli_observation.load_settings` 返回 closure-bound Settings。
**Source:** 01.1-03-SUMMARY.md Auto-fixed #2

### L11 — `make snapshot-markets` 系列 silent failure 暴露 Makefile 是单点
Typer 重构后 CLI 入口改 `python -m polyarb.snapshot snapshot`，但 Makefile 5 个 target 仍用旧 `python -m polyarb.snapshot` → typer 显示 help → exit 0 → 用户以为成功。

**Context:** SESSION 15 acceptance 实跑发现 `make snapshot-markets-v` 立刻"完成"没抓数据。教训：CLI 升级要把 Makefile 当 first-class 测试目标（make 入口断裂 silent failure 比代码 bug 更难发现）。修复在 commit b2a2e0d。后续应该把 `make --no-builtin-rules <target>` 加 smoke test。
**Source:** STATE.md SESSION 15 / threads/market-observation-architecture.md §2.5.a (CLI 入口断裂)

### L12 — "snapshot is_valid" 二态太粗，必须三态 OK/DEGRADED/FAILED
原本 `is_valid: bool`，但 L1 count jitter ≤ 1% 应当算 DEGRADED 不是 FAILED。Translation 失败让整个 snapshot 标 invalid 是污染。

**Context:** Acceptance 期间用户洞察"snapshot validation 是 binary 的"，并入 amendment commit `24f52ba`。三态后 latest_snapshot_pair 过滤的逻辑也清晰：只挑 OK 跑 diff，DEGRADED 单独标记。
**Source:** 01.1-06-SUMMARY.md (Amendment 24f52ba)

## Patterns

### P1 — Trust split 工厂方法 + validator 守门
`Recipe.from_builtin(...) → _is_trusted=True`，`Recipe.from_yaml(...) → _is_trusted=False`；validator 接 `trusted: bool` 参数决定是否绕过黑/白名单。Layer 1 (engine-level read-only) 和 Layer 4 (DoS guard) 对所有路径强制。

**When to use:** 任何"git 受控 vs 用户提供"的 dual-source 配置/规则系统。m2 套利规则、m4 LLM prompt 模板都可复用。
**Source:** 01.1-03-SUMMARY.md (Trust split implementation)

### P2 — Restricted AST expression evaluation
`ast.parse(mode='eval')` + 递归 `_eval_node` walker + 节点白名单 + 变量白名单 + 数值常量限定 + 长度上限。绝不调用 Python 内置 eval/exec，CI 字符串扫描守门。

**When to use:** 任何用户配置文件里需要"小型表达式语言"的场景（watchlist alert、scan 过滤条件、m4 策略门槛）。比内置 eval 安全，比 LangChain expression 轻。
**Source:** 01.1-05-SUMMARY.md (patterns-established #1)

### P3 — Multi-source single-entity detail composition
单一 dict 返回值，内部融合 SQLite (热) + DuckDB Parquet (冷) + 跨表 JOIN + cross-snapshot tail；CLI 按段渲染。`show_market` 是 reference 实现。

**When to use:** 任何"详情视图"场景。m2 套利机会单条详情、m4 策略 explain 视图都应该走这个 pattern 而不是各起一套查询。
**Source:** 01.1-05-SUMMARY.md (patterns-established #2)

### P4 — Fail-soft load with dry-run validation
yaml 加载时即用 dummy dict 跑一次表达式求值；坏表达式 → `logger.warning + alert_when=None`，entry 保留但 alert 禁用。

**When to use:** 任何"用户配置文件 + 单条坏数据不应整文件爆"的场景。配置即代码场景的稳健性比单条 fail-loud 重要。
**Source:** 01.1-05-SUMMARY.md (patterns-established #3)

### P5 — Two-path error mapping：ConfigError 致命 / TransientError retry++
Translation 的 11 类 openai/pydantic 异常映射表：Authentication / NotFound / 部分 BadRequest → ConfigError (exit 1)；APIConnection / APITimeout / RateLimit / InternalServer / ValueError → TransientError (retry_count++)。

**When to use:** 任何"外部 API + 自动 retry" 场景。把 fatal 错误（key 错 / model 不存在）和 transient 错误（限流 / 5xx）分开，前者立刻 fail loud 后者吞掉 + retry counter。
**Source:** 01.1-02-SUMMARY.md (ConfigError vs TransientError table)

### P6 — `resolve_snapshot_path`: int → read-only SQLite lookup → DuckDB
用户永远不传裸路径，只传 snapshot_id (int)；int 校验 + `file:...?mode=ro` URI lookup + DuckDB 参数化查询。永不字符串拼 path/glob。

**When to use:** 任何"用 ID 而不是路径作为用户输入"的 cross-snapshot 工具。M1.2 quality scorer、M1.3 watchlist diff 都将复用。
**Source:** 01.1-04-SUMMARY.md (decisions: resolve_snapshot_path 模式)

### P7 — Schema 演进硬约束："只能加列不能改类型"
DuckDB `union_by_name=true` 仅对齐列名，不对齐类型。schema 升级必须"加列 + NULL 默认"，绝不"删列 + 加同名不同类型列"或"改列类型"。

**When to use:** 任何 parquet 长期归档 + 跨版本读取的场景。改 schema 前先问"老 parquet 还能读吗"。
**Source:** 01.1-04-SUMMARY.md (Decision) / docs/learning/07-观察市场.md §设计取舍 4

### P8 — Plan SUMMARY 落地三件套：pre-commit hook + `make planning-status` + CLAUDE.md 纪律
工程化"plan 末必出 SUMMARY"：(1) `.githooks/pre-commit` 阻断缺 SUMMARY 的 plan-scoped commit；(2) `scripts/planning_status.py` 扫描 + `make planning-status` 报告 DRIFT；(3) CLAUDE.md "每个 Plan 末"条目强制要求。

**When to use:** 任何长周期项目的"文档同步代码"纪律落地。比"约定俗成"强，避免文档漂移积累。
**Source:** 01.1-06-SUMMARY.md (Phase 01.1 收尾 #3) / process_planning-hygiene-infrastructure memory

## Surprises

### S1 — Phase 01.1 真正的产出是两份 thread，不是 6 个 plan 的代码
代码层面 6 个 plan + 402 tests + 11 commits 都按计划落地，但 phase 真正的价值产出是 `market-observation-architecture.md`（三层金字塔 + 平台框架抽象层）+ `deployment-architecture.md`（872 行云栈选型 + 用户 4 锚点决策）。它们直接驱动 Phase 02 设计。

**Impact:** "phase 完成 = 计划任务全 ship" 是错的；phase 完成 = "下一 phase 的输入已就位"。本 phase 的 plan 是 vehicle，洞察才是 cargo。
**Source:** threads/market-observation-architecture.md (drafting) / threads/deployment-architecture.md (locked) / 01.1-06-SUMMARY.md

### S2 — 99% 市场 9 分钟内 mid 漂移 = 0
预期是"8 分钟模糊影像，所有市场都有漂移"，实测是 99.15% 完全静止 + 1% 长尾。Polymarket 薄市场结构在数据特征上是"99% 清晰 + 1% 严重失真"。

**Impact:** L1 用于日级画像 / 候选池完全够用（原以为可能要降级为 demo）；L2 定向跟踪的价值来自切出那 1% 长尾市场。三层金字塔架构在数据上有实证支持。
**Source:** threads/market-observation-architecture.md §2.1.a #3

### S3 — `make` 注释的 "~1-2 hours" 和实测的 "15-20 分钟" 差一个数量级
full snapshot 模式 CLI 注释写 "~1-2 hours" 是 Phase 1 LIVE-RUN-001 (26m25s, 北美白天高峰) 推断的 worst case，2026-05-11 实测 typical 是 15m19s。

**Impact:** "全量 = 慢 = 周/月跑"的预设有数量级误差；实际上 full 每天可以跑一次而不只是周/月。但仍然不该用 full 当 L1 主力（多抓的 31k 长尾市场不是策略目标）。
**Source:** threads/market-observation-architecture.md §2.1.a #2 + §2.7 / STATE.md SESSION 15

### S4 — Polymarket 在 AWS eu-west-2 (London)，不在美东
部署 thread 调研发现 Polymarket 后端 region 是 London，不是预设的 us-east-1。

**Impact:** 后端 region 选 eu 主流（Fly AMS / Render Frankfurt）而非美东，对所有 API 调用延迟敏感的 daemon 有直接影响。Phase 02 不再考虑美东 VPS。
**Source:** threads/deployment-architecture.md §0.2.1.b + §8 引用

### S5 — Phase 01.1 plan 04/05/06 落代码后 SUMMARY 缺失了一整天
2026-05-09 commit `f7a02cf` / `049705d` / `ac4f334` 全部 ship 代码 + 测试，但没走 `gsd-execute-plan` 的 `create_summary` step，SUMMARY 文件缺失到 2026-05-10 才被发现。

**Impact:** 触发 Phase 01.1 工程纪律基础设施补强（pre-commit hook + planning-status drift detector + CLAUDE.md plan-末纪律明文化）。"约定俗成"不够，必须工程化。
**Source:** 01.1-04-SUMMARY.md / 01.1-05-SUMMARY.md / 01.1-06-SUMMARY.md (retroactive 警示段)

### S6 — Task 3 PLAN 设计的 "5 题 Q&A" 装不下用户的架构级反馈
Plan 06 Task 3 设计是 Claude 提 5 题 → 用户答 → 写 VERIFICATION.md。实际用户在 E2E 验收时给的洞察"8 分钟全量是模糊影像不是主角"是架构方向问题。

**Impact:** Task 3 升格为 thread，Phase 01.1 不再产出 VERIFICATION.md，靠 thread + SUMMARY + extract_learnings 三件套闭口。Acceptance checkpoint 不能预设"反馈一定能塞进固定 Q&A 模板"。
**Source:** 01.1-06-SUMMARY.md (Decision 1 + Deviation 1)

### S7 — "subset 元数据不全"是字面正确但策略目标 100% 完整
SESSION 15 之前的判断"subset 缺失元数据 → 不完整 → full 才是 ground truth"是片面的；subset 缺的 31k 市场全是 liquidity ≤ $1k 的小池子 + 死市场，IMDEA $40M 套利 100% 在头部市场（subset 完全覆盖）。

**Impact:** L1 "日级全量" 语义重新锁定为 subset，不再说"先跑一次 full 当基线"。"看上去更全" ≠ "对目标更完整"。
**Source:** threads/market-observation-architecture.md §2.7.f / STATE.md SESSION 15

### S8 — 自动批准 plan 阶段后再走 amendment 反而比 plan 内多决策更高效
Phase 01.1 多次出现"plan 内决策 → 验收发现要调整 → amendment commit"模式（Translation 解耦 / make overview / E2E guide / SUMMARY 三件套）。提前预想 "plan 必须 100% 完整" 反而拖慢节奏。

**Impact:** plan 阶段锁"必要决策" + acceptance 阶段允许"非 scope amendment"是更健康的节奏。Plan completeness 不等于 perfection，over-planning 的代价是延迟 first ship。
**Source:** 01.1-06-SUMMARY.md (Acceptance-Driven Amendments 段) / 反复发生的"plan vs amendment"节奏
