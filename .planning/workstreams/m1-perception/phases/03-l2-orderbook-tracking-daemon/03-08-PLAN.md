    ## 30 秒心智模型

    polyarb-l2 是独立 Fly 进程 (vs polyarb-l1 cron daemon). 数据流是 "Polymarket WS → WsConsumer → L2SupabaseMirror → Vercel dashboard"; 控制流是 "L1 cron → NOTIFY snapshot.complete → L2 LISTEN → candidate_refresh → diff → WS subscribe".

    ```
    ┌─ polyarb-l1 (existing) ──────────────┐         ┌─ polyarb-l2 (Phase 03) ──────────────┐
    │ cron 每 6h → Gamma+CLOB snapshot     │         │ WsConsumer (long-lived asyncio task)  │
    │ → SQLite + Supabase mirror + R2     │         │ WsWatchdog 30s — issue #292 mitigation│
    │ → pg_notify('snapshot_complete') ───┼─────────┤ EventListener (asyncpg LISTEN)        │
    │                                     │         │ → on_snapshot_complete                │
    │                                     │         │ → compute_candidates (recipe ∪ list)  │

    │                                     │         │ → ws_consumer.subscribed_assets 更新  │
    └──────────────────────────────────────┘         │ → L2SupabaseMirror 写 4 张表          │
                                                     └─ Vercel dashboard 4 页 (D-07) ────────┘
    ```

    故障路径: WS 30s 无 event → WsWatchdog 触发重连 (退避 1/2/4/8/16/30s); >10 重连/小时 → DEGRADED_REST_POLLING (R5 防 IP-ban).

    ## 关键代码片段

    ### WS 数据平面

    **`src/polyarb/clients/ws_market_client.py:<XX>`** — async iterator + reconnect-iterator 形式 (websockets 16+):

    ```python
    async for ws in websockets.connect(
        WS_URL, ping_interval=10, ping_timeout=10, max_size=2**22,
    ):
        try:
            await ws.send(json.dumps({"type":"market","assets_ids":...,"initial_dump":True}))
            async for raw in ws:
                yield json.loads(raw)
    ```

    三个关键值:
    - `ping_interval=10` — Polymarket 服务器 10s 没流量就断, NOT 20s 默认 (`src/polyarb/clients/ws_market_client.py:<XX>`)
    - `max_size=2**22` — 4 MiB 帧上限, initial_dump 时的 book snapshot 可能超过默认 1 MiB
    - `async for ws in connect(...)` — 16+ 的 reconnect-iterator 写法, 不要写成 `async with`

    ### WS 业务层心跳 (Issue #292 mitigation)

    **`src/polyarb/daemon/ws_watchdog.py:<XX>`** — state machine:

    ```python
    _BACKOFF_S = (1, 2, 4, 8, 16, 30)   # D-03 + R5

    async def watch(self, stop_event):
        while not stop_event.is_set():
            elapsed = time.monotonic() - self._state.last_event_time_s
            if elapsed > self.stale_s:    # 30s
                await self._on_stale()    # 触发 on_reconnect + 退避
            else:
                await asyncio.wait_for(self._last_touch_event.wait(), ...)
    ```

    ## 设计取舍

    ### 1. 为什么独立 daemon (D-06)?

    Crash 隔离: WS 重连风暴不影响 L1 cron; L1 cron crash 不影响 L2 实时流. Chaos verification 独立做.

    单 binary 双部署: 同 Dockerfile, 两 `fly.toml`. polyarb-l2 不带 cron 进程组.

    ### 2. 30s watchdog 而不是 Polymarket PING?

    Polymarket PING 是 TCP 层 keepalive. Issue #292: TCP 没断, PONG 仍回, 但 event 流冻结. 唯一可靠信号 = 业务层 event-presence.

    30s 是 RESEARCH 推荐值 — 平衡误报 vs 时延. 流动性差的市场可能误报 — INFO log + Sentry breadcrumb (NOT alert), 7 天 soak 观察.

    ### 3. Postgres NOTIFY 而不是 Redis Pub/Sub?

    D-05: Phase 03 初期复用 Supabase Pro 投资 (90 连接池够用), 不引新基础设施. Phase 04+ 多 daemon 时再考虑 Redis.

    NOTIFY 8000-byte 上限, payload ~80 bytes, 安全. 持久化用 `l2_event_cursor` 补 LISTEN 漏掉的.

    ### 4. 候选集 500 cap?

    R9: initial_dump=true 时, 500 个 token 的 book snapshot 已经几 MiB; 1000+ 会撞 `max_size=2**22` 上限或超时. Watchlist 永远保留 (用户钉住的); recipe 按 ranking_score liquidity 截断.

    ### 5. fail-soft 双锚点 (Phase 02.2 preemptive)?

    Phase 02.1 L1 教训: daemon fail-soft 跳过, daemon 不 crash → Sentry breadcrumb buffer 永远不 upload. 解 = 成功路径也 emit breadcrumb (level=info), 至少一条 visible.
