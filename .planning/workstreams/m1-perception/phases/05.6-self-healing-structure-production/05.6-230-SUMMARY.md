# 05.6-230 Summary — Prove live-attempt heartbeat recovery

## Outcome

- Added a cleanup-safe `heartbeat-outage` commissioning adapter for all eight
  M1 production nodes. It stops issuing the worker heartbeat after the real
  transaction's durable progress checkpoint and advances only through the
  persisted policy clock; no lease/runtime row is aged directly.
- While the exact lease is still current, `RuntimeReconciler` must classify the
  candidate as the warning/non-breaking `job.lease-at-risk -> heartbeat-job`
  decision. Lease expiry, reclaim, process restart and Machine restart are all
  rejected outcomes for this fault stage.
- The real `RecoveryExecutor` executes one database-fenced heartbeat action
  using the persisted lease duration. The durable runtime state must retain the
  same attempt ID, worker owner and lease epoch while extending both job and
  runtime lease deadlines exactly.
- The renewed lease capability—not the pre-renewal object—then completes the
  same prepared business transaction and closes the warning incident through
  its real terminal success and node-specific business postcondition.

## Executable workflow

- Extended the shared isolated harness with the `heartbeat-outage` command,
  preserving one migrated database per node and owned-resource cleanup.
- Added `make m1-production-commissioning-heartbeat-outage`, requiring an
  explicit loopback-only test DSN plus exact release/config identity. It has no
  production fallback, node-skipping CLI or all-run timeout.
- Registered H-043 and added the eight-node adapter, isolated one-node harness
  and exact Make argv cases to the deterministic production-enablement profile.

## Chain-truth evidence

- Eight real-PostgreSQL tests prove exactly one attempt at epoch 1, eventually
  succeeded with no error class; no replacement attempt or recovery restart is
  permitted.
- Each test proves one completed successful `heartbeat-job` action, one warning
  incident that becomes resolved, one `job.recovery-started` event classified
  as `job.lease-at-risk`, and a causal node business postcondition.
- The persisted `last_heartbeat_at` equals the action's logical `started_at` and
  the renewed deadline equals that time plus `profile_lease_seconds`. Action
  `finished_at` remains the database transaction's real wall-clock completion
  and is intentionally not conflated with logical policy time.
