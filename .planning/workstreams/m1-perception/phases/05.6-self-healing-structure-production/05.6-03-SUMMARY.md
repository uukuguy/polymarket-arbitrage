# Plan 05.6-03 Summary: Resumed issue-source keyset performance

## Root cause

Production `EXPLAIN QUERY PLAN` for the resumed issue normalizer showed that
the old query materialized the entire market/event-only union before applying
the cursor. Every bounded chunk therefore scanned candidates again and created
temporary B-trees for `COUNT(DISTINCT event_id)` and ordering. The active
window contains 130,555 market rows and 165,347 event-market rows, making this
a material recovery latency risk even though every child checkpoint progressed.

## Delivered

- Cursor predicates now apply independently to market and event-only inputs;
  each source is bounded before the final ordered union.
- The event-only singleton proof uses `COUNT(*)=1`; the staging primary key
  `(window_id,event_id,market_id)` makes this equivalent to distinct event
  cardinality for a grouped market identity.
- Added a 2,000-row tail-resume regression with SQLite opcode measurement.
  The old query performed 17,700 instructions for the final 50 rows and
  failed the test's 10,000-instruction budget; the repaired query completes in
  about 7,800 instructions while preserving exact ordering.

## Verification

## Remaining production gate

The currently running publication started on the prior release and is left
