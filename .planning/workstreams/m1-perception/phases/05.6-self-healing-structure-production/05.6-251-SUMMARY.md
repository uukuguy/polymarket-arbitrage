# Plan 05.6-251 Summary: Bounded Database Pressure and Terminal Stale Inputs

**The release replaces per-transaction PostgreSQL connection churn with bounded
session reuse and prevents immutable stale Quote inputs from consuming retry
budgets and opening circuits.**

## Production evidence and root causes

- Under a fresh Structure generation, five `structure-normalize` jobs failed at
  `psycopg.connection.connect`, while the independent API intermittently
  returned typed 503 responses. The common connection factory created a new
  TCP/TLS/libpq session and repeated session bootstrap for every claim,
  heartbeat, progress and receipt transaction across 12 concurrent lanes.
- Temporary targeted recovery reduced all 146 legacy Quote circuits to zero.
  The controller was then restored from `execute` to `observe-only` with every
  other Machine config field and the exact image digest preserved.
- A newly observed `opportunity-certify` circuit contained three identical
  `StaleQuoteGenerationError` attempts. Re-executing the same immutable Quote
  generation can only increase its age, so retry was structurally incapable of
  recovery.

## What changed

- `ScopedConnectionFactory` now owns one lazy `psycopg_pool.ConnectionPool`,
  exposes bounded safe counters and closes explicitly. Worker owners cap at 32;
  the API divides that same process authority into 31 operational and one
  readiness connection.
- `OperationalError`, `PoolTimeout`, `TooManyRequests` and `PoolClosed` map to
  `database.unavailable`. Typed 503 responses include only pool size,
  availability, waiting and error counters; successful responses remain
  unchanged.
- API shutdown, general CLI commands, runtime policy replay and qualification
  commands close their pool owner in `finally`. Qualification construction
  reuses the already role-verified factory instead of silently creating a
  second pool.
- Incomplete Quote generations remain retryable. Stale Quote generations now
  commit a terminal quarantine, a warning freshness incident with
  `qualification_breaking=true`, and closure of any existing circuit in one
  transaction. A fresh successor job continues to close the shared freshness
  incident through the existing recovery chain.
