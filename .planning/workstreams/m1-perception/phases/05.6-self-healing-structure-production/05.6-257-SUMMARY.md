# Plan 05.6-257 Summary: Remove Qualification Consumer Starvation

Production showed the qualification worker applying exactly 100 facts on almost
every 30-second tick while the runtime continued producing facts. A successful
fresh Opportunity pointer therefore did not make the epoch eligible: the cursor
could not reach the new freshness fact when ingress rate met or exceeded the
hard-coded consumer ceiling.

`QualificationService.tick` still reads and commits at most one configured page.
Its result now states whether that source page was full. The sequential service
loop yields once to the asyncio scheduler when full and immediately starts the
next bounded tick; a short page retains the normal 30-second polling wait. There
is still one writer, one cursor CAS, no overlapping tick and no unbounded
transaction. SIGTERM can be observed between every page and the existing
cooperative database stop path remains unchanged.

The production template continues to make the page size and idle cadence
explicit (`100`, `30s`). Throughput is no longer calculated as `page / cadence`:
the cadence now means “how often to poll an idle source,” not “how long to sleep
while known backlog exists.” The tick JSON exposes `source_batch_full` so a
future control-plane projection can report catch-up pressure without guessing
from `applied == 100`.

Deployment proof remains required after the exact release is committed and
built: the existing epoch must retain identity/cursor, consume the pending
Opportunity freshness fact, transition to eligible and advance
`eligible_seconds` without a breaker.
