runtime evidence: one start event, monotonic meaningful progress, and one
terminal success fact, without depending on the periodic sampler as the primary

## Eight covered job types

The Task 5 gate asserts the exact real `RUNTIME_STAGE_REGISTRY` keys:

1. `structure-fetch`
2. `structure-materialize`
3. `structure-normalize`
4. `structure-certify`
5. `quote-admit`
6. `quote-batch`
7. `quote-certify`
8. `opportunity-certify`

For each job type, the persisted fixture enqueues and claims one job, records
every registered stage as `job.stage-changed`, completes through that job
type's real public/specialized terminal boundary, and then verifies:

- exactly one `job.started`;
- exactly one stage-progress event per registered stage;
- exactly one `job.succeeded`;
- contiguous event sequences;
- terminal success stage and progress match the final registered stage;
- no secret-like detail keys are persisted.

## Deadline profiles

Production workers use the shared derived profile:

- `policy_version = runtime-v1`
- `bounded_lease = max(3, lease_seconds)`
- `heartbeat_seconds = max(1, min(30, bounded_lease // 3))`
- `progress_seconds = max(bounded_lease, heartbeat_seconds * 3)`
- `attempt_seconds = max(progress_seconds, bounded_lease * 10)`

For the default 120-second worker lease, this resolves to:

- lease: 120 seconds
- heartbeat: 30 seconds
- progress: 120 seconds
- attempt: 1200 seconds

The Task 5 persisted cross-job fixture uses that default 120/30/120/1200
profile.
