# Plan 05.6-252 Summary: Deployment-Wide Database Session Capacity

**The runtime now preserves business concurrency while keeping every declared
database owner within the production Supavisor session limit.**

## Root cause

The first pool repair bounded each process independently at 32 connections. A
targeted recovery command then failed before mutation with Supavisor
`EMAXCONNSESSION`: the production session-mode role permits only 15 clients.
Lazy construction prevented startup preallocation but did not prevent several
Machines from retaining a combined total above the provider limit. This was a
deployment-resource contract defect, not a reason to increase a timeout or
restart Machines until one connection happened to win.

## What changed

- Database scheduling now distinguishes three quantities: at most 32 business
  lanes, at most 32 bounded waiters, and normally two physical sessions per
  worker process. Pool acquisition remains under the existing five-second
  database deadline.
- API operational/readiness pools are 1+1, controller and qualification are one
  each, and every rendered DB-owning service declares an explicit budget. The
  complete topology sums to 12, leaving three support slots below the observed
  limit of 15.
- Pool `max_idle=60s` releases burst sessions after two cycles of the slowest
  30-second persistent owner. It is resource reclamation, not a new outer task
  timeout.
- The runtime-event writer now owns one lazy pool, checks out that bounded
  connection for real HTTP requests, and closes it through Starlette lifespan.
  Its transaction-local timeout setup is parameterized with
  `pg_catalog.set_config`.
- Machine rollout rendering now admits only the exact pool-budget env key in
  addition to the existing qualification identity keys, so fresh optimistic
  updates carry the reviewed template budget without opening arbitrary env
  mutation authority.
- The historical `runtime-observe-only.json` remains explicitly `not-run`; its
  reviewed-template hashes and amendment were advanced without claiming a
  production decision window or mutation.

## Verification

- Full control-plane tests, runtime-event-writer behavior tests, transactional
  runtime coverage, and production commissioning harness passed in one clean
  run after the final edit.
- A real PostgreSQL test completed two waves of twelve concurrent lanes with
  exactly two reused backend sessions.
- Changed production files pass Pyright with zero errors; changed Python files
  pass Ruff; `git diff --check`, `uv lock --check`, and `make planning-status`
  pass.
- Independent review found the initially omitted alert-delivery and unbounded
  event-writer owners; both were repaired. Final review verdict is APPROVE with
  zero remaining findings.

The old release remains deployed while Structure and qualification stay
stopped and the controller remains observe-only. No failed recovery attempt
mutated the database. The next operation is an OrbStack-only exact-commit image
build and digest-verified rollout, followed by targeted circuit recovery and
