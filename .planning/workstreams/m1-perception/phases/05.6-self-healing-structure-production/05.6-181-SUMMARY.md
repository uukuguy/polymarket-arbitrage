# 05.6-181 — Bounded R2 control-plane preflight

## Root cause

The shared R2 boto3 configuration set retry policy but inherited botocore's
60-second connection/read defaults. `control-plane preflight` calls R2
`head_bucket`, so a blackholed endpoint could hold the production migration
gate far beyond its intended bounded read budget.

## Change

- The shared R2 client config now uses a five-second connection timeout and a
  fifteen-second read timeout.
- Standard retry mode and its three-attempt policy are unchanged. The change
  applies to the same client used by control-plane artifact operations, so a
  network failure becomes a typed bounded failure instead of an indefinite
  preflight wait.

## Verification

- The new timeout contract test failed first against the inherited 60-second
  default, then passed after the configuration change.
- `uv run pytest tests/m1-perception/test_r2_sync.py tests/m1-perception/test_control_plane_cli.py -q` — passed.
- `uv run ruff check src/polyarb/storage/r2_sync.py tests/m1-perception/test_r2_sync.py` — passed.
- `uv run python -m py_compile src/polyarb/storage/r2_sync.py` — passed.

## Follow-up

Use the bounded preflight against the separately designated production
Supabase/R2 authority before applying revision 014 or creating production
control-plane machines. A preflight failure remains a stop gate, not a reason
to reuse a staging pointer.
