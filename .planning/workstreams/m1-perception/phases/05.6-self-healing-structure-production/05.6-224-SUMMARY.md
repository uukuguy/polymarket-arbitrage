# 05.6-224 Summary — Execute stale-owner proofs through isolated databases

## Outcome

- A release/config-bound harness executes the real stale-owner adapter in one
  newly migrated disposable PostgreSQL database per selected production node.
- The public CLI always covers the complete eight-node chain and exposes one
  uniform `m1-production-commissioning-stale-owner` Make target. A node subset
  exists only for integration-test cost control.
- The harness requires `POLYARB_CONTROL_PLANE_TEST_DSN`, accepts loopback
  PostgreSQL only and never falls back to the production database environment.

## Lifecycle and interruption boundary

- Commissioning and the deterministic runtime fault matrix share one database
  lifecycle authority: validated name, cluster advisory lock, empty database,
  Alembic upgrade, migrated-authority verification, unconditional database drop,
  migration-role cleanup and lock release.
- Cleanup ownership is acquired only after proving the migration-created roles
  were absent. A pre-existing role therefore fails closed and is never deleted.
- Attack, database cleanup, role cleanup, unlock and connection-close failures
  are preserved together; a late cleanup error cannot hide the original fault.
- There is no experiment-wide timeout. Database operations retain their named
  connection/statement policies and interrupted bodies still run cleanup.

## Verification

- Real PostgreSQL tests prove one complete node, normal cleanup, interrupted-body
  cleanup, pre-existing-role preservation and dual failure retention.
- Make contracts prove the DSN/root/release/config guards and exact harness argv.
- Ruff and targeted Pyright pass. The deterministic production-enablement climb
  profile now includes these database, interruption and Make gates.
