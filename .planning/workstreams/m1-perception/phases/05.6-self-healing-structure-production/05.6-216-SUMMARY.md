# 05.6-216 Summary — Make qualification restart select the causal head

## Outcome

- Qualification restart now selects the most recently persisted active epoch,
  rather than using a content-hash ID to break equal business timestamps.
- Qualification failures expose only safe diagnostic identifiers: exception
  class, PostgreSQL SQLSTATE, and a validated constraint name. Exception text,
  SQL, hosts, credentials, and DSNs remain suppressed.
- No timeout, retry count, uniqueness constraint, or qualification policy was
  relaxed.

## Root cause

- One durable tick may invalidate an accumulating epoch, create a recovering
  epoch, and consume a recovery confirmation that creates its accumulating
  child. The parent and child intentionally share the same `started_at`.
- `_fetch_current_runtime_epoch()` ordered equal timestamps by `epoch_id`, but
  epoch IDs are content hashes and contain no causal ordering. Production v22
  selected the stale recovering parent, attempted to create another active
  accumulating child, hit `uq_m1_qualification_active_identity`, exited, and
  repeated until the resident Machine exhausted its restart policy.
- The CLI rendered every unexpected tick exception as the same fixed
  `qualification-service.tick-failed`, so the actionable unique-violation
  identity was hidden even though the secret-bearing error message was
  correctly suppressed.

## Repair

- Runtime-head selection is now `updated_at DESC, started_at DESC, epoch_id
  DESC`. Persistence order owns causal precedence; business time and stable ID
  are only secondary deterministic ties.
- A real-PostgreSQL regression creates the complete same-batch
  invalidated/recovering/accumulating chain, restarts a fresh state store, and
  proves it restores the existing accumulating child.
- The failure renderer emits validated identifiers only. Generic errors expose
  their class; PostgreSQL errors may additionally expose a five-character
  SQLSTATE and an ASCII identifier constraint name. Tests inject a credential-
  bearing error message and prove none of it reaches stderr.

## Verification

- The regression was RED before the ordering repair and GREEN afterward.
- All qualification-focused real-PostgreSQL tests pass: 23 cases.
- The complete CLI, qualification policy, identity, and service suites pass:
  153 cases.
- Ruff, Ruff format, Pyright for both changed production modules, and

- The full M1 gate and exact-release production rollout are the next release
