# Plan 05.6-212 Summary: Attempt Lifecycle and Recovery Episodes

Plan 212 is in progress. Production evidence isolated the remaining Structure
source failure to the long-lived coordinator transport: the exact page and
cursor completed quickly in a fresh local client and a fresh Fly Machine using
the same image, while retries in the resident coordinator timed out before the
first durable stage checkpoint. The existing client survives failed attempts,
so later attempts reuse the same transport generation.

The audit also found that recovery budgets are keyed to a target forever. A
new failure fingerprint therefore inherits an exhausted budget from an older
incident. The selected design replaces transport after a failed durable
attempt, persists stage-start facts before blocking I/O, and keys action budgets
by immutable failure episode. This summary is the required plan anchor and will
be updated with implementation, verification and production evidence after
each atomic task.

Task 1 is complete. `GammaClient.reset_transport()` retires the failed HTTP
pool within the existing cleanup bound and installs a new pool even when close
times out or fails; the service-owned `AsyncLimiter` is unchanged. Every
retryable Structure source failure invokes replacement before its durable
failure receipt. A secondary replacement error is logged by exception class
only and cannot overwrite the original failure identity. Both complete focused
test files pass, and Ruff/Pyright report zero findings.

Task 2 is complete. Runtime `current_stage` advances only after the matching
progress fact is durable. Structure source now writes start and completion
facts around fetch, validation and upload, so a timeout cannot collapse back
to the generic `started` state. Retry fingerprints include that durable stage.
The prior false `commit-page=1/1` written before the fenced receipt was also
removed: `commit-page=0/1` now precedes commit-side DB work, and the terminal
job receipt is the only completion authority. Runtime, source-worker and real
PostgreSQL runtime-progress tests pass; Ruff/Pyright remain clean.

Task 3 is complete. Revision 035 extends the budget primary key with an
immutable `episode_key`: job actions use the exact attempt ID and circuit
actions use the exact failure fingerprint. Existing target-only rows remain
under `legacy` and are never rewritten or refilled. Live reconciliation,
observe-only snapshots, historical replay, action idempotency, action detail,
budget locking and consumption now carry the same episode identity. A real
PostgreSQL proof retained a legacy exhausted row while two fingerprints for
the same circuit independently consumed their own budgets. The
034→035→034→035 round trip conservatively preserved exhaustion and scoped-role
privileges. Recovery/CLI/observe suites and Ruff/Pyright pass.

Task 4 is complete. `docs/dev/m1-runtime-boundary-inventory.md` classifies
every production provider, worker-I/O, DB, attempt, cadence, retry, circuit,
terminal and qualification clock, including cancellation and durable resume
evidence. The audit found two additional sequencing defects: rollout and
role-admin gates still expected revision 034 after revision 035, and the
scheduler reused a cadence remainder measured before a slow observer callback.
Both now have one checked authority. Fault matrix v3 runs 16 deterministic
real-PostgreSQL cases and selects each case by exact job identity instead of a
global `LIMIT 1`; transport replacement, pre-I/O timeout, service interruption
and recovery-episode isolation are explicit cases. Scheduler, role, rollout,
policy and full fault-matrix suites pass.

Task 5 is complete. `planning-status` now reads the reachable Git history once,
builds a path-creation/rename/commit-graph index in memory, and reuses it across
all plan rows while preserving each plan's exact creation-to-summary lifetime.
A regression test proves two plans require one Git subprocess instead of six.
The full planning-status suite passes, and the real 90-plan repository check
reports zero drift and valid evidence hashes in 0.86 seconds, down from the
observed approximately 53-second per-plan scan.

The first complete focused gate exposed one stale direct PostgreSQL test caller
that scheduled a circuit action without forwarding the newly mandatory failure
episode. Production callers and the fault matrix already carried the value.
The test now exercises the same explicit episode contract instead of relying on
the removed target-only fallback.

The first revision-035 production probe replaced the poisoned Gamma transport
but exposed a second, independent defect: the coordinator still timed out the
same page three times at `fetch-page=0/1`. The exact release, cursor, provider
policy, app and region returned 100 records in 0.164 seconds in an isolated
Machine. A second read-only probe measured eight sequential claim-shaped
database reads in 2.292 seconds. The page and individual query were healthy;
the coordinator alone combined eight source lanes and eight extra
materializer turns whose asynchronous `run_once()` methods called synchronous
`claim_job()` on the event-loop thread.

Task 7 is locally complete. `claim_worker_job()` routes all five asynchronous
claim sites through the existing cancellable daemon bridge without adding a
timeout; PostgreSQL connect, statement and lock policies remain the only DB
authorities. The source failure-path spec lookup is bridged as well. A
behavioral regression blocks a fake claim while proving an unrelated loop task
still advances, and an AST coverage test rejects any direct `.claim_job()` in
the audited async worker methods. Seven affected worker/policy/scheduler files
pass, Ruff is clean, and modified production files report zero Pyright errors.
Production coordinator validation is complete on exact release `33ad6826` and
child manifest `sha256:aa723729…e93b6`. The source circuit one-shot executed in
the runtime-controller app with its scoped DSN, consumed only the exact current
episode, changed zero pointers, and auto-removed. The formerly failing page
then completed as `succeeded:1/8`; subsequent pages continued succeeding while
the other coordinator lanes remained live. This is the production proof that
event-loop claim starvation, rather than provider or single-query latency, was
the second root cause.

The resident controller, coordinator, Structure worker, Quote worker and
qualification worker now run the same exact v7 child digest. All preserve
`SIGTERM/40s`; the resident controller remains observe-only with an empty
allowlist. Qualification is bound to full release
`33ad682654f2ccd5766e5c78265d79b8142b3005`, so predecessor evidence cannot be
transferred into the new certificate window.

The older Quote-admit circuit was recovered separately with an exact
`probe-circuit` one-shot in the controller app. Action
`9edb8dbd-9a97-4b3b-9a62-66a3ac081588` succeeded, consumed one action from its
fingerprint-scoped episode, and changed zero pointers. Its resumed lease epoch
11 was observed at `upload-batches=65/148` with a 1.8-second progress age,
fresh heartbeat, and the job's own 20-minute attempt boundary. Other lanes
continued to complete source pages concurrently; the old 29-second outer
timeout no longer kills or stalls this legitimate long task.

M1 remains incomplete. A new 86,400-second release-bound qualification
certificate is still required after the revision-035 production recovery.
The fresh full M1 regression is running without an outer timeout; this summary
will record its terminal count and the resumed Quote pipeline terminal evidence
before Plan 212 is closed.

That resumed pipeline exposed a third independent sequencing defect before the
qualification gate could be accepted. The dedicated Quote process advertised a
`pool-turns` bound, but `TransactionalWorkerLoop` executed those turns as a
serial list. Production measured roughly 11–12 seconds per 500-token batch; 148
batches therefore required about 28 minutes on one lane and contradicted the
900-second freshness gate. Increasing the freshness or attempt timeout would
have hidden a capacity defect rather than made the task recoverable.

Task 8 is locally complete. `TransactionalQuoteBatchPool` now gives every lane
an independent worker identity and durable lease while sharing the existing
bounded CLOB reader and R2 client. The lane count is derived from the single
`clob_batch_max_concurrency` authority (default 12), not a second scheduler
constant. A wave waits for healthy siblings before propagating one failed lane;
the role loop records that failure and continues instead of terminating the
Machine and stranding the queue. SIGTERM cancellation propagates to every
active lane, whose existing worker path owns its fenced `finish_interrupted`
transition, and the pool exposes the common lease-derived terminal grace.
Focused pool, lifecycle, CLI and deployment suites pass; Ruff and modified-file
Pyright report zero findings. Production rollout and final freshness evidence
remain pending.
