## Action classes and boundaries

- Automatic job/circuit classes: `heartbeat-job`, `cancel-job`, `retry-job`,
  `reclaim-job`, and `probe-circuit`.
- Durable but disabled classes: `restart-worker-process` and `restart-machine`.
  There is no process spawn, Fly Machine API, deployment, migration, capacity,
  credential, configuration, R2 publication, receipt, or pointer authority in
  this plan.
- Stale controller, stale attempt/lease, active-target conflict, expired
  action-worker lease, conflicting replay, exhausted budget, and cooldown are
  explicit bounded outcomes rather than silent retries.

## DB-clock and atomicity evidence

Task 2/3 action transitions use bounded Postgres transactions and
`clock_timestamp()` for terminal action finish/event timestamps where the
database owns the write. Task 4's status/fact projection executes
`SET TRANSACTION READ ONLY`; reconciliation passes one validated UTC instant
through pure evaluation and the fenced store calls. Controller renewal keeps
the same epoch so a pending action cannot be stranded between service turns.

## Issues and deviations

- The existing Task 2/3 store APIs were module-level and had no read projection
  or same-epoch renewal. Task 4 added those minimal APIs in
  `recovery_store.py` so status remains read-only and the long-lived loop does
  not fence its own pending work on every interval.
- Review-fix store conflicts now fail loud through the runtime CLI. Only an
  active-target race under controller/runtime/target locks creates a durable
  `stale-noop`; budget, idempotency, runtime-fence, and incident/event
  conflicts are not converted into synthetic CLI outcomes.
- No production deployment, cloud migration, process restart, Machine action,
  or live control-plane mutation was performed.
