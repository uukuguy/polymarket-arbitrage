## Area A: 数据源覆盖度

### 教练讲解（Polymarket 的 4 层数据宇宙）

| 层 | 内容 | 套利角色 | Phase 1 范围 |

### 关键讨论

**对手测试 1**：仅靠 Gamma 数据能不能下单？

**对手测试 2**：YES @ 0.32 量 100 / NO @ 0.68 量 50，最多放多少钱？利润几何？$5000 进去会怎样？
- 用户答（A）："各买50份"——正确
- 用户承认 B/C 不会，教练展开讲解：流动性瓶颈、冲击成本、$5000 会扫单簿到平均 0.42+0.78=1.20，亏 17%
- 元教训三条沉淀进 CONTEXT.md `<specifics>` 段

## Area C: 存储模型

### 教练讲解（4 种数据访问模式）

| 场景 | 谁用 | 特点 | 工具 |
|---|---|---|---|
| 实时查询 | Phase 3 异常检测 / Phase 4 dashboard | 低延迟、单点查询、跨市场聚合 | SQLite |
| 历史回放 | Phase 3 回测 | 时间维度大、列式扫描 | Parquet + DuckDB |
| 训练数据 | M4 LLM 策略 / M5 自动调参 | 全量批量读 | Parquet + DuckDB |
| 审计调试 | 用户 | 随机访问任意时间点 | Parquet |

### 三个候选方案

| 方案 | SQLite | Parquet | 评估 |
|---|---|---|---|
| 1 | 最新 snapshot（覆盖式） | 历史归档 | ✅ 推荐 — 冷热边界清晰 |
| 2 | 所有 snapshot（按 timestamp） | 仅导出 | ❌ 表会膨胀到上亿行，列式聚合崩溃 |
| 3 | 仅 catalog/metadata | 唯一事实表 | ❌ Phase 3 实时查询要先开 parquet 太重 |

### Parquet 文件粒度

- **C.a 单文件 per snapshot**：✅ 推荐（写入简单、回滚容易、DuckDB glob 跨文件无负担）
- C.b 按天聚合：写入需要 read-append-write，回滚难
- C.c 按月聚合：同上更甚

### 对手测试 3

> Phase 3 检测到机会，要 (1) 确认当下还在不在，(2) 查 7 天历史是否常出现这种不一致。SQLite 还是 Parquet？

用户答："1. SQLite 快速 2. Parquet 历史数据" — **正确**

教练补充元教训：**热/冷不是按"新/旧"分，是按"访问模式"分**。

### 决策

| 问题 | 选项 | 选择 |
|---|---|---|
| C.1 整体架构 | 方案 1 / 2 / 3 | **方案 1** |
| C.2 Parquet 粒度 | a / b / c | **C.a 单文件 per snapshot** |

## Area D: 完整性校验

### 教练讲解（4 层校验金字塔）

| Layer | 内容 | Phase 1 是否做 |
|---|---|---|
| 1 数量校验 | API 报告数 == 落库数 | ✅ |
| 2 字段完整性 | 每条记录必有 N 个核心字段 | ✅ |
| 3 业务一致性 | YES+NO≈1 等业务规则 | ❌ 推到 Phase 3 |
| 4 跨源一致性 | Gamma 有 / CLOB 无 | ✅ |

### 失败处理策略

- **D.x.1 严格 + 标记**：✅ 推荐（落库带 `is_valid=false` + `validation_issues` 表 + 退出码非零）
- D.x.2 宽容（仅日志，snapshot 仍 valid）：❌（养成告警麻木）

### 对手测试 4（关键讨论）

> snapshot 30 次中 3 次 invalid，原因都是"缺 5 个市场"。第一反应？
> A 调高阈值忽略 / B 忽略不管 / C 展开调查 / D 回滚重拉

用户答：D（回滚重拉）

教练拨正：**正确答案是 C**。理由：
- D 错在不知道根因就盲目重试，且重拉等于拿 T+90s 数据冒充 T → 时间一致性破坏（比缺数据更危险）
- A/B 是温水煮青蛙的告警麻木入口
- C 才是套利从业者反射动作：**任何缺失都假设它在告诉你什么**

展开讨论 4 种可能的根因情况（zombie / negrisk group / resolving / 真随机），每种应对不同。

**核心元教训**：**完整性的本质不是"数据齐全"，是"知道哪里不齐全以及为什么"**。
- 阈值 = 反模式（让你在不理解时关上眼睛）
- 规则 = 正模式（强制理解，每个异常必须能归类）

### 衍生决策（教练课后追加）

D.3：`validation_issues` 表必须有 `category` 字段做根因归类，新发现的根因模式立即手工补到归类，让 `unknown` 不断收敛。**这是把"调查根因"机制化进系统的最小动作。**

### 决策

| 问题 | 选项 | 选择 |
|---|---|---|
| D.1 校验范围 | A 同意拆分 / B 加 L3 / C 别的 | **A** |
| D.2 失败策略 | A 严格 / B 宽容 | **A** |
| D.3（衍生） | 增加根因归类字段 | **是** |
