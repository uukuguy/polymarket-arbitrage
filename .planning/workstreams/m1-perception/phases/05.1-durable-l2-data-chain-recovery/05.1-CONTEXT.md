<decisions>
## Implementation Decisions

### Durable event consumption

- PostgreSQL NOTIFY is a low-latency wake-up hint, never the durable source of truth.
- `l2_event_cursor` is the durable boundary; a serialized reconciliation pump wakes on NOTIFY and at least every 60 seconds.
- The pump processes only the newest snapshot when cursor lag is positive because candidate computation reads current `markets_latest`.
- Candidate refresh must be awaited; cursor advances only after refresh and required candidate reconciliation succeed.
- Overlapping NOTIFY/poll wake-ups coalesce and must never run concurrent refreshes.

### Listener lifecycle

- The asyncpg listener must observe actual connection termination and enter bounded reconnect.
- Periodic cursor reconciliation continues while LISTEN is unavailable.
- Shutdown and `CancelledError` retain prompt propagation.

### Candidate projection

- Candidate history identity is `(asset_id, recipe_name)` and preserves multiple inclusion/removal cycles.
- Each successful refresh reads currently active keys, closes stale keys, inserts newly active keys, and retains unchanged keys.
- WS subscriptions remain the unique `asset_id` projection of desired candidate rows.
- Candidate reconciliation failure prevents cursor advancement.

### Chain-truth health

- Health exposes actual event-bus connection state, last notification age, last successful reconciliation age, cursor lag, and reconnect count.
- Positive cursor lag or stale reconciliation must fail strict health after the defined grace window even if LISTEN appears connected.
- Every new fail-soft path must answer the five chain-truth questions in `.planning/threads/market-observation-architecture.md` §1.6.

### Delivery discipline

- All behavior changes use RED → GREEN TDD.
- Every new executable diagnostic or chaos command has a documented Makefile target and appears in `make help`.
- Plan completion requires immediate `05.1-XX-SUMMARY.md`, then `make planning-status` with no drift.
- Teaching documentation uses the mental model: “NOTIFY is a doorbell; the durable cursor is the ledger.”

### the agent's Discretion

- Exact class/module boundary for the reconciliation pump, provided ownership is singular and testable.
- Exact bounded reconnect backoff values, using existing project conventions where possible.
- Exact health grace thresholds, provided they account for a 60-second poll and are explicit Settings fields when configurable.
- Whether candidate reconciliation uses Supabase REST reads or a narrow Postgres helper, provided service boundaries and failure semantics remain explicit.

</decisions>

<specifics>
## Specific Ideas

- Production recovery evidence: cursor `482 → 516`, strict `/health` 503 → 200, and candidate/WS/mirror freshness returned to seconds after L2 restart.
- Projection-drift evidence: Supabase had 117 distinct active candidate assets while WS subscribed to two current assets.
- A valid direct `pg_notify('snapshot_complete', ...)` was not consumed before restart, proving the cached `listening` state was false business liveness.

</specifics>
