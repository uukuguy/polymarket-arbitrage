# Phase 05.1: Durable L2 Data-Chain Recovery — Research

**Researched:** 2026-07-18
**Domain:** asyncpg LISTEN lifecycle · durable cursor consumption · Supabase history projection · strict health
**Confidence:** HIGH — findings are based on production evidence and the current repository implementation

## Summary

The production outage was not a missing-data problem. L1 snapshots continued to
land, but L2's asyncpg connection died while the daemon remained blocked on
`stop_event.wait()`. The outer reconnect loop therefore never ran and
`_EventListenerWrapper.is_listening` remained true. Restarting L2 immediately
moved the durable cursor from 482 to 516 and restored candidate, WS, and mirror
freshness, proving the process-local listener lifecycle was the first break.

The current startup catch-up then introduces a second correctness risk: it
creates one task per missed snapshot and commits the cursor to the newest row
before any task has completed. Candidate refresh also treats WS and mirror
failures as non-blocking. A failed refresh can therefore be permanently skipped.

The repair should replace notification-driven task fan-out with one serialized
reconciliation pump. NOTIFY only sets a wake event. The pump also wakes every 60
seconds, reads cursor and latest snapshot, refreshes the current candidate set,
reconciles the durable candidate projection, and only then commits the cursor.
Because candidate computation reads `markets_latest`, processing every
intermediate snapshot is unnecessary; the newest snapshot is the correct
coalescing target.

No database migration is required. `l2_event_cursor` already provides the
consumer boundary and `l2_candidates` already permits repeated active/inactive
history cycles. The storage API needs key-aware reads and updates, not a schema
change.

## Production Evidence

| Observation | Before restart | After restart | Meaning |
|---|---:|---:|---|
| strict `/health` | HTTP 503 | HTTP 200 (L3 warning only) | upstream L2 chain recovered |
| L2 cursor | 482 | 516 | durable work existed but was not consumed |
| candidate age | ~3.49m s | <1 s | refresh was stalled in-process |
| WS event age | ~1.81m s | 0 s | subscriptions recovered after refresh |
| mirror age | ~1.83m s | <1 s | write path itself remained functional |
| active candidate assets in DB | 117 | — | stale active history was never closed |
| actual WS subscriptions | 2 | 2 | database projection did not describe reality |

A valid direct `pg_notify('snapshot_complete', ...)` was not consumed before the
restart. This rules out L1 publishing as the immediate cause. L1 nevertheless
had `POLYARB_EVENT_BUS_ENABLED` absent and defaulted false; production was
corrected to `POLYARB_EVENT_BUS_ENABLED=1` as part of recovery.

## Root-Cause Map

### R01 — connection loss cannot wake reconnect

`src/polyarb/events/listener.py:68-80` opens the connection and then awaits only
`stop_event.wait()`. asyncpg exposes `Connection.add_termination_listener()` and
`Connection.is_closed()` in the pinned 0.31.0 version. A termination future must
race the stop event. Connection loss should update live state and re-enter a
bounded reconnect loop; cancellation must still propagate.

### R02 — cursor can advance before business success

`src/polyarb/daemon/l2_main.py:533-563` dispatches all missed rows as independent
tasks, then advances `l2_event_cursor` to the last row immediately. The cursor
write also omits `updated_at`, whose schema default only runs on insert. This
violates at-least-once business processing and makes cursor freshness misleading.

### R03 — health reports cached intent, not connection truth

`src/polyarb/daemon/l2_main.py:587-602` sets `is_listening=True` before connection
establishment. `src/polyarb/http/l2_health.py:187-208` reads only that cached
boolean. It has no cursor lag, reconciliation freshness, or reconnect count, so
a dead listener can remain green indefinitely.

### R04 — candidate history diffs against process memory

`src/polyarb/observation/l2_candidate_refresh.py:410-481` compares desired rows
only with `ws_consumer._candidate_set`. On restart that set is empty, so old
active database rows are never closed. `mark_candidates_removed()` filters by
asset only, while the history identity is `(asset_id, recipe_name)`.

### R05 — required side effects are currently fail-soft

The refresh handler updates the in-memory candidate set before confirming WS
subscribe/unsubscribe and ignores false return values from WS and mirror calls.
That behavior is acceptable for frame persistence, but not for the durable
cursor transaction boundary. Phase 05.1 must return an explicit success result
and prevent cursor advancement when required reconciliation fails.

## Recommended Architecture

```text
asyncpg LISTEN ──NOTIFY──┐
                        ├── wake_event (coalescing)
60s timer ──────────────┘
                              │
                              v
                    one reconciliation pump
                              │
              read cursor + latest snapshot id
                              │ lag > 0
                              v
                  await candidate refresh
                 ├─ compute desired keyed rows
                 ├─ reconcile WS candidate set
                 ├─ read active DB candidate keys
                 ├─ close stale keyed rows
                 └─ insert newly active keyed rows
                              │ all required steps succeeded
                              v
                 commit cursor + updated_at
```

Ownership should be singular: the pump is the only caller allowed to advance the
`l2-candidate-refresh` cursor. NOTIFY callbacks must never invoke candidate
refresh directly.

## Detailed Design Guidance

### Listener lifecycle

- Extend `listen_snapshot_complete` with lifecycle callbacks or a small state
  object: connected, disconnected, notification received, reconnect attempt.
- After `LISTEN`, race `stop_event.wait()` with a future completed by
  `add_termination_listener`.
- Set connected only after `add_listener`/`LISTEN` succeed; clear it immediately
  on termination and before reconnect sleep.
- Use bounded exponential backoff with a cap; reset after successful connection.
- Cancel and await helper tasks in `finally`; never swallow `CancelledError`.

### Durable reconciliation pump

- Add narrow cursor helpers: read cursor/latest snapshot and commit cursor with
  `updated_at=now()`.
- Wake immediately at startup, on every notification, and on a configurable
  poll interval (default 60s).
- Coalesce wakes with `asyncio.Event`; do not queue snapshot-sized work.
- If `latest_snapshot_id <= cursor`, record a successful reconciliation heartbeat
  without rerunning candidate computation.
- If lag is positive, process only the newest snapshot ID and await completion.
- On any required-step failure, retain the old cursor; the next wake retries.
- Startup prime becomes the pump's initial wake, removing sentinel snapshot `-1`
  and independent task dispatch.

### Candidate projection reconciliation

- Desired history identity is `(asset_id, recipe_name)`; WS identity remains
  unique `asset_id`.
- Add a mirror read for active candidate rows and derive active keys.
- Close `active_keys - desired_keys` using both asset and recipe filters.
- Insert `desired_keys - active_keys` with the current snapshot and inclusion
  timestamp; leave the intersection untouched.
- Repeated include/remove/include cycles remain separate rows by design.
- Mirror read/write failure returns false to the pump and blocks cursor commit.
- To avoid partial truth, compute desired state first, then perform reversible WS
  convergence and durable projection convergence. A retry must be idempotent.

### Chain-truth health

Expose these checks without secrets or payload bodies:

| Health fact | Write source | Read source | Strict behavior |
|---|---|---|---|
| listener connected | actual LISTEN success/termination | listener state | disconnected is warn during grace, then fail |
| last notification age | callback after valid JSON | listener state | diagnostic; quiet L1 alone is not failure |
| last successful reconciliation age | pump success path only | pump state | stale beyond grace fails |
| cursor lag | latest snapshot minus committed cursor | pump state | positive lag beyond grace fails |
| reconnect count | listener retry entry | listener state | diagnostic counter |

The grace threshold must account for a 60-second poll. Recommended defaults are
`event_reconcile_poll_seconds=60` and
`event_reconcile_stale_seconds=180`, represented as explicit Settings fields.
Connection loss does not stop polling, so health can distinguish “LISTEN down but
durable chain caught up” from “business processing stalled.”

## Chain-Truth Checklist

1. **Which health checks observe it?** New event-bus connection,
   reconciliation-age, and cursor-lag checks in `l2_health.py`.
2. **What data do they read?** A single live listener/pump state object passed by
   `l2_main` into the app state.
3. **What flags gate them?** `supabase_db_dsn` availability plus explicit poll
   and stale Settings; no undeclared config field.
4. **Where is state mutated?** Listener connect/termination callbacks and the
   pump's successful reconciliation/cursor commit branches only.
5. **Which end-to-end chaos triggers them?** A diagnostic target that terminates
   the LISTEN connection or restarts Postgres connectivity, then proves periodic
   cursor reconciliation advances without a new NOTIFY and strict health
   recovers without restarting L2.

## Test Strategy

All behavior changes use RED → GREEN.

1. Listener unit tests: termination wakes reconnect; state transitions reflect
   actual connection; bounded backoff; stop and cancellation remain prompt.
2. Pump unit tests: NOTIFY coalescing; timer-only catch-up; one refresh at a time;
   newest-snapshot processing; cursor retained on refresh/projection failure;
   cursor and `updated_at` advance only on success.
3. Projection tests: cold-start stale rows close; unchanged keys remain; new keys
   insert; recipe-level identity; repeated cycles; partial REST failure is
   retry-safe.
4. Health tests: real listener state, stale reconciliation, cursor lag grace,
   reconnect count, and no false fail during a quiet but caught-up period.
5. Integration/chaos: break LISTEN while L1 produces a snapshot; do not restart
   L2; prove the 60-second poll catches up, candidate DB active keys equal desired
   keyed rows, WS assets equal desired unique assets, and strict health returns.

## Security and Operational Notes

- Health and logs must never expose DSNs, service keys, or NOTIFY payload bodies.
- Snapshot IDs must be parsed as non-negative integers; malformed notification
  payloads only wake reconciliation and cannot choose SQL identifiers.
- All SQL remains parameterized.
- The poll is bounded to one latest-snapshot read per interval and cannot amplify
  a NOTIFY storm into concurrent Supabase fetches.
- No new dependency is needed; asyncio, asyncpg, pytest, and existing Supabase
  client surfaces are sufficient.
- No chaos primitive requires a missing container binary; use Python/asyncpg or
  Fly machine operations, consistent with the image-aware rule.
