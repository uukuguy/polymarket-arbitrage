# Phase 05.5 Learnings: Production Opportunity Feed

## Decisions

### Run the producer inside the L1 app process

The quote worker runs beside the HTTP service so both producer and consumer use
the volume-backed `/data/state.db`.

**Rationale:** The Fly cron process has no shared volume, so its successful
writes would not become visible to the opportunity endpoint.
**Source:** 05.5-01-SUMMARY.md

---

### Keep collection sequential at a 120-second cadence

One collection completes before the worker waits for the next interval; no
overlapping CLOB collection is introduced.

**Rationale:** The measured three-batch production run completed in 1.013
seconds, so concurrency would add complexity without solving a capacity limit.
**Source:** 05.5-01-PLAN.md

---

### Preserve the 300-second public quote SLA

Operationalizing the producer did not extend the consumer freshness contract:
health warns before expiry and fails when the latest complete run is too old.

**Rationale:** A producer outage must become visible instead of relabelling an
old ask as current.
**Source:** 05.5-01-SUMMARY.md

---

### Bind L1 health identity to the deployed Git SHA

The deployment workflow now passes `GITHUB_SHA` as `POLYARB_RELEASE_ID`.

**Rationale:** Runtime health must be directly attributable to an exact source
revision, rather than reporting the default `dev`.
**Source:** 05.5-01-SUMMARY.md

## Lessons

### A deployed consumer chain is not a live feed without a producer

The store, scanner, and HTTP route were present in production, but the route
truthfully returned HTTP 503 until a complete quote run existed.

**Context:** The initial failure was absence of scheduled production, not an
empty opportunity set.
**Source:** 05.5-01-SUMMARY.md

---

### Process placement is part of durable data correctness

A job can execute successfully and still be useless if it writes a different
filesystem from the service that consumes its result.

**Context:** The L1 app owned the SQLite volume while the existing cron machine
did not.
**Source:** 05.5-01-PLAN.md

---

### Durable success time and process state answer different questions

Complete-run age proves when publishable quote truth last succeeded; worker
state explains whether the current collector is cold, collecting, passing, or
failing.

**Context:** Both are needed so a transient attempt failure warns without
forging freshness, while an expired complete run fails closed.
**Source:** 05.5-01-SUMMARY.md

---

### Health storage failures must fail closed

An unreadable quote store is represented as a failed quote-health check rather
than escaping as an unstructured HTTP 500.

**Context:** The self-review added the unreadable-store regression before
production deployment.
**Source:** 05.5-01-SUMMARY.md

---

### Historical PASS never replaces current health

The three-run production proof qualifies the design, but operators still need
the current quote age, collector state, and feed response before using data.

**Context:** The phase distinguishes readiness evidence from live operational
state.
**Source:** 05.5-01-PLAN.md

## Patterns

### Immediate attempt followed by cancellable interval wait

Start producing as soon as the HTTP service is bound, then wait on the shared
stop event between sequential attempts.

**When to use:** A lightweight producer must recover quickly after deployment,
avoid overlap, and share graceful shutdown with a daemon.
**Source:** 05.5-01-SUMMARY.md

---

### Complete-or-failed atomic run publication

Only a fully terminal quote set becomes the latest readable run; a failed
attempt never publishes a partial projection.

**When to use:** A downstream scanner must distinguish incomplete collection
from a valid zero-result market observation.
**Source:** 05.5-01-PLAN.md

---

### Capacity observation before cadence commitment

Measure real universe size, batch count, response coverage, and wall time before
choosing the production interval.

**When to use:** An external read workload is being moved from local-only code
to a periodic production task.
**Source:** 05.5-01-SUMMARY.md

---

### Structural deployment test for runtime identity

Keep a small test that asserts the workflow injects `GITHUB_SHA` into the
application release identifier.

**When to use:** Deployment metadata is part of a public health or evidence
contract and can silently fall back to a default value.
**Source:** 05.5-01-SUMMARY.md

## Surprises

### Production capacity was much larger than required

All 1,278 books arrived in three batches in about one second, far below the
120-second worker interval.

**Impact:** A simple sequential worker was sufficient; no batching concurrency
or VM resize was needed.
**Source:** 05.5-01-SUMMARY.md

---

### The repository deployment credential had expired

The first exact workflow deployment failed with Fly `unauthorized` before any
production release occurred.

**Impact:** The credential was safely refreshed and the same exact workflow run
was rerun successfully.
**Source:** 05.5-01-SUMMARY.md

---

### Exact source deployment still reported `releaseId=dev`

Fly release 130 came from the intended commit, but the L1 workflow had never
passed that identity into application settings.

**Impact:** A follow-up RED/GREEN workflow contract and release 131 restored
end-to-end source traceability.
**Source:** 05.5-01-SUMMARY.md

---

### The worker did not create a rising-memory signal

Observed Python RSS decreased from approximately 400 MB to 356 MB while
automatic collections continued.

**Impact:** The new producer stayed within the existing 1 GB L1 capacity during
the acceptance window.
**Source:** 05.5-01-SUMMARY.md
