<objective>
Phase 02 Wave 3.5 — fix the L1 daemon's memory architecture so it survives long-running on the 256MB Fly VM that Plan 02-04 just deployed to. Convert the Gamma paginator from "fetch-all-then-process" to true streaming (`AsyncIterator[dict]`), restructure the snapshot orchestrator to consume that stream (per-page: normalize → branch → batch-write → discard), and add chunked writers for parquet (`pq.ParquetWriter`) and SQLite (single transaction with batched `executemany`) so target_markets are flushed in bounded batches instead of buffered as one large structure.

Purpose: D-23 amendment locks streaming pagination as a hard L1 production-stability constraint. The 2026-05-15 prod OOM proved that the Plan 02-04 field-stripping fix (raw dict size reduction) was necessary but not sufficient — even at ~160MB peak the daemon sits at the OOM edge on a 256MB micro-VM (~150MB usable after kernel). This plan removes the full-buffer architecture entirely.

Output: refactored paginator + orchestrator + storage writers; a memory-regression test that fails under the old code and passes under the new (≤130MB peak); a docker smoke under `--memory=256m`; one teaching doc; a thread amendment. After this plan, Wave 4 (Plan 02-05 observability) and Wave 5 (Plan 02-07 7-day soak) become meaningful because the daemon is actually stable.
</objective>

<design_decisions>
The orchestrator has several batch operations that cannot be naively streamed. Each is explicitly resolved here so the executor does not re-decide.

### Decision A: Events stay fully materialized (small; needed by markets pass)

`normalize_events()` builds `market_to_event_map: dict[str, str]` (~10k entries, ~2MB) which markets normalize requires. Two options were evaluated:

1. **Two-pass**: stream `/events` into the map, then stream `/markets`. Requires the entire `/events` payload in memory anyway (just as a map instead of as raw dicts).
2. **Materialize events first, stream markets** (chosen).

Rationale: `/events` returns ~10k items of small JSON (already field-stripped via `_EVENT_KEEP`). Holding them as `raw_events` for the duration of `normalize_events()` call is cheap (~5MB peak). The dominant memory consumer is the `/markets` path (~20k full dicts). Refactoring `/events` streaming gives ~5MB savings for significant code complexity — **out of scope for Plan 02-09**, deferred to a future plan if needed.

**Implementation:** keep current `fetch_all_active_events() -> list[dict]` API (under the hood it can be `[item async for item in self._iter_events_pages()]` so the iterator primitive is shared). The orchestrator continues to call `await gamma.fetch_all_active_events()`. `del raw_events` after `normalize_events()` returns frees them immediately (already in current code).

### Decision B: Dedup uses running `seen_ids: set[str]`

Already a set in the existing code (`orchestrator.py:251`). Streaming-compatible as-is. Memory: ~50k market_id strings × ~32 bytes ≈ 1.6MB. Negligible.

### Decision C: Layer 1 count from running counters

Current code: `gamma_count_reported = len(raw_markets)` (the raw input count) vs `len(markets)` (post-normalize). Both need totals.

Streaming approach: maintain two counters (`raw_market_count`, `normalized_market_count`) bumped inside the stream loop. After the stream finishes, call `layer1_count(raw_market_count, normalized_market_count)`. Identical semantics, no list materialization needed.

### Decision D: Layer 2/4 validation operates on persisted records only

Already true in current code: Layer 2 runs on `target_markets` (filtered, small), Layer 4 cross-references `target_markets` + `books_by_token` + `prices_combined`. None of those need the full 20k markets list.

`target_markets` is the subset post-mode-filter. At the production `$1k` liquidity threshold (config.py:44 default), prior live runs and the T5 log-normal fixture (P(X>$1k)≈36%) both predict **6000-8000 target_markets** at 20k total active markets — not "a few hundred". Memory cost: 7000 × ~2KB ≈ ~14MB (accounted in the working-set budget table). **Keep target_markets in memory**; the savings are not in this subset, they are in the ~65% filtered-out non-target markets that today sit in `markets` list through dedup/validate but get dropped at write time, AND in the raw Gamma response (~160MB) that today materializes before normalize.

### Decision E: Parquet writer uses `pyarrow.parquet.ParquetWriter` for chunked write

Verified via pyarrow docs (arrow.apache.org/docs/python/generated/pyarrow.parquet.ParquetWriter.html, 2026-05-15):

- `ParquetWriter(where, schema, compression='snappy')` is documented for "incrementally building a Parquet file"
- Methods: `write_table(table, ...)`, `write_batch(batch, ...)`, `close()`
- Multiple `write_table()` / `write_batch()` calls produce the same on-disk format as one single-shot `pq.write_table(...)` call
- **Context-manager IS supported** in our pinned pyarrow (verified at `.venv/lib/python*/site-packages/pyarrow/parquet/core.py:1049-1052` — `ParquetWriter` defines `__enter__` / `__exit__`). Prefer `with pq.ParquetWriter(tmp, SCHEMA, compression="snappy") as writer:` — `close()` runs on both normal exit and exception path. The atomic-write contract still requires `tmp.unlink(missing_ok=True)` on exception, so the structure is `with writer:` *inside* a `try/except tmp.unlink + raise` block.

**Atomicity preserved** via the existing tmp-file + os.replace pattern in `parquet_writer.py:50-63`:
1. Compute `tmp = out_path.with_suffix(out_path.suffix + ".tmp")`
2. `writer = pq.ParquetWriter(tmp, SNAPSHOT_SCHEMA, compression="snappy")`
3. For each batch of N rows: `writer.write_table(pa.Table.from_pylist(batch, schema=SNAPSHOT_SCHEMA))`
4. `writer.close()` (in finally)
5. On exception: `tmp.unlink(missing_ok=True)` + reraise
6. On success: `os.replace(tmp, out_path)`

Rejected alternatives:
- **Per-page parquet shards (multiple files per snapshot)**: breaks the "1 snapshot = 1 parquet file" invariant assumed by `compute_snapshot_path`, the SQLite `snapshots.parquet_path` column, and R2 sync. Rejected.
- **Switching format (ndjson / avro)**: out of scope; pyarrow ParquetWriter is the standard answer.

### Decision F: SQLite uses single open transaction + batched executemany

Current code (`sqlite_store.py:184-245`) opens one `BEGIN IMMEDIATE`, runs `DELETE FROM markets`, then a single `executemany(MARKETS_INSERT_SQL, market_tuples)`, then `COMMIT`.

Streaming version (new `write_snapshot_streaming` method):
1. `con.execute("BEGIN IMMEDIATE")`
2. `con.execute("DELETE FROM markets")`
3. Insert snapshots row, capture `snapshot_id`
4. Insert events / event_tags (still fully materialized — small)
5. For each batch of N market dicts produced by the orchestrator: `con.executemany(MARKETS_INSERT_SQL, [row_to_tuple(r, snapshot_id) for r in batch])`
6. Insert issues
7. `con.execute("COMMIT")` (on exception → `ROLLBACK`)

Atomicity guarantee: the snapshot is still all-or-nothing because the entire write happens inside one transaction. A crash mid-batch causes the SQLite engine to abort the transaction at next open; the `snapshots` row is never visible.

Rejected alternatives:
- **Staging table swap**: more SQL gymnastics, no atomicity benefit.
- **Multiple short transactions**: breaks per-snapshot atomicity. Rejected.

### Decision G: target_markets stays in memory for CLOB phase

CLOB fetch (`get_books`, `get_prices_buy_sell`) needs the full `token_ids` list to issue batched RPC calls (already chunked internally). It is downstream of normalize and mode-filter, so `target_markets` must be materialized at that point.

Two options:
1. **Two-pass**: stream Gamma → accumulate token_ids only (~thousands of strings, ~100KB) → CLOB → re-iterate SQLite to attach books. Requires re-reading SQLite rows, extra IO.
2. **Single-pass with bounded target_markets** (chosen): keep `target_markets` in memory; it is post-filter (subset mode typically <500 markets in production data). Memory cost: <1MB.

**Implementation:** the streaming Gamma consumer branches each normalized market into two sinks:
- **non-target**: drop immediately (the big win — these are the 95% filtered out)
- **target**: append to `target_markets` AND stage into the current parquet/SQLite batch buffer (without books; books attached in stamp phase as today)

Then CLOB phase runs against `target_markets` exactly as today, books are attached in-place on the dicts. The dicts already exist in two places (target_markets list + the batch buffer mid-write). Solution: do the CLOB phase BEFORE the writes are finalized, so we attach books to the target dicts and only THEN flush them to parquet+SQLite.

Refined pipeline (see Task 4 for implementation):

```
events: fetch full, normalize, build map, free raw
streams pass 1 (Gamma /markets streaming):
    async for raw in gamma.iter_active_markets():
        normalized = normalize_market(raw, market_to_event_map)
        if normalized is None: continue
        mid = normalized["market_id"]
        if mid in seen_ids: continue
        seen_ids.add(mid)
        raw_count += 1
        normalized_count += 1
        if (normalized.get("liquidity_usd") or 0) > threshold:
            target_markets.append(normalized)
        # non-target: dropped from scope, no buffer needed
        # NOTE: raw is naturally GC'd at next loop iter (no references kept)

CLOB phase: unchanged — runs on target_markets

stamp phase: unchanged — runs on target_markets, attaches books in-place

validate: unchanged

persist:
    parquet: streaming write of target_markets in batches of 500
    sqlite: single-tx streaming write of target_markets in batches of 500
```

In practice subset mode at the $1k production threshold produces 6000-8000 target_markets (log-normal P(X>$1k)≈36% × 20k ≈ 7k). Streaming the persist phase is partly about discipline (pattern hygiene + future-proofing for full mode at 20k+) and partly about avoiding the 65% filtered-out non-target markets sitting in a `markets` list through dedup/validate. The architectural win is in the markets stream itself — the 20k full-Gamma-list never materializes.

**Memory budget — calibration first, fixed numbers second:**

The previous draft of this plan stated a static budget (`baseline ~80MB + working set ~25MB = ~105MB peak`). The checker (B-1) rejected this as arithmetically wrong: empirical Python baseline with our stack imported (pyarrow + httpx + sqlite + uvicorn + sentry-sdk + loguru) is closer to **100-130MB**, not 80MB. The 80MB figure is stripped-Python-no-imports, not this stack's reality. Additionally, `pa.Table.from_pylist(batch)` allocates Arrow C-side memory invisible to `tracemalloc`.

**Approach: measure baseline first, then assert delta + ceiling.**

T5.0 (new sub-step in Task 5 below) calibrates `baseline_rss` on the executor's machine by importing the stack and instantiating `Settings(...)` BUT NOT calling `run_snapshot()`. That measured number is then used as the floor for the regression assertion.

The architectural claim being tested is: **transient working-set above baseline ≤ 30MB during a 20k-market snapshot**. That is the streaming guarantee. The absolute ceiling (130MB) is a belt-and-suspenders OOM-relevance check; if the executor's local baseline is unusually high (e.g. 110MB on a system with extra modules loaded), the absolute may be hit while the delta passes — that's information, not failure.

**Transient working set above baseline (what we DO know how to estimate):**

| Component | Estimate | Notes |
|-----------|----------|-------|
| raw_events (during normalize_events, then freed) | ~5MB | 10k events × ~500 bytes post-strip |
| market_to_event_map | ~2MB | ~10k str→str entries |
| seen_ids set (50k strs) | ~5MB | str hash + intern overhead |
| target_markets list (subset mode, post-filter) | **see B-2 note** | ~few-thousand dicts at $1k prod threshold; ~6-8MB |
| Current Gamma page (1 page yielded) | ~1MB | 100 dicts × ~10KB pre-strip during yield |
| Parquet write batch buffer (500 dicts) | ~1MB | Python-side; cleared after each flush |
| pa.Table.from_pylist(batch) transient | ~1-3MB | Arrow C-side, invisible to tracemalloc but visible to RSS |
| validation issues list | <1MB | bounded by Layer1+Layer2+Layer4 cap |
| CLOB books_by_token (target tokens only) | ~5MB | ~thousands of tokens at $1k threshold |
| **Working-set subtotal** | **~26-30MB** | leaves ~0-4MB slack to the 30MB delta target |

These are not derived from a single empirical run; they are upper-bound estimates from code inspection + the 02-04 SUMMARY observations. T5 records actuals.

**Risk:** if `baseline_rss` is unexpectedly high on the Fly VM (>110MB), T6 step 4 will discover this. **The response is NOT to raise the absolute ceiling** — Fly 256MB VM has only ~150MB usable after kernel, so raising the ceiling to 140MB leaves <10MB headroom and the next Gamma response peak will still OOM. The correct response is to further shrink the working set: investigate which transient is unexpectedly large (likely candidates: pyarrow C-allocator slack, CLOB books_by_token at high target_markets count, or seen_ids set growing past projected 50k strings). Document the live Fly baseline in T7's plan SUMMARY so the next memory plan starts from real data; if the working set cannot be shrunk further, plan 02-10 will need to attack a different axis (e.g. process per snapshot to release pyarrow heap, or events streaming despite Decision A's deferral).

**Why not just measure once and pin a number?** Because baseline differs by host (Fly machine vs developer laptop vs CI runner). Pinning a delta is portable; pinning an absolute is not.

    def write_parquet_streaming(rows, out_path, *, batch_size=500):
        out_path = Path(out_path)
        out_path.parent.mkdir(parents=True, exist_ok=True)
        tmp = out_path.with_suffix(out_path.suffix + ".tmp")

        # N-1 fix: pyarrow ParquetWriter IS a context manager
        # (.venv/lib/.../pyarrow/parquet/core.py:1049-1052). Use `with` for the
        # writer; wrap in a try/except so the atomic-write contract (delete
        # .tmp on failure, os.replace on success) is honored.
        total = 0
        batch: list[dict] = []
        try:
            with pq.ParquetWriter(tmp, SNAPSHOT_SCHEMA, compression="snappy") as writer:
                for row in rows:
                    batch.append(row)
                    if len(batch) >= batch_size:
                        table = pa.Table.from_pylist(batch, schema=SNAPSHOT_SCHEMA)
                        writer.write_table(table)
                        total += len(batch)
                        batch.clear()  # release row references so dicts become GC-eligible
                if batch:
                    table = pa.Table.from_pylist(batch, schema=SNAPSHOT_SCHEMA)
                    writer.write_table(table)
                    total += len(batch)
                    batch.clear()
            # `with` block exited normally → writer.close() ran → file finalized
        except Exception:
            tmp.unlink(missing_ok=True)
            raise

        os.replace(tmp, out_path)
        logger.info(f"Parquet streaming written: {out_path} ({total} rows, batch_size={batch_size})")
        return total

                                 event_rows=None, event_tag_rows=None, batch_size=500):

        event_rows = event_rows or []

        con.execute("PRAGMA journal_mode=WAL")

    from typing import AsyncIterator

    async def _paginate(
        self,
        *,
        path: str,
        params: dict,
        label: str,
        keep_fields: frozenset[str] | None = None,
    ) -> AsyncIterator[dict]:
        """Paginate ``path`` and yield individual dicts one at a time.

        Memory-bounded: internal state is one page of ~100 dicts plus counters.
        No accumulator. Caller is responsible for buffering if they need a list.

        Yields each filtered dict (with `_page_fetched_at_ms` stamped). Honors
        MAX_PAGES, 422-offset-cap graceful stop, and all retry semantics from _get.
        """
        offset = 0
        pages_fetched = 0
        items_yielded = 0
        PROGRESS_EVERY = 50

        logger.info(
            f"Gamma: starting streaming fetch of {label} (page_limit={self.PAGE_LIMIT})"
        )

        while True:
            page_params = {**params, "limit": self.PAGE_LIMIT, "offset": offset}
            try:
                page = await self._get(path, page_params)
            except _NonRetryableHTTPError as exc:
                if "422" in str(exc) and items_yielded > 0:
                    logger.warning(
                        f"Gamma {label}: 422 at offset={offset}, "
                        f"stopping at {items_yielded} items yielded so far"
                    )
                    return
                raise
            if not isinstance(page, list):
                raise RuntimeError(
                    f"Gamma {path} returned {type(page).__name__}, expected list"
                )

            page_fetched_at_ms = int(time.time() * 1000)
            for raw in page:
                if not isinstance(raw, dict):
                    continue
                raw["_page_fetched_at_ms"] = page_fetched_at_ms
                if keep_fields is not None:
                    raw = {k: v for k, v in raw.items() if k in keep_fields}
                yield raw
                items_yielded += 1

            pages_fetched += 1
            await asyncio.sleep(0)  # cooperative yield for uvicorn / health check

            if pages_fetched == 1 or pages_fetched % PROGRESS_EVERY == 0:
                logger.info(
                    f"Gamma: {label} page {pages_fetched} fetched "
                    f"({items_yielded} {label} so far)"
                )

            if len(page) < self.PAGE_LIMIT:
                break
            if pages_fetched >= self.MAX_PAGES:
                raise RuntimeError(
                    f"Gamma {label} pagination exceeded {self.MAX_PAGES} pages — possible runaway response"
                )
            offset += self.PAGE_LIMIT

        logger.info(
            f"Gamma streamed {items_yielded} active {label} in {pages_fetched} pages (final)"
        )

    ## 30 秒心智模型

    [一段话讲清楚：Polymarket 有 ~20k 个 active markets，每个市场是一个 ~10KB 的 JSON

    ## 设计取舍（为什么这样而不是那样）

    1. 为什么 events 还是 fully materialized？
       答：events 只有 ~10k 条且每条很小（~500 bytes 后 strip），且 markets 的
       normalize 需要 market→event_id map 这个全量结构。再 streaming 一遍 events
       省下的内存（~5MB）不值得复杂度。

    2. 为什么 target_markets 还是 list（不全程 streaming）？
       答：CLOB 阶段需要全量 token_ids 才能批量调用；stamp 阶段需要在 dict 上 in-place
       attach books。subset 模式 target_markets ~500 条，内存代价 <1MB。
       架构胜负点不在这里，而在 phase 2 的 20k 流过去不留下。

    3. 为什么 parquet 用 ParquetWriter 而不是写多个 shard？
       答：snapshots.parquet_path 是单文件契约（compute_snapshot_path / R2 sync 都
       依赖）；ParquetWriter 让我们在单文件里写多个 row group，输出格式与
       pq.write_table(table) 完全一致。

    4. 为什么 SQLite 不写多个短事务？
       答：per-snapshot 原子性是硬不变量（半个 snapshot 比没 snapshot 更糟）。
       BEGIN IMMEDIATE → 多次 executemany → 一次 COMMIT 同时拿到批量写性能 +
       原子性。
