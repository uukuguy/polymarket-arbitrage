## Finding 2 — Pitfall 4 watchdog false-trip is REAL and OBSERVED 🔴 (headline)

The 30s-silence staleness watchdog **false-trips on a healthy-but-quiet connection**. In a low-activity window with no events, 30s of legitimate silence is misread as "stale":

- **During the BASELINE window (BEFORE any storm):** `13:13:18Z` and `13:17:19Z` (and every few min from 13:05) → `ws_watchdog: stale (30.0s silence) → RECONNECTING attempt=1`. The connection was healthy; the market was simply quiet.
- These pre-storm false-trips **burned the reconnect budget**. Post-storm the watchdog escalated attempt 1→5 (backoff 1s→16s), then:
  - `13:22:10Z ws_watchdog: reconnect storm cap hit (11 reconnects in last 60min); degrading to REST polling`
- After the cap, the watchdog **stopped trying** (deliberate circuit-breaker) → state stuck at DISCONNECTED, `/health overall=fail`, for the rest of the hour. Frames would still flow via REST fallback, but `ws:connection_state` reports DISCONNECTED.

**Why this is exactly Pitfall 4 (D-06.3):** Phase 04 could never observe this because every chaos iteration restarted the process, resetting the reconnect counter. With G-03 (no restart), the same process accumulates false-trips across a healthy window — the watchdog's reconnect-storm-cap is consumed by silence, not by real failures.

### Root cause (chain-truth)

`ws_watchdog` treats `30.0s of silence` as `stale → RECONNECTING` unconditionally. It does not distinguish:
- **healthy-but-quiet** (no market events; connection fine) — should be WAITING_FOR_EVENT, no reconnect
- **genuinely stale** (connection dropped; frames should be arriving but aren't)

In a quiet window every healthy connection looks "stale" every 30s, so the watchdog reconnect-storms itself into the REST-polling degradation. This is a **watchdog design bug**, surfaced by the very re-run designed to expose it.

## Carry-forward / next-phase candidate

**GAP-401 (NEW, from this run): watchdog must not false-trip on healthy-but-quiet WS.**
The 30s staleness watchdog needs to distinguish "no events because market is quiet" from "no events because connection is broken". Candidate fixes (for a follow-up phase — NOT this one):
- Add a lightweight WS-level liveness signal (ping/pong or server heartbeat) independent of market frames, so silence ≠ staleness when the socket is alive.
- OR raise the staleness threshold to a market-activity-aware value (longer in known-quiet windows).
- OR only count a reconnect against the storm-cap when it was triggered by a *real* close, not a silence-timeout.

This is the genuine bug Phase 04.1 was built to find. The three fixes (G-02/03/04) all work; they made the watchdog flaw observable for the first time.
