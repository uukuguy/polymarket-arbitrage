## Warnings

### WR-01: Behavioral tests for G-02 startup-prime are tautological — they test the helper, not `l2_main.py`

**File:** `tests/m1-perception/test_l2_startup_prime.py:221-296`
**Issue:** The three `@pytest.mark.asyncio` tests (`test_catchup_block_dispatches_prime_on_no_missed`, `test_catchup_block_dispatches_prime_after_missed_replay`, `test_catchup_block_dispatches_prime_when_catchup_raises`) share a helper `_run_catchup_and_prime_block`. That helper **directly calls `_fake_dispatch({"snapshot_id": -1, "_startup_prime": True, ...})` at line 294-296** to simulate the prime — it does not run any code from `l2_main._run_l2_daemon`. The prime call is in the test fixture itself, so these tests will pass even if the prime is deleted from `l2_main.py`. The only real regression protection comes from the four structural (text-search) tests, not from these behavioral ones.

To illustrate the failure mode: if someone removes lines 433-435 from `l2_main.py` (the `_dispatch_on_snapshot` prime call), all four structural tests fail immediately, but all three behavioral tests still pass — because `_run_catchup_and_prime_block` manufactures the prime dispatch itself.

**Fix:** Restructure the behavioral tests to actually exercise `_run_l2_daemon` by patching `_dispatch_on_snapshot` as a spy and running the real code path, rather than re-implementing the catchup+prime block inline. A minimal approach:

```python
# Patch the module-level _dispatch_on_snapshot inside the daemon closure by
# intercepting asyncio.create_task (since _dispatch_on_snapshot is defined
# inside the async function and uses it). Or refactor _run_l2_daemon to accept
# a dispatch_fn argument (testability seam).
#
# Simplest regression guard without full daemon spin-up:
# Patch `on_snapshot_complete` to record calls, then call
# `_run_l2_daemon` with all heavy I/O mocked. The prime dispatch
# through _dispatch_on_snapshot → asyncio.create_task(on_snapshot_complete(...))
# will be captured.
```

The four source-text structural tests (`test_startup_prime_exists_in_l2_main`, `test_startup_prime_uses_sentinel_minus_one`, `test_bootstrap_and_replay_paths_unchanged`, `test_prime_placed_after_catchup_envelope`) do provide meaningful regression protection and should be kept as-is.

### WR-02: `bool()` coercion in `ws_test_kill_handler` silently enables the kill flag when `"enabled"` is the string `"false"`

**File:** `src/polyarb/http/l2_control.py:70`
**Issue:** The handler does `enabled: bool = bool(body.get("enabled", False))`. Python's `bool()` coerces any non-empty string to `True`, so `{"enabled": "false"}` (string, not JSON boolean) silently sets `enabled=True` and enables the WS-kill flag. The docstring and Makefile both specify JSON boolean literals, but the code does not enforce this. A misconfigured caller (e.g., someone hand-crafting a curl command) who passes `"false"` (string) to disable the flag would accidentally enable it instead.

The endpoint is HMAC-gated so an external attacker cannot exploit this. The practical risk is low (only the Makefile invokes this endpoint in normal use), but the semantic inversion for `{"enabled": "false"}` is dangerous for a chaos primitive: the operator intends to clear the flag and instead sets it.

**Fix:**
```python
# Replace:
enabled: bool = bool(body.get("enabled", False))

# With:
enabled_raw = body.get("enabled", False)
if not isinstance(enabled_raw, bool):
    logger.warning(
        f"ws_test_kill_handler: 'enabled' must be a JSON boolean, "
        f"got {enabled_raw!r} ({type(enabled_raw).__name__})"
    )
    return JSONResponse(
        {"error": "'enabled' must be a JSON boolean (true or false)"},
        status_code=400,
    )
enabled: bool = enabled_raw
```

### WR-03: `chaos-ws-kill` Makefile target silently proceeds with an empty `POLYARB_SCAN_SHARED_SECRET`; produces a misleading 401 with no diagnostic

**File:** `Makefile:905-911`
**Issue:** The `chaos-ws-kill` target sources `.env` then computes the HMAC, but never validates that `POLYARB_SCAN_SHARED_SECRET` is non-empty. If the secret is absent from `.env` (or `.env` itself is missing), `openssl dgst -hmac ""` computes an HMAC with an empty key, the signature is wrong, and the server returns 401. The operator sees `{"error":"invalid X-Signature"}` with no indication that the root cause is a missing secret. The existing `unpause-prod` target at line 466 correctly guards against this with `[ -n "$$POLYARB_SCAN_SHARED_SECRET" ] || (echo "ERROR: ..."; exit 1)`. The new target lacks this guard, creating an inconsistency and a confusing failure mode when the chaos recipe is run at a critical moment.

Additionally, if `.env` does not exist, `set -a; . ./.env; set +a` fails with a shell error (`No such file or directory`), which terminates the recipe with exit 1 but without a clear diagnostic.

**Fix:**
```makefile
chaos-ws-kill:
	@test -n "$(ON)" || { echo "usage: make chaos-ws-kill ON=1|0"; exit 1; }
	@set -a; [ -f .env ] && . ./.env; set +a; \
	  [ -n "$$POLYARB_SCAN_SHARED_SECRET" ] || { echo "ERROR: POLYARB_SCAN_SHARED_SECRET not set in .env"; exit 1; }; \
	  BODY=$$([ "$(ON)" = "1" ] && echo '{"enabled":true}' || echo '{"enabled":false}'); \
	  SIG=$$(printf '%s' "$$BODY" | openssl dgst -sha256 -hmac "$$POLYARB_SCAN_SHARED_SECRET" | sed 's/^.* //'); \
	  curl -sS -X POST https://polyarb-l2.fly.dev/control/chaos/ws-test-kill \
	    -H "X-Signature: sha256=$$SIG" -H 'Content-Type: application/json' -d "$$BODY" | jq .
.PHONY: chaos-ws-kill
```

### IN-01: `chaos:ws_test_kill_flag` `observedValue` is hardcoded string `"1"` but the flag is now a `bool`

**File:** `src/polyarb/http/l2_health.py:386`
**Issue:** The sub-check sets `"observedValue": "1"` (a string) when the flag is active, which is a carry-over from the original `os.getenv("POLYARB_WS_TEST_KILL") == "1"` implementation. Now that the underlying flag is a `bool`, the observed value is semantically inconsistent: a boolean flag reporting a string representation. The sister sub-check `process:rss_kb` uses a numeric `observedValue`. For operator tooling that parses `/health` JSON programmatically, this type inconsistency could cause surprises.

**Fix:** Change `"observedValue": "1"` to `"observedValue": True` to match the actual type of the flag, and update the corresponding test assertion in `test_ws_test_kill_flag.py::test_health_surfaces_kill_flag_when_set`.
