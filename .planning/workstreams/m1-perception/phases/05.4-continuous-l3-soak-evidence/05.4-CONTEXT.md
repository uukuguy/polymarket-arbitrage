# Phase 05.4: Continuous L3 Soak Evidence - Context

**Gathered:** 2026-07-22
**Status:** Ready for planning
**Source:** Approved design contract

<domain>
## Phase Boundary

Make the Phase 05 assertion “five L3 markets remained healthy throughout a
24-hour soak” mechanically provable. Deliver durable evidence for every
scheduled promoter run, truthful WebSocket membership state, 30-second
process/per-market samples, runtime events, exact-window operator reports, and
the test/chaos/teaching surface needed to trust them.

The phase includes local schema/code/tests/documentation plus an explicitly
gated production migration, deployment, readiness proof, and fresh 24-hour soak.
Design or local implementation does not itself authorize production mutation.

</domain>

<decisions>
## Implementation Decisions

### PHASE05.4-R01 — Append-only evidence schema

- Add Alembic revision `007`, chained from `006`, with five append-oriented
  tables: `l3_runtime_boots`, `l3_promote_runs`, `l3_health_samples`,
  `l3_market_samples`, and `l3_runtime_events`.
- Retain evidence for at least 30 days. Add exact-window and boot/sequence
  indexes. Never synthesize missing historical rows after recovery.
- A process restart creates a new `boot_id`; a second boot inside a strict
  window invalidates that window.

### PHASE05.4-R02 — Promoter ledger

- Persist one terminal `l3_promote_runs` row for the initial run and every
  scheduled 300-second tick.
- `(boot_id, run_seq)` is unique and contiguous; terminal status is one of
  `success`, `frozen`, `underfilled`, or `failed`.
- Persist scheduled/start/finish times, counts, mapping/token hashes, WS
  generation, add/remove results, mirror result, bounded reason, and duration.
- No scheduled-to-start gap may exceed 360 seconds in a strict PASS window.

### PHASE05.4-R03 — Truthful membership transaction

- Track three distinct states: desired, control-committed, and
  business-evidenced membership.
- `promote_run` must consume `False` from `add_subscriptions` and
  `remove_subscriptions`; a failed control operation leaves committed state
  truthful and makes the run non-success.
- `l3_promoted_at_ts` mirrors control-committed membership only after
  reconciliation. Socket send success is not business evidence.
- Same-generation initial/book frames supply business evidence; evidence from an
  older socket generation cannot be reused.

### PHASE05.4-R04 — Bounded-gap process and market evidence

- Sample process health and all five intended market pairs every 30 seconds.
- A strict window allows no consecutive sample gap greater than 75 seconds.
- Store per-market/token membership, same-generation business evidence, book
  timestamp/age, Yes-side OHLC timestamp/age, status, and bounded reason.
- There is no strict quiet-market exception. Quiet refresh must keep every
  promoted market within the existing freshness policy; one hot market cannot
  refresh another market's clock.

### PHASE05.4-R05 — Runtime events and chain-truth health

- Persist watchdog stale decisions; reconnect lifecycle; WS generation changes;
  subscription-control failure/compensation; evidence-writer failure/recovery;
  and shutdown signals in `l3_runtime_events`.
- Add `/health` subchecks for evidence sample freshness, promoter-ledger
  freshness, desired-versus-committed equality, and worst per-market freshness.
- Each health check must read data mutated by the actual success/failure path and
  have an end-to-end chaos/integration test. A failed evidence write leaves its
  success anchor unchanged so health ages into failure.

### PHASE05.4-R06 — Exact-window operator contract

- Add Makefile targets `l3-evidence-status`, `l3-soak-checkpoint`,
  `l3-soak-verify`, and `l3-evidence-retention-check`.
- Six-hour checkpoints query the complete `[T+0, checkpoint)` durable interval;
  they are human summaries, not primary evidence.
- Outputs include UTC bounds, boot/release/machine anchors, row counts, expected
  versus observed promoter ticks, maximum gaps, cardinality minima, per-market
  freshness/coverage, event counts, hashes, and explicit `PASS`/`NOT-CLOSED`.
- Missing evidence, extra boots, non-success promoter runs, identity/digest
  changes, gaps, or critical events fail closed with a non-zero exit.

### PHASE05.4-R07 — Test-first and operator learning

- Implement in RED/GREEN slices covering migration roundtrip, all promoter
  outcomes, WS Boolean failure, generation isolation, one-hot/four-silent market
  failure, sampler gaps, restarts, retained events, and exact interval bounds.
- Run focused tests, full repository pytest, Ruff, compile, image-aware chaos
  checks, `make planning-status`, and M1 manual contracts before completion.
- Add a new `docs/learning/NN-<topic>.md` mental-model document and update
  `docs/learning/00-INDEX.md`.

### PHASE05.4-R08 — Production and strict-soak gates

- Production Alembic 007 and daemon deployment require a separate explicit user
  authorization after local verification.
- After deployment, prove readiness and start a new exact-identity T+0. The
  release-37 window beginning `2026-07-21T14:29:47.941Z` remains diagnostic-only.
- A strict 24-hour PASS requires one boot identity, sample gaps at most 75
  seconds, every expected promoter tick successful at five markets/ten desired
  and committed tokens, locked per-market freshness/coverage, zero disallowed
  critical events, 5/5 book and Yes-OHLC coverage, and hash-bound T+0/T+6/T+12/
  T+18/T+24 reports.
- Any violation permanently makes that window `NOT-CLOSED`; recovery starts a
  new formal window instead of rewriting the failed interval.

### the agent's Discretion

- Exact PostgreSQL column types, JSON versus normalized detail columns, and
  index names, provided the locked fields and query semantics remain intact.
- Internal Python module/class names and batching mechanics, provided evidence
  writes remain append-oriented and failure-visible.
- Whether the 30-second sampler writes process and five market rows in one RPC
  transaction or an equivalent atomic database operation.

</decisions>

<specifics>
## Specific Ideas

- Treat the 24-hour duration as exposure time and the 30-second/event ledgers as
  observation resolution; never conflate them again.
- Expected daily volume is modest: about 1,440 process rows, 7,200 five-market
  rows, and 288 promoter rows.
- Fly logs stay useful for diagnosis but are never the source for strict absence
  claims.

</specifics>
