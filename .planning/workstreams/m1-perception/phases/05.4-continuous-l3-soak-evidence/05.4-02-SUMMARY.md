## Accomplishments

- Replaced the legacy L3 active set with independently inspectable desired,
  committed, and evidenced membership. Offline/failed control never becomes
  committed, and every generation/connection exit invalidates old evidence.
- Replaced the one-hot quiet refresh with an all-required-token barrier. The real
  production dispatcher distinguishes TOB from depth-write success and supports
  the no-L3 candidate fallback without permanently expanding depth writes.
- Refactored the promoter into one typed terminal path with one append attempt per
  scheduled sequence, exact state hashes/counts/control results, durable-anchor
  semantics, mutation-free dry-run, and bounded retryable dashboard cleanup.
- Anchored the scheduler to the immutable boot time and wired one canonical
  AcceptanceConfig/runtime/boot/store through WS membership and every tick.
- Removed the owner/migration DSN from the L2 daemon path. Missing, rejected,
  service, superuser, retention, or mixed credentials cannot start any direct
  PostgreSQL task or counterfeit evidence.

## Decisions Made

- `set_l3_desired()` is the only reconnect-intent mutation; add/remove methods
  report current-generation control truth and never imply desired state.
- A refresh request registers required identities before sending. The dispatcher
  consults the exact consumer, so candidate fallback depth is temporary and
  disappears when the barrier is cleaned up.
- `PromoteRunResult.persisted` separates business outcome from durable ledger
  truth. A writer failure cannot advance anchors or persisted selection caches.
- Mirror reconciliation is at-least-once and idempotent. Every tick refreshes the
  complete current Yes set and clears at most 100 database-discovered stale
  identities; a full batch remains `mirror_cleanup_pending` until an empty/short
  proof batch is observed.
- An unexpected pre-append promoter exception gets one failed terminal attempt.
  After append begins, no fallback retry is allowed; the scheduler marks writer
  failure and stops, preventing a later sequence from hiding the gap.
- Boot persistence is the authorization boundary for every daemon-owned direct
  PostgreSQL task. It does not gate HTTP, WS, or Supabase REST availability.

## Deviations from Plan

### Auto-fixed Issues

**1. Initial-subscribe and consumer-exit lifecycle races**
- **Found during:** Task 1 independent review
- **Issue:** Desired could change during initial send and be falsely committed;
  nonstandard stream exits could retain old committed/evidenced state.
- **Fix:** Freeze and validate the sent snapshot, compensate on drift, and funnel
  all exits through one idempotent lifecycle cleanup.
- **Committed in:** `0114c42`

**2. Strict dispatch timestamp typing**
- **Found during:** Task 2 independent review
- **Issue:** Wrong observed-at types leaked `AttributeError` instead of the typed
  evidence contract.
- **Fix:** Require exact `datetime | None` and test wrong, naive, and non-UTC values.
- **Committed in:** `6f2c35a`

**3. Promoter terminal, cache, and reconciliation gaps**
- **Found during:** Task 3 reviews
- **Issue:** Post-selection exceptions could escape, invalid config could be
  disguised as a matching hash, caches advanced before append, mirror retries
  lost identity, and repeated remove failures could inflate membership.
- **Fix:** Added total terminal boundaries, persisted Mapping semantics,
  cache-after-append staging, remove-first controls, complete-set idempotent
  mirror, and bounded database-driven stale cleanup.
- **Committed in:** `3e1379f`, `d48255e`, `d7067bf`

**4. Daemon startup and scheduler authorization gaps**
- **Found during:** Task 4 independent review
- **Issue:** An unbound server could write boot evidence; rejected credentials
  still started PG tasks; config was rebuilt per tick; unexpected errors could
  leave later sequence rows after a gap.
- **Fix:** Enforced server lifecycle cleanup, boot-gated all PG tasks, passed the
  exact AcceptanceConfig object, and stopped the scheduler on ambiguous escape.
- **Committed in:** `94b5e08`

**5. Cross-task terminal-attempt and fallback-depth contradictions**
- **Found during:** final whole-branch review
- **Issue:** Pre-append unexpected errors had no terminal attempt, while the
  no-L3 candidate refresh requested depth that the production dispatcher would
  never write; failure logs also exposed identity lists/exception text.
- **Fix:** Added an append-attempt fence and total pre-append fallback, wired
  consumer-owned temporary depth eligibility, and reduced logs/Sentry to bounded
  reason/type/generation/count data.
- **Committed in:** `1380f20`
