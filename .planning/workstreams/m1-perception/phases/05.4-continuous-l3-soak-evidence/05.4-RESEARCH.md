# Phase 05.4: Continuous L3 Soak Evidence — Research

**Researched:** 2026-07-22
**Scope:** local code, schema, tests, deployment and operator contracts
**Conclusion:** ready for planning

## Planning Summary

Phase 05.4 is not a generic telemetry addition. It must replace four optimistic
latest-state shortcuts with durable facts: every scheduled promoter outcome,
the difference between desired/committed/evidenced WS membership, five separate
market freshness chains, and runtime/control events that outlive Fly logs.

The implementation should use five sequential plans. Schema and storage APIs
come first; truthful WS/promoter transactions second; sampling/health/runtime
events third; exact-window CLI/Make/chaos/teaching fourth; production migration,
deployment and the fresh soak fifth. Plan 05 must remain `autonomous: false` and
must stop at explicit migration/deploy and wall-clock gates.

## Current Code Truth

### Promoter

- `src/polyarb/observation/l3_promote.py:448` owns `promote_run`.
- The intended set is diffed against module-global `_l3_active_set`; at lines
  664–666 the Boolean results of `WsConsumer.add_subscriptions` and
  `remove_subscriptions` are ignored.
- Exceptions are caught, but execution still mirrors `l3_promoted_at_ts`, assigns
  `_l3_active_set = new_token_set`, and advances `_last_promote_at_s` at lines
  681–682. Current health can therefore report intended membership as actual.
- `run_periodic` at line 721 runs once immediately and then uses
  `asyncio.wait_for(stop_event.wait(), timeout=interval_s)`. It has no scheduled
  time, boot ID, sequence number, or durable terminal outcome.
- Existing dry-run isolation is valuable and must remain mutation-free.

### WebSocket membership and business evidence

- `src/polyarb/daemon/ws_consumer.py:125` already serializes subscription control
  and separates `_candidate_set` from `_l3_active_set`.
- `_connection_generation` and same-generation book waiters exist, but there is
  no public immutable snapshot of generation, committed tokens, or per-token
  business evidence.
- `add_subscriptions`/`remove_subscriptions` return `False` when offline or when
  control fails. The offline fallback still mutates `_l3_active_set`, so its
  semantics are desired/reconnect intent rather than wire-committed truth.
- `request_book_refresh` creates one Future and registers it for every asset.
  `record_book_evidence` resolves that shared Future after the first qualifying
  asset; the log then says all assets were evidenced. Phase 05.4 must require a
  set/barrier of all expected assets on the same generation.
- Frame dispatch calls `record_book_evidence` with the Boolean returned by
  `_on_event`.

### Book and health chain

- `src/polyarb/daemon/l2_main.py:331` returns TOB mirror success from `_on_event`.
  For promoted `book` frames it calls `push_book_levels` but ignores that result.
  Consequently same-generation book evidence currently means TOB success, not
  necessarily L3 depth success. The new evidence path must propagate both facts
  explicitly and bind strict L3 business evidence to the required write.
- `src/polyarb/http/l2_health.py:543` reads three module-global latest values.
  `l3:active_count` is informational and does not affect overall severity;
  promoter and global book ages do. One market can keep the global book anchor
  fresh for four silent markets.
- New health checks should consume an immutable in-memory evidence snapshot whose
  fields are advanced only after successful durable writes/control outcomes.
  Required checks: sampler persistence age, promoter-ledger persistence age,
  desired/committed equality, and worst per-market book/OHLC freshness.

### Storage and schema

- Production head is `alembic/versions/006_add_no_token_id.py`; revision 007 must
  chain directly to 006.
- `L2SupabaseMirror` provides fail-soft Boolean methods and breadcrumbs, but the
  evidence model spans multiple related rows. Add a focused storage module such
  as `src/polyarb/storage/l3_evidence_store.py` instead of growing the mirror into
  a mixed-responsibility class.
- The store should expose typed input records and bounded methods for boot start/
  stop, terminal promoter run, atomic health+five-market sample batch, runtime
  event, current status, and exact-window query. Prefer one Supabase RPC for the
  process+market sample batch so a partial five-market snapshot cannot look
  complete.
- Suggested keys/indexes:
  - boots: primary `boot_id`; indexes on `started_at`, identity/digest;
  - promoter: unique `(boot_id, run_seq)`; indexes on `(scheduled_at, boot_id)`
    and `status`;
  - health: unique `(boot_id, sample_seq)`; index on `sampled_at`;
  - market: unique `(boot_id, sample_seq, market_id)`; indexes on
    `(sampled_at, market_id)` and token IDs;
  - events: primary UUID/bigserial; indexes on `(occurred_at, kind)` and boot.
- Downgrade may drop only the five new tables/RPC/indexes. Contract tests should
  follow `tests/alembic/test_006.py`: source assertions plus Testcontainer-backed
  upgrade → downgrade → upgrade replay.

### Deployment path

- `.github/workflows/deploy-l2.yml` only watches migration `003_*` and omits
  `l3_promote.py`. Phase 05.4 changes would therefore not reliably trigger a
  push deployment. Update paths to include the full L2 daemon/observation/storage
  surfaces and `alembic/versions/007_*` (or a safe `alembic/versions/**` rule).
- `make deploy-l2-prod` is a production mutation. It and `make supabase-migrate`
  stay behind an explicit user gate after all local checks pass.

## Failure Semantics to Lock in Plans

1. Evidence write failure never advances the success anchor and emits/retries a
   recovery event without fabricating the missing row.
2. Promoter selection/fetch freeze and under-fill are terminal ledger statuses,
   not missing ticks.
3. A WS `False`, exception, or generation change prevents `success` and prevents
   desired state from being reported as committed.
4. Per-market sampling uses the bound five-market mapping at that sample; zero
   rows or fewer than five market rows make the sample incomplete.
5. Interval tools derive expected promoter ticks from the formal start and
   cadence, not from min/max rows that happen to exist.
6. Missing historical logs are irrelevant to PASS because the database event
   ledger is authoritative; unavailable database evidence fails closed.
7. A second boot/config/mapping digest inside the window is an explicit
   NOT-CLOSED reason.

## Security Threat Model Inputs

- **T-054-01 evidence forgery/backfill:** append-only APIs, server timestamps or
  bounded clock validation, unique sequences, hash-bound reports.
- **T-054-02 cardinality inflation:** database uniqueness on sample market/token
  identities plus deterministic mapping hashes.
- **T-054-03 secret leakage:** operator commands accept normal environment-backed
  credentials and never print service keys or raw auth headers.
- **T-054-04 unbounded evidence growth:** 30-day retention contract with explicit
  retention check and bounded cleanup mechanism; cleanup cannot touch current
  formal window.
- **T-054-05 production mutation by read command:** status/checkpoint/verify/
  retention-check are read-only; schema/deploy targets remain separately named
  and gated.

Block on unresolved High severity threats under default ASVS L1 enforcement.

## Validation Architecture

### Test layers

| Layer | Command family | What it catches |
|---|---|---|
| schema contract | `uv run pytest tests/alembic/test_007.py -q` | DDL, indexes, chain, replay |
| evidence/store | focused `tests/m1-perception/test_l3_evidence*.py` | hashes, atomic batches, write failures |
| promoter/WS | existing promoter and dynamic-subscribe tests plus new focused cases | Boolean/generation/membership truth |
| health/sampler | focused health and sampler tests | anchors, gaps, five-market isolation |
| verdict CLI | fixture-backed script tests | exact bounds, missing ticks, exit codes |
| chaos/chain | focused chaos tests + image check | killed sampler, restart, event persistence |
| regression | `uv run pytest -q` + Ruff + compile | repository compatibility |

### Sampling rule during implementation

- Every task begins with a failing focused test and ends with that focused suite
  green before commit.
- Every plan ends with its union of focused suites plus Ruff/compile on touched
  files.
- Every wave ends with the full repository pytest suite.
- No three consecutive tasks may rely on manual-only verification.

### Required automated cases

1. 007 upgrade/downgrade/re-upgrade, keys, constraints and indexes.
2. Initial and timed promoter runs create contiguous sequences for success,
   frozen, underfilled, exception and writer failure.
3. add/remove `False` leaves desired != committed and produces non-success.
4. old-generation frames cannot satisfy current-generation business evidence.
5. quiet refresh requires all expected assets, not the first asset.
6. TOB success with book-level failure does not satisfy L3 depth evidence.
7. one hot/four silent makes worst-market health fail while global age is fresh.
8. sampler pause >75 seconds and daemon restart remain visible without backfill.
9. exact-window verifier fails on row/tick gaps, non-success, second boot, hash
   changes, incomplete 5/5 coverage and critical events.
10. retention check proves at least 30 days and protects the active window.

### Manual-only gates

- Production Alembic 007 push and daemon deployment require explicit approval.
- Exact Fly machine/instance/image/release verification and starting fresh T+0
  occur only after deployment/readiness proof.
- The 24-hour wall clock cannot be simulated for the production verdict; its
  reports are generated from durable rows and reviewed at T+6/T+12/T+18/T+24.

### Feedback budget

Target focused feedback under 60 seconds, plan-level feedback under 5 minutes,
and full-suite feedback at each wave. Long production soak time is exposure, not
test feedback latency.

## Research Risks

- Atomic Supabase RPC DDL details need verification against existing migration
  conventions during Plan 01, but this does not change the locked atomicity
  requirement.
- OHLC is a view derived from durable rows; the sampler should record observed
  timestamp/age rather than attempt to write OHLC.
- Retention scheduling mechanism is implementation discretion. The strict gate
  requires retained evidence and a check, not a new always-on scheduler service.

## RESEARCH COMPLETE

The local code supports the planned architecture but contains four concrete
truth gaps: ignored WS Boolean outcomes, a first-asset quiet-refresh barrier,
ignored book-level write success, and latest/global-only health. Five sequential
plans can close them without changing the locked L3 recipe or adding a scheduler
dependency.
