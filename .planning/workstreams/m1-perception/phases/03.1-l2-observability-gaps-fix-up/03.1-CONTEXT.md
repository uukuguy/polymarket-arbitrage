## Implementation Decisions

### Fly DNS chronic failure (GAP-100)

- **D-01:** **采 A+D+C 组合修法** —
  - A: `tenacity @retry(stop_after_attempt=3, wait=exponential)` 包裹 `iter_active_markets()` (`src/polyarb/snapshot/orchestrator.py:251` 附近),抹平秒级 DNS jitter
  - D: GAP-101 调高 `failure_threshold` 配合 (见 D-02)
  - C: 并行开 Fly support ticket 报 chronic DNS 问题,deploy 一个内部 cron 跑 `dig gamma-api.polymarket.com` 拿节点级 baseline 数据 (async,不阻 03.1 close)
- **Why not B (IPv4 only transport)**: 没有先验证是否真是 IPv6 路径炸,盲改 transport 可能改了无关变量。等 C 拿到诊断数据再决定要不要补 B
- **预期效果**: retry 抹平 ≥80% 的偶发 jitter; 真节点级故障由 D 顶住; 长期病灶等 C 数据回来定

### Failure threshold (GAP-101)

- **D-02:** **`failure_threshold` 从 3 调高到 5** (1 行 config 改)
- **Why**: 配合 D-01 A retry,5 次连续 fail 需要 ~3 小时 (snapshot 间隔 ~37s);healthz-watcher 每 15min 轮询会先一步 auto-unpause + Telegram。 真持续故障 5 次内能被 watcher 兜底
- **Why not B (transient error 分类)**: 是更优解但 4-6h 工程量,与 03.1 P0 节奏不符。 **写进 m1-perception backlog**: "若出现新 fail 类型需要再衡量分类时启动"
- **Why not C (时间窗 N-of-M)**: healthz-watcher 已兜底,实现成本不值

### Sentry alert routing (GAP-102)

- **D-03:** **3 步 sequential**:
  1. **Audit (必做)**: 用 playwright-cli 登 Sentry, 翻 Alerts → Rules 看每条 rule 的 conditions (是否 `environment=production` filter); 翻 Issue 121111789 "Linked Alerts" 看实际触发的 routing; 翻 Telegram bot history 确认 SCHEDULER_PAUSED 3 次 message 真发送
  2. **修法**: `sentry_sdk.init(environment="production")` (Fly machine prod app 名实对齐); 同时按 audit 结果调 alert rule 的 env filter
  3. **二次升级 backlog**: PagerDuty / SMS escalation 推到 m5-industrialize Polywatch phase backlog (healthz-watcher 已能 16min 内自动 unpause,人响应不响应都恢复)
- **Why**: polyarb-l1 / polyarb-l2 都是 prod app, `environment="dev"` 是历史残留 — 名实不符必导致 alert routing 漂移

### Chaos Inj L2-4 cross-bug storm

- **D-04:** 设计 = **B sustained (100 msg/s × 30s) + B 环境变量作用域 (`POLYARB_WS_TEST_KILL`) + A 双故障叠加 (storm + Supabase pause 同时)**
- **在 03.1 跑** (非延 Phase 04): 当前 polyarb-l2 candidate set 只 3 个 bootstrap asset (memory CURRENT-CALL 已记),低负载下验证 WS 合函数/watchdog/storm cap **逻辑正确性**,不验 throughput;throughput 类验证等 Phase 04 candidate refresh 真做完再补
- **Why B sustained over burst/random**: 最接近真实 DoS;burst 太人为,random 难复现
- **Why A 双故障 over 分两次**: 这就是 Inj L2-4 的全部意义;分两次相当于回到 L2-3a (已验过)
- **作用域安全**: prod fly secret 永远不设 `POLYARB_WS_TEST_KILL`,代码里 `if os.getenv(...)` 简单 guard 即可
