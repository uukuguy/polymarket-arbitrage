## Where the WS subscribe loop actually lives

Plan 06's `<read_first>` flagged that Phase 03 LEARNINGS L2 had guessed the kill branch would go in `ws_market_client.py` (~10 LoC). Investigation:

- `src/polyarb/clients/ws_market_client.py` — owns the LOW-level connection (websockets.connect) + emits `stream_market_events` async iterator
- `src/polyarb/daemon/ws_consumer.py` — owns the HIGH-level subscribe-loop iteration (`async for event in stream_market_events(...)`) + on_event dispatch + watchdog.touch()

The actual message-iteration boundary is in `ws_consumer.py:99` (the `async for event` loop). That's where the kill check belongs — checking inside `stream_market_events` would be checking inside the WS framing reader, where raising a custom exception would have to traverse the websockets library's own retry logic. Cleaner to check at the consumer's iteration boundary, which already has a proper exception handling envelope.

Final shape:
- `_check_ws_test_kill()` (5 LoC) called at top of the loop body (line ~149 in current ws_consumer.py)
- `WsTestKillRequested` (Exception subclass, 2 LoC)
- Outer `except WsTestKillRequested` handler (8 LoC: log warning + set state DISCONNECTED + return)
- Total ~15 LoC including docstrings — close to the LEARNINGS estimate.
