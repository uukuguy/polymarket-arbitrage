## Decisions Made

**D-PLAN01-01: Schema column reality vs CONTEXT**

CONTEXT.md `<code_context>` claimed `l2_top_of_book.observed_at_ms` exists. Verification: that table lives in Supabase Postgres (not local SQLite), and the actual column is `ts` (alembic `003_l2_tables.py`). The plan body acknowledged this and pivoted the design to a local SQLite singleton — implementation followed the plan's `<interfaces>` correction, not the (incorrect) CONTEXT reference.

**D-PLAN01-02: Cache, not query**

Why local cache rather than reading Supabase from /health? Sub-second /health probes must not round-trip to Supabase (latency + Free-tier request budget). Cache lives in same local SQLite file as scheduler_state and is read via `mode=ro` URI (HTTP server NEVER writes — P3.8 invariant preserved).

**D-PLAN01-03: Cache write is best-effort**

If the cache write fails (disk full, lock contention), the mirror still returns True for its actual Supabase write success. A `logger.warning` + Sentry breadcrumb anchor the failure but don't propagate. Reasoning: freshness staleness will surface via /health as WARN regardless, and breaking the mirror to protect a freshness anchor inverts the priority.
