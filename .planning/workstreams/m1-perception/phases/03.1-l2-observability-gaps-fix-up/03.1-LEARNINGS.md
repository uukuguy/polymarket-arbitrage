## Decisions

### D-01: Fly DNS chronic failure — A+D+C combo (NOT B blind transport-swap)
Adopt three mitigations together: (A) `tenacity @retry(stop_after_attempt=3, wait_exponential)` around Gamma `iter_active_markets()` to absorb second-scale DNS jitter, (D) raise `failure_threshold` 3→5 to give healthz-watcher time to auto-unpause, (C) ship `dns_baseline_probe.py` + Fly support ticket in parallel for diagnostic data. Explicitly rejected B (httpx IPv4-only transport) because no prior evidence confirms IPv6 path as the cause — blind transport swap risks changing an unrelated variable.

**Rationale:** Retry absorbs ≥80% of jitter; threshold + watcher absorb the rest; diagnostic data informs whether B is even needed.
**Source:** 03.1-CONTEXT.md (D-01)

### D-02: failure_threshold 3 → 5 — minimal change, NOT transient classification
1-line config bump. Rejected B (transient error classification by errno/category) as more correct but 4-6h work; logged to m1-perception backlog with trigger "if a new fail type appears under Phase 04+ candidate load". Rejected C (time-window N-of-M) as overengineering since healthz-watcher already provides 15-min auto-unpause floor.

**Rationale:** 5 × ~37s ≈ 3min observation window before PAUSE; healthz-watcher cron (15-min) auto-unpauses well within human-response cadence.
**Source:** 03.1-CONTEXT.md (D-02), 03.1-04-SUMMARY.md

### D-03: Sentry alert routing — 3-step sequential (audit → env=production → escalation→backlog)
Audit FIRST via playwright-cli (don't change rules blind), THEN flip `POLYARB_SENTRY_ENV=production` on both Fly apps and rewire `sentry_sdk.init(environment=...)` from buggy release_id derivation, THEN defer PagerDuty/SMS escalation to m5 Polywatch backlog. Defer Sentry-side rule changes (add Telegram action target, env filter) to user manual review — they require org-level integration install + risk silently reducing alert reach.

**Rationale:** polyarb-l1/l2 are prod apps; `environment="dev"` from `if release_id != "dev" else "dev"` was a logic bug. Audit-driven discipline avoided multiple wrong fixes.
**Source:** 03.1-CONTEXT.md (D-03), 03.1-05-SUMMARY.md, sentry-audit-report.md

### D-04: Inj L2-4 design — B sustained + B env-scope + A double-fault, run in 03.1 (NOT defer)
Choose B sustained (100 msg/s × 30s) over burst/random for realism; gate via `POLYARB_WS_TEST_KILL` env var (literal `"1"` only — boolean-like guard); stack A double-fault (WS storm + Supabase pause simultaneously). Run in 03.1 even though candidate set is only 3 bootstrap assets — the purpose is verifying daemon LOGIC under storm, not throughput; throughput validation waits for Phase 04 real candidate scale.

**Rationale:** Splitting into two single-fault injections degenerates back to L2-3a (already verified). Logic correctness IS the test.
**Source:** 03.1-CONTEXT.md (D-04), 03.1-06-SUMMARY.md, 03.1-SOAK-LOG.md (Task 4)

### D-PLAN02-02: Status boundary semantics — `>=` ordering (NOT `<` ordering)

**Rationale:** Matches IETF-style threshold semantics and makes boundary-value tests stable.

**Source:** 03.1-03-SUMMARY.md

### D-PLAN04-01: Strategy B (async-for wrap with sentinel) over Strategy A (helper returning first-frame + stream)
Wrap `async for raw in gamma.iter_active_markets()` inside `tenacity.AsyncRetrying`; use `first_frame_seen` sentinel so mid-stream errors are NOT retried (partial-stream is not an idempotent retry boundary).

**Rationale:** Strategy A required the "anything you anext you must yield" invariant — easy to break on future refactor. B avoids the trap entirely.
**Source:** 03.1-04-SUMMARY.md

### D-PLAN04-02: Strict-DNS retry predicate (string-match, NOT errno introspection)
`_is_dns_jitter(exc)` matches `[Errno -5]`, `[Errno -3]`, `EAI_NODATA`, `EAI_AGAIN`, `Name or service not known`, `Temporary failure in name resolution`. `Connection refused`, `TimeoutError`, raw `OSError` return False — they signal real outages and must surface as `API_UNREACHABLE` issue immediately.

**Rationale:** httpx wraps `socket.gaierror` in ways that don't always preserve `.errno` across versions — string-match is more robust.
**Source:** 03.1-04-SUMMARY.md

### D-PLAN06-01: `POLYARB_WS_TEST_KILL` accepts ONLY literal `"1"` + CI gate against prod-config drift
Env flag triggers WS drop ONLY when value is the literal string `"1"`. `"0"`, `"true"`, `"yes"`, empty string all silently ignored. A pytest test greps `fly.toml` / `fly-l2.toml` for forbidden flag names on every commit.

**Rationale:** Boolean-like values from misconfigured secret managers must NOT trigger. The CI gate stops accidental prod opt-in at commit time, not runtime.
**Source:** 03.1-06-SUMMARY.md

## Lessons

### L1: Sentry email routing WORKS — silence was issue grouping, NOT env-tag (audit-driven 翻案)
SESSION 27 hypothesis ("env=dev tag silences alert routing") was REFUTED at the rule-filter level (neither active rule has env filter) but CONFIRMED at perception level (env=dev tag visually downgrades urgency). The TRUE dominant root cause: **Sentry issue grouping collapsed 3 SCHEDULER_PAUSED events (2026-05-19/22) into issue 121111789** — only the FIRST event triggered a "new issue" email; events 2+3 produced NO email at all. Combined with 0 Telegram action targets: 1 email + 0 follow-ups + 0 Telegram = 3.5 days unnoticed. Gmail post-hoc verification at 04:47Z confirmed: `from:noreply@sentry.io` Inj L2-2 alert delivered to user inbox at 11:33 AM 北京 (= 03:33Z) — end-to-end <1 min.

**Context:** Two翻案 in one phase — original env-tag hypothesis 翻案 by Plan 05 audit; "Sentry email never arrives" sub-hypothesis 翻案 by Plan 07 Gmail post-hoc. Verification before remediation prevented multiple wrong fixes.
**Source:** sentry-audit-report.md, 03.1-VALIDATION.md (Gmail validation block)

### L2: Parallel-worktree branched-before-merge produces stealthy dueling-implementation
Plan 05's worktree-built deploy (v5 image) branched from origin/main BEFORE Plan 02's merge to local main — so v5 prod was missing the `mirror:l2_tob_age_seconds` sub-check that Plan 02 had wired. Detected during Plan 07 pre-flight only because autopilot explicitly grepped the deployed image's /health output. Without the pre-flight discovery, Inj L2-2 would have "passed" against a daemon that didn't have the code being tested.

**Context:** Worktree isolation prevents file-overlap collisions but creates a deploy-source-freshness gap that hand-checking commits won't catch. Pre-flight must verify deployed image == latest plan-merged main, not just "worktree commits look OK".
**Source:** 03.1-07-SUMMARY.md (Pre-flight Rule-3 blocker fix), 03.1-VALIDATION.md (Pre-flight discovery)

### L3: `.env` single-quote wrapping + naïve grep+sed = 219 vs 221 byte mismatch
During Plan 07 Inj L2-2 cleanup, first key-restore attempt used `grep KEY=.env | sed ...` to extract value. The sed left `'` quote chars in the output → fed 221-char value to `flyctl secrets set` when real key is 219 chars. Daemon booted with mirror enabled but pushed 401 Unauthorized every time. Took ~28 min to identify the off-by-2-byte mismatch.

**Context:** Shell-native `set -a; . ./.env; set +a` handles quoting correctly; ad-hoc grep+sed extraction is fragile. Logged as GAP-201; audit all chaos-l2-* cleanup blocks.
**Source:** 03.1-SOAK-LOG.md (Inj L2-2 recovery), deferred-items.md (GAP-201)

### L4: Config-disabled fail-soft is also a chain-truth gap (GAP-200 inverse)
When `POLYARB_SUPABASE_SERVICE_KEY` is unset, daemon disables mirror entirely; /health drops the `mirror:l2_tob_age_seconds` sub-check from `.checks` (not just stale-and-failing — entirely absent). Operator unsetting key by accident → silent loss of mirror writes, visible only in container startup log. The Phase 03 chain-truth lesson was about runtime-fail fail-soft; this is its inverse — config-disable fail-soft also needs a chain-truth surface.

**Context:** Possible fix: when `supabase_url` is set but `service_key` is empty, /health should still register `mirror:l2_tob_age_seconds` with `status=fail+output="mirror disabled by config (service_key empty)"`. Deferred to Phase 04+ as GAP-200.
**Source:** 03.1-SOAK-LOG.md (Inj L2-2 diagnostic outcome), deferred-items.md (GAP-200)

### L5: pydantic-settings env_prefix maps full field name, NOT short alias
Default env_prefix `POLYARB_` mapped `sentry_environment` field to `POLYARB_SENTRY_ENVIRONMENT`, not the plan-specified `POLYARB_SENTRY_ENV`. Test 2 + manual smoke failed silently — env var ignored entirely. Fix: `validation_alias=AliasChoices("sentry_environment", "POLYARB_SENTRY_ENV")` supports BOTH the kwarg-by-name path (for tests) AND env-var-by-alias.

**Context:** A string-only alias breaks the kwarg-by-field-name path that tests need; `AliasChoices` (not bare `validation_alias=str`) is the right tool.
**Source:** 03.1-05-SUMMARY.md (Deviation #1)

### L6: Worktree pre-commit hook silently exits 0 (no SUMMARY enforcement)
The SUMMARY-presence pre-commit hook falls back to `.git/COMMIT_EDITMSG`, which in worktrees lives at `.git/worktrees/<name>/COMMIT_EDITMSG` — hook exits 0 silently. Plan-scoped commits land WITHOUT SUMMARY enforcement in worktrees. Not a regression introduced by 03.1, but a portability gap noticed and logged.

**Context:** Belongs to m5/Polywatch backlog as a hook-portability follow-up; mitigated by always writing SUMMARY upfront per plan instructions.
**Source:** 03.1-03-SUMMARY.md (Issues Encountered)

### L7: Mid-execution `git stash` + `git checkout main -- file` lost un-staged edits
While diagnosing whether 26 orchestrator async test failures were pre-existing, ran stash + checkout-from-main to compare. Restoring with `git checkout HEAD -- ...` then `git stash drop` lost the un-staged GREEN edits (they were stashed and then dropped silently). Re-applied via Edit tool; no commits lost because RED was already committed.

**Context:** When diagnosing pre-existing failures, run targeted test on a fresh sub-shell rather than moving files in the active working tree. Save edits to a real commit before diagnosis branches.
**Source:** 03.1-02-SUMMARY.md (Issues Encountered)

### L8: `python:3.12-slim` lacks `procps` — pkill chaos primitive is unusable
Phase 03's Inj L2-2 cleanup precedent codified into 03.1: chaos primitives must be image-aware. Plan 06 replaced pkill with `POLYARB_WS_TEST_KILL` env flag (in-process synthetic close) precisely because `python:3.12-slim` has no `procps`. Container probe target `chaos-l2-fly-image-check` added — auto-resolves deployed image and runs `docker run + command -v` against 8 primitives.

**Context:** Every new chaos primitive in a future plan needs image-check evidence in `<verify>` before plan lock. Codified as PROCESS-2 in CLAUDE.md.
**Source:** 03.1-06-SUMMARY.md, 03.1-03-SUMMARY.md, CLAUDE.md (chaos 工具 image-aware 设计 section)

### L9: `tenacity` first-frame trap — Strategy A's invariant is easy to forget
Plan 04's Strategy A would have wrapped the retry in a helper that consumed the first frame to detect "retriable" vs "in-progress" and yielded the rest. The invariant "anything you anext you must yield" is easy to break on a future refactor. Strategy B (wrap the entire async-for with `first_frame_seen` sentinel) avoids the trap entirely.

**Context:** Choose retry boundaries that don't depend on a one-frame consume-and-yield pattern — boundaries that future maintainers cannot accidentally violate.
**Source:** 03.1-04-SUMMARY.md (D-PLAN04-01)

### L10: Plan 02 PLAN.md framed mirror sub-check as "TODO/placeholder" — it was actually live
Initial Plan 02 task framing said the mirror sub-check was a placeholder needing implementation. Inspecting `_build_l2_health_checks` showed Phase 03 Plan 06 had ALREADY wired the live getter call. The missing piece was the Settings field (`l2_mirror_enabled`) that gated the entire block. Task scope pivoted from "sub-check rewrite" to "thresholds-overridable refactor + l2_main constructor kwarg".

**Context:** Plan body framing can lag actual code state by 1-2 plan iterations. Always grep the actual code before assuming a task scope from the plan body.
**Source:** 03.1-02-SUMMARY.md (Decision #1)

### L11: pytest-asyncio + psutil not in `uv sync` without `--extra dev`
`tests/m1-perception/test_orchestrator.py` (26 async tests) + `test_streaming_memory_*.py` (2 files) fail collection without `pytest-asyncio` and `psutil`. `pyproject.toml` lists them under `[project.optional-dependencies] dev` but plain `uv sync` doesn't install dev extras. Fix is one command: `uv sync --extra dev`. Logged as D-DEFER-1 / D-DEFER-2.

**Context:** Pre-existing env-setup gap, not a regression — but every fresh worktree must run `uv sync --extra dev` before running async tests. Worth a chore(deps) plan to make dev extras default or document the requirement.
**Source:** deferred-items.md (D-DEFER-1, D-DEFER-2)

### L12: B-3 hard gate proof = status flip + HTTP 503 + REAL timestamp (NOT code-level OK)
Phase 03 Inj L2-2's failure was "code-level OK but chain dead". Plan 07's GAP-5 closure required B-3 hard gate: status field on the actual sub-check must reach `"fail"` value, HTTP must return 503, with real timestamps logged. Mechanical chain-truth proof (`mirror:l2_tob_age_seconds status="fail"` at 2026-05-27T03:33:19Z, age=1729.3s, HTTP 503 confirmed by curl) is the discharge criterion — NOT Sentry/Gmail UI verification (those can come post-hoc).

**Context:** When closing a chain-truth gap, the proof must be the chain itself producing the observable signal end-to-end, not adjacent evidence.
**Source:** 03.1-VALIDATION.md (Phase Goal Verification), 03.1-SOAK-LOG.md (CHAIN-TRUTH PROOF block)

## Patterns

### P1: Local SQLite singleton cache for sub-second /health probes
Singleton-row + `CHECK(id=1)` + `ON CONFLICT(id) DO UPDATE` — mirrors `scheduler_state` DDL. `mode=ro` URI for read-only access from HTTP layer. Backed by best-effort write from the actual data path (mirror push success branch). Pattern applies whenever /health needs to surface "last-time-something-happened" without touching network.

**When to use:** Any /health sub-check needing sub-second response that would otherwise round-trip to an external store.
**Source:** 03.1-01-SUMMARY.md

### P2: Settings field + model_validator auto-detect when paired secrets present
`Settings.l2_mirror_enabled` flips to True automatically when both `supabase_url` and `service_key` are non-empty — mirrors the `supabase_mirror_enabled` pattern. No explicit env var needed; secret-presence IS the gate. Add a separate explicit Settings field only when behavior must be overridable (e.g. chaos knob).

**When to use:** Feature should be on whenever its required secrets are present; off otherwise. Avoids the "did the operator remember to set the enable flag?" misconfig class.
**Source:** 03.1-02-SUMMARY.md

### P3: Env-overridable thresholds for chaos knobs
Hardcoded constants become Settings fields with `Field(default=300, description="...")`. Defaults stay as defensive fallbacks in code (`_MIRROR_PASS_S_DEFAULT`). Plan 07 chaos uses `flyctl secrets set` to lower warn/fail to 15s/30s for fast-trip; restored to defaults after run via `flyctl secrets unset`.

**When to use:** Any threshold that chaos / soak / debugging would want to lower temporarily. The Settings field pays its weight as soon as you need to flip /health in 60s instead of 10 min.
**Source:** 03.1-02-SUMMARY.md, 03.1-SOAK-LOG.md

### P4: Eat-own-dog-food via /health (chain-truth own-dog-food)
Any new fail-soft envelope OR chaos primitive MUST register a /health sub-check that reads a REAL data source (not a dead-code gate). Plan 06's `chaos:ws_test_kill_flag` (status=warn) is the first time the rule was applied to a chaos primitive itself; the flag's presence surfaces to /health so chaos windows are visible.

**When to use:** Every fail-soft path. Every chaos primitive. Codified as thread §1.6 5-question plan-template checklist; plan-checker enforces at plan-lock time.
**Source:** 03.1-03-SUMMARY.md, 03.1-06-SUMMARY.md, market-observation-architecture.md §1.6

### P5: Image-aware chaos validation (`docker run + command -v` before plan lock)
Every new chaos primitive's `<verify>` block MUST include image-check evidence: either `make chaos-l2-fly-image-check` output or hand-run `docker run --rm IMAGE /bin/sh -c "command -v TOOL"`. Substitutes for missing tools (Python / shell builtin / flyctl machine command) are preferred over `apt-get install` (image bloat + attack surface).

**When to use:** Any plan introducing a new chaos primitive that depends on a shell tool. The matrix in `docs/dev/chaos-toolkit.md` lists 8 primitives × OK/MISS for `python:3.12-slim`.
**Source:** 03.1-03-SUMMARY.md (PROCESS-2), CLAUDE.md, docs/dev/chaos-toolkit.md

### P6: Pre-flight worktree-freshness check before chaos
Before running any chaos against prod, verify deployed image contains the latest plan-merged main — not just "this worktree's commits look OK". For Plan 07, this was: grep deployed /health output for sub-check presence + cross-check with merged plans. Caught Plan 05's worktree-built v5 missing Plan 02 code.

**When to use:** Any chaos / soak run that depends on cross-plan code interactions. Cheap (one grep + one curl) relative to the cost of running chaos against the wrong code.
**Source:** 03.1-07-SUMMARY.md, 03.1-VALIDATION.md

### P7: `FLY_API_TOKEN=` prefix on EVERY flyctl invocation (not just chaos)
Belt-and-suspenders: `FLY_API_TOKEN=` prefix on the same logical shell line + `unset FLY_API_TOKEN` after `set +a` in recipes that source `.env`. If a backslash continuation breaks or someone refactors, either guard saves you.

**When to use:** Universal — apply to every flyctl invocation in Makefile, scripts, and ad-hoc commands. Banner comments at section boundaries explain the invariant to future editors.
**Source:** 03.1-03-SUMMARY.md (D-PLAN03-01)

### P8: Hypothesis refinement in audit reports — REFUTED / CONFIRMED / NEW dominant cause
When a SESSION-N hypothesis gets audited, the report explicitly states: where the hypothesis is REFUTED, where it's CONFIRMED (often at a different level than originally claimed), and what the NEW dominant root cause is. Plan 05's sentry-audit-report.md uses this structure — REFUTED at rule-filter level, CONFIRMED at perception level, NEW dominant cause = missing Telegram/Slack action targets.

**When to use:** Any audit driven by a prior session's hypothesis. Forces precise thinking and produces a diffable artifact for re-running.
**Source:** sentry-audit-report.md (Hypothesis Validation section), 03.1-05-SUMMARY.md (patterns-established)

### P9: playwright-cli + JSON-lines baseline for dashboard drift detection
`scripts/sentry_alert_audit.py` emits a JSON-lines baseline; future runs diff against it to detect rule drift. Re-runnable via `make sentry-alert-audit`. Pattern is: drive playwright-cli via Edge persistent profile (per `reference_playwright-cli-edge-profile.md`), capture structured data, write JSON lines, diff over time.

**When to use:** Any external dashboard (Sentry, Better Stack, Grafana) where rules/config can drift silently. Baseline + diff > screenshots + manual review.
**Source:** 03.1-05-SUMMARY.md (patterns-established)

### P10: Class-attribute-driven test loops (NOT hardcoded constants)
Tests drive off `SnapshotScheduler.FAILURE_THRESHOLD` (class attribute) rather than hardcoded `3` — assertions stay invariant under future threshold tuning. Pair with ONE explicit-literal test (`test_pause_after_5_failures_not_3`) that pins the current value as a silent-regression guard.

**When to use:** Any tunable threshold tested across multiple test files. The class-attribute approach + 1 literal pin is the right shape — tests adapt to tuning but a tuning regression can't slip through.
**Source:** 03.1-04-SUMMARY.md
