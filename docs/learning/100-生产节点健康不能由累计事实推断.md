# 生产节点健康不能由累计事实推断

## 30 秒心智模型

`succeeded=106306` 只能证明系统过去成功过，不能证明这一秒 Gamma 应该继续产生
流量。生产健康必须绑定**当前任务节点**：Structure certifier 健康推进时，source-fetch
被背压是正确序列；只有一个 `structure-fetch` 已运行超过它的生产窗口却仍没有任何
metered egress，才说明云输入事实缺失。

告警也必须是一条原子生产链：watchdog 检测 → writer 写 incident/event → 同事务写
Dashboard/Telegram outbox。writer 进程健康但缺 outbox 权限，等价于这条链没有上线。

## 为什么累计计数会制造永久假警报

旧逻辑把 `runnable/leased/succeeded` 任一非零解释为 active。`succeeded` 是单调累计值，
所以系统第一次成功后，active 永远为真。最后一页 Gamma egress 超过 15 分钟后，
watchdog 就永久报告 stale，即使 normalize/certify 正按秒推进。

新逻辑把 15 分钟解释成 source-fetch 的**任务局部宽限**：

```python
if not source_started_at or all(
    now.astimezone(UTC) - started_at <= self._max_age
    for started_at in source_started_at
):
    return observation
```

这不是放宽健康标准。长 source-fetch 仍会 fail closed；非 source 节点由自己的
heartbeat、progress、lease、attempt 和发布 freshness 负责，避免一个时钟替所有节点
做错误裁决。

## 为什么 writer 权限错误不能只记日志

writer 在插入 `m1_alert_outbox` 时抛 `InsufficientPrivilege`，整个事务回滚。因此
Dashboard `runtime_watchdog.current` 仍为 null，Telegram 与 Dashboard 也没有同源事件。
Machine `/healthz` 为 200 只证明 HTTP 进程活着，不证明业务后置条件成立。

revision 037 不把 writer 换成宽权限 runtime controller，也不补 `ALL PRIVILEGES`；它只
恢复 `INSERT .. ON CONFLICT` 所需的 `INSERT + SELECT`。真实升降级测试同时证明
UPDATE/DELETE 始终为 false。

## 设计取舍

- 不用更大的 stale timeout：错误的激活判据无论设 15 分钟还是 24 小时都会最终误报。
- 不让 watchdog 直接连 Postgres：独立监控边界保留，writer 仍是唯一数据库写入口。
- 不把 certifier progress 当 egress：每个节点只证明自己的产品事实。
- 不以 writer HTTP 201 之外的状态认定闭环：检测日志不是持久化后置条件。
