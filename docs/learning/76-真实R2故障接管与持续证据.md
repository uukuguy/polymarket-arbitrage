# 76 — 真实 R2 故障接管与持续证据

## 30 秒心智模型

云端采集不是“某台机器没有报错”，而是：一条 job 可以被至少一次执行，但它的**持久化效果**
只能有一次。R2 上传完成到 Postgres receipt 写入之间是最危险的缝隙：进程此刻消失，下一台
机器必须能接管，却不能重新生成第二份效果。

所以验收分两条独立证据：

1. 对一个精确 job 注入一次 R2 后崩溃，确认下一 lease epoch 接管且 receipt 仍为一条。
2. 在恢复后的稳定拓扑上，每 15 分钟以内只读采样；24 小时内 API、五角色机和失败计数
   都不能退化。

## 关键路径

```python
# quote_worker.py:90-114
prior = self._control_plane.quote_batch_receipt(lease.job_key)
if prior is not None:
    self._control_plane.finish(lease, state=JobState.SUCCEEDED, now=self._now())
    return QuoteBatchWorkerResult(job_key=lease.job_key, outcome="recovered")

artifact, successful_count = await self._fetch_artifact(batch)
self._crash_after_r2_upload(lease)       # staging-only acceptance boundary
self._control_plane.record_quote_batch(lease, ...)
self._control_plane.finish(lease, state=JobState.SUCCEEDED, now=self._now())
```

这里的要点是：R2 object 不是完成标记；**fenced receipt + 同一 lease 的 terminal finish** 才是。
如果第一台机器在 crash boundary 死掉，job 留在 `leased`；120 秒后 `claim_job` 以更高 epoch
领取。接管者发现或写入同一 job 的唯一 receipt，然后完成 job。

## 2026-08-15 staging 实证

对 `quote:13dc…9485:batch:69` 注入了 `staging-r2-upload-before-receipt`：

- 故障 worker 在 R2 上传后抛出预期 `KeyboardInterrupt`。
- 备用 Quote pool 在 expiry 后接管；最终 `attempt_count=2`、`lease_epoch=2`、`state=succeeded`。
- `m1_quote_batch_receipts` 对该 key 的行数为 **1**，artifact digest 为
  `1f3abd…8ac2ec`，成功响应数为 487。

这三个数共同排除两种假成功：只有崩溃没有恢复，或恢复时重复交付。

## 持续运行证据如何读

```bash
make control-plane-soak-start evidence=<soak.jsonl> control_api_url=<url> machine_ids=<五个ID>
make control-plane-soak-sample evidence=<soak.jsonl> control_api_url=<url> machine_ids=<五个ID>
make control-plane-soak-verify evidence=<soak.jsonl>
```

第一条是 baseline，历史遗留的 circuit/expired lease 允许存在；之后任何**新增**都会失败。
这避免把旧 staging 垃圾误判为刚刚发生的退化，同时仍对新的故障 fail-closed。
