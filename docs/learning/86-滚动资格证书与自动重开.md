# 滚动资格证书与自动重开

## 30 秒心智模型

旧的 24 小时资格验证像一次手工考试：失败后人要重新开一场，手动说明前一场为什么不算。
Plan 05.6-204 把它改成连续的滚动资格机：每个 epoch 累积 durable facts，遇到 breaking
事实就把当前 epoch 永久封成 `INVALIDATED`，进入 `RECOVERING`；只有恢复确认事实到来，才自动
开一个新的 `ACCUMULATING` epoch。新的 epoch 连续覆盖 86,400 秒且 gap、freshness、fence、
recovery SLO 都合格时，才生成不可变 certificate。

关键点是“双视角”：

1. 任务自身事实：runtime、incident、recovery action 是 worker/controller 写出的事实，回答“任务自己发生了什么”。
2. freshness 事实：qualification service 每 tick 主动重验 Structure、Quote、Opportunity 当前指针的新鲜度，回答“即使没人报错，读模型是否仍然新鲜”。

证书不是当前状态截图，而是 canonical JSON 的 SHA-256。读取证书时还会重验 payload、canonical
bytes、digest、epoch 和数据库列是否一致，所以它可以离线复算，也能防止直接伪造。

## 任务事实与 freshness 双视角

如果只看任务事实，会漏掉“没有任何任务报错，但当前 Structure/Quote/Opportunity 指针已经 stale”
的情况。如果只看 freshness，会解释不了 retry、reclaim、circuit probe 是否真是 contained。

Plan 04 的 service tick 同时消费两类输入：

- runtime/incident/recovery：由已有 self-healing runtime、incident ledger、recovery action ledger 投影进入 qualification ingress；
- freshness：service 每 tick 对 Structure、Quote、Opportunity 当前指针做一次只读观察，缺失或超 SLO 都进入同一个 ingress ledger。

这让 certificate 里的事实既能说明“任务没有破坏围栏”，也能说明“读模型在窗口内没有变旧”。

## ingest_seq、cursor 与迟到事实

不能用 `occurred_at` 做唯一进度条。数据库里可能先提交一个较晚时间的行，再迟到提交一个较早时间的行；
如果 cursor 按时间推进，后者会被永久跳过。

024 migration 建了 `m1_qualification_ingress_ledger`，所有来源先投影成 append-only ingress 行。
service 只记住最后消费的 `ingest_seq`。这表示“我处理到数据库提交顺序的第 N 条”，而不是“我处理到某个业务时间”。
同一个 source/source_id/source_version 重放必须 digest 相同，否则 fail closed。

## epoch 不可变与恢复观察

`INVALIDATED` epoch 是历史结论，不能被恢复事实修好；`QUALIFIED` epoch 是证书边界，也不能再加事实。
`RECOVERING` epoch 也有特殊规则：非 `recovery.confirmed` 的事实不进入 epoch fact history，而是进入
`m1_qualification_recovery_observations`。这样 status 能显示恢复期间又观察到了什么 breaker，同时不会把
“恢复前的脏事实”混入新 24 小时窗口。

恢复确认后，新 epoch 的 `started_at` 就是确认事实时间。旧 invalidated epoch 保留原 breaker，新 epoch
重新开始累积 clean window。

## 证书 trust 边界

证书 payload 由 `QualificationDecision` 派生，调用方不能提交自定义 counts、bounds、SLO、evidence digest
或 certificate id。Postgres 的 SECURITY DEFINER 函数再次派生 certificate id，表上 UPDATE/DELETE 被 trigger
拒绝，应用读取时还会：

- 复算 canonical JSON；
- 复算 certificate digest；
- 验证 epoch identity、bounds、payload 列与 digest 列一致；
- 列表读取时逐条执行同样检查。

所以 `qualification-certificates` 是读操作，但不是“信任数据库行原样返回”：它是 read + reverify。

## Make/CLI 权限边界

本轮新增三条 Make 入口：

- `make qualification-status`：只读当前 epoch、last breaker、recovery observations 和最近证书；
- `make qualification-certificates limit=20`：只读最近证书并逐条重验；
- `make qualification-serve enable=1 interval_seconds=30`：顺序跑 tick；没有 `enable=1` 时不调用 CLI 并非零退出。

这些 target 不执行 Alembic、deploy、Fly、R2、job mutation 或 Machine 操作；DSN 只通过 CLI 的
`POLYARB_QUALIFICATION_DB_DSN` 读取。生产是否启用仍是后续 Plan 05/06 的部署问题，本计划只完成本地合同。

## 关键设计取舍

1. **纯 policy + 有状态 store**：policy 可重放、易测；store 负责 cursor、CAS、append-only 和证书写入。
2. **ingest_seq 优先**：牺牲按业务时间直觉，换来迟到提交不丢事实。
3. **恢复观察独立表**：恢复期间的 breaker 可见，但不会污染新 epoch。
4. **读取时重验证书**：读路径更重一点，但 operator 看到的是可验证 artifact，不是裸行。
5. **Make 只暴露入口**：不在 Makefile 里自动迁移或加载 production DSN，避免“查状态”变成隐式上线动作。

## FAQ 增量

**“这是否表示生产 qualification 已经启用？”** 没有。Plan 04 提供 policy、migration、service、CLI 和
Make 合同；没有部署、没有生产 migration、没有启动常驻服务。上线启用需要后续计划单独授权。

**“contained retry 会不会让证书不干净？”** 会被记录在 certificate 的 contained/recovery evidence 中。
它不是假装没有故障，而是证明故障在 SLO 内被围栏恢复，且没有破坏 freshness、integrity、progress 和 evidence gap。

**“为什么 status 还要显示 recovery observation？”** 因为 recovering 期间可能继续看到 breaker。
这些事实不能进入新 epoch，但 operator 仍然需要知道恢复卡在哪里、最新 breaker 是什么。
