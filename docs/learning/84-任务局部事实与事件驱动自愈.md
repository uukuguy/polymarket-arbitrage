# 任务局部事实与事件驱动自愈

## 30 秒心智模型

一个长任务不能只回答“进程还活着吗”，还必须持续回答三个问题：

1. 我已经开始哪一次 attempt？
2. 我正在推进哪个业务阶段，进度有没有前进？
3. 我最终成功、进入重试，还是需要恢复？

因此 M1 把 `started → stage/progress → terminal` 作为任务自己写入的主事实；
heartbeat 只证明租约仍活着，watchdog/定时器只负责发现“本应出现的事实没有出现”。
如果任务的 R2 receipt 或 current pointer 已提交，`job.succeeded` 必须在同一事务里
提交，不能等下一轮采样器猜测。这样失败在发生时就可见，后续 reconciler 才能按
job key、attempt 和 lease epoch 做有界重试或修复。

## 三个时钟不是一回事

| 时钟 | 回答的问题 | 超时意味着什么 |
|---|---|---|
| lease / heartbeat | 这个 worker 还拥有写权吗？ | epoch 可被接管，旧 worker 不得再提交 |
| progress deadline | 业务阶段是否真的前进？ | 活着但卡住，需要 retry/reconcile 判断 |
| attempt deadline | 整次尝试是否已超总预算？ | 必须终止或进入明确恢复，不能无限续命 |

关键点是：heartbeat 不更新 `last_progress_at`。下面这段代码只有
`progress()` 持久化成功后才增加 sequence；一次 heartbeat 不能伪装成业务前进。

```python
# src/polyarb/control_plane/runtime_contract.py:240
sequence = self._sequence + 1
progress = RuntimeProgress(
    sequence=sequence,
    current=current,
    total=total,
    stage=stage,
)
self._store.record_runtime_progress(self._lease, **kwargs)
self._sequence = sequence
```

## 为什么 terminal fact 必须和业务结果原子提交

考虑 Quote admission：R2 batch 已经上传，Postgres 也已经提交 batch identity，但
进程在返回前被取消。如果 success event 另开事务，系统可能把已经成功的 admission
当成失败重试，重复制造任务或错误报警。

当前边界先在同一事务内追加 terminal fact，再完成 fenced job/attempt 和 batch
写入；任何一步失败都整体回滚：

```python
# src/polyarb/control_plane/postgres.py:2028
with self._connection_factory() as connection, connection.cursor(...) as cursor:
    _set_fenced_transaction_timeouts(cursor, lease=lease, now=now)
    ...
    self._append_quote_admission_success_cursor(cursor, lease=lease, now=now)
    cursor.execute("UPDATE m1_jobs ... WHERE lease_epoch = %s", (..., lease.lease_epoch))
    ...
```

反过来，generic failure 也不能只抛 exception。`finish_retryable_with_incident()`
在一个事务里更新 retry schedule、attempt、circuit、incident、runtime event 和 alert
outbox。任务失败是系统状态，不是日志文本。

## 为什么还需要 watchdog

任务局部事件覆盖的是“任务知道自己发生了什么”。watchdog 仍负责另一类问题：

- worker 进程在写出失败事实前直接消失；
- 数据库/API 整体不可达；
- heartbeat 或 progress 在 deadline 内没有再出现；
- 监控器自身停止工作。

所以两者不是二选一。正确关系是：

`任务事件（主证据） → deadline reconciler（动作判断） → watchdog（缺失事实兜底）`

把 timer 放在最前面，会得到“过很久才知道失败”；只保留任务事件，则无法发现
进程瞬间死亡。两层都要有，但责任不同。

## 关键设计取舍

1. **封闭 stage registry，而不是任意字符串**：Dashboard、重放和告警能稳定解释
   每个阶段，也阻止异常文本或秘密进入 stage。
2. **terminal point of no return**：业务事务一旦提交，后续 cancellation 不能把结果
   改写成失败；恢复失败显示为 `recovery-pending`。
3. **lease epoch fencing**：旧 worker 即使迟到返回，也无法覆盖新 attempt 的状态。
4. **有界 detail**：runtime evidence 只保存诊断分类和有限标识，不保存凭据、响应体
   或任意 exception 文本。
5. **真实终态测试**：跨任务 gate 调用八个专用完成方法，而不是直接写 event 表；
   否则测试只能证明“数据库能插入一行”，不能证明业务边界真的原子。

## 自检题（对手测试）

1. 一个 worker 每 30 秒 heartbeat，但 10 分钟没有 progress。你会把它判健康、
   失败，还是等待？需要读取哪些 deadline/profile 事实？
2. R2 receipt 和 `job.succeeded` 已提交，但 `record_job_recovery()` 超时。为什么不能
   把整个任务改成 retryable？Dashboard 应显示什么？
3. 旧 epoch 的 worker 在新 worker 接管后才完成上传。哪一个数据库条件阻止它发布
   pointer？如果只比较 job key 会怎样？
4. 某异常 detail 想写入 `authorization_header` 和完整 HTTP body。系统应在哪一层
   拒绝，为什么不能指望 Dashboard 再脱敏？
5. 如果八任务测试直接调用 `_append_job_succeeded_cursor()`，它会漏掉哪三类真实
   回归？至少说出 receipt/pointer atomicity、terminal stage 和 lease fencing 中的两类。

## FAQ 增量

**“有 heartbeat 为什么还需要 progress？”** heartbeat 只能证明执行者仍持有租约。
死循环、阻塞查询和不断重试同一个 page 都可能持续 heartbeat；只有业务 checkpoint
或 stage 前进才证明系统正在接近产出。

**“为什么不让 watchdog 直接重启所有失败进程？”** Machine 重启是粗粒度动作，
可能重复已提交的业务效果，也无法区分某一个 job 卡住与整个进程失效。恢复应先由
job-level、lease-fenced 的 reconciler 判断；只有进程/Machine 边界真的失效时才使用
拓扑级恢复。

**“24 小时 soak 还有价值吗？”** 有，但它是连续性验收，不是第一次发现单任务
失败的机制。即时事件/告警/恢复先闭环，rolling qualification 再证明长时间没有证据
缺口。
