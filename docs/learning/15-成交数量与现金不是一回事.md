# 成交数量与现金不是一回事：别让一个 `size` 同时戴两顶帽子

> Phase 6 / H-004。读完后你应该能看到 `100 @ 0.50` 就立即说出：
> quantity 是 100 shares，BUY cost basis 是 50 pUSD，它们不能做相等比较。

## 30 秒心智模型

预测市场仓位像买电影票：

- **quantity** 回答“有多少张票”——100 shares；
- **price** 回答“每张多少钱”——0.50 pUSD/share；
- **cost basis / collateral** 回答“收银机锁了多少钱”——50 pUSD；
- **PnL** 回答“每张价格变化 × 张数”——`100 × (0.60 - 0.50) = 10 pUSD`。

旧代码把 100 同时当 shares 和 pUSD：余额从 1000 扣到 900，但 PnL 又用
`100 × price_delta`。最终 PnL 碰巧正确，开放仓位期间的余额、风险敞口和资金利用率全错。

```text
Quantity(100 shares) ──× entry price 0.50──► Money(50 pUSD cost basis)
         │
         └─────────────× price delta 0.10──► Money(10 pUSD PnL)
```

## 为什么 Money 和 Quantity 都是 6 位整数，还要分两个类

相同存储 scale 不代表相同物理维度。`50_000_000` 可能是 50 pUSD，也可能是
50 shares；裸整数无法阻止误加。`Money + Quantity` 在 Python 类型层直接失败，bug 在进入
SQLite 前就暴露。

这和“米”和“公斤都能用整数存”一样。把单位编码进类型，不是为了数学更花哨，而是为了
让错误代码写不出来。

## BUY 与 SELL 为什么 collateral 公式不同

BUY 100 shares @ 0.60，最坏归零，最多损失 60，所以锁 `q × p = 60`。

当前 paper SELL 是 fully-collateralized binary short：卖 100 shares @ 0.60，最坏结算到 1，
需要准备 `q × (1-p) = 40`。价格跌到 0.50 时盈利 10，关闭后返还 `40 + 10 = 50`，账户
从 1000 → 960 → 1010。

这不是在声称 live Polymarket 允许无持仓裸卖。真实 SELL 的 token inventory、allowance 和
wire amount 属于 live adapter/reconciliation；H-004 只让 paper risk model 在二元支付上
自洽。

## 官方 SDK 的 `amount` 为什么特别危险

官方 V2 market order 把同一个字段名做成 side-dependent：

- BUY `amount` = 想花的 pUSD；
- SELL `amount` = 想卖的 shares。

因此领域层不能复制一个裸 `amount` 到处传。它应先持有明确的 `Quantity` 和 `Money`，只在
最外层 SDK adapter 根据 side 翻译。否则 BUY partial fill 返回的 shares 很容易和请求 cash
做“是否 full fill”的错误相等比较。

参考：

- <https://docs.polymarket.com/trading/orders/create>
- <https://docs.polymarket.com/trading/orders/overview>
- <https://docs.polymarket.com/concepts/positions-tokens>

## Phase 5 数据库为什么要修余额

旧库的开放 BUY 100 @ 0.50 已经从余额扣了 100。新模型推导 cost basis=50；如果只加新列，
余额仍少 50，迁移只是给错误状态换了名字。

迁移在同一个 `BEGIN IMMEDIATE` 中计算：

```text
refund = legacy_reserved_as_cash - derived_cost_basis
       = 100 - 50
       = 50

balance: 900 → 950
```

写入 `quantity_micros/cost_basis_micros` 和余额修复一起提交。第二次启动发现两列完整存在，
只验证不再 refund。只出现其中一列说明外部/人工制造了 partial v3，直接 fail closed。

## 设计取舍

1. **保留 `size/stake/filled_size` 兼容别名**：旧 CLI 与调用者不中断，但内部计算不再读取它们。
2. **stake 兼容值仍显示 shares**：不偷偷改变已有 JSON 的数字含义；同时新增 `quantity` 和
   `cost_basis`，让新调用者离开歧义字段。
3. **价格没有改 fixed point**：价格是每 share 的观察值；只在 shares→cash 边界用十进制文本量化。
4. **没有顺手实现 partial fills**：单位边界是 H-005 的前置条件；一次只验证一个假设。
5. **没有接 live SELL inventory**：真实 token balance/allowance 是 venue truth，不用 paper 假设冒充。

## FAQ 增量

### Q1：为什么 `stake` 还等于 quantity，不直接删掉？

删除会让已有脚本和 JSON 消费者在同一 phase 全部 flag day。更危险的是把 `stake` 的数值从
100 shares 静默改成 50 pUSD：旧消费者不会报错，却会改变行为。因此旧字段冻结为 quantity
投影，新代码只使用显式字段；删除安排在能做版本化契约升级的后续 cleanup。

### Q2：SELL collateral `q × (1-p)` 和真实钱包余额一致吗？

不一定。它是当前 paper binary-short 的最大损失模型。真实 Polymarket SELL 需要已有 outcome
tokens 和 allowance，venue 还会返回实际 cash/fee。H-006 会把这些 venue truth 接到精确账本，
届时 paper collateral 只是 pre-trade risk estimate，不冒充结算事实。
