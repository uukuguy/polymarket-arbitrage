# 事务型云端控制面：进程会重试，事实只提交一次

## 30 秒心智模型

旧 M1 把采集、SQLite 写入、健康读取和 HTTP 放在同一台带 volume 的
Fly machine。它慢下来时，观察者也会一起失明。

新模型把“进程执行”与“持久事实”拆开：Structure/Quote worker 可以因为
部署、OOM 或网络错误重复执行；但它们只能用当前 Postgres lease epoch
提交回执。R2 放不可变大对象，Postgres 放 job、lease、receipt、manifest
和 pointer。于是得到的是 **at-least-once 执行 + exactly-once durable
effect**，不是不现实的“进程只跑一次”。

```
legacy SQLite (只作 shadow source / cache)
              │
              ▼
R2 immutable bundle/range/batch ──► Postgres lease + receipt + pointer
              ▲                              │
 Structure / Quote workers                   ▼
                                  independent control-api / operator read
```

## 最重要的事务边界

Structure worker 的顺序不是偶然的：先从控制面拿 lease，再由冻结的 R2
bundle 构造输出，随后才在同一条 fenced DB 路径写 receipt：
[structure_worker.py:74](../../src/polyarb/control_plane/structure_worker.py:74)。

若 R2 上传成功后进程死掉，替代 worker 会重新上传同一内容地址 key；这
不是重复的业务效果。真正的业务效果是 Postgres receipt，它按 job/lease
fence 幂等，只能形成一条。测试：
`test_structure_worker_takeover_after_upload_before_receipt_has_one_receipt`
和 Quote 的同构测试。

## 为什么控制 API 必须独立

`/healthz` 的成功只代表“此 API 进程能读到 durable control plane”。它不
假装 Quote/Structure 都正在成功，也不因 SQLite 变忙改成空的成功。见
[api.py:22](../../src/polyarb/control_plane/api.py:22)。这让 data worker
挂掉时，operator 仍能看到 retry、lease、incident 与 pointer 身份。

## 上线顺序

1. `make control-plane-preflight expected_database=<designated-name>`：只读
   核验目标 DB、011 schema 与 R2。
2. 对指定非生产环境做 011 migration，部署隔离 API 和只持有 Gamma/R2
   写入凭据的 worker。API 永远不接 SQLite、Gamma 或 R2 写入凭据。
3. 用 `make structure-control-plane-source-once enable=1
   window_key=<opaque-window-id>` 可人工创建一个可审计 source window；常驻
   `control-plane-serve` 也会每 300 秒尝试准入一个时间桶 window。该准入在
   Postgres advisory transaction lock 内执行：同一桶幂等，任何未完成 traversal
   都会阻止下一桶，因此多个 worker/restart 不会重叠读取 Gamma。
4. 连续取得三次新的 source-window Structure/Quote shadow；再验证 R2
   上传后崩溃、lease 接管和 API 可读。
5. 保留 24 小时连续证据后，才可另行授权、可回滚地 pointer switch。

这里最容易混淆的是两种“Structure 输入”：旧的
`structure-control-plane-shadow-once` 从本机 SQLite 导出，只能用于历史
比较；新的 `structure-control-plane-source-once` 从 Postgres/R2 source window
接入 Gamma 页，才是未来常驻采集的候选权威输入。二者在 pointer switch 前都
不会改 legacy current。

新的事务链里，Structure certifier 不会直接请求 CLOB。它在认证 manifest 的
同一 Postgres 事务中释放一个绑定 bundle key/digest 的 `quote-admit` intent；
Quote-admitter 独立读取这个 R2 bundle，过滤为 active、未 closed、neg-risk
且拥有完整 event/condition/YES token 身份的 legs，冻结 universe hash 后再创建
现有的 Quote batch/certifier 作业。这样 CLOB 延迟或 worker 替换只能重试
quote-admit，不会破坏已经认证的 Structure truth。

常驻 scheduler 的轮转顺序是 source admission、source page、source materialize、
Structure range、Structure certify、Quote admit、Quote batch、Quote certify。每个
turn 最多 claim 一个 fenced job；因此即使 worker 在任意 turn 后退出，下一个
machine 也只会从 Postgres receipt/lease 继续，而不会重建 SQLite universe。

独立 control-plane API 的 snapshot 会分别给出 source fetch、source
materializer、Structure range/certifier、Quote admit、Quote batch/certifier 的
job state；source 与 Quote-admit 还给出 oldest retryable age。它们来自 Postgres
控制面，只读 API 不接 SQLite、Gamma、R2 或 CLOB，因此 worker 停止时仍可区分
“刚进入 backoff”与“已长时间没有恢复”。

其中第一步的 `ready-for-shadow-only` **不是**“可以切流量”。它明确没有
授权 migration、常驻 worker 或 pointer 修改。
