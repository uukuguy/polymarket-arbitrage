# 二次故障与运行镜像漂移

## 30 秒心智模型

这次 `public.digest` 不是最先发生的故障，而是**记录原故障时发生的二次故障**：

```text
旧 worker 的上游任务失败
  → 写 incident / recovery 事实
  → qualification trigger 投影事实
  → SECURITY DEFINER 调 public.digest
  → Supabase 只有 extensions.digest
  → SQLSTATE 42883 反过来杀死 worker
  → Fly 重试 10 次后停止
```

revision 027 修掉了最后一段，但还不够。三台生产 worker 仍在旧镜像上，根本没有 Plan 201+ 的 runtime-event 代码。完整修复因此有两部分：

1. 让失败事实能安全写入 qualification ledger；
2. 让正在运行的进程真正包含 runtime-event instrumentation。

只修数据库会得到“进程不再因二次异常退出，但 controller 仍看不见任务生命线”的半修复。

## 为什么会耗尽 Fly 重试

Fly 看到的只是主进程非零退出。每次重启后，旧镜像继续执行同一类任务；一旦写 incident/recovery，触发器又进入同一个缺失函数，于是形成确定性循环。`max_retries=10` 没有制造缺陷，它只是阻止一个确定性错误无限烧资源。

关键诊断动作不是“再 start 一次”，而是把时间线串起来：

1. 找到最先出现的上游任务失败；
2. 找到紧随其后的 incident/recovery insert；
3. 展开数据库 trigger chain；
4. 用 catalog 证明 `public.digest` 不存在、`extensions.digest` 存在；
5. 对照 Machine image digest 与 runtime-event 代码进入仓库的时间。

这样才能区分：上游失败是**原始故障**，`public.digest` 是**终止进程的二次故障**，旧镜像则是**修完数据库后仍不可观测的部署漂移**。

## 设计取舍

### 为什么 027 不直接写死 `extensions.digest`

因为 `extensions` 是 Supabase 的部署选择，不是 pgcrypto 的协议。普通 PostgreSQL 常把扩展装在 `public`。027 读取 catalog，既适配两种环境，也保留 SECURITY DEFINER 的显式 schema 解析。

### 为什么只改写四个 token

直接重写整段函数源码容易悄悄改变 owner、ACL、SECURITY 或 search path。027 先核对函数签名和 token 数，再做最小替换；生产验证还比较函数定义哈希与权限投影。

### 为什么滚动原 Machine，而不是新建三台

任务 lease、worker role、告警与拓扑审计都绑定既有身份。这里需要的是镜像一致性，不是拓扑扩容。更新时保留 Machine ID，并对排除 image 后的 config 做前后哈希，能把最大影响限制为“执行了新代码”。

### 为什么 quote worker 没有 runtime event 也能通过

runtime event 描述任务生命周期，不描述 idle loop。验证窗口内没有 quote job，所以它只输出健康 idle tick。coordinator 与 structure-range 的真实任务已经证明共享 instrumentation、数据库 trigger 和 qualification ingress 链；不能为了制造 quote event 而擅自注入生产任务。

## 实战诊断清单

遇到“同一异常重启到停机”时，依次问：

1. 第一条业务错误与最后一条进程错误是否同一个？
2. 错误处理路径会不会写 incident、metric、outbox 或 qualification？
3. 这些写入后面是否还有 trigger / hook / callback？
4. 本地 schema、扩展 namespace、生产 provider 是否一致？
5. 生产 Machine 的 immutable image digest 是否真的包含修复？
6. 修复后，观察者读的数据源是否由新代码持续 mutate？

## 自检题

1. 如果 027 已应用，但 worker 仍是旧镜像，系统恢复了什么、还缺什么？
2. 为什么 `max_retries=10` 不是根因，但仍是重要证据？
3. 为什么成功执行一次 freshness insert 不能证明 task runtime chain 完整？
4. 为什么 quote idle 时不应该人为塞一个生产 job 只为得到 event？
5. 若 observe verifier 偶尔在新 job 与下一 controller tick 之间失败，什么证据能区分短暂 parity 窗口和真实控制器停摆？

## FAQ 增量

### `public.digest` 修好后，为什么还要滚镜像？

因为 schema migration 只改变数据库函数，不会把新 Python 代码注入已经运行的旧容器。旧容器不再被二次异常杀死，但仍不会写 runtime events；controller 和 qualification 的 runtime source 继续失明。

### 为什么旧镜像问题没有在普通 health check 中暴露？

health check 能证明进程与数据库基本可用，却不能证明每个任务生命周期都进入 controller 真正读取的表。chain-truth 要求从写入侧、durable source、观察器到端到端任务事件逐段验证。
