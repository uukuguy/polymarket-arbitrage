# 多应用运行时看门狗

## 30 秒心智模型

持续验收的 sampler 不能和采集 worker 共用进程：否则 worker 仍在运行时，
验收证据可能已经停写。它也不能把数据库权限交给告警进程。正确的形状是
三个独立应用：worker 写业务事实、evidence sampler 写只追加验收事实、alert
只读取 API/Fly 状态并向 Telegram 报警。

看门狗必须同时检查 worker 的三台 Machine 和 sampler 的一台 Machine。所有
身份以 `app/machine` 限定，避免不同应用里同名机器被混淆；任一读取错误也
按不健康处理。还要读取 Fly 的 restart counter：Machine 显示 `started` 只说明
虚拟机活着，并不能证明其中的 Python 主进程没有反复退出。

## 关键代码

- `src/polyarb/cli_control_plane.py:_read_runtime_watchdog_observation`：分别读取主
  worker 应用与可选 secondary 应用，将结果规范成 `app/machine` 身份后交给
  fail-closed 的 `assess_runtime`；同时读取每台 Machine 的 restart counter。
- `src/polyarb/control_plane/watchdog.py:RestartEventGate`：首个 counter 只作为
  基线；后续任何增长都会产生一次 incident，下一次稳定检查产生 recovery，避免
  历史重启永久污染健康状态。
- `src/polyarb/control_plane/watchdog.py:ProgressGate`：当 API 表示还有 runnable
  或 leased 作业，但 durable succeeded 计数超过五分钟没有增加时报警。没有待
  处理作业时不会把正常空闲误判为停摆。
- `deploy/control-plane/fly-control-alert.toml.template`：生产 watchdog 同时从
  `POLYARB_WORKER_APP` 和 `POLYARB_EVIDENCE_APP` 取得被监控对象；它没有
  Postgres 或 R2 凭据。
- `Makefile:control-plane-watchdog-verify`：可在不发 Telegram、不改云端状态的
  前提下，验证两应用的实时门。

## 设计取舍

把 sampler 塞进 worker 应用看似少一台机器，却会让它继承 worker 的 R2 与业务
数据库权限，也会让“worker 活着而验收已失明”无法被独立发现。把它放入 alert
应用同样会让纯监控进程获得数据库权限。独立应用多占一台 256MB Machine，但
保留了最小权限和可观察性边界。

## 自检题

1. sampler Machine 已停止但三台 worker 均为 `started`，Telegram 应收到什么？
2. 为什么 watchdog 不能读取 `m1_soak_observations` 来判断 sampler 健康？
3. `machine:worker-a:started` 为什么不如 `machine:app/worker-a:started` 可审计？
4. Machine 状态仍为 `started`、restart counter 从 4 变成 5 时，为什么仍应报警？
5. 为什么成功数不变在队列为空时不应报警，但在 `runnable=1000` 时五分钟就应报警？

## FAQ 增量

- **这是否等同于业务采集器自身重启？** 不是。watchdog 只报警，不自行篡改
  采集事实；Fly 的 `restart=always` 负责进程重启，证据账本的时间缺口仍会被
  24 小时验收器 fail-closed 地识别。
