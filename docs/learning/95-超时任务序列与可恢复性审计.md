# 超时、任务序列与可恢复性审计

## 30 秒心智模型

控制面里不能有一个笼统的“timeout”。每个时间边界只允许拥有一种权力：数据库 deadline 终止
一次 I/O，runtime watchdog 终止一次 fenced attempt，terminal grace 决定服务何时放弃等待，cadence
wait 只决定何时再调度。谁越权，系统就会出现“外层已经失败、内层还在写”的矛盾。

任务顺序也不能只写在进程内 DAG。真正的依赖必须落在数据库 eligibility：前驱未全部留下 terminal
receipt 时，barrier job 必须是 `waiting`；最后一条 receipt 与唤醒 barrier 必须在同一事务。进程随时
可死，恢复只依赖 lease epoch、checkpoint、append-only evidence 和数据库状态，不依赖旧协程的记忆。

## 四类时间权威

| 边界 | 唯一职责 | 不能做什么 |
|---|---|---|
| runtime attempt/progress | 判定一个已 claim 任务是否仍健康 | 不能代替 DB/R2 单次 I/O timeout |
| DB connect/statement/lock | 限制一次连接、语句、锁等待 | 不能声明整个业务任务失败 |
| terminal grace | 停止新 claim 后等待安全收尾；到期允许服务退出 | 不能绕过 lease fence 强写终态 |
| cadence/condition wait | 下一轮何时醒来 | 不能取消已 claim 的工作 |

代码中的顺序不变量是：`lock <= statement`，新连接的 HTTP request envelope 覆盖 `connect +
bootstrap + data statement + bounded transfer`，worker I/O deadline 小于 progress 与 terminal grace。未知 worker 不再继承一个拍脑袋
的 3 秒 fallback；它必须声明自己的 grace policy，否则 fail closed。

## 这次查出的系统性缺陷

### 1. timeout 写了，但实际上不能终止

旧 helper 在收到取消后无限等待同步线程；`asyncio.run()` 还会在退出时 join 默认 executor。于是外层
5 秒、30 秒甚至 grace 都只是日志上的数字。现在阻塞调用运行在不参加 loop shutdown 的 daemon
bridge；单次 I/O deadline 可舍弃非终态调用，服务停止则只允许一次安全排空，第二次取消必须获胜。

### 2. 多处复制不同数据库 timeout

连接、statement、lock、HTTP 外壳散落在多个模块，甚至出现 HTTP 上限短于一次合法的
`connect + statement`。现在正式控制面的 PostgreSQL session 都先安装默认边界；fenced transaction
只可按剩余 lease 向下收紧，不能向上放宽。API 的等待上限从同一 DB policy 推导。

### 3. DAG 正确，持久层顺序却错误

Structure/Quote certifier 原来与分片任务一起进入 `runnable`。并行 lane 会让 certifier 提前 claim、
反复 retry；Structure terminal receipt 路径还漏掉了 wake，导致它可能永久停在 `waiting`。现在两个
certifier 都以 `waiting` 创建；terminal receipt 只做非阻塞 direct wake，claim 前再从 durable facts
修复 lost wakeup。certifier 内部仍保留完整性复核，形成 eligibility + validation 两层防线。

### 4. 可中断路径会在 grace 到期后重新开始 I/O

第一次取消会进入 interruption 终态事务，释放 lease 并保留原 defect streak；但过去第二次取消仍可能被
reader 或 cleanup 吞掉，甚至再次启动数据库调用。共享 bridge 现在拒绝在 grace-expiry cancellation
下启动新 I/O，Quote reader 也把第二次取消视为最终边界。

### 5. 可恢复信息存在，但增长方式会让恢复本身失效

qualification 曾在每轮重写完整历史，运行越久越难停止、越难重启。Revision 030 把事实拆成
append-only rows，epoch 只保存固定标量；restart 每 500 行重放并用 cursor/version CAS 校验。长历史
的恢复成本是一次 O(n)，不再是每 tick O(n) 形成累计 O(n²)。Revision 031
先逐 epoch 校验计数、连续序号、fact payload、digest 索引的 fact ID 和 contained recovery
索引，再清空三个旧 JSON 数组，并用 CHECK constraint 禁止回长。

### 6. 迁移有 statement timeout，但仍可无限等锁

Alembic 原来只在 `env.py` 私有硬编码 30 秒 statement timeout，没有 connect timeout 和
lock timeout。这会让“每条 SQL 有界”与“迁移可无限卡在拿锁上”同时成立。现在
migration policy 明确为连接 10 秒、语句 30 秒、锁 1 秒，并且满足 `lock < statement`。

### 7. 新主路已修复，兼容写路仍可绕回旧模型

完整 PostgreSQL 门禁发现 `qualification_store.transition_qualification_epoch()` 仍会重写增长
数组。031 的约束正确地拦下了它。现在兼容路径也只追加规范化 fact rows，epoch
仅写标量计数；并发 CAS loser 的事务整体回滚，不会留下半条事实。

### 8. 单条 SQL 有 timeout，不代表整个操作有界

角色权限预检曾按“对象 × 权限”逐条查询 catalog。每条 SQL 都有 statement timeout，但一次预检会
串行制造几十次网络往返；任何一条都没超时，整个操作却能卡数分钟。qualification 的健康批次也曾
按 fact 重复 append、verify、epoch update、cursor update，规模越大，允许消耗的总时间越大。

现在角色权限矩阵按 schema/table/sequence 各固定一次查询；qualification 的普通 accumulating
批次用一次 bulk append、一次区间核验、一次 epoch 更新和一次 cursor 更新。新的审计规则是：
**固定业务操作除了约束单次 I/O，还必须约束 I/O 轮数；数据量增长只能进入明确的 bulk/page/checkpoint
协议，不能隐式乘出一个新的总时限。**

### 9. 连接成功后再安装 timeout，会留下启动空窗

旧的 scoped connection 先建立连接，再执行一条 `set_config` bootstrap SQL，最后 commit；但 timeout
正是这条 SQL 之后才生效。HTTP 外壳按“connect + 一条业务 SQL”推导，真实序列却是 connect +
无边界 bootstrap + commit + 业务 SQL，内外合同彼此矛盾。

现在连接边界是两层而不是单点假设：libpq startup options 为直连 PostgreSQL
提供第一层；连接后的单条、autocommit bootstrap 为不转发 options 的 Session Pooler
提供第二层。bootstrap 由同一中央 statement policy 派生取消边界，完成后必须回读
`current_schemas(false)` 及两个 timeout；超时、值不一致或任何异常都关闭连接，绝不把半初始化
连接交给业务层。

### 10. climb 的统一 120 秒外杀破坏了正式门禁的恢复语义

旧 evaluator 给所有 gate 套同一个 120 秒 subprocess timeout：小单测和真实 PostgreSQL / 性能门禁
共用拍脑袋数字。它还只在全部 gate 完成后写结果，所以后段被杀时，前面已经通过的昂贵 gate 也会
从头重跑。

现在 gate 自己拥有其领域内的时限，evaluator 不再制造竞争性外层 deadline；每个 gate 完成后原子
写入 progress baton，baton 绑定 exact git head 与完整 argv。相同运行身份只重跑未完成 gate；身份、
命令或文件格式不一致一律 fail closed，不把旧通过结果冒充当前证据。

### 11. observe-only controller 也可能被候选数拖成单点

runtime controller 虽然处于 observe-only，但旧 turn 会为最多 100 个候选分别开连接写 decision，并在
event loop 上同步执行整轮 PostgreSQL 工作。它不会执行恢复动作，却仍可能阻塞 SIGTERM，并把一次
2 秒 statement policy 乘成几十次串行连接/语句。

现在同一 controller turn 的全部 decision 在一个 lease-fenced bulk transaction 中写入并统一核对
idempotency；service turn 运行在 stop-aware daemon bridge 上。停止先发送 cooperative hint，写事务会在
SQL 边界回滚并拒绝下一轮 I/O；不协作调用超过 recovery DB grace 后隔离，controller lease 继续阻止
过期身份产生权威结果。

### 12. 有 HTTP timeout 的 alert 仍可能阻塞主 event loop

旧 alert service 直接在主 loop 执行 async turn；turn 里的 PostgreSQL claim/finish 是同步调用。默认
Telegram client 虽有 5 秒 timeout，但数据库调用期间 loop 不能处理 SIGTERM，注入 client 还可以完全
绕过默认 httpx 边界。

现在整次 delivery turn 在 stop-aware daemon bridge 的独立 event loop 中运行。worker 收到停止提示后，
在 claim、provider response、retry 和 finish SQL 前检查，不允许晚到 HTTP 结果重新开始数据库写；不
协作 provider 到 DB-derived grace 后隔离。已 claim outbox 由 lease expiry 恢复，已开始的 fenced finish
仍由数据库事务决定最终状态。

### 13. SDK 内建重试会与 durable retry 相乘

旧正式 R2 client 一次调用可在 SDK 内重试三次，外层 durable job 又可重试三次，实际最多形成九次
provider attempt；Gamma 的 15 秒请求还可在一次 worker I/O envelope 内重复三次。内层退避与外层
熔断互不知道对方的状态，既放大延迟，也让“第几次失败”无法从 durable evidence 解释。

现在正式 Gamma、CLOB、R2 调用都只有一次 inner attempt，并显式使用小于 worker I/O deadline 的
provider envelope。失败只交给 PostgreSQL durable retry/circuit；两个 retry transaction 共用
`RuntimePolicy.retry_backoff_seconds()`。历史 archive 路径可以保留自己的 legacy retry，但不得把该
client 注入 runtime-v2。

### 14. 名为 `waiting` 的结果实际是无限 5 秒轮询

Quote 和 opportunity certifier 在输入不完整时返回 `waiting`，却把 job 写回 `retryable` 并用模块内
固定 5 秒再次调度。它既不消耗中央失败预算，也不开 circuit，所以持久层 barrier 出错时会永久热循环。

现在不完整 barrier 通过 `finish_retryable_with_incident` 进入同一 durable backoff/circuit 路径；无效的
`retry_delay` 构造参数被删除。`waiting` 只表示数据库 eligibility 尚未满足，不能成为绕开恢复策略的
第二种任务状态机。

### 15. proof loop 有单次 timeout，仍可能收不到停止信号

cloud-soak 每个 provider/DB 调用都有局部 timeout，但整次同步 sample 曾直接占用 signal event loop。
SIGTERM 到达时，服务不能发送 cooperative stop，也可能在停止已经获胜后继续 append 一条证据。

现在 sample 运行在 stop-aware daemon bridge；停止先传入 blocking 代码，在数据库写边界前再次检查，
进入 DB point-of-no-return 后只按 DB-derived grace 排空。本机 `flyctl` 子进程也有操作专属上限，超时
只返回净化后的错误类别，不泄露 provider body。

### 16. 固定请求 timeout 不等于固定 observation round

watchdog 过去按 app、再按 Machine 串行读取 restart detail。每个请求都可以在自己的 timeout 内成功，
但 app/Machine 数量会把一次 30 秒 cadence 乘成数分钟，最终看门狗本身成为失联单点。

现在目标上限为八个 app、每 app 十六台 Machine；控制 API 与各 app snapshot 同轮并行。单个 app 只做
一轮 list，再对 exact Machine detail 做一轮并行读取，以保留 list event 中没有的
`request.restart_count` 语义。整轮 observation 还有共同的舍弃边界，晚到只读结果不能生成半条 verdict。

### 17. Alert 的四个时钟必须显式排序

“HTTP 有 5 秒 timeout”仍不足以证明 outbox 安全，因为 provider attempt、服务 stop grace、outbox lease
和 retry cadence 原来分别散落。现在它们由一个 `AlertDeliveryPolicy` 声明：一次 provider attempt、5 秒
provider timeout、DB-derived 16 秒 stop grace、30 秒 outbox lease、15 秒 retry cadence，并验证
`provider timeout < stop grace < lease`。完整 DB 序列已包含 session bootstrap；lease 是恢复权威，
retry cadence 只安排下一次领取。

### 18. 只读诊断也可能改变生产运行状态

在 256MB live controller Machine 内 SSH 启动第二个 Python role verifier，虽然它只执行 `SELECT`，却与
常驻进程竞争 cgroup 内存并触发 exit 137 OOM。Fly 自动重启了 Machine，controller lease epoch 随之
重建，已有 1,800 秒 observe-only 窗口不能跨 epoch 继续计算。

因此“无数据库写入”不等于“零生产 effect”。角色/权限门必须从 operator 主机通过固定轮次 catalog
preflight 完成，再用 Fly secret-name presence 绑定目标身份；不得在受限 live Machine 内启动额外解释器
做发布前证明。若 Machine 因任何原因重启，连续性门必须从新 boot/lease epoch 重新计时，不能拼接旧证据。

### 19. 在本地成立的启动参数，不等于经过生产 Pooler 后仍成立

为了删除“无边界 bootstrap”，一次修改把所有 session policy 都移到 libpq startup
options，却删掉了已被生产证明必需的连接后补设。Supabase Session Pooler 接受客户端
`options` 却不把它传给后端 session；新控制器因此在 `active-search-path` 门失败并
crash-loop。生产 canary 立即回滚到原不可变 digest，没有继续更新其他 Machine。

根因不是“超时数字又太小”，而是修复只保留了一层传输假设，且违背了项目已有的
Session Pooler 生产证据。现在的规则是：**startup intent 是 defense-in-depth，连接后回读才是
active truth；回读之前的 bootstrap 必须自己可取消、固定一轮、失败关闭。**

### 20. 只集中“失败后重试”，仍会遗漏“probe 释放后再试”

两条 retryable 失败事务已经共用 `RuntimePolicy.retry_backoff_seconds()`，但真正执行
`probe-circuit` 的恢复事务仍把 `next_probe_at` 固定写成当前时间加五分钟。这会让
控制器的重试判定和执行后 holdoff 使用两套时钟；即使 observe-only 门全绿，一旦开启
recovery 仍会出现隐藏分叉。

修复不是把五分钟改成一分钟字面量，而是抽出不依赖 lease 的 `RuntimeRetryPolicy`。
两条失败事务和 probe 释放事务都按 job type + consecutive failures 读同一 retry budget/base/cap；
不再为了取 backoff 传入没有业务意义的伪 lease `3`。

### 21. 验收门知道失败原因，CLI 却只报异常类型

`runtime-observe-verify` 原本能区分边界锚点不足、决策过时、gap 超限和 replay
mismatch，但最外层 CLI 把它们统一收缩成 `RuntimeObserveVerificationError`。这会把
可计算的证据资格问题变成操作员猜测，并诱发重复试跑或放宽门槛。

修复后，验证器对窗口不足报告 `available_seconds` 和 `required_seconds`，CLI 仅对
`RuntimeObserveVerificationError` 保留这个预定义安全理由；DSN、provider body 和普通未知异常
仍不能透出。门仍然非零退出，只是不再隐藏“还差多少证据”。

### 22. 一次快照不能同时使用两个时间世界

`operational_snapshot()` 过去在建立连接前读取客户端 `datetime.now()`，随后用默认
`READ COMMITTED` 串行执行约 45 条 SQL。活跃 controller/worker 可以在这十几秒里提交新的
heartbeat/progress；后面的查询于是拿“旧客户端时间”减“新数据库事实”，生产上真实出现
`lease_age_seconds is negative` 和 `progress_age_seconds is negative`。

现在 operator read 使用 `REPEATABLE READ READ ONLY`，并在同一个 PostgreSQL 数据语句里取得
`clock_timestamp()`。显式 `now` 只保留给确定性故障矩阵；生产 CLI/HTTP 不再注入客户端时间。
这不是时钟同步调参，而是让状态事实和比较时点属于同一数据库快照。

### 23. “一条 SQL 的预算”只能包住一条数据 SQL

控制面 HTTP 的 10.5 秒 envelope 明确定义为 `connect + one statement + transfer`，但旧
operator snapshot 实际串行约 45 条数据 SQL，生产一次读取耗时 15.5–17 秒。每条语句都没有超过
5 秒，整个请求仍必然超过外壳；增大 HTTP 秒数只会继续掩盖 operation-round 缺陷。

现在 snapshot 把有界标量、列表和资格投影合成一个 PostgreSQL 数据语句；事务、statement 和 lock
设置与数据语句通过同一次客户端 execute round 发送。`current_opportunities()` 也从“先读 pointer、
再读 page”合并成一个数据语句。结构回归测试同时约束：一个客户端 execute、三个 setup result、一个
data result，禁止以后悄悄加回串行 round。生产等价验证把 snapshot 降到 2.85–4.56 秒，HTTP 连续
三次为 200；机会页直读为 5.15 秒，均在同一中央 envelope 内。

### 24. SIGKILL 之后不能再无限等管道

历史 Structure subprocess 的 event-member 路径已经有 TERM → KILL → 放弃 wedged pipe drain，
但 drift 和 full snapshot 两条复制实现仍在 `kill()` 后无限 `await communicate()`。它们现在共用
`_terminate_then_kill_subprocess()`：TERM 和 KILL 各只有一个明确 stage budget；两段都耗尽后取消
本地 pipe reader，SIGKILL 与 durable checkpoint 成为恢复权威。wedged-pipe 测试证明函数会返回，
而不是让 resident scheduler 永久失去一个执行 lane。

### 25. 外层 5 秒不能取消内层 30 秒恢复协议

旧 daemon shutdown 在取消 scheduler 后，又给全部 task 套 `wait_for(..., 5s)`。Structure 子进程的
正式清理协议却是 `15s TERM + 15s KILL`；第 5 秒的二次取消会截断清理、terminal receipt 和 child
reap。更糟的是，`asyncio.wait_for()` 会等待被取消任务真正结束，所以“5 秒后退出”的注释本身也不
成立。

现在每个 task 只由自己的 cancellation/recovery owner 收尾，daemon 不再制造竞争性外杀；Uvicorn
grace 与最长 Structure shutdown budget 同源为 30 秒。Fly 是唯一进程级 backstop：`kill_timeout=40`
覆盖 30 秒 child protocol 及 terminal evidence/解释器退出余量。Producer supervisor 的 KILL 后
`process.wait()` 和 stdout/stderr drain 也都有界，避免兼容生产路径重新引入同一种无限等待。

### 26. 超时分支本身也有进程退出竞态

`returncode is None` 只是一次观察，不是“子进程之后一定存活”的锁。子进程可以在这次
观察与 `terminate()` 或 `kill()` 之间退出，操作系统正确地返回 `ProcessLookupError`。旧
ProducerSupervisor 把它当成 supervisor control failure，会污染 terminal receipt 和 incident 语义。

现在 TERM/KILL 两个边界都把 `ProcessLookupError` 解释为“目标已经达到停止终态”并返回；
其他异常仍保持可见。回归测试分别在 TERM 前和 KILL 前注入该竞态，证明停机路径有界且
不把正常的 already-exited 状态误报为新故障。同时，控制面聚合 JSON 的数值、数组和字符串都在
边界先验证再进入领域快照，避免损坏数据在恢复/观测路径中产生二次异常。

### 27. 代码里的 30 秒协议，不能由平台隐式 5 秒终止

Task 12 已把 Structure 的 TERM/KILL 协议、daemon task owner 和 Uvicorn grace 对齐到最长
30 秒，但正式 runtime-v2 Fly 模板没有声明 `kill_timeout`。现网 Machine 回读因此是
`kill_signal=null / kill_timeout=null`，等价于继承平台历史 5 秒默认值。内部协议写得再严密，
第 5 秒仍会被平台从进程外截断；这正是“代码修好了、部署语义却仍旧矛盾”的系统性漏层。

修复不是给每个角色再猜一组 15/20/40，而是让全部七份正式长运行模板声明同一个平台
backstop：`SIGTERM + 40s`。40 秒由最长内部 owner `15s TERM + 15s KILL/reap` 加
10 秒 terminal evidence / 解释器退出余量推导；正常退出不会等待 40 秒。测试同时读取原始
模板和六份 renderer 输出，防止发布工具把字段丢掉。旧候选镜像在发现该缺口后未部署，
controller 也未为了“先试试看”而重启。

### 28. 发布构建也是任务序列，下载必须有 owner 和身份

Task 13 精确镜像构建在 `curl` 下载 Supercronic 时沉默了 138.8 秒。进程仍在网络等待，
但 Dockerfile 没有连接上限、传输上限或 checksum；断线可无限占住发布 lane，即使下载成功也只由
HTTPS URL、不能由内容身份证明。把 CI 外壳再套一个短 timeout 只会重演父层抢杀子操作。

现在下载边界由工件本身推导：固定 v0.2.30 amd64 文件为 12,432,517 bytes，以 64KiB/s
作为最低可接受吞吐约需 190 秒；单次 transfer 给 240 秒，connect 给 15 秒，允许一次瞬态重试，
500 秒 owner 覆盖两次 transfer、retry delay 和退出余量。下载后必须匹配固定 SHA256 才 chmod。
这个 500 秒只拥有 immutable build input，不得复制成 runtime job deadline。

### 29. 配置文件通过，不等于平台对象真的持久化

Task 15 首次 controller 更新后，Fly API 返回成功、镜像也正确，但 Machine 回读仍是
`kill_signal=null / kill_timeout=null`。随后直接 POST 完整 Machine config，若仍把这两个
TOML 名字放在 JSON 顶层，API 同样返回成功并静默丢弃字段。问题不是 40 秒取值，而是两个
配置域的 schema 不同：`fly.toml` 使用顶层 `kill_signal/kill_timeout`；Machines API 使用
`config.stop_config.signal/timeout`，其中 timeout 是 `"40s"` duration string。

因此远端发布的完成定义必须是闭环，而不是命令退出码：fresh GET 当前 Machine → 用
`instance_id` 作为 `current_version` → 复制完整 config → 只改 image 与 `stop_config` → POST
→ fresh GET → 要求新 version、Machine ID/region 不变、其余 config 完全相等。renderer 只
输出 preserved-config SHA256，不输出 env；verifier 只允许 Fly 给 image 追加解析后的 digest。
模板测试负责源契约，Machine verifier 负责平台事实，二者缺一都可能是假绿灯。

### 30. job key 相同，不等于失败根因相同

生产 source job 的五个 epoch 依次是 `TimeoutError`、`ValueError`、`TimeoutError`、
`TimeoutError`、`ValueError`，旧 circuit 却只按 job key 把它们累加成五次“连续同一故障”。
这不是 retry budget 太小，而是数据模型丢了 failure identity；把三改成五只会延后下一次假熔断。

Revision 033 给 circuit 持久化当前 `failure_fingerprint`。worker 用 component、异常类型和
最内层代码位置生成不含 message 的 SHA-256 身份；只有新指纹与持久指纹相同才加一，
根因变化则回到一并保持 circuit closed。attempt 和 operator snapshot 同时保留有界
fingerprint 与粗粒度 signature，不保留 provider body 或 exception message。Gamma 的 2xx 畸形
JSON 也被包装为 body-free `GammaMalformedResponseError`，不再只留一个含糊的 `ValueError`。

同一次反向审计还发现：`ServiceStopRequested` 原来也进入 defect circuit。连续三次合规
部署停机就可以把健康 job 熔断。现在 `finish_interrupted()` 在同一 fenced transaction 内关闭
attempt、写入 `service.interrupted` 事件并让 job 立即可重新 claim；它不新建 incident、
不增加也不清空真实 defect streak。

### 31. 绝对 deadline 不能再被转换成第二个相对 cooldown

生产 circuit 明明只允许最多 300 秒退避，recovery budget 却显示约 16 小时后才能再执行。根因是 live
projection 用 `next_probe_at - opened_at` 计算相对 cooldown，再由 action scheduler 写成 `now +
cooldown`。`opened_at` 不随失败探针更新，所以 circuit 每多开一段时间，下一次预算门禁就把这段历史
再次加到未来，两个看似合理的时间字段组成了累积停摆。

Revision 034 明确单一权威：circuit 只比较绝对 `m1_job_circuits.next_probe_at`；recovery budget 只计
action 次数，circuit cooldown 固定为零，任何调用者传入非零值都 fail closed。迁移只清除 circuit
budget 的派生 deadline，不动 job cooldown、不补预算、不改 publication。历史 observe payload 可以在
replay 时一次性翻译旧字段，但 live projection 不再重建第二个时钟。

### 32. async 函数不代表它不会阻塞 event loop

生产中同一 Structure source page 在新 Machine 中 0.164 秒返回 100 条，八次 claim-shaped
数据库读合计也只需 2.292 秒；但常驻 coordinator 仍在约 29 秒后把同页判为
`fetch-page=0/1` 超时。真正的乘法发生在调度层：八个 source lane 和八个
materializer turn 的 `async run_once()` 都在 event-loop thread 上同步调用 `claim_job()`。

单次 SQL 没有超时，但多个连接、bootstrap、查询和锁等待被串行叠加，loop 无法及时
驱动 HTTP future，连 15 秒 provider timer 也不能按时被观察，最后由更外层的 29 秒
worker I/O 边界报错。这解释了为什么“实际请求很快”和“生产总超时”可以同时成立。

修复不是放大 29 秒或 15 秒，而是把五个 async worker 的 claim 都放到共享可取消
daemon bridge；claim 仍只消费数据库的 connect/statement/lock policy，不新造一个外层
timeout。回归测试同时从两个方向守门：行为测试阻塞假 claim 但要求独立 loop task
仍继续；AST 测试禁止已审计的 `async run_once()` 内再出现直接 `.claim_job()`。

### 33. 恢复预算必须属于故障 episode，不是 target 的永久户口

即使 failure fingerprint 已经区分了不同根因，旧 recovery budget 仍只以 target 为键。
因此新缺陷可以继承旧缺陷的零预算，出现“系统已知道根因变了，但仍拒绝恢复”。
Revision 035 把预算主键扩展为 `(controller, target_type, target_id, episode_key)`：job episode
使用 exact attempt ID，circuit episode 使用 exact failure fingerprint。旧 target-only 记录保留为
`legacy`，不会被重写、补额或删除。

生产恢复的一次性 Machine 还必须在正确的 Fly app 内运行。镜像相同不代表权限相同：
control-worker app 继承的 DSN 不是 runtime-controller scoped login，第一次错 app 探针因
`session_user=postgres` 与角色合同不匹配而 fail closed，没有任何变更。正确做法是在 controller
app 中运行 exact target/type/action、`--rm`、restart=no 的隔离 Machine，常驻 controller 始终保持
observe-only 和空 allowlist。

### 34. readiness 不能复用完整 operator snapshot

生产控制 API 周期性出现 16–56 秒健康失败。Fly 的 `/healthz` 外层只给 5 秒，但 handler 直接调用
完整 `operational_snapshot()`；旧应用 envelope 是 10.5 秒，而且这个数字还漏算了每个 scoped
connection 必做的 bootstrap/readback。于是平台先判失败，内部只读线程仍在继续，两个层次对同一次
请求给出相反结论。

修复把“进程可服务且 durable authority 可读”和“生成完整运营视图”拆开。`/healthz` 只执行一次
`SELECT 1`，使用独立策略覆盖完整序列：1 秒连接 + 1 秒 bootstrap + 1 秒探针 + 0.5 秒传输余量 =
3.5 秒，测试要求它严格小于 Fly 5 秒。默认 DB request/stop envelope 的公式也改为显式计算
`connect + bootstrap + data statement`，不再把初始化 SQL 当成零成本。健康检查失败只返回净化后的
503，不构建大 JSON、不读取运营投影，也不产生 durable mutation。

### 35. 健康测试不能偷读宿主机的动态资源状态

一次 31 分钟全量门禁有四个 `pass -> warn` 失败。目标 Quote/Structure check 都是 pass，真正改变
overall 的是 `shutil.disk_usage()`：开发盘当时只有 20.18% 空闲，测试生成物和 Docker layer 让它短暂
跌破生产 20% 告警线。相同代码单独运行又恢复，形成典型的顺序/负载相关假失败。

生产磁盘阈值没有放宽。通用 health contract fixture 固定 50% headroom；唯一专门验证磁盘逻辑的测试
仍显式注入 25%、19%、9%，分别断言 pass、warn、fail。测试的业务输入必须由测试拥有，不能让宿主机
当时的资源状态成为未声明的第二个判定权威。

## 剩余计时器的权威分类

| 类型 | 可以决定什么 | 不可以决定什么 | 当前来源 |
|---|---|---|---|
| attempt / progress | 当前 leased attempt 是否超过绝对或进度边界 | scheduler 不得另设更短外杀 | `RuntimePolicyRegistry` + persisted attempt snapshot |
| provider / DB I/O | 一次网络或 SQL 是否失败 | 不直接将 job 改为下一状态 | runtime provider policy / DB deadline registry |
| terminal grace | 停止后当前有界 effect 能否排空 | 不撤销已获得的 lease fence | 同一 job policy 或 DB policy 派生 |
| cadence / poll | 下一次 tick 何时有资格开始 | 不杀死已 claim 的工作 | 服务 CLI/config，并可被 stop event 打断 |
| evidence window | 需要连续观察多久才能通过验收 | 不是对被观察进程的存活上限 | `runtime-observe-verify` / qualification certificate policy |
| operator read | 一次可重试的 Fly/API 读是否失败 | 不产生 worker failure 或 Machine restart | 固定 target-cardinality 的 read envelope |

对正式部署模板的反向核对还确认：生产 process groups 只启动 transactional
`serve`、`runtime-reconcile-serve` 和 `qualification-serve`。历史 SQLite/L3 路径没有 process group、
没有 scoped role，也没有 runtime-v2 claim/receipt 权威；其内部的历史 retry/timeout 不能被误认为
当前生产任务的第二生命周期控制器。

## 任务序列的持久化真相

```text
range/batch jobs runnable
        │
        ├─ terminal receipt（lease epoch fence）
        │
        └─ 同一事务内的 best-effort 非阻塞 wake
                         │
                         ▼
                 certifier waiting → runnable
                         ▲
                         └─ claim 前 durable repair（丢失 wake / 竞争 / 重启）
                         │
                         ▼
              重新核对全部 input/receipt identity
                         │
                         ▼
                  publication pointer + successor
```

调度器的拓扑顺序只改善效率；数据库状态才决定一个 job 是否有资格被任何进程 claim。因此换进程、
重启 Machine、同一 job 被新 lease epoch reclaim，都不会改变依赖关系。

## 设计取舍

### 为什么 terminal grace 到期后不把 job 立即强写成 retryable？

旧线程可能正处于数据库 point-of-no-return。没有 attempt fence 的外层强写会制造双写竞争。正确做法
是让服务退出，保留 lease/checkpoint；lease 到期后由 reclaim 事务关闭旧 attempt，新 epoch 才能提交。

### 为什么只读 watchdog 可以零 grace，terminal DB transaction 不可以？

只读 observation 被舍弃不会改变 durable truth，也不会发送半条结果。terminal transaction 已进入
不可分割提交边界，第一次取消必须给它一个由 DB policy 推导的收尾窗口；但第二次取消仍要让服务退出。

### 为什么不把所有旧 daemon 的 `asyncio.to_thread` 一次性替换？

本次审计的权威边界是当前生产 `control-plane worker-serve`、qualification、runtime watchdog 和
control-plane HTTP。历史 SQLite daemon 不是 runtime-v2 的 claim/receipt authority；盲目把它们套进
同一语义会改变旧任务合同。它们保留为非正式路径，不能重新接管 M1 生产发布权。

## FAQ 增量

### daemon thread 是否意味着可以不设客户端 timeout？

不是。daemon bridge 只保证进程退出不会被 Python executor join 反向绑架；客户端 deadline 控制资源
占用，lease fence 控制晚到写入，checkpoint 控制恢复位置。三者缺一不可。

### real PostgreSQL barrier 测试为什么比 mock 更重要？

问题发生在并发可 claim 状态与 receipt/wake 的事务边界。mock 能验证调用顺序，却不能证明另一个
连接在最后一条 receipt 之前 claim 不到 certifier，也不能证明 commit 后立刻可见。

### FAQ 增量：为什么“最后一条 receipt 负责唤醒”仍会永久卡住？

因为“最后一条”只在提交顺序确定后才存在。两个并发事务都先写自己的 receipt，再统计当前可见
receipt；在 PostgreSQL 的事务可见性下，它们都看不到对方尚未提交的行，于是都判断“还差一条”，
提交后也不会再有人负责唤醒。这不是等待时间不够，而是 lost wakeup。

现在终态路径遵守三个不变量：

1. receipt 只证明产物已落库，不能代替 producer job 的 `succeeded`；
2. producer 先完成终态迁移，再对 certifier 行执行 `FOR UPDATE SKIP LOCKED`；忙碌只跳过 direct wake，
   不能回滚 producer 自己的终态；
3. certifier claim 前最多修复一个“事实已齐全但仍 waiting”的历史行，且使用
   `FOR UPDATE SKIP LOCKED`，不会制造新的并发单点。

所以可恢复性来自数据库事实和幂等状态迁移，不来自更长 sleep、更大 freshness 或额外 watchdog。

### 为什么 031 的 downgrade 不恢复旧 JSON 数组？

因为 append-only facts 已经无损保留全部信息。Downgrade 只撤销“数组必须为空”的防回长
约束；重造一份增长副本不是恢复，而是重新引入已证实的故障模式。

### 为什么恢复代码和单测都存在，生产任务仍可能永远停住？

因为恢复是完整权限链，不只是算法。生产 controller 能读到 due circuit、能算出
`probe-circuit`，但 Revision 026 的 scoped login 只有 observe 权限，第一条 action ledger
INSERT 就会被 PostgreSQL 拒绝。Revision 032 只补 fenced recovery transaction 所需的
SELECT / INSERT / UPDATE，仍禁止 DELETE、TRUNCATE、sequence 和 publication 写入；真实 PG16
测试必须用受限登录角色跑完整 schedule → claim → execute → terminal action，而不是用管理员连接代替。

### 为什么不能在 256 MiB controller 里 SSH 再跑一个 Python one-shot？

主 daemon 和第二个 interpreter 的峰值会超过 cgroup；现场两次都 OOM 杀死主进程。正确入口是先
SIGTERM 停常驻 controller，再用同 app、512 MiB、`--rm` 的隔离 Machine 执行 one-shot，最后恢复
observe-only controller。one-shot 还必须同时钉死 `target_type`、`target_id` 和 `expected_action`；
当前事实不完全匹配就停止，不能依赖“排序后第一个 actionable”。

### 20 分钟 attempt deadline 是否仍会让长 Quote 任务从零开始？

不会。生产 epoch 7 在 shard 156 到达 attempt 边界，job 已持久化 checkpoint 150；epoch 8 在同一
次 reclaim 事务后从 shard 151 继续。attempt deadline 限制单次所有权，checkpoint 保存累计工作，
lease epoch 阻止旧 attempt 晚到提交。三者一起才构成可中断、可恢复语义。

### 精确选中 target 后，为什么还必须精确领取 action？

只约束 reconcile 判定和 schedule 还不够。通用 executor 默认按请求时间领取队头；若库中
有更早的 pending action，操作员 one-shot 可能安排了 A 却执行 B。因此精确命令会把
刚调度的 `action_id` 传到 claim SQL；指定项不可领取时返回空，绝不回退到队头。
常驻服务不带该 fence，仍保留 oldest-first 队列语义。

### 为什么 `pool-turns=12` 不等于 12 并发？

参数名称不是执行语义。旧 role loop 的实现是列表推导式逐个 `await`，因此无论
`pool-turns` 多大，同一时刻都只有一个 Quote batch 在运行。生产每批实测约
11–12 秒，148 批串行约 28 分钟，与 900 秒 freshness gate 逻辑矛盾。

修复后，`pool-turns` 仍表示每个 tick 最多跑几个波次；每个波次内的 lane 数由
已有 `clob_batch_max_concurrency` 唯一限制。每个 lane 有独立 worker ID 和 lease，共享限流器与
R2 client。这样“调度波次”、“资源并发上限”、“单任务 attempt deadline”三个概念不再
混成一个数字。

### 并发 lane 里一个失败，为什么不应让整个 Machine 重启？

失败 lane 已经持有自己的 durable attempt，应由它写 retryable/incident。进程级崩溃会取消
健康 sibling，把本可局部恢复的 provider 故障放大为队列停摆。现在 pool 先 drain 全部
sibling，role loop 只记录有限 `error_class` 并继续下一波。SIGTERM 则是另一种语义：
它会取消所有活跃 lane，每个 lane 各自写 fenced interruption，再受共同 lease policy 推导的
terminal grace 约束。

### circuit 关了，为什么 recovery incident 还可能是 open？

因为失败工人和恢复控制器原先写了两个 incident 命名空间：`job-retry:<job>` 与
`recovery:{job|circuit}:<job>`。任务成功只关闭前者，导致 action 成功、circuit 关闭、
job 终态，但 Dashboard 仍显示“正在恢复”。这是 chain-truth 断裂，不是 UI 问题。

现在同一个 lease-fenced 成功事务会查找三个有界 dedupe key，对每个 open incident 原子写
`resolved_at + recovered event + alert outbox`。如果以后同一 target 发生新 episode，调度事务必须把
incident 重新设为 open 并清空 `resolved_at`。因此 incident 是可重开的状态投影，event 才是
不可变历史。

### 子 lane 都有 lease，为什么 SIGTERM 仍会因 `ValueError` 退出？

终止宽限由外层 scheduler 根据“当前 worker 的 durable lease policy”推导。pool 是 scheduler 看到的
worker；如果 pool 没把所有 lane 共同的 `_lease_seconds` 暴露出来，外层就无法证明应该采用哪个
grace。旧 Structure pool 正是这样，导致真正排空之前先在 policy lookup 失败。

修复不是给 pool 再写一个 40 秒：构造 pool 时验证所有 lane 的 lease 相同且为正，然后只暴露这个
派生值。`service_lifecycle` 再从 `structure-fetch` 的中央 runtime policy 计算 grace。这样 lease 改动、
lane 并发和 Fly `kill_timeout` 仍能通过同一条契约校验。

### 为什么每次 R2 请求都很快，长任务仍会报 `stale-lease`？

旧桥接器只在“单次调用连续阻塞满一个 heartbeat interval”时续租。Opportunity 连续读取 148 个
对象时，每个请求都可能小于 30 秒，于是没有任何一次进入 timeout 分支；但整个序列超过 120 秒后，
lease 已经失效。结果是单次 I/O 越健康，长序列反而越稳定地丢租约。

修复点不是把 120 秒改成 1,200 秒。每个非终态子调用返回后都执行一次
`heartbeat_if_due()`；该方法根据累计时间决定是否真正写续租。慢调用期间仍周期检查，绝对 attempt
deadline 仍不延长。terminal transaction 提交后不再续租，因为成功终态已经取代 lease 成为权威。

### 26. 能恢复单个任务，不等于整条流水线满足新鲜度

Structure range 已经具备 lease、heartbeat、checkpoint 和 reclaim，单个任务因此可以正确中断恢复；但生产
一代有 1,115 个 range，单 lane 实测只有约 8.2 range/min，完整排空约 136 分钟，而发布新鲜度只有
15 分钟。更严重的是旧 `structure_high_water=2000`：第一代留下 1,115 个未完成任务时仍低于门槛，
第二代会继续入队。这里再延长 attempt timeout 只会让慢流水线更久地占有单点，不会增加吞吐。

修复把三个原本混淆的量分开：

1. `structure_range_max_concurrency=12` 是资源容量；每个 lane 有独立 worker ID、lease 和 checkpoint；
2. `pool-turns` 只是每个 tick 的波次数，不代表并发；
3. `structure_high_water=1` 是代际背压，只要上一代还有一个 range 未终态，就不准新源窗口继续堆积。

12 不是随意的 timeout 数字：`ceil(136 / 15) = 10` 是满足新鲜度的最低吞吐倍数，另外两 lane 给
数据库/R2/调度波动留出容量余量。它不改变 15 分钟 freshness、120 秒 lease、绝对 attempt deadline、
artifact 或 pointer 语义。生产仍必须用 canary 实测并发 lease、内存和完整代排空时间；若不满足就回滚
镜像，而不是放宽新鲜度。

### 27. `with sqlite3.connect()` 管事务，不拥有连接关闭

取消全套测试的外层 timeout 后，120k Structure classifier 持续计算时一度同时打开约 600 个同库句柄，
测试结束才被 cyclic GC 回收。这里容易产生一个错误心智模型：Python 的
`with sqlite3.connect(path) as con` 会在退出时 commit/rollback，但不会保证调用 `con.close()`。
分页函数每 500 行新建多个 connection，单页都很快、checkpoint 也正常，长序列仍可能先耗尽容器文件
描述符；这和“每个 R2 调用都快但累计 lease 过期”是同一种组合层缺陷。

现在高频 drift read 使用唯一的 context-managed owner，在 success、early return 和 exception 上都显式
close。它不增加超时、不跨页共享连接，也不改变 writer/transaction/checkpoint 边界。回归测试用真实 SQLite
connection 包装器连续跑十页，并要求每个已打开句柄都观察到 `close()`；性能大样本继续证明业务结果和
45 秒 child-slice SLA。

第一次修完生产 reader 后，句柄峰值从约 600 降到约 160，但没有归零。剩余连接来自性能测试自己每个
chunk 都执行的 phase observer。observer 虽然只读，也必须用 `closing(sqlite3.connect(...))` 明确释放；
否则测试会把自身泄漏错算成被测系统的资源曲线。审计工具不是生命周期边界之外的特殊进程。
修复后的独立 12 万 gate 在 902.94 秒完成；校准与三个正式样本期间重复采样最多只有 4 条 `lsof`
记录、3 个 DB/WAL/SHM 路径，且不随 2,000 次 phase observation 增长。

生产止血也不能和最终修复混淆：把 coordinator 的 admission high-water 调成 1，只负责阻止第三代继续
入队，并保留前两代的 lease/checkpoint；它不创造吞吐。最终接受条件仍是精确镜像 canary 实测 12 个不同
lease owner 同时工作、内存有界、完整代预计在 900 秒内排空。两项证据不可互相替代。

### 28. worker ID 如果不约束所有权，就不是并发上限

第一轮 12-lane canary 确实出现了 lane 0–11，但 PostgreSQL terminal 写失败后，lane 6 和 10 各自又
领取了第二个 live job。旧数据库只约束“同一个 job 只有一个 lease”，没有约束“同一个 worker ID
只能拥有一个 live lease”。因此名义上 12 lane，实际 `leased` 可以超过 12；连接竞争越严重，系统反而
开启越多 attempt，形成正反馈。

现在 `claim_job()` 先用 worker ID 的 transaction advisory try-lock 串行化同身份 contender，再在同一
SQL round 检查该身份是否已有未过期的 `leased` job。`checkpointed` 的 attempt 已结束，仍允许立即进入
新 epoch 恢复。任一 live-lease 条件不满足就返回 idle。若 terminal
数据库写本身失败，该 lane 会失去部分吞吐，直到原 lease 到期后按正式 reclaim 路径恢复；它不能通过
领取新任务来“补吞吐”。这是有意的 fail-closed：容量可以暂时下降，所有权绝不能静默膨胀。

### 29. 共享 successor 行不能成为所有 producer 的提交前置条件

第二轮 12-lane canary 已把 live ownership 限制在 12，但五分钟只有 229 个成功 attempt，同时出现
34 个 `OperationalError` 和 10 个 `LeaseExpired`。数据库连接总量远低于 `max_connections`；真正的
共同点是每个 range terminal transaction 都要对同一个 certifier 行做阻塞 `FOR UPDATE`。一秒
`lock_timeout` 因此不再是“单次异常 SQL 的边界”，而变成“正常并发 producer 是否能提交”的随机闸门。

正确修复不是把一秒改成十秒：那只会让 12 条 lane 一起等更久。现在 producer 先把自己的
receipt/job/attempt 写入同一事务，再以 `FOR UPDATE SKIP LOCKED` 尝试 direct wake。行忙时只跳过这项
优化；下一次 certifier turn 会用 inputs + receipts + producer `succeeded` 的 durable facts 修复最多
一个 waiting successor，然后再 claim。这样三种情况——并发最后两条 receipt、进程在 wake 前退出、
Machine 被 SIGTERM——都走同一条恢复链，不再靠放宽 timeout 碰运气。

### 30. 背压必须跟随 generation 的形态，而不是只看某张队列表

Structure 一代不是从头到尾都表现为 range：它先是一个 `structure-materialize` job，原子展开成很多
`structure-normalize` job 和一个 waiting `structure-certify`，最后只剩 certifier。旧 high-water 只数
range，因此 materializer 还没展开、或 range 刚清零但 certifier 未完成时，都会错误观察到零。

生产里两个 source window 在 stopgap 前已入场，数小时后才 materialize；所以即使 coordinator 命令上
确实有 `--structure-high-water 1`，它们仍能在 stopgap 后各生成 1,117 个 range。修复需要两层：

1. admission 用同一个 high-water 有界 probe 统计 materializer/range/certifier 三种 unfinished shape；
2. materializer claim 只允许最老任务，并在任何旧 range/certifier 未终态时返回 idle。

materializer terminal transaction 已经原子地把旧 shape 换成新 shape，因此两层 predicate 闭合后不需要
另建 mutable generation counter，也不需要用 sleep 等待“队列稳定”。进程停止、lease expiry、retryable
materializer 都仍由既有持久状态恢复。

### 31. 吞吐不达标时，资源形态也不能伪装成 timeout

v14 已把五分钟内的并发提交风暴从 34 个 `OperationalError` 降到零，但 shared-1x 的完整滑动窗口仍只有
288 个成功 range，即 57.6/min，低于 74.3/min。持久 stage 事件进一步把完整任务拆成约 2.52 秒
claim/read、6.38 秒 read/normalize、2.75 秒 R2 upload、1.43 秒 commit stage 和 1.59 秒 terminal
commit。这里延长 lease、attempt 或 15 分钟 freshness 都不会增加单位时间算力。

但“把 CPU 改成 2”也不能成为手工特例。正式 Machine renderer 只接受完整
`cpu_kind + cpus + memory_mb` 三元组，并继续携带 fresh `current_version`、精确镜像、`SIGTERM/40s`
与非目标配置哈希。少一个字段、给零值，或远端返回任何未请求配置差异都会失败。这样资源 A/B 与 timeout
调参具有不同证据：前者必须在相同 900 秒门槛下证明吞吐提升，后者根本不参与这次实验。

### 32. SQL 有 `LIMIT`，不代表它的工作量有界

operator snapshot 只返回最近 5–100 条 attempt/outbox，但旧执行计划会先扫描、连接、排序全部历史，再做
`LIMIT`。生产 warm plan 仍花 2.337 秒；12 lane 并发写入时更直接撞上 5 秒 statement deadline，整个
status 变成 `QueryCanceled`。这也是一种单点：业务仍在推进，观察面却因为自己的历史增长而失明。

修复不是把 5 秒改成 15 秒。Revision 036 为最新 attempt 增加
`(started_at DESC, attempt_id DESC)`，为 pending outbox 增加只包含 pending 行的
`(created_at DESC, outbox_id DESC)` partial index。真实 PostgreSQL planner 测试必须看到两个 index name；
只检查“索引存在”不够。生产创建/删除使用 `CONCURRENTLY`，因为修观察面时阻塞 writer 会制造比原问题
更严重的停摆。这样 deadline 继续表达故障边界，索引负责让正常工作量落在边界内。

### 33. `make -n` 能看到命令，但证明不了命令能执行

精确恢复入口的 Make recipe 用未转义括号表达“三个 selector 要么全有、要么全无”。
`make -n` 只打印 recipe，不让 `/bin/sh` 解析；所以测试是绿的，真正操作时却在 CLI 启动前因
syntax error 停止。这种问题不是参数错，而是公共入口根本未经执行证明。

现在测试把一个无 I/O 的假 `uv` 放到 `PATH` 前端，真正执行 Make target，同时验证
`enable=1` 和三个精确 selector 的转发。心智模型很简单：干跑证明“Make 会生成什么”，执行测试才
证明“shell 能否跑到业务边界”。

### 34. 恢复控制器的候选查询也必须受 deadline 约束

恢复动作没有执行，并不代表 action budget、circuit probe 或权限有问题。这次 execute-only 探针在
action INSERT 之前就被 SQLSTATE 57014 取消。旧查询用
`state NOT IN ('succeeded', 'quarantined')`，为找十几个候选先扫描 102,828 个终态 job 和
7,010 个 runtime state；恢复器本身因此撞上两秒 statement boundary。

正确修复是正向枚举五个合法非终态，让现有 `m1_jobs_state` 索引先缩小 join 的选择侧。
生产 warm plan 从 739.698ms 降到 19.528ms，真实 candidate read 在原边界内成功。这里没有
调大 timeout，因为 deadline 设计没错；错的是正常工作量随历史数量无界增长。

### 35. “精确目标”必须在 `LIMIT` 之前精确

旧恢复 CLI 先读最旧 100 个候选，再在 Python 里过滤 `target_id`。当目标排在第 101 个时，
操作员明明给了精确 job 和精确 action，系统却报“目标不唯一或不存在”。这不是容量过小，
而是操作语义与查询顺序相反。

现在 exact `job_key` 先进 PostgreSQL predicate，然后才排序和 `LIMIT`；`target_type` 与
`expected_action` 仍在读回持久事实后二次验证。因此“指定谁”、“它现在是什么”和“准备对它
做什么”三层仍然独立 fail closed。

### 36. 正常关闭也是中断协议的一部分

运行中 transport replacement 和 cancellation cleanup 都有两秒边界，但正常 SIGTERM 的最后一步
`scheduler.aclose()` 曾直接等待无界 `GammaClient.aclose()`。这会产生反直觉结果：异常路径可停，
正常关停反而可能等到 Fly 的 40 秒硬杀。

现在显式关闭复用同一 transport cleanup authority。超时或 close error 只记录错误类，不替换已完成的
durable stop 结果。cleanup 不是第二个 attempt，更不能拥有进程寿命。

### 37. 绝对 deadline 不能写成 lease 倍数

Structure certifier 的设计是一小时绝对 ceiling，旧实现却是 `lease_seconds * 120`。lease=30
时恰好得到 3,600，测试因此没有暴露问题；lease=120 时它就静默变成 14,400 秒。
这是两个 authority 偶然数值对齐，不是派生关系。

现在 policy spec 明确二选一：普通 job 用 lease multiplier，certifier 用独立 3,600 秒 ceiling。
修改 lease 只影响 heartbeat/progress/fence；若 lease 大到让 progress boundary 超过一小时，配置直接拒绝，
不会暗中改写 attempt 寿命。

### 38. 镜像 tag 不是可验证的 release identity

第一次 v15 构建的 tag 包含短 SHA，linux/amd64 和 UID 10001 也都正确，但镜像配置里的
`org.opencontainers.image.revision` 是空的。tag 是调用者输入的名字；它可以拼错、复制错，也无法证明
镜像到底来自哪个完整 commit。把它当 release identity，等于让发布序列依赖操作员记忆。

现在唯一公共入口是 `make runtime-image-build image_tag=...`。它从 Git 自己读取完整 HEAD，先拒绝任何
偏离 HEAD 的镜像输入，再用 `--build-only --push` 明确禁止部署，同时写入可独立 inspect 的完整 revision
label。测试真正执行假 `flyctl`，验证参数和被清空的环境 token；不再靠一段临时 shell 命令承担发布契约。

### 39. 半开探针的“开始许可”也要能跨受信任中断恢复

电路恢复动作并不是给任务永久通行证，而是把 `next_probe_at` 推到未来，打开一个有界认领窗口。问题在于
Structure certifier 可以健康运行一小时，而这个窗口按重试策略只有 60 秒。任务运行超过 60 秒后遇到部署
SIGTERM，旧实现虽然正确写入 `ServiceStopRequested`、释放 lease、也不增加 defect streak，但 replacement
worker 仍被已经到期的 open circuit 拦住。每次正常部署都要再花一个 recovery action，最终会把同一 episode
的三次预算耗尽。

修复不是把 60 秒改成一小时。60 秒仍是认领迟滞的边界；受信任中断的 fenced terminal transaction 只为
同一 open circuit 续开一个新的 60 秒窗口。它不关闭 circuit、不清零 `consecutive_failures`、不改
fingerprint、不新建 episode，也不扣 action budget。于是“故障是否已修复”仍只能由后续业务成功证明，
而“进程正常换代”不再被错误计作一次恢复尝试。

### 40. 测试 watchdog 不能偷偷变成产品 deadline

完整 M1 套件曾在 Structure fan-in 并发测试的 `Barrier.wait(timeout=5)` 失败，但该用例单独连续五次通过。
这里的五秒没有业务含义：测试只想让两个事务同时进入 wakeup 判定，却把机器负载误判成 fan-in 缺陷。
同一文件还混有十秒和一个完全无界的 barrier，说明测试基础设施自己复制了多套时间 authority。

现在所有真实 PostgreSQL 并发 barrier 只用一个命名 watchdog：复用控制面数据库完整事务/停机包络。
它的职责仅是“若 peer 永远不来则让测试失败而不是挂死”；断言仍只检查 durable state、CAS、budget 和
wakeup 结果，不检查完成用了几秒。这样慢主机不会制造假业务故障，真死锁也不会把整套验证永久卡住。

### 41. 单一 authority 不等于固定三个消费者

静态契约原本用字符串计数断言 `runtime_retry_policy()` 在 PostgreSQL store 中恰好调用三次。这能抓住
复制 backoff 公式，却也把“当前有几个调用点”错当成架构约束。半开中断续窗口合理地成为第四个消费者后，
4,082 个测试通过，只有这条计数断言失败。

真正要守的是数据流：每个 `retry_backoff_seconds()` 使用前都有中央 policy lookup，并继续禁止任何
`15 * 2**n`、固定 retry budget 等私有公式。消费者可以随生命周期扩展，authority 仍只有一个。

### 42. `create_task()` 不是 ownership

L2 handler 为避免每帧等待 PostgREST，把 top-of-book 合并后交给 `asyncio.create_task()`。局部性能目标没错，
但 closure 只保存 task 引用，外部既不能等待 idle，也不能在 SIGTERM 后 drain。轻载测试里 depth 的
`to_thread()` 恰好让后台 task 得到调度，所以一直误以为 handler 返回时写入已发生；完整套件负载下这个
偶然顺序消失，`call_count` 仍是零，pytest 还报告 pending task 被销毁。

现在 callable dispatcher 同时拥有 pending map、drain generation 和 closed 状态。普通帧仍只 enqueue，
不把 PostgREST 延迟放回 WS 接收路径；需要确定性证据的调用者显式 `wait_idle()`。daemon 则先停止 WS
producer，再在所有退出路径 `aclose()`，确保最后一批已合并数据有唯一 owner，close 后的新帧明确失败。

### 43. 进程内 drain 小于平台 kill window，必须是显式契约

L2 过去把 `_drain_daemon_tasks()` 默认写成五秒，但 `fly-l2.toml` 没声明 `kill_signal` 和
`kill_timeout`。这意味着代码认为自己有五秒，实际平台边界却取决于供应商默认值；换平台配置或默认值变化后，
进程可能收到不同信号，也可能在 durable writer 排空前被硬杀。这个五秒既不是 provider timeout，也不是
lease、attempt 或业务 freshness，所以无法从现有 authority 推导。

现在 `daemon.lifecycle` 只声明一对进程级边界：40 秒平台终止窗口，30 秒 cooperative task drain。
`fly-l2.toml` 明确使用 `SIGTERM/40s`，L2 drain 的默认值直接引用 30 秒 authority，保留十秒给 VM reap
和日志刷新。测试同时读取 Python signature 与 Fly TOML；任一侧私改都会失败。重点不是把五改成三十，
而是把顺序固定为 `producer stop -> owned drain <= 30s -> platform kill at 40s`，让中断行为可证明。
