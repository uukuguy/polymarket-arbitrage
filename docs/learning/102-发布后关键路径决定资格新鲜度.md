# 发布后关键路径决定资格新鲜度

## 30 秒心智模型

资格器不关心一个 Structure 在发布前做了多久；它关心的是下游消费者看到的当前
Structure、Quote 和 Opportunity 是否在 900 秒内形成同一 lineage。生产取证得到：

```text
Structure publish 18:31:15
        | 680s
Quote publish     18:42:35
        | 224s
Opportunity       18:46:19
        = 904s > 900s
```

因此不能凭“哪个任务看起来最久”调 timeout。要先定义窗口起点，再用发布时间戳
分解关键路径。这次真正的直接修复是把 Opportunity 读取 143 个 Quote 批次从串行
改为有界 wave，而不是把 900 改大。

## 关键代码地图

- `src/polyarb/control_plane/opportunity_worker.py:241`：以受控并发度切分 projection wave。
- `src/polyarb/control_plane/opportunity_worker.py:338`：每个 lane 读取认证输入引用和 Quote artifact。
- `src/polyarb/control_plane/opportunity_worker.py:370`：`executor.map` 保持冻结批次顺序。
- `src/polyarb/cli_control_plane.py:1315`：生产调度器使用已有的 CLOB 批次并发上限。
- `tests/m1-perception/test_transactional_opportunity_projection.py:455`：验证峰值有界、顺序不变、线程排空。

## 为什么不直接并发整个 certifier

Opportunity pointer 仍然只有一个 lease owner 和一次 terminal publish。并发的只是无副作用的
数据装载：读取 batch 的 Postgres 引用、R2 输入和 R2 Quote artifact。主线程按原始顺序
合并结果，最后仍只调用一次 `publish_opportunity_projection`。这使吞吐和发布权威分离。

## 心跳、中断与排空

一个 wave 由外层 runtime synchronization 包裹，因此 R2/DB 读取时 lease 心跳仍在继续。
如果收到 stop，未开始 I/O 的 lane 会 fail fast；已开始的 I/O 不会被不安全地强杀，线程池
先 drain 再向外抛出中断。任务记为 interruption，不消耗缺陷重试预算。

## 设计取舍

- 不改 900 秒：这是业务 SLO，不是内部任务 timeout。
- 不引入新魔法数字：Opportunity 复用 `clob_batch_max_concurrency`，默认为 12，且配置强制 1–32。
- 不改结果顺序：批次顺序是发布重现性的一部分，并发只改变完成时间。
- 不因新鲜度暂停整条链：qualification 只暂停有效秒，生产仍继续生成 successor lineage。

## FAQ 增量

### 为什么不先假设并发 12 就一定能进 900 秒？

本地测试只证明语义和并发上限，不证明 Fly→Supabase→R2 的真实延迟。修复完成的门是新精确
image 上线后，下一个同 lineage 的 Structure→Quote→Opportunity 发布差小于 900 秒，且
qualification 的 `eligible_seconds` 实际增长。
