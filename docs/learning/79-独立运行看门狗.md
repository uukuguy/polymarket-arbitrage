# 独立运行看门狗

## 30 秒心智模型

24 小时验收器是在“系统已经健康”时积累合格证据；运行看门狗是在“系统已经坏了”时立即让人知道。两者不能共用 Postgres：数据库失效时，依赖数据库的告警系统正好也会失明。

`polyarb-control-alert` 因而只做外部观察：每 30 秒读取控制 API 与五台精确业务 Machine 的状态。任一 API 超时、返回非 `available`，或某台 Machine 不是 `started`，都会形成故障状态；状态第一次变坏发 Telegram，持续相同故障只写心跳日志，恢复时再发一条通知。它绝不替业务 Worker 做重启决定。

## 关键取舍

Fly 没有可由 CLI 生成的只读组织 token；当前凭据在能力上是组织 token，但看门狗源码只发 `GET /v1/apps/{app}/machines`，并且它只存在于告警 app 的 secret 中。这个限制需要被诚实记录：代码最小权限不等于 bearer token 的平台最小权限。

“同一故障每 30 秒都发消息”会淹没 Telegram，导致真正的新故障被忽略。因此消息只在状态转换时发送；每轮 JSON 心跳则保留在 Fly 日志中，能证明看门狗持续在实际探测，而不是仅仅进程仍然存活。
