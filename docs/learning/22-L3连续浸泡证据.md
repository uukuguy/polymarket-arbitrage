# L3 连续浸泡证据：把“24 小时看起来正常”变成可重算的结论

## 30 秒心智模型

六小时看一次 `/health`，只能证明五个瞬间；它证明不了两次查看之间的约 72 个 promoter
tick、WS membership 变化、writer 失败和每个市场的 freshness。连续证据链把运行时事实写进
五张 append-only 表：boot 是身份锚，promoter 是控制账，30 秒 process/market sample 是
连续观察，runtime event 是故障账。T0 前再用 manifest 锁住身份、mapping、阈值和五个报告
路径。

操作者在 T+0/T+6/T+12/T+18/T+24 生成的是累计区间报告，不是五张“现场照片”。最终
verify 重载 manifest 和五份报告，并对同一个 `[T0,T24)` 重查数据库原始行：

```text
runtime → 五张 server-timestamped evidence tables
                │
T0 前 manifest ├─ identity + mapping + AcceptanceConfig
                └─ T+0 / T+6 / T+12 / T+18 / T+24 paths
                              │
                              ▼
                canonical report + four nested hashes
                              │
                              ▼
             final verify re-queries every exact interval
```

任何一环缺失都得到 `NOT-CLOSED`。本地 PASS 只证明工具合同，不授权生产 migration、
credential、deploy、manifest bind、retention cleanup、chaos 或交易。

## 关键代码地图

### 1. membership 必须区分“想要、发成功、业务证明”

`src/polyarb/daemon/ws_consumer.py:228-251` 生成不可变 `WsMembershipSnapshot`：

- `desired`：promoter 希望重连后拥有的 token；
- `committed`：当前 connection generation 上控制消息已成功的 token；
- `evidenced`：同 generation 已有成功 depth write 的 token。

同步 observer 在每个 mutation boundary 发布快照，因此 sampler 不必从几个会漂移的 set
拼接一个“差不多同时”的状态。`src/polyarb/daemon/ws_consumer.py:530-554` 进一步规定：
只有 `book_levels_succeeded=True`、generation 仍是当前代、asset 属于 committed set 时，
book 才能升级成 evidenced。旧连接的晚到 frame 不能替新连接作证。

这个模型解决了两个常见误判：成功 `send(subscribe)` 不是服务端已接受，更不是 book 已经
持久化；desired=10 也不等于 committed/evidenced=10。

### 2. `recorded_at` 是数据库事实，append-only 是权限事实

五张表的 `recorded_at` 不是客户端传入。`alembic/versions/007_l3_soak_evidence.py:33-61`
用 `clock_timestamp()` 给出 server 时间，并为每张表安装 append-only trigger。
`alembic/versions/007_l3_soak_evidence.py:389-428` 的 trigger 会在 INSERT 时覆盖
`recorded_at`；普通 UPDATE/DELETE 直接拒绝。health/market sample 还要求
`sampled_at <= recorded_at < sampled_at + 30s`，所以未来样本不能提前写进数据库。

daemon 的正常能力只有 SELECT/INSERT。`alembic/versions/007_l3_soak_evidence.py:508-553`
把 cleanup 函数从 PUBLIC、service、daemon 撤权，只授予 NOLOGIN capability role
`l3_retention_operator`。真正的登录凭据通过 membership 获得这项能力，并且只能调用
SECURITY DEFINER retention RPC；它没有 evidence 表的任意 DELETE 权限。

这也是 secret boundary：runtime 使用 `POLYARB_L2_RUNTIME_DB_DSN`，cleanup 只读取
`L3_RETENTION_DSN`，绝不 fallback 到 daemon DSN。凭据检查只输出 target、role、TLS 和
capability 布尔结论，不打印 DSN。

### 3. `AcceptanceConfig` 把“验收环境”也纳入证据

`src/polyarb/observation/l3_evidence.py:373-418` 定义 frozen `AcceptanceConfig`，不仅有
recipe hash，还包括：

- sample interval 30s、最大 sample gap 75s；
- promoter interval 300s、最大 start gap 360s；
- book/OHLC freshness 都严格小于 120s；
- 5 markets、10 tokens；
- retention 至少 30 天、schema revision 007；
- code version。

manifest 保存完整 config 和 `acceptance_config_hash`。runtime boot、promoter 和 process
sample 也写同一个 digest。这样修改 recipe、阈值、schema 或代码后，即使输出仍是 10/10，
也不能混入原窗口。`src/polyarb/observation/l3_soak_verdict.py:959-979` 会把任何 R08
偏离变成 `acceptance_config_not_locked`。

### 4. manifest 与五份报告是同一个 soak 的密码封条

`src/polyarb/observation/l3_soak_verdict.py:188-311` 的 `SoakManifest` 锁住精确 T0/T24、
唯一 boot、release/machine/version、digest-pinned image、mapping、AcceptanceConfig 和
五个累计报告：

| 报告 | 精确窗口 |
|---|---|
| T+0 | `[T0, T0+30s)` |
| T+6 | `[T0, T0+6h)` |
| T+12 | `[T0, T0+12h)` |
| T+18 | `[T0, T0+18h)` |
| T+24 | `[T0, T0+24h)` |

四层 hash 各回答一个问题：

- `soak_hash`：这是不是同一个 T0、boot、release/image、mapping、AcceptanceConfig？
- `interval_hash`：这是不是同一个 soak 的这个 report end？
- `raw_row_set_hash`：五张表的原始行（含 server `recorded_at`）和 SQL coverage 是否完全相同？
- `report_hash`：报告里的 bounds、aggregates、identity、reasons 是否有一个字节被改过？

`manifest_hash` 则认证 manifest 自身（除自身 hash 字段外的 canonical payload）。
`src/polyarb/observation/l3_soak_verdict.py:422-538` 计算 report hash 并规定唯一 canonical
bytes；`src/polyarb/observation/l3_soak_verdict.py:745-892` 按表主键排序全部 raw rows，
同时绑定 10-token book coverage 和 5-Yes-token OHLC coverage。数据库返回顺序变化不会
改变 hash，但增删改任何一行都会改变。

最终 `scripts/l3_evidence.py:617-660` 逐个读取 manifest 声明的五个文件，检查 canonical
bytes、bounds、manifest/soak hash，然后为每个 interval 重新
`fetch_window → build_soak_report`。报告文件本身通过，不代表 raw database 仍匹配。

### 5. event kind 拒绝不依赖可变 `severity`

严重度适合告警展示，却不是稳定的验收语义。一次 `reconnect_failed` 即使被错误标成
`info`，仍然说明连续性发生过失败。`src/polyarb/observation/l3_soak_verdict.py:1334-1350`
因此按 event kind 拒绝以下默认集合：

- `watchdog_stale`
- `reconnect_failed`
- `subscription_control_failed`
- `evidence_writer_failed`

只有 T0 前写入 immutable manifest 的 exact-kind exception 才能例外；它会同时改变
manifest/soak hash。运行中修改 severity 或事后解释日志都不能把失败变 PASS。

### 6. R08 是区间约束，不是最终状态

`src/polyarb/observation/l3_soak_verdict.py:924-979` 先锁 exact bounds、24h 和
AcceptanceConfig；`src/polyarb/observation/l3_soak_verdict.py:1086-1207` 再验证每个
300s promoter tick、boot-grid sample、75s gap 和 10/10/10 membership；
`src/polyarb/observation/l3_soak_verdict.py:1217-1350` 验证五对市场身份、每个市场双 token
freshness、10-token book coverage、5 Yes OHLC coverage和 runtime event。

`src/polyarb/storage/l3_evidence_store.py:827-885` 在 repeatable-read、read-only transaction
里一次取得五张 evidence 表和两组 exact-window SQL coverage，避免报告的一半来自查询前、
另一半来自查询后的新写入。

## 操作面：先分清读取与 mutation

四个日常证据命令是只读的：

```bash
make l3-evidence-status
make l3-soak-checkpoint manifest=<path> start=<ISO> end=<ISO> output=<unique-path>
make l3-soak-verify manifest=<path> start=<ISO> end=<ISO>
make l3-evidence-retention-check
```

checkpoint 唯一的本地写是 O_EXCL 创建新报告；它不覆盖文件、不写数据库。另有两个必须
单独授权的生产 mutation：

```bash
make l3-soak-manifest-bind manifest=<path>
make l3-evidence-retention-cleanup cutoff=<ISO> \
  protected_start=<ISO> protected_end=<ISO> \
  approve=DELETE_EXPIRED_L3_EVIDENCE
```

执行任何生产 gate 前，先用已经实现的稳定 proof 命令核对 target/revision/role：

```bash
make supabase-prod-revision expected_ref=<ref> expected_revision=007
make l3-runtime-credential-check expected_ref=<ref>
make l3-retention-operator-check expected_ref=<ref>
```

这些命令通过仍不是 deploy 或 cleanup 授权。

## 设计取舍

### 高频写 raw evidence，而不是只存聚合

- 收益：阈值实现有 bug 时仍能用原始行重算；能定位哪一个 market、tick 或 generation 断裂。
- 代价：30 秒 × 五市场带来稳定写量，因此必须有 30 天 retention 和独立 cleanup capability。

### 五份累计报告，而不是五个独立六小时桶

- 收益：每次 checkpoint 都重新覆盖从 T0 到当前的全部历史，早期证据不能在后续报告中消失。
- 代价：越靠后的 checkpoint 查询越重，但换来更简单的 common soak hash 和边界语义。

### fail-closed，而不是“缺数据等于没有故障”

- 收益：缺 report、缺 row、缺 coverage、读取失败、hash 不同都不会产生假 PASS。
- 代价：基础设施短暂不可读也会得到 NOT-CLOSED；这是“无法证明”，不等于“已证明 daemon 故障”。

### 独立 retention operator，而不是 daemon 自删

- 收益：攻陷 runtime credential 不能擦除失败历史；cleanup 有专门 secret、approval 和 protected window。
- 代价：多一个需 provisioning/审计的角色，但职责边界清晰。

## 失败模式

- **只看 release 37 五个 spot check**：它是 diagnostic-only；没有连续 ledger，不能升级为 strict evidence。
- **desired=10 就宣称 10/10**：控制可能失败，或当前 generation 尚无 depth-write evidence。
- **把 `info` 当无害**：验收按 event kind；severity 不改变失败事实。
- **报告文件存在就通过**：verify 必须重查 raw rows；数据库变更会触发 raw/report hash mismatch。
- **用 capped REST page 算 coverage**：热点 token 会挤掉安静 token；coverage 必须在 SQL exact window 聚合。
- **用 daemon DSN 做 cleanup**：命令必须拒绝；cleanup 只接受 `L3_RETENTION_DSN`。
- **把 local GREEN 当 rollout**：LOCAL PASS DOES NOT AUTHORIZE PRODUCTION。

## FAQ 增量

### Q：为什么 T+0 报告不是零长度？

零长度窗口没有 process sample，也无法证明 T0 真的命中 boot 的 30 秒 grid。T+0 报告覆盖
`[T0,T0+30s)`，要求 exact scheduled-T0 sample；若这一格缺失或失败，该 manifest 永久
NOT-CLOSED，不能把 T0 后移。

### Q：为什么有 `manifest_hash` 还需要 `soak_hash`？

manifest hash 认证整份声明，包含五个文件路径和 bounds；soak hash 专门表示跨报告共享的
运行身份与验收配置。不同 checkpoint 的 interval/report hash 可以变化，但它们必须共享
同一个 soak hash。

### Q：append-only trigger 为什么还允许 DELETE？

普通会话不允许。只有 SECURITY DEFINER retention 函数在事务内设置私有 gate，且以表 owner
身份执行时，trigger 才放行符合 30 天 cutoff、protected window 和引用完整性顺序的 DELETE。

### Q：为什么 OHLC freshness 不能直接看一分钟桶的 `bucket_ts`？

`bucket_ts` 是 `date_trunc('minute', ts)` 得到的桶标签，不是桶内最后一次源观测的时间。
把它当 freshness 会凭空增加 0–60 秒年龄：真实源数据可能只有 90 秒旧，桶标签却显示成
130 多秒旧，从而误触发严格 `<120s` 门。

`src/polyarb/storage/l3_evidence_store.py:160-177` 因此从
`l2_top_of_book` 读取 Yes token 最新的非空 `mid_price` 源时间。字段仍叫
`yes_ohlc_at`，但精确定义是“最新 OHLC 源观测”。T+6 到 T+24 的累计覆盖仍查询
`l2_ohlc_1m`，所以 freshness 修正不会凭空制造 OHLC bucket coverage。

### Q：sampler 为什么启动时可以跳过几格，却不能吞掉后续采集失败？

promoter 与 sampler 是 sibling tasks；冷启动时 sampler 可能先抢到 seq 0，而五市场、
十 token 的 desired mapping 尚未建立。此时“五对映射不足”是输入尚未初始化，不是 writer
故障。若把它记成 `evidence_writer_failed`，每次部署都会靠任务调度运气决定 boot 是否可用。

`src/polyarb/observation/l3_sampler.py:391-427` 只在 `desired != 10` 时推进到下一个
boot-grid boundary，不写样本也不伪造事件。一旦 desired 精确为 10，committed/evidenced
未收敛仍会形成正常的失败 health sample；aggregate read、mapping、slot 或 append 异常也
继续留下原有 fail-closed 证据。跳过的启动格永远不能当 T0，readiness 还必须另取连续
12 个 passing samples。

### Q：为什么 checkpoint 不能从历史命令里拼一个 Pooler DSN？

DSN 也是生产身份的一部分。Supavisor 的 endpoint 必须来自**当前项目**的 Dashboard
Connect 原文，username 采用 `[USER].<project-ref>`；一个“看起来属于同一 region”的旧
hostname 不能证明 tenant 正确。`Tenant or user not found` 也不能单独判断到底是 endpoint
还是 user 错。

因此 operator 在生成不可变报告前必须先跑 target/user/TLS/capability proof。本项目的
自定义 runtime LOGIN 已有直连 IPv6 实测证据，所以 checkpoint runner 使用
`db.<exact-ref>.supabase.co` 与裸 runtime role，并在进程内临时组装 DSN。错误 Pooler
preflight 在 not-before 之前被终止、且没有创建文件，不能被后续 PASS 悄悄抹去。

同理，checkpoint 的 path/start/end 也不能从 checkpoint 名手拼。A5 manifest 对 T+6
声明的是 `...-T6.json`，不是 `...-T+6.json`。等待 runner 必须从 immutable manifest
读取三者并核对，manifest 才是真正的执行契约，而不只是事后验 hash 的附件。如果等待器
只支持整数 epoch，必须对带微秒的 not-before **向上取整**；向下截断会留下不足一秒的
提前执行窗口，即使 CLI 还有第二层拒绝也不应依赖它。

最后，生成报告的本地 verifier 也属于证据语义。runner 应确认当前 `src/`、`scripts/`、
migration、Makefile 与 dependency locks 相对 manifest 的 deployed SHA 没有变化；允许
planning/docs/report artifact 前进，但不能拿后来修改过的判定代码给旧生产 binary
签名。只比较两个 commit 还不够：到点执行前也要要求 worktree 完全干净，覆盖 staged、
unstaged 和 untracked 文件，防止本地 import shadow 改变 verifier 行为。

### Q：`websockets.connect(ping_interval=10)` 为什么仍会被 Polymarket 断开？

因为这里有两层名字相同、协议不同的 heartbeat：

- `websockets` 的 `ping_interval` 发送 RFC WebSocket **Ping control frame**；
- Polymarket CLOB market/user channel 要求每 10 秒发送一个 **text frame**
  `PING`，并用 text frame `PONG` 回复。

前者不能替代后者。A5 中 generation 6/8/9 分别只建立了 7/2/7 个
current-generation depth evidence，随后连接又重建；这不是 sampler 可以忽略的瞬时
噪声。正确修复点在连接 owner：每个 socket 建立一个可取消的 text-PING task，
receive loop 在 JSON decode 前过滤精确 `PONG`，所有退出路径都清理 task。协议层 Ping
可以继续作为独立的 TCP/WebSocket liveness 探针，但命名和测试必须明确区分。

为什么不能“重连附近的样本不算”？因为严格 ledger 的问题正是证明每个 30 秒槽的真实
membership。A5 seq 201/216/217 已经永久记录为 fail；四个后续 checkpoint 必须取消，
修复后只能用新 boot、新 readiness 和唯一 A6 manifest 从头计时。

### Q：既然 promoter 和 WebSocket 都在 daemon 启动，为什么 run 0 还会失败？

“都创建了 task”不等于“WebSocket 一定先初始化完成”。`l2_main` 创建的是两个 sibling
task，event loop 可以先调度 promoter。release 68 就在这个窗口里先读取 generation 0，
随后 WebSocket 初始化发布 generation 1；严格终态行因此正确地记录
`generation_changed`，而不是把启动竞态伪装成成功。

修复不是给 run 0 加 sleep，也不是把 `generation_changed` 改成可忽略。`WsConsumer`
现在暴露只读的 `has_active_connection`，其真值直接来自成功初始化后才发布的
`_current_ws`；promoter 在每个 boot 的第一轮之前可取消地等待这个事实。等待期间：

- 保留 run 0 原始 `scheduled_at=boot_started_at`，实际延迟仍可由 `started_at` 看见；
- stop/cancel 不制造 terminal row；
- 永远连不上时，readiness 因缺失 promoter truth 而拒绝该 boot；
- 首轮开始后，所有 generation change 仍按原来的严格失败语义处理。

这条边界的核心是：启动前置条件可以延迟**第一次尝试**，但不能改写已发生尝试的终态。
release 68 已有失败行，所以永久拒绝；修复只能部署为新 release、新 boot，再重新通过
两轮 promoter 和 12 个 sample 的 readiness。

### Q：quiet refresh 少一个 book，为什么不能直接断开重连？

因为“控制命令是否明确”和“业务证据是否完整”是两种不同的不确定性：

- unsubscribe/subscribe 发送失败、socket 身份变化或任务取消，意味着 wire membership
  不再可证明，必须关闭该 generation 并重新收敛；
- 同一 generation 的最终 subscribe 已明确成功，但 25 秒内少一个成功写入 depth 的
  book，只能证明业务证据缺失，不能推出 socket membership 已损坏。

旧实现把第二种情况也送进 compensation。新连接的十个 token 尚未自然收敛时，60 秒
quiet gate 又立即刷新，因而把一次间歇性少 book 放大成持续 reconnect loop。现在
`src/polyarb/daemon/ws_consumer.py:686` 使用两阶段 barrier：第一次刷新后等待 8 秒，
再只对 waiter 中仍缺失的 token 重订，并继续使用总计 25 秒的预算。

若最终仍超时，`src/polyarb/daemon/ws_consumer.py:844` 只保存
`missing_assets + generation` 并返回失败，不伪造 freshness，也不关闭健康 socket。
下一次到期刷新只处理这个集合；真实 depth write 进入
`record_book_evidence`（`src/polyarb/daemon/ws_consumer.py:536`）后会自然移除对应身份。
控制发送、generation identity 或 cancel 失败仍走原 compensation 路径。

冷启动还有单独的 60 秒收敛宽限（`src/polyarb/daemon/ws_consumer.py:853`）：
它只是推迟第一次 quiet refresh，不会补写缺失样本或降低 10/10/10 验收条件。
