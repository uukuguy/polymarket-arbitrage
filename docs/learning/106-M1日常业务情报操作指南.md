# M1 日常业务情报操作指南

## 30 秒业务心智模型

M1 只观察，不交易：`Structure → Quote → 认证机会 → 资格/异常证据`。
每天先证明读数可信，再判断有没有值得交给 M2 研究的候选；认证机会不代表成交、收益或 P&L。

## 每日三步

1. `make smoke-control-plane-prod`：公共入口是否能读取权威；200/available 不是机会结论。
2. `make control-plane-business-brief`：每日默认的一屏业务结论；它读取线上一次
   `BusinessOverviewV1` 原子快照，不会交易、下单或修改 M1 数据。
3. 需要审计或排障时，再下钻到 `make control-plane-status limit=20`、
   `make control-plane-capacity` 和 `make control-plane-opportunities limit=50`；后者分页时传 `after_group_id=`。

### 三层阅读：默认结论、自动日报、审计真值

- **默认 text**：运行 `make control-plane-business-brief`。它给出业务结论、Structure、
  Quote、Analysis、认证机会与业务阻塞；运行异常与恢复只在 `/control-plane` 审计。
- **JSON 自动化**：运行 `make control-plane-business-brief format=json`。这和默认 text
  来自同一份摘要，可作为自动日报的稳定输入；不要在脚本中重新计算 edge、收益或风险评分。
- **审计下钻**：当摘要显示资格暂停、升级或异常时，读取原始的
  `control-plane-status`、`control-plane-capacity` 与 `control-plane-opportunities` 输出，核对
  漏斗、完整机会页、生命周期与容量证据。简报只显示最多 5 个机会候选，审计命令才保留完整页。

任一简报权威读失败时，命令非零即表示**业务数据不可用**。这不是“暂无认证机会”，也不能
用旧的 text/JSON 输出继续做自动日报。

固定按北京时间执行：每天 `08:30` 跑完整三步作为日基线；`09:00–23:00` 的活跃会话每 `15` 分钟复查 `status`、`capacity` 与 `opportunities`（即 `:00/:15/:30/:45`）。这只是观测节奏，不会触发交易、下单、部署或修改 M1 数据。

以下情况**立即升级**为观察故障：任一命令非零、HTTP 503、`status=unavailable`，或 `.open_incidents` 出现未关闭的 P1/生产者 incident。保留 brief 和必要的审计命令输出及时间戳，先核对 incident、runtime incident、watchdog 与 recovery action；绝不把它写成零机会或交易信号。其余状态按连续样本处理：同一 `freshness` 停滞、同一 `eligibility_state=paused`、或同一未完成 recovery action 连续 `2` 个活跃会话样本（`30` 分钟）才升级；`.runtime_watchdog` 的同类异常连续 `2` 个样本同样升级。中间有一次恢复/推进即重新计数。

## 一眼摘要：只读业务状态

下面命令只从 `control-plane-status` 的顶层业务路径提取摘要，不会交易、下单或修改 M1 数据：

```bash
make control-plane-status limit=20 | jq '{
  Structure: .structure,
  Quote: .quote,
  qualification: .qualification,
  incidents: .open_incidents,
  runtime_incidents: .runtime_incidents,
  recovery_actions: .recovery_actions,
  watchdog: .runtime_watchdog
}'
```

Structure 和 Quote 用于判断市场覆盖及报价推进；qualification 用于判断当前是否具备解释机会的资格；`.open_incidents` 是当前仍开启的业务/生产者 incident，`.runtime_incidents` 是运行时生命周期的事件记录，`.recovery_actions` 给出已排队、执行中或完成的恢复动作，`.runtime_watchdog` 给出独立看门狗近期检测与恢复证据。摘要中的任何异常都只触发 M1 观察升级，不构成交易动作。

## 结论矩阵

| 看到的状态 | 日报结论 | 下一步 |
| --- | --- | --- |
| `status=available` 且 `current_opportunity_count>0` | 有认证机会 | 记录 group、edge、容量；仅作为 M2 研究候选 |
| `status=available` 且 count=0 | 暂无认证机会 | 正常记录，不报故障 |
| `eligibility.state=paused` | 资格暂停 | 记录 `reason_code`，继续研究最后已知产品，等待资格推进 |
| `analysis.status=available` | 研究漏斗可读 | 记录 Structure → Quote → Certified 的同 lineage 数量；candidate/reject 未持久化时不得自行推算 |
| `analysis.status=lagging` | 研究漏斗代次不一致 | 只做历史研究，等待同 lineage Quote 或机会产物 |
| `database_capacity.state=warning` | 存储进入预警 | 检查最大关系、增长率与保留策略；不得新增无界明细 |
| `database_capacity.state=critical/exhausted` | 存储风险 | 暂停会放大存储的生产动作，按容量预案处置 |
| HTTP 503 或 `status=unavailable` | 业务数据不可用 | 不写零机会，按 incident/watchdog 排障 |

## 可记录的业务数据

- Structure：市场覆盖范围、当前 generation，以及该 generation 是否已完成。
- Quote：当前 pointer、对应 generation、推进时间与 freshness；它证明报价可用于当前观察，不能证明可成交。
- 研究漏斗：同一条 lineage 的 Structure records、Quote records 与同代 Certified opportunities；它说明数据从市场宇宙到报价、认证结果的覆盖，不是 candidate/reject 决策明细。
- 认证机会：`count`，以及值得跟进的 group、event、edge、size。它们是交给 M2 研究的候选，不是订单。
- 容量：`make control-plane-capacity` 的 state、used percent 和最大关系；容量 warning 也是业务观测的一部分，因为无界存储会让后续情报不可用。
- qualification：资格状态与 `eligibility_reason`，用来区分“没有机会”和“当前不具备判断机会的资格”。
- `.open_incidents`：当前异常是否仍开启，以及影响范围；它是即时升级的主要证据。
- `.runtime_incidents`：运行时检测到的生命周期事件；与 `.open_incidents` 一起区分“当前故障”和“已记录的运行时事实”。
- `.recovery_actions`：恢复请求的状态、开始/结束与结果；连续两个样本未完成才按上述 30 分钟规则升级。
- `.runtime_watchdog`：独立检测、重启/恢复与近期事件；连续两个同类异常样本才升级。

### Quote 换代后的容量断言

Quote 在生成候选代际时会暂存研究行，因此换代过程中容量可以短暂上升；候选行不会被 Dashboard
读取。一次 Quote 认证完成后，运行 `make control-plane-capacity` 并核对：当前业务快照只有一个已发布
Quote generation、`m1_business_quote_staging_rows` 没有残留行、容量状态回到 `healthy`。认证完成后仍为
`critical` 或 staging 有残留，不属于正常波动，按存储故障升级，不能继续让后续采集放大占用。

## 不要据此下的结论

- 简报中的认证机会不代表成交、收益或 P&L，也不构成真实资金下单授权。
- HTTP 200 只说明公共读取入口可达；它不说明行情新鲜、策略可执行或存在套利。
- `opportunities.status=available` 且 `count=0` 是暂无认证机会；资格暂停说明当前不能把
  该读数升级为可执行结论，但它不是数据不可用。
- edge 和 size 是观察投影，未计入实际订单簿冲击、费用、下单延迟、撤单和对手方风险。

## 代码地图

- `src/polyarb/control_plane/api.py:34`：严格 readiness 的只读公开入口；每日第一步从这里确认控制面权威读取是否可达。
- `src/polyarb/control_plane/api.py:61`：认证机会的只读分页入口；只有 `status=available` 且 `count=0` 才是实际零机会。
- `src/polyarb/control_plane/api.py:95`：`/perception/business-overview` 的只读公开入口；brief 和 Dashboard 都从这里理解同一快照。
- `src/polyarb/control_plane/postgres.py:8809`：单事务 `BusinessOverviewV1` 持久化读模型；产品状态、generation 与 count 必须从这条权威投影理解。
- `Makefile`：把生产巡检收束为只读目标，避免临时拼接 URL、secret 或写操作。

## 设计取舍

日报把“可读”“零机会”“资格暂停”和“不可用”分成四个结论，而不是用一个绿/红状态压平。当前线上快照例如可出现 `opportunities.available + count=0` 与 `eligibility.paused / not-yet-qualified`：前者是可信市场观察，后者限制其业务消费范围，二者都不是 503。

机会列表只记录有限、可复查的候选字段。记录 group/event/edge/size 足以让 M2 复核，同时不把 M1 扩展成交易、收益归因或持仓账本。

## 自检题

1. `status=available` 且 count 为零时，为什么不应创建 incident？
2. `eligibility_state=paused` 时，为什么不能把机会 count 当成“零机会”写入日报？
3. 看到 HTTP 503 时，应优先查哪两类生命周期证据？
4. 为什么 group、edge、size 只能成为 M2 研究候选，而不能成为 P&L 结论？

## FAQ 增量

### 为什么先跑 smoke，再读 status 和 opportunities？

先确认公共入口正在读取权威，brief 的业务解释才有共同前提。smoke 成功仍不是机会结论，
所以要继续读 brief；只有需要核验原始事实时，才下钻到 status 与 opportunities。
