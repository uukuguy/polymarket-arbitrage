# M1 生产恢复边界

## 30 秒心智模型

M1 生产恢复不是“进程重新启动了”，而是三条完整事实链重新成立：

```text
Structure complete ─▶ Quote certified ─▶ opportunity HTTP 200
L2 candidate set ───▶ 5 markets / 10 tokens ─▶ durable evidence 10/10/10
failure detected ───▶ alert ─▶ recovery fact ─▶ one recovery notification
```

任意一条只停在内存状态、日志或降级标签，都不能代替链尾证据。

## 这次生产故障的四个边界

### 1. 成功边界要早于 housekeeping

Quote 完整认证和机会投影完成后，公共 feed 已经可用。历史清理、observer ledger 和
Telegram 是后续副作用；它们可以有自己的失败计数与告警，但不能让可用 feed 长期
留在 `collecting`。

关键实现：`src/polyarb/daemon/quote_worker.py` 的成功路径先
`publish_certified_feed()`、`mark_success()`，再执行有界 retention。

### 2. PostgreSQL 类型进入 SQLite 前必须显式适配

`asyncpg` 把 `NUMERIC` 解成 `Decimal`，把 `TIMESTAMPTZ` 解成带时区
`datetime`。SQLite 不接受 `Decimal`，旧时间转换器也把 `datetime` 变成
`NULL`。结果不是异常，而是 L3 recipe 的一小时条件把 110 行全部过滤掉。

修复后的适配器同时转换两种类型。测试必须读取并断言 `ts`、价格、深度，而不能只
证明 INSERT 没抛异常。

### 3. price-only 帧不能抹掉 book 深度

Polymarket 的 `book` 帧带 bids/asks，后续 `best_bid_ask` 只带价格。latest-row
查询若让后者写入 `NULL depth`，promoter 就会把真实厚盘口当成无深度。L2
coalescer 因而按 asset 保存最近一次真实 depth，价格帧继承它，直到新 book 替换。

### 4. 触发节拍不是陈旧 SLA

生产 Quote 尝试从 120 秒缩短到 60 秒，但硬 SLA 仍是 300 秒：

- 60 秒：何时尝试启动下一轮；
- 240 秒：旧报价预警；
- 300 秒：停止把它作为可成交输入。

缩短节拍是在增加恢复余量，不是在放宽“新鲜”的定义。

## 生产验收读法

```bash
make smoke-health-prod
make smoke-market-truth-prod
make diagnose-arb-feed-prod min_edge_bps=0
make scan-arb-live min_edge_bps=0
make smoke-l2-health-strict-prod
make polywatch-resident-status
```

L1 需要 strict HTTP 200、完整 market truth 和合法机会 payload。L2 需要 5/5
market、10/10 mapping/desired/committed/evidenced，以及连续 durable samples。
Polywatch 则需要同时证明首次告警、去重和一次 recovery，而不是只看 cron 存活。

## 当前仍开放的设计门

Structure 新版本发布后，旧实现立即让前一版机会 feed 503，直到新 Quote 完整提交。
生产实测窗口为 93 秒。推荐的一版本双缓冲只会继续服务仍小于 300 秒的**完整旧
revision**，并标记 `refreshing`；新完整 revision 原子替换它。任何 partial、
混合 revision 或超过 SLA 的数据仍 fail closed。

这是可用性与一致性的产品政策，必须显式批准，不能靠临时改 health 状态偷偷实现。

## FAQ 增量

### Q：顶层 health 是 warn，是否一定不能使用？

不一定。要读命名子检查和具体接口合同。归档未启用、WS 安静等 warn 可以与 strict
HTTP 200 共存；Quote 超过 300 秒、L3 证据不收敛或机会接口 503 则不能解释为可用。
