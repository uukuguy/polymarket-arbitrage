# 精确现金账本：价格可以近似，钱必须有唯一答案

> Phase 5 / H-003。目标不是把所有 `float` 消灭，而是让你能一眼判断：
> 哪些数只是市场估计，哪些数一旦写入账户就必须可逐 micro 对账。

## 30 秒心智模型

把系统想成两块仪表：

- **雷达屏**：价格、概率、预期滑点。它们不断变化，允许用 `float` 做快速排序。
- **收银机**：余额、stake、费用、已实现 PnL。它必须回答“到底有多少个最小货币单位”，所以只认整数 micro-pUSD。

`1 pUSD = 1_000_000 micros`。外部传进来的 `0.1` 会在收银机入口量化一次为
`100_000`；以后账户加减只对整数操作。CLI 最后仍可显示 `0.1`，但显示值不再是账本真相。

```text
价格 float ── Decimal(str(price)) ──┐
                                    ├─ 计算一次 PnL ─► Money(micros)
stake 输入 ── HALF_EVEN 量化 ──────┘                    │
                                                        ├─ SQLite INTEGER
                                                        └─ tagged receipt
```

## 为什么不是 `Decimal(float_value)`

`float` 的二进制展开不是用户看到的十进制数。`Decimal(0.1)` 会把那串二进制误差
完整保留下来；`Decimal(str(0.1))` 得到用户/协议表达的 `0.1`。

```python
# src/polyarb/routing/money.py:25
decimal_value = Decimal(str(value))
micros = int(
    (decimal_value * MICROS_PER_PUSD).to_integral_value(
        rounding=ROUND_HALF_EVEN
    )
)
```

`ROUND_HALF_EVEN` 的意义不是“金融世界永远这样舍入”，而是给当前 paper model 一个
集中、可测试、无长期单向偏差的规则。未来 venue 明确返回实扣费用/成交现金时，venue
truth 覆盖 modeled PnL，而不是再猜另一套 rounding。

## Position 为什么同时看见 `stake` 和 `stake_money`

`stake_money` 是 authority；`stake` 是兼容投影。

```python
# src/polyarb/routing/position_tracker.py:80
@property
def stake(self) -> float:
    return self.stake_money.to_float()
```

旧调用者仍能展示、格式化和生成 JSON，不需要一次性改完整个 M2。但风险判断不能把
`stake` 拿回来相加；它必须使用 `stake_money.micros`。这就是 migration seam：内部先
变正确，外部接口逐步演进。

## 为什么 receipt 不能直接存 JSON 整数

JSON 里的 `true` 在 Python 中还是 `int` 的子类；裸 `10000000` 也无法说明它是 micros、
分还是 pUSD。新 receipt 因此带类型标签：

```json
{"kind":"money","micros":10000000}
```

codec 要求 key 集合恰好是 `kind/micros`、`micros` 的类型恰好是 `int`（不是 bool），并
验证 signed 64-bit。Phase 4 已有的 `true`、`false`、float、`null` 仍按原类型读取，历史
不会被重写。未知 tag 或多一个 `extra` 字段都会 fail closed。

## SQLite 迁移为什么保留 REAL 列

这次采用 additive migration：在同一个 `BEGIN IMMEDIATE` 中新增 `*_micros`、从旧 REAL
量化 backfill、验证 `typeof(column) == 'integer'`，然后提交。失败则 ALTER 和 backfill
一起回滚。

旧 REAL 暂时保留为**派生投影**，方便旧诊断工具继续查看；每次写入都从 Money 生成它。
读取和风险计算只看 INTEGER。这样没有 flag day，也不会出现“两套 authority”。删除
REAL 是未来 schema cleanup，不和本次风险修复绑在一起。

一个容易忽略的防线是：不仅启动时验证，`load()` 也验证 SQLite 动态类型。否则有人把
`balance_micros` 改成 `1.5`，Python 的 `int(1.5)` 会静默变成 `1`，精确账本反而制造
假精确。

## 设计取舍

1. **没有把 price 全改定点数**：price 是估计/排序输入；现金在落账边界量化，范围清晰。
2. **没有只加 epsilon**：epsilon 只能掩盖比较，不能生成可审计 receipt。
3. **没有立刻删 REAL**：可回滚迁移优先于 schema 美观；INTEGER 已是唯一读 authority。
4. **没有把 live order wire 混进来**：tick size、签名 amount、venue fee truth 是下一条
   独立 chain，需要真实 SDK/账户证据。

## FAQ 增量

### Q1：既然最后 CLI 还是 float，精确化有什么意义？

CLI float 是一次只读投影。幂等判断、余额更新、风险门、SQLite 和 receipt 在转成 float
之前已经完成；展示误差不会反向进入下一笔账。关键不是“任何地方都看不到 float”，而是
“float 永远不能成为账户 authority”。

### Q2：micro-pUSD 会不会溢出？

`Money` 构造时强制 signed 64-bit，对应约 9.22 万亿 pUSD，远高于当前 paper account，
但仍在任何 SQLite 写入前 fail closed。不能依赖 Python 大整数无限扩张后到数据库才炸。
