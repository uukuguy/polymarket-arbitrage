# 89. 数据库能力角色与进程身份

## 30 秒心智模型

`LOGIN role` = who connected and whose password can be rotated/disabled.
`Capability role` = the reviewed bundle of allowed database actions.
`Startup contract` = proof that effective authority and namespace resolution are neither missing nor broader than expected.

这次 Plan 05.6-207 把两个常驻进程拆成四个数据库身份：runtime controller 和
qualification worker 各有一个可登录角色、一个不可登录能力角色。登录角色只负责连接、
轮换密码、被 `NOLOGIN` 停用；能力角色承载经过 review 的表、函数和 sequence 权限。进程
启动时先证明自己连接的是指定数据库、指定 login、指定 capability，而且没有继承到多余
权限，然后才允许工作。这里的“没有多余权限”不是检查几个已知反例，而是枚举全部
非系统 namespace 的完整安全包络：每个 relation/sequence/routine 的有效权限与所有权、
数据库 CREATE、active/role/database search path，以及 PostgreSQL 16 会员关系的
`admin_option`/`inherit_option`/`set_option`，再与闭集 allowlist 比较。权限检查之外，
两个 daemon 的应用 SQL 全部显式写 `public.`，因此对象解析本身也进入契约。

## 能力角色 vs 登录角色

能力角色是“可审查的权限包”。revision 026 创建：

- `m1_runtime_controller_capability`
- `m1_qualification_worker_capability`

它们必须没有登录能力、不能继承别的角色、不能建库/建角色/复制/绕过 RLS。这样 review 时看的不是某个会被轮换密码的账号，而是一组稳定 capability。

登录角色是“进程身份”。operator tooling 创建或轮换：

- `m1_runtime_controller_login`
- `m1_qualification_worker_login`

它们必须 `LOGIN INHERIT`，且只继承自己的 capability。密码可以轮换，角色可以被 `NOLOGIN` 禁用，但不应该被手工加到别的 capability 或 elevated role。

## 闭集权限：正权限和完整负空间

runtime controller 的正权限很窄：能读 runtime/job/circuit/budget/action 状态，能写 controller lease 和 observe decision。对应代码是 `db_role_contract.py:23` 到 `db_role_contract.py:36`，migration grant 在 `026_m1_runtime_scoped_roles.py:133` 到 `026_m1_runtime_scoped_roles.py:143`。

runtime controller 的负权限同样重要：不能写 `m1_recovery_actions`，不能执行 qualification ingress/certificate 函数，不能碰 public schema 里的任何 sequence。review 后的 verifier 在 `db_role_contract.py:229` 到 `db_role_contract.py:232` 调用 sequence deny，具体 public sequence 枚举在 `db_role_contract.py:509` 到 `db_role_contract.py:534`。

qualification worker 的正权限是读 qualification/publication truth、写 source cursor/epoch/recovery observation，并执行 freshness wrapper 与 certificate inserter。对应 profile 在 `db_role_contract.py:145` 到 `db_role_contract.py:157`。

qualification worker 的负权限是不能直接 insert ingress ledger、不能使用 ledger identity sequence、不能执行 general ingress 或 hardened trigger functions。它只通过 `public.m1_record_qualification_freshness_ingress(...)` 写 freshness fact；业务代码调用点在 `qualification_service.py:582` 到 `qualification_service.py:594`。

闭集契约解决了“未命名权限”问题。例如后续在非 public schema 新建了一张无关表，
数据库通过 PUBLIC 给了 CREATE，或者 capability 因为额外会员关系间接
获得 `l3_retention_cleanup` 这类 SECURITY DEFINER 的 EXECUTE，它们都会被 catalog
枚举发现，即使原来的正权限仍然存在也不会放行。对预存 capability role，
migration 和 admin preflight 还要求没有任何非预期的 incoming/outgoing membership、
application object ownership 或 direct ACL；provision 后 incoming member 必须恰好是匹配的
login，不能再有第二个成员，并且会员选项必须精确为
`ADMIN FALSE, INHERIT TRUE, SET TRUE`。

## DSN 是进程能力的一部分

operator 的 preflight/provision/disable 只从
`POLYARB_CONTROL_PLANE_DB_ADMIN_DSN` 连接；runtime controller 只从
`POLYARB_SUPABASE_DB_DSN` 连接；qualification worker 只从
`POLYARB_QUALIFICATION_DB_DSN` 连接。CLI reader、verify、Fly template/process 和
runbook 都使用这三个不重叠的映射。不要为“兼容”往 Fly 里装 alias；每个 app 只能拿到
自己的 scoped credential，admin DSN 不进入任何 app。

DSN 也不能自带 `options=-csearch_path=...` 或 `search_path=...`。reader 在连接前拒绝
这类 override，再由 connection factory 固定 `pg_catalog,public`。这条检查必须早于任何
SQL，否则“启动 verifier 会拒绝”仍可能已经在错误 namespace 中执行了查询。

## Namespace 与 TEMPORARY 的取舍

只检查 `public.some_table` 的 ACL 不够：PostgreSQL 默认 search path 可能把 `"$user"`
schema 放在 `public` 前面。如果 login 预先拥有同名 schema，而业务 SQL 没有限定 schema，
看似精确的 public 权限仍可能读写 shadow table。

这次选择是：持久应用对象全部 schema-qualified；拒绝 database CREATE、非系统 schema
的所有权/权限、role/database/DSN search-path override；连接时固定受控 path。数据库
`TEMPORARY` 则明确保留，因为原四个应用可能依赖 PostgreSQL 默认的临时表能力。它不是
“没检查到”，而是一个有文档、有测试的兼容性 allowance；临时 namespace 不能改变已经
schema-qualified 的持久对象解析。

## SECURITY DEFINER / search_path threat

`SECURITY DEFINER` 的价值是让低权限 caller 触发一段受限写入：qualification worker 不直接拿 ledger INSERT，却能通过 wrapper 写 freshness fact。风险是 search-path hijack：如果函数体里写未限定对象名，攻击者可能通过自己的 schema 放同名函数或表影响 definer 权限下的执行。

revision 026 的防线有三层：

1. definer 函数固定 `SET search_path = pg_catalog`，例如 freshness wrapper 在 `026_m1_runtime_scoped_roles.py:410` 到 `026_m1_runtime_scoped_roles.py:418`。
2. 应用对象用 `public.` schema-qualified 名称，例如 wrapper 最终调用 `public.m1_record_qualification_ingress`，见 `026_m1_runtime_scoped_roles.py:433` 到 `026_m1_runtime_scoped_roles.py:436`。
3. trigger/certificate/general ingress 的 ambient EXECUTE 被从 `PUBLIC`、Supabase fixture roles 和两个 capability roles 撤销，集中在 `026_m1_runtime_scoped_roles.py:250` 到 `026_m1_runtime_scoped_roles.py:270`。

这不是“给函数加 definer 就安全”。真正的契约是：definer 只暴露 bounded wrapper，wrapper 只接受闭集 product identity 和 bounded payload，ambient caller 不能绕过 wrapper 去执行更通用的内部函数。

## Release / Config Identity

DB 权限只证明“谁能做什么”，不能证明“当前进程运行的是哪次发布和哪组配置”。qualification worker 还必须绑定 release/config identity：

- release id 必须是 40 位 lowercase Git SHA，验证在 `qualification_identity.py:92` 到 `qualification_identity.py:95`。
- config payload 固定 policy version、86,400 秒窗口、900 秒 max gap、role order、observe-only recovery mode 和 allowlist，生成在 `qualification_identity.py:35` 到 `qualification_identity.py:57`。
- config digest 用 deterministic JSON 和 `sha256:`，见 `qualification_identity.py:60` 到 `qualification_identity.py:68`。
- runtime env 提供的 digest 用 `hmac.compare_digest` 对比，见 `qualification_identity.py:103` 到 `qualification_identity.py:105`。

rollout renderer 只产出本地 artifact。`rollout.py:125` 到 `rollout.py:176` 把 artifact version 10、revision 026、两新 app、observe-only、空/显式 allowlist、release id 和 config digest 写进 checklist；`cloud_actions_performed` 保持 false。

## FAQ 增量

**Q: 既然 capability role 是权限包，为什么不让进程直接用 capability role 登录？**

A: 因为密码生命周期和权限审查生命周期不同。登录角色承担连接和轮换，能力角色承担 reviewed authority。这样 rotation/disable 不会改权限包，权限 review 也不会绑定到某次密码。

**Q: observe-only 写数据库，会不会已经算 mutation？**

A: 它是受控证据 mutation，不是 recovery mutation。observe-only 只写 controller decision/idle 事实，用来证明 controller 判断链在生产持续运行；它不得创建 recovery action、不得重启进程、不得改 pointer。

**Q: 为什么 final production next action 是 authorization package，而不是直接 `make control-plane-render-rollout`？**

A: 因为生产现在只到 revision 025，两个新 app 和两个 scoped login 还不存在。render-rollout 是本地 artifact 生成；真正生产步骤需要先把 release SHA、数据库、migration、login role、app、allowlist、rollback、evidence directory 写成一份可审计授权包。
