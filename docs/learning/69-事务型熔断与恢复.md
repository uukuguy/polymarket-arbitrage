# 事务型熔断与恢复

## 30 秒心智模型

M1 不是在失败三次后把整套采集停掉，而是只给那个不可变 `job_key` 记一张
电路卡。失败事实、下一次 probe 时间、incident 和告警 intent 在同一 Postgres
事务落库；成功的终态工作再以同一个 lease epoch 关闭卡片并写 `recovered`。

```text
current lease failure → retry + circuit + incident/outbox (one transaction)
current terminal success → circuit reset + incident resolved + recovery outbox
```

## 代码地图

- [014 migration](../../alembic/versions/014_m1_transactional_circuits.py)：每个
  `job_key` 一行 circuit，不存在全局 breaker。
- [retry transition](../../src/polyarb/control_plane/postgres.py:2545)：延迟固定为
  15、30、60、120、240、300 秒；第三次失败才进入 `open`。
- [recovery transition](../../src/polyarb/control_plane/postgres.py:2700)：终态
  `succeeded` 加 lease epoch 是恢复的围栏，旧 worker 无法“假恢复”。
- [operator snapshot](../../src/polyarb/control_plane/postgres.py:2790)：只读 API
  显示有界 `open_circuits`，不依赖 SQLite 或 worker 内存。

## 设计取舍

这里刻意没有 jitter，也没有跨作业的总开关。前者让测试和故障复盘可重放；后者
避免一个 Gamma/CLOB 局部问题把不相关的 Structure 或 Quote job 一并暂停。五分钟
上限保证持续故障不会以越来越长的盲区隐藏，但也不会形成紧循环。

成功不是“日志里没报错”。只有 durable receipt/finish 已提交、并且仍对应当前
lease epoch 时，才会 resolve 那一个 `job-retry:<job_key>` incident 并产生 recovery
outbox intent。
