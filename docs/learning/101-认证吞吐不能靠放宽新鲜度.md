# 认证吞吐不能靠放宽新鲜度

## 30 秒心智模型

Structure certifier 要把每个规范化 range 与原始 shard 做内容一致性校验。生产中的
1,088 个 range 串行跑了约 24 分钟，这是真实容量缺陷，但后续时间线取证也纠正了一个
重要误判：qualification 的 900 秒从 Structure **发布**开始计，发布前的 parity 并没有
消耗这个窗口。因此本优化提高整体周转与恢复速度，但不单独宣称修复资格新鲜度。

正确模型是：一个 certifier lease 仍是唯一提交者，但 lease 内可以并行做只读、无副作用的
R2 parity。只有一个完整 wave 全部成功后，主线程才推进 progress；只有到达 durable
checkpoint 边界后，才提交前缀证明。并发提升吞吐，不改变发布权威。

## 为什么 wave 必须与 checkpoint 对齐

假设 checkpoint 每 25 个 range 提交一次，并发度是 12。若一个 wave 从 20 跑到 31，
失败后无法诚实地声称 25 已完整验证，也无法只重放 26–31。实现因此把这一波截成
20–25，再从 26 开新 wave。checkpoint 永远表示连续、完整、可重放验证的前缀。

## 为什么一个 lane 失败后要等 sibling 排空

R2 read 已经在线程中开始，Python 不能安全强杀它。若主线程立刻写 retryable，旧线程可能在
新 lease 开始后继续读或抛错，造成“终态已提交但旧工作仍活着”。线程池上下文会先 drain
所有已启动 sibling，再向外暴露第一个按输入顺序确定的错误。失败 wave 最多重读一个并发波次；
已经提交的 checkpoint 前缀不会重读。

## pause 为什么不是生产停机

qualification 的 `freshness.*` 是阻塞计时事实，不是 breaking fact。产品过旧时 epoch 保持
`accumulating + paused`，eligible seconds 不增长；新一致 lineage 发布后同一 epoch 可以继续。
因此生产链照常采集、告警和恢复，只有证据有效秒被扣除。这正是“普通故障不重启 24 小时，
严重身份/完整性缺陷才作废”的运行模型。

## 时间线纠错：不要把发布前工作算进消费窗口

实际生产时间线是 Structure 18:31:15 发布，Quote 18:42:35 发布，Opportunity
18:46:19 发布。Structure→Quote 用了 680 秒，Opportunity 又用了 224 秒，总计 904 秒。
真正超出 900 秒的是发布后关键路径，不是发布前 parity。后续修复见
`102-发布后关键路径决定资格新鲜度.md`。

## 设计取舍

- 不提高 900 秒 SLO：它是产品可用性目标，不是给发布后串行关键路径兜底的 timeout。
- 不创建 certifier 集群：唯一 lease/唯一发布事务保持不变，只并发无副作用读取。
- 不跨 checkpoint 并发：牺牲每 25 个任务边界处少量 lane 利用率，换取精确恢复证明。
- 复用 Structure 容量配置：避免 range worker 是 12、certifier 又出现另一个魔法数字。

## FAQ 增量

### 并发读同一个 boto3 client 安全吗？

这里复用的低层 client 与 Structure range pool 已经在同一进程中受同一并发上限共享；每个调用
只创建独立 response body，没有跨线程 mutation。若以后换成非线程安全 client，必须改成每 lane
client factory，不能把并发降回 1 来掩盖接口契约。
