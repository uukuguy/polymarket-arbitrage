# 生产机会流：为什么“会计算”还不等于“持续可用”

## 30 秒心智模型

机会接口像收银台，quote worker 像每分钟尝试送一次新价签的人。

只有收银台代码，没有人送价签，接口就只能回答 503；这不是“没有便宜货”，而是
“我没有足够新的价格，不能回答”。worker 每 60 秒触发一次完整盘口采集，SQLite 只把
完整的一轮公开给接口。采集失败不会杀死 L1，但成功时间不会被伪造，旧报价超过
300 秒后健康检查和机会接口一起失败。

```text
latest complete + published market truth
          │
          ▼
QuoteWorker（60 秒触发）──公开 CLOB 读取──▶ atomic quote run
          │                                  │
          │ failure: 不刷新成功时间          ├──▶ /arbitrage/opportunities
          │                                  └──▶ /health quote_feed:*
          └── retry next interval
```

## 代码地图

- `src/polyarb/daemon/quote_worker.py`：一次只跑一个采集，按 60 秒触发；上一轮较慢时不并发复制生产者。
- `src/polyarb/daemon/quote_worker.py:159`：只有显式启用时才构造生产 worker，并绑定同一个 `db_path`。
- `src/polyarb/daemon/main.py:67`：L1 主进程创建 worker。
- `src/polyarb/daemon/main.py:108`：HTTP 绑定后启动 snapshot scheduler 和 quote worker。
- `src/polyarb/http/health.py:354`：240 秒预警、300 秒失败。
- `src/polyarb/http/arbitrage.py:30`：接口只读最新完整 run，任何不可用/过期都返回 503。

## 三个时钟

1. **尝试触发 60 秒**：上一轮已收口时多久启动下一次；不是承诺 60 秒内完成全量采集。
2. **预警线 240 秒**：已经错过一次正常节拍，需要运维关注。
3. **硬过期 300 秒**：超过后不能再称为“可成交报价”，接口必须 503。

为什么不把硬过期放宽到 12 小时？因为那只是把旧价改名成新价。市场价格可以在几秒
内变化，系统宁可不回答，也不能拿陈旧 ask 冒充可执行输入。

## 为什么不能放到 Fly cron

L1 的 HTTP `app` 机器挂着 `/data/state.db`，当前 `cron` 机器没有这块 volume。
cron 即使采集成功，接口也读不到它写的 SQLite。更糟的是 cron 只有 256 MB，
2026-07-26 的 snapshot 已经以 exit 137 被杀。

把 worker 放入 L1 app 的核心理由不是“少一个服务”，而是读写必须落在同一本账。

## 失败为什么不会拖垮快照

`QuoteWorker.run()` 捕获普通采集异常，只记录异常类型和失败计数，然后等下次重试。
它不吞 `CancelledError`，所以部署或停机仍能在现有五秒边界内结束。

SQLite complete run 是成功事实。失败 run 不会替换上一轮 complete run：

- 上一轮仍小于 300 秒：接口可以继续读，collector state 发 warn；
- 失败持续到超过 300 秒：durable age 变 fail，接口 503；
- 下一轮恢复：新的 complete run 接管，年龄重新归零。

## 实战操作

```bash
make smoke-health-prod
make diagnose-arb-feed-prod min_edge_bps=0
```

先看 L1 `/health`：

- `quote_feed:last_complete_age_seconds < 240`：报价节拍正常；
- `240–300`：旧 run 尚在硬 SLA 内，但 worker 已经漏了一拍；
- `>300` 或 `null`：停止使用机会 feed；
- `quote_feed:collector_state=error`：看最近错误类型和日志，但不要手工制造零机会。

再看诊断输出：

- `available-zero`：在当前完整、新鲜、已知 universe 内没有满足阈值的 gross edge；
- `available-opportunities`：有观察线索，仍需验证费用、滑点、成交、规则和组完整性；
- 任何 503/transport/invalid：不知道机会数，绝不能解释成零。

## 为什么 2026-07-26 的旧验收被撤销

capacity run 1 和生产 run 2→3→4 确实证明了 worker 可以稳定取得当时 universe 的
1,278/1,278 个报价，但那个 universe 来自旧 offset 分页：请求走到第 2,100 行
遇到 HTTP 422 后，客户端把它误写成“正常结束”。因此内部 quote run 虽然原子，
却只是对一个未知子集原子。

Michigan 事件 `111080` 暴露了实质后果：子集里只有两条腿，权威 event 结构却有
33 个成员，且事件是 augmented neg-risk。旧 feed 把两腿 ask 之和当成买齐成本，
报告了虚假的巨大 edge。

新的生产验收必须同时证明：

- `market_truth:coverage=complete/pass`；
- opportunity 顶层 `coverage=verified-standard-neg-risk`；
- 每个候选带 event、membership、source snapshot、universe 与 quote run 身份；
- Michigan 只出现在 `augmented-neg-risk-not-supported` 拒绝统计，永不出候选。

在这组证据完成前，机会 feed 暂停供应 M2。详见
[市场全集不是请求成功](25-市场全集不是请求成功.md)。

## 设计取舍

- **选 app 内 worker**：保证与接口共享 SQLite；代价是与 snapshot 共用一台机器。
- **串行而非并发批次**：生产实测三批只需 1.013 秒，没有必要增加并发复杂度。
- **失败只记异常类型**：健康页足够诊断类别，同时避免把 URL、响应内容或秘密带到公开 surface。
- **默认关闭、生产显式开启**：本地测试不会因为载入设置就意外访问真实 CLOB。

## FAQ 增量

### Q：生产实测 1 秒完成，为什么不每秒采一次？

因为这次 phase 的目标是消除 503 并稳定满足五分钟 SLA，不是建立高频交易系统。
每秒采集会显著增加外部请求、日志和故障面，也没有订单执行端来消费这种频率。
生产全集扩大后，实测 120 秒触发会让保守 quote age 在切换前触及 311.9 秒。
因此触发缩短到 60 秒，但 240 秒预警和 300 秒硬失败没有放宽；这是提高恢复余量，
不是把旧报价改名成新报价。
