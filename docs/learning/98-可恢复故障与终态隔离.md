# 可恢复故障与终态隔离

## 30 秒心智模型

“发生错误”不等于“应该重试”。判断标准是：**再次执行同一个 immutable input，结果有没有
可能改变？**

- 当前 Quote generation 尚未完整：同一输入稍后可能补齐，进入有界 retry/circuit。
- 当前 Quote generation 已经超过 freshness SLA：时间只会继续增加，同一输入永远不会变新；
  应一次性 quarantine，发出 freshness 告警，等待下一代 Quote 产生新 job。
- publication pointer 已被更新：旧输入已被取代，终态 superseded，不影响 qualification。

```text
同一 immutable input 再跑一次能恢复吗？
        | yes                         | no
  retry + backoff + circuit     terminal quarantine/superseded
        |                         保留 incident，不开熔断
  成功后关闭同 job circuit            |
                              successor generation 成功后恢复 incident
```

## 生产事故如何暴露分类错误

一次旧 Quote 的 `opportunity-certify` 在生产中连续出现三次
`StaleQuoteGenerationError`，最终打开 circuit。重试没有读取到“更新后的同一个 Quote”；它每次
仍然认证同一 generation，而这个 generation 的 age 从 301 秒继续增长。因此这不是偶发失败，
而是确定性的终态输入。

原逻辑把 `IncompleteQuoteGenerationError` 和 `StaleQuoteGenerationError` 放在同一个 except
分支。异常类虽然不同，调度语义却被抹平了；这正是“重试耗尽并停摆”的根因。

## 为什么 freshness 告警仍然是 breaking

quarantine 只回答“是否继续调度这个旧 job”，不回答“生产链是否有效”。没有新鲜 Quote 时，
Opportunity 节点确实不可生产，所以 `freshness.quote` incident 保持 open、qualification 仍被阻断。
区别在于系统不再用三次无意义重试制造另一个 circuit 故障。

下一代 Quote 会生成不同的 `opportunity-certify` job key。它成功发布后，既提交新 Opportunity
pointer，也通过既有 recovery chain 关闭 `freshness:quote`。这是由新生产事实恢复，而不是由
重启整窗或人工清数据库恢复。

## 设计取舍

1. **终态 job 与开放 incident 可以并存。** job 表达旧输入不可再执行；incident 表达当前能力链
   仍缺少新鲜上游，两者不是同一种状态。
2. **终态隔离不删除历史 circuit。** circuit 行被原子重置为 closed，事件历史仍保留先前失败，
   既避免控制器继续探测，也不抹除事故证据。
3. **不把 stale 降级为成功。** 没有发布 Opportunity 就不能伪装 succeeded；`quarantined` 明确
   表达该 generation 没有合法业务产出。
4. **攻击测试验证整条 chain。** 测试不止断言异常类型，还验证 job/attempt/runtime event、incident、
   alert outbox、publication pointer、successor recovery 与 disposable DB cleanup。

## FAQ 增量

### 这是否意味着生产出现 stale 就要中断资格整窗？

不意味着重启或丢弃全部历史证据。它会暂停“有效生产秒”的累计并触发预案；新 Quote 与新
Opportunity 恢复后继续观测。只有 release/config 身份改变、数据真值被破坏或无法自动恢复的
代码级缺陷，才需要重新建立资格 epoch。
