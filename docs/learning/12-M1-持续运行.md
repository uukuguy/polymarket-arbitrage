# 12-M1 — M1 持续运行（生产巡检、告警与恢复）

← [11-L3-K线](11-L3-K线.md) | [00-INDEX](00-INDEX.md) | [M1 使用手册](../M1-市场感知平台使用手册.md)

> 这一篇回答一个操作问题：M1 上线之后，怎样判断它今天仍然能为实战提供可信输入。
> 它不是下单手册；M1 只负责发现、报价和观察，不授权交易。

## 30 秒心智模型

M1 不是一个绿色圆点，而是四个必须同时成立的生产面：

```text
L1 快照与报价 ─┐
机会 feed ─────┼─→ Fly 常驻 Polywatch 每 2 分钟巡检 ─→ Telegram 状态变化告警
L2/L3 实时链 ──┤
Dashboard ─────┘
                    GitHub 定时器 ───────────────→ 异地兜底（不作准点 SLA）
```

- **L1** 证明市场 universe、快照归档和独立 quote worker 仍在更新。
- **机会 feed** 证明最新完整 quote run 能按固定 schema 被 M2 读取；合法空列表也是健康。
- **L2/L3** 证明 WS、候选账本、5 个市场/10 个 token 和逐市场持久证据仍在收敛。
- **Dashboard** 证明生产部署入口存在；登录后的页面内容和时间戳仍需浏览器验收。

只有四面都绿，M1 才是“持续可用的决策输入”。这仍不等于机会可交易：返回的是
`gross-before-fees`，没有替你完成费用、滑点、成交、oracle 和资金门控。

## 代码地图：谁写真相，谁负责报警

| 责任 | 代码位置 | 关键事实 |
|---|---|---|
| L1 R2 与 quote health | `src/polyarb/http/health.py:186-270` | R2 看最近 snapshot 的 `parquet_r2_url`；quote freshness 只认最新完整 run |
| quote 时钟与单-run投影 | `src/polyarb/routing/opportunity_scanner.py:15-17,162-200` | `<240s` pass、`240–300s` warn、`>300s` fail；一次扫描不混多个 run |
| L3 旧链与持久证据 | `src/polyarb/http/l2_health.py:795-937` | active count、promote/book 时钟和四个 Phase 05.4 strict evidence 检查共同暴露 |
| 四面巡检决策 | `scripts/polywatch/healthz_watcher.py:302-436` | L1、机会、L2/L3、Dashboard 各自 fail-closed |
| 状态变化与去重 | `scripts/polywatch/healthz_watcher.py:194-294` | 首次故障立即告警、同类故障抑制、30 分钟提醒、恢复只发一次 |
| 一次 tick 与合并告警 | `scripts/polywatch/healthz_watcher.py:444-560` | 四面都先探测，再汇成一条 Telegram 消息并持久化运行态 |
| Dashboard 首响应探针 | `scripts/polywatch/healthz_watcher.py:108-122` | 不跟随重定向，区分 Vercel SSO 与部署不存在 |
| 生产调度 | `crontab:3` | 独立 Fly cron 机器每 2 分钟运行；不依赖 GitHub 是否准点 |

这里最重要的设计是：**顶层状态只是摘要，显式子检查才是操作合同**。例如 L2
可以因为 `WAITING_FOR_EVENT` 显示 `warn`，但只要 WS age 新鲜、L3 正好 10
个 token、四个持久证据检查均为 `pass`，Polywatch 不报警。反过来，
`l3:active_count=8` 即使没把底层 overall 升成 `fail`，Polywatch 仍会报警。

## 每日实战：六条命令

按这个顺序运行，全部是只读或 dry-run：

```bash
make smoke-health-prod
make diagnose-arb-feed-prod min_edge_bps=0
make smoke-l2-health-strict-prod
make smoke-l2-dashboard
make polywatch-healthz-dry
make polywatch-resident-status
```

逐条读法：

1. `smoke-health-prod`：L1 strict `/health`。重点看 snapshot、R2 和
   `quote_feed:last_complete_age_seconds`、`quote_feed:collector_state`。
2. `diagnose-arb-feed-prod min_edge_bps=0`：验证机会 feed 的 HTTP 与 schema。
   `available-zero` 是健康的“当前无机会”；503、无效 JSON 或 schema 错误都不是零机会。
3. `smoke-l2-health-strict-prod`：重点看 cursor、WS age、mirror age、
   `l3:active_count=10` 和四个 `l3:*` strict evidence 检查。
4. `smoke-l2-dashboard`：证明 canonical Vercel 项目路由/认证入口可达。
   它不能证明登录后的应用内容正确。
5. `polywatch-healthz-dry`：用自动值守的同一套决策复核四面，打印决定但不发消息、
   不执行 unpause。
6. `polywatch-resident-status`：确认 Fly cron 机器仍在运行，并查看最近巡检日志、
   当前故障集合、最近告警和恢复状态。

仪表盘的最终人工验收要在**已认证浏览器**中打开 `/status`、`/candidates`、
`/signals`，再从真实候选进入 `/l3/<asset_id>`，确认看到应用内容、真实数据和
近期时间戳。HTTP 302/307 只证明 Vercel SSO/部署存在，不能冒充页面验收。

## 告警怎么读

| 告警面 | 它真正表示什么 | 第一项只读检查 |
|---|---|---|
| L1 snapshot stale | 快照调度超过阈值；这是唯一允许自动 unpause 的路径 | 保存 `/healthz` 的 release、snapshot age、collector 状态 |
| L1 quote | 最新完整 run 过旧，或 collector 为 error/stopped | 看两个 `quote_feed:*` 子检查和最新 run |
| Opportunity | endpoint 不可达或 strategy/profit basis/list 合同错误 | 跑 `make diagnose-arb-feed-prod min_edge_bps=0` |
| L3 under-fill | active token 不是严格 10 个 | 联合四个 strict evidence 检查，不能只看 overall |
| L3 evidence | sampler、ledger、membership 或逐市场 freshness 未通过 | 记录失败键、observedValue、release 和时间 |
| Dashboard | 404 `DEPLOYMENT_NOT_FOUND`、5xx 或传输失败 | 看 canonical URL 首响应与 Vercel deployment 状态 |

两个容易误判的正常状态：

- `WAITING_FOR_EVENT` 是安静窗口标签。WS age 和 L3 strict evidence 新鲜时，不单独报警。
- `opportunities: []` 是合法响应。它说明当前没有满足 gross edge 的组合，不是 feed 故障。

Polywatch 只有 snapshot stale 路径会尝试 HMAC `unpause`。quote、机会、L2/L3
和 Dashboard 故障都只报警，不会自动重启、改阈值、改 secret 或下单。

生产主监控每 2 分钟运行。首次出现新的故障集合会立即发 Telegram；同一故障不会
每 2 分钟刷屏，而是在 30 分钟后仍未恢复时再次提醒；恢复后只发一条 recovery。
GitHub Actions 仍会独立执行相同判断，但云端 schedule 可能延迟或漏 tick，因此只
作为 Fly/区域级故障的异地兜底，不能把 `*/15` 配置误读成准点 SLA。

## 最小恢复流程

收到告警后遵循同一条链，避免“为了变绿”破坏证据：

1. **先保存身份与时间**：记录 health body、`releaseId`、UTC 时间、失败键和
   最新成功时间；不要先重启。
2. **定位到一个生产面**：L1、机会、L2/L3 或 Dashboard。顶层 warn 不足以定因。
3. **验证写入侧真相**：例如 quote 只认完整 run，L3 只认持久 sampler/ledger/
   per-market freshness，Dashboard 内容只认认证后的页面。
4. **做最小已授权修复**：只改已证实错误的配置或进程；不顺手改阈值、轮换 secret、
   清数据或扩大交易权限。
5. **等待自然新鲜度恢复**：让下一次 quote、promoter、evidence sample 或部署完成，
   不拿修复前的成功时间冒充修复后结果。
6. **用原检查复验**：重新跑对应 Make target，再跑
   `make polywatch-healthz-dry`；若涉及 UI，再做认证浏览器四路验收。
7. **记录证据**：写清故障、最小变更、修复后身份、首个新鲜成功时间和剩余限制。

如果修复触发了 L1 restart，任何“连续 24 小时 quote 可用”证明都必须从重启后的
第一条完整 quote run 重新计时，不能拼接重启前数据。

## 设计取舍

### 等待 24 小时是不是空等？故障多久能发现？

不是。quote worker 每 60 秒触发一次尝试并写入完整 `neg_risk_quote_runs` 事实；最终 24 小时
查询能发现任何失败、卡死、数量不一致或 `>180s` 间隔。运行途中，Fly cron 机器每
2 分钟读四个生产面：

- collector `error/stopped`、L2/L3 strict fail、机会合同错、Dashboard 不可达：
  最坏约 2 分钟发现；
- quote 年龄到 `240s` 从 pass 变 warn 后，最坏再等一个 tick，因此约 6 分钟内告警；
- snapshot stale 仍按锁定的 30 分钟阈值判断，最坏约 32 分钟触发并尝试 unpause。

持久记录回答“窗口内到底发生过什么”，途中告警回答“现在是否需要介入”；两者缺一
都不能叫持续可用。GitHub 定时器不准点这一实证正是 resident watcher 成为主监控的
原因。

### 为什么 Dashboard 302/307 算部署可达？

Vercel Deployment Protection 会先返回 SSO 重定向。非跟随探针接受
200/302/307，是为了证明 canonical deployment 存在；404
`DEPLOYMENT_NOT_FOUND`、5xx 和传输失败才是部署报警。这个探针刻意不声称页面内容
通过，认证浏览器验收是另一道独立门。

### 为什么只有 snapshot stale 能自动修？

项目已有窄化的、HMAC 保护的 scheduler unpause 合同，而且动作可预测。其他故障
可能来自 schema、数据库、WS、部署或权限；自动重启或改配置会抹去证据，并可能把
局部故障扩大。因此它们保持 alert-only。

## 5 道自检题

1. `/healthz` 顶层是 `warn`，L2 为 `WAITING_FOR_EVENT`，但 WS age 新鲜、
   active count 是 10、四个 strict L3 检查全 pass。Polywatch 会不会报警？为什么？
2. opportunity endpoint 返回 HTTP 200、正确 strategy/profit basis，
   `opportunities=[]`。这是故障还是健康？它允许下单吗？
3. canonical Dashboard 返回 302。自动巡检能证明什么，不能证明什么？
4. quote worker 修复后重启了 L1。你能否把重启前 12 小时和重启后 12 小时拼成
   24 小时连续证据？
5. L3 active count 从 10 变成 8，但顶层 health 仍不是 fail。为什么运维仍要处理？

<details><summary>答案</summary>

1. 不报警；安静标签本身不等于数据陈旧，显式 WS/L3 子检查才是巡检合同。
2. 健康的零机会；它既不是 feed 故障，也不是下单授权。
3. 只证明部署/SSO 入口存在；不能证明登录后的四个应用页面和数据时间戳正确。
4. 不能。restart 改变连续运行身份，窗口必须从首条 post-restart 完整 run 重开。
5. 底层 active count 为启动兼容保持 informational，但 Polywatch 的生产合同要求严格 10。

</details>

## FAQ 增量

> 用户在实战中提出的问题追加到这里；同一问题出现至少 3 次后提升进正文。

### Q：自动巡检全绿，为什么还要人工浏览器验收？

自动巡检验证后端合同和 Vercel deployment 是否存在。它看不到认证后页面是否取到
真实数据、是否停在错误 banner、动态 L3 路由是否使用真实 asset，以及页面时间戳
是否在推进。发布收口时必须两者都通过；日常值守则在 Dashboard 告警、发布变更或
数据与 health 矛盾时补做浏览器验收。

### Q：等待 24 小时是不是空等？中途能不能发现故障？

不是空等。SQLite 按 60 秒触发节拍保留完整 quote run，Fly resident Polywatch 每 2 分钟
检查并在状态变化时 Telegram 告警，GitHub 再做异地兜底。24 小时只是最终连续性
判定所需的观察长度，不是发现故障的等待时间。
