# 有围栏的截止时间协调器

## 30 秒心智模型

任务自己写出的 `started / progress / terminal` 是第一事实；reconciler 不是另一个
“每 24 小时看一眼”的定时器，而是把当前 attempt 的 heartbeat、progress、lease、
deadline、circuit 和 recovery budget 组合成一次确定性判断。

判断本身不改数据库。真正恢复前，Postgres 还要同时确认 controller epoch、attempt、
job lease、action worker lease 和预算都仍然有效。确认后，job 变更与 action 终态在同一
事务提交。这样即使旧 worker 迟到、两个 controller 同时判断、executor 在中途崩溃，
也只有当前围栏持有者能产生一次业务效果。

整个闭环是：

`任务局部事实 → 纯 deadline 判断 → DB 围栏/预算仲裁 → job-level 原子恢复 → status/告警`

watchdog 仍然负责“事实没有出现”或整个控制面失联，但不再承担第一次发现普通任务
失败的职责。

## 判断、授权和执行为什么必须分层

`RuntimeReconciler.evaluate()` 只接受一个不可变状态。它先处理旧 fence、人类介入类
失败和预算耗尽，再判断 heartbeat、lease、circuit、attempt deadline 与 progress：

```python
# src/polyarb/control_plane/reconciler.py:18
if not state.owner_is_current:
    return self._decision(None, "recovery.stale-fence", ...)

if state.recovery_budget.remaining_actions == 0 and self._has_recoverable_condition(...):
    return self._decision(None, "recovery.budget-exhausted", ...)

if heartbeat_missing and now >= state.lease_expires_at:
    return self._decision(RecoveryActionType.RECLAIM_JOB, "job.heartbeat-missing", ...)
```

这段函数能回答“应该做什么”，却不能回答“现在仍由我做吗”。两个 controller 可能读到
同一份事实并得到相同 decision；只有数据库事务中的 controller epoch、attempt/lease
epoch、active-target 唯一约束和 durable budget 才能决定谁有写权。

## 为什么 action 也需要自己的租约

job lease 保护业务任务，action worker lease 保护恢复执行器。这是两种不同所有权：

- job lease 过期，可能正是 `reclaim-job` 要处理的对象；
- action lease 过期，说明执行恢复的 worker 已无权继续，即使它稍后恢复运行；
- 新 executor 可以把过期的 `running` action 以新 worker epoch 重领；
- 旧 executor 在事务中重新验证失败，不能先改 job 再发现 finish 被拒绝。

terminal update 使用数据库时钟再次检查 action lease：

```sql
-- src/polyarb/control_plane/recovery_store.py:1666
UPDATE m1_recovery_actions
SET state = 'completed', result_code = %s, finished_at = clock_timestamp(), detail = %s
WHERE action_id = %s
  AND worker_lease_expires_at > clock_timestamp()
```

job/circuit mutation 和这条 terminal update 共用一个事务。若事务执行跨过 action lease，
或在两者之间注入失败，全部回滚；action 到期后可由新 worker 重领，不会永久 `running`。

## `stale-noop` 与真实错误不能混为一谈

`stale-noop` 是有数据库证据的预期竞争结果，例如旧 controller、旧 attempt，或同一
target 已有权威 active action。它必须作为 completed action 留在 ledger 中，Dashboard
才能解释“为什么没执行”。

下面这些则是真错误，必须让 once/serve 非零退出并触发外部监测：

- 调度过程中预算权威发生变化；
- 同一 idempotency key 对应不同 payload；
- runtime recovery state 或 incident identity 冲突；
- store/fence 事务失败。

如果 CLI 把所有 `RecoveryActionConflict` 都显示成 `status=ok/stale-noop`，常驻服务会
永远循环并静默失败——这正是本轮 review 明确抓住并修掉的反模式。

## Dashboard 应怎样读这条链

`runtime-controller-status` 是纯只读视角，至少分开呈现：

1. controller owner/epoch/lease：谁拥有调度权；
2. job/attempt/runtime fact：哪里停住、最后 heartbeat/progress 是何时；
3. decision/action/reason/next check：系统如何解释事实；
4. budget/cooldown：为什么允许或拒绝下一次恢复；
5. action state/worker lease/outcome：恢复正在执行、已成功、已 stale-noop，还是失败。

只读 status 不会 claim controller、schedule/claim action 或消耗预算。mutation 命令必须
显式 `enable=1`；常驻 serve 也不拥有部署、进程或 Machine 重启权限。

## 关键设计取舍

1. **纯判断与写权分离**：纯函数易覆盖所有 deadline 边界；数据库负责并发真相。
2. **持久预算而非调用方参数**：并发 controller 不能各自认为还有“最后一次”额度。
3. **active-target 唯一**：同一 job 同时只有一项 pending/running 恢复；竞争者留下
   durable stale-noop，而不是制造第二次业务效果。
4. **job-level 优先**：自动动作只含 heartbeat、cancel、retry、reclaim、circuit probe；
   process/Machine 动作保持 `disabled-action`，避免粗粒度重启重复已提交效果。
5. **fail-loud service**：预期竞争有 ledger；未知 store/fence 错误非零退出，让
   supervisor、报警和 Dashboard 能及时发现。

## 自检题（对手测试）

1. 两个 controller 同时读到同一个 progress-stalled attempt，并都决定 `cancel-job`。
   哪些数据库条件保证只有一次 mutation？另一个判断应留下什么证据？
2. action worker A 的租约过期，worker B 已重领；A 随后从阻塞 SQL 返回。为什么仅在
   `finish_action()` 检查 worker epoch 仍然不够？
3. 同一幂等键第一次 cooldown=60，第二次 cooldown=90。为什么第二次必须 fail closed，
   不能返回第一次 action？
4. `runtime-controller-status` 看到了预算为 0。它能否顺便 reset budget 或 claim controller？
   为什么？
5. serve 遇到 “recovery budget changed during scheduling” 后若继续下一轮，会重新制造
   什么静默失败模式？正确的进程退出与报警行为是什么？

## FAQ 增量

**“既然任务自己能报告失败，为什么还要 reconciler？”** 任务只能报告它已经知道的
结果；进程可能在写失败事实前死亡，或持续 heartbeat 但 progress 不前进。reconciler
把“应该出现却没出现的事实”按 deadline 转成明确 decision，并受数据库围栏约束执行。

**“为什么不直接在任务 exception handler 里重试？”** 本地 handler 不知道自己是否
仍持有最新 lease，也无法和另一个 controller 原子竞争 durable budget。它可以记录
retryable failure，但是否重试、由谁重试必须由持久围栏仲裁。

**“这是否已经替代 24 小时 soak？”** 没有。即时事实、报警和自愈解决的是发现/处理
及时性；soak 证明长时间连续性。现在 soak 的某次失败会立即有 ledger、Dashboard、
告警与 bounded recovery，而不是等 24 小时结束才第一次知道。
