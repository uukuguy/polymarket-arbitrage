# R2 回执边界与租约接管

## 30 秒心智模型

R2 对象上传成功不等于这个工作已经完成。真正的完成事实是：**当前 lease
epoch 把 artifact identity 写成一条 fenced Postgres receipt**。因此进程恰好在
“R2 已验证、receipt 未写”时消失并不丢数据：lease 到期后，新 epoch 可以从同一
冻结输入重新产生同一内容寻址工件，并只提交一条 receipt。

这是一种 `at-least-once` 执行加 `exactly-once durable effect` 的组合：运行次数
可能超过一次，数据库可见效果只能是一份。

## 关键代码片段

```python
artifact, record_count = self._process_range(spec)
if self._crash_after_r2_upload is not None:
    self._crash_after_r2_upload(lease)
self._control_plane.record_structure_range(
    lease, artifact_key=artifact.key, artifact_digest=artifact.sha256,
    record_count=record_count, now=self._now(),
)
```

这段顺序来自 [structure_worker.py](../../src/polyarb/control_plane/structure_worker.py:95)：
故障钩子唯一允许的位置就是 R2 上传/HEAD 之后、fenced receipt 之前。若钩子在上传前，
测到的只是普通重试；若在 receipt 后，测不到“悬空工件”边界。

## 本次 staging 实证

对 fresh Structure range `event_tags:115`，故障钩子让进程以 `exit_code=130` 退出。
epoch 1 没有 receipt；120 秒 lease 到期后 epoch 2 写入了唯一 receipt，工件摘要仍为
`51bdef…bea3`（425 rows）。这证明 lease fence 和 receipt 唯一性，而非保证 R2 PUT
绝不重复：内容寻址相同 key 的幂等覆盖是允许的。

## 关键取舍

### 为什么不把“对象存在”当作已完成？

对象存储不能表达哪个 worker epoch 有权发布它，也不能阻止过期 worker 把旧输入当成
新结果。Postgres receipt 同时绑定 job key、epoch、冻结 range digest 与 artifact digest，
才是发布授权。

### 为什么测试要让进程真的退出？

普通 `Exception` 会进入 worker 的 retry/incident 路径，不能证明 OS 级进程消失时的
lease 行为。`KeyboardInterrupt` 绕过该 catch，Fly 看到 unrequested exit；恢复只能依赖
持久 lease 和 input，而不是当前 Python 调用栈。
