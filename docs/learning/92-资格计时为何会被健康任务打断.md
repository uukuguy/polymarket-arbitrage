# 92. 资格计时为何会被健康任务打断

## 30 秒心智模型

一个任务“还活着”至少有四层含义：lease 证明它仍有写权限，heartbeat
证明进程还能响应，progress 证明业务在向前走，attempt deadline 则限制一次尝试最多
占用多久。前三层都健康，不代表第四层配置一定合理。

这次 `structure-certify` 每秒都在校验下一个 range，heartbeat 和 progress 完全正常，
却因为通用 300 秒 attempt deadline 在约 290/1117 处被取消。下一次尝试又从第一个
range 开始，于是形成“永远健康推进、永远无法发布”的活锁。

资格计时的另一条纪律是：观察真正被生产消费者使用的 truth。事务化 Structure 链不会
写 legacy `structure:current`；当前 Quote 的 `quote:<digest>` identity 已经绑定它消费的
`structure:<digest>`。因此 Structure freshness 应由 `quote:current` 映射到对应 certified
manifest，而不是等待一个设计上不会出现的兼容指针。

## 四个时钟不要混为一谈

| 时钟 | 回答的问题 | 当前生产值 | 超时后的含义 |
| --- | --- | ---: | --- |
| lease | 我还有提交权限吗？ | 30 秒，可续期 | fence 丢失，旧 worker 禁止提交 |
| heartbeat | 进程还能按时响应吗？ | 10 秒 | 进程或 DB/R2 调用可能卡住 |
| progress | 业务结果还在前进吗？ | 30 秒 | 当前 stage 没有有效进展 |
| attempt | 这次尝试最多占用多久？ | certifier 3600 秒 | 即使持续推进也必须在绝对上限前结束 |

修复只改变最后一行。`structure-normalize` 等其他 job 仍是 300 秒；certifier 的
heartbeat/progress 仍是 10/30 秒。因此真正卡住时不会等一小时才被发现。

## 为什么不是“看到 progress 就无限续命”

无限 progress-renewed deadline 会让错误实现通过不断写无意义计数永久占用任务。
一小时绝对上限同时满足两件事：当前 1117 ranges 按生产实测速率约 19 分钟可完成；
异常但持续吐 progress 的实现最终仍会被围栏终止。若数据规模继续增长到逼近一小时，
应优化 parity 或引入可认证 checkpoint，而不是再次无界放宽。

## 为什么 freshness 跟随当前 Quote

Qualification 不是在问“数据库里有没有任何新 Structure manifest”，而是在问“当前可供
下游使用的市场快照，其 Structure 是否新鲜”。`quote:current` 是原子发布权威，
generation key 的 digest 来自 Structure bundle。将 `quote:<digest>` 映射成
`structure:<digest>` 后再 join manifest，可以确保两者是同一快照。

这条 SQL 只读取 qualification capability 已有的两张表：
`m1_publication_pointers` 和 `m1_generation_manifests`。如果 pointer identity 畸形或
manifest 缺失，join 返回空行，现有逻辑继续生成 `evidence.gap`，不会伪造健康。
同样地，pointer 必须匹配 `^quote:[0-9a-f]{64}$`；即使攻击者或损坏数据同时造出
`quote:bad` 与 `structure:bad` 两个互相匹配的 manifest，也只能得到 gap。

## 设计取舍

- 没有创建 `structure:current`：兼容指针会制造第二个可漂移 authority。
- 没有读取 `m1_quote_admission_inputs`：qualification 角色没有该权限，而且当前 Quote
  pointer 已经是 admission/certification 完成后的 durable proof。
- 没有只依赖 substring：先验证完整 generation grammar，避免两个相互匹配的畸形 key
  绕过 fail-closed freshness。
- 没有改 migration 或 role：最小权限包不因一个可由现有 truth 完成的查询而扩大。
- 没有启用 recovery action：这次修的是正常路径的 deadline 与 observation contract。
