# 87. 任务自愈与滚动验收

## 30 秒心智模型

自愈系统不能只靠一个外部定时器醒来问“是不是坏了”。正确模型是两条事实链汇合：任务本身事件触发先在执行事务里写 heartbeat、progress、terminal fact、policy verdict 和 recovery action；watchdog 兜底检测只处理任务没有自己说清楚的情况，例如 controller 失联、deadline 过期、lease stale 或 fact 流停止推进。

这两条链最终都落到 durable incident、recovery action、outbox 和 rolling qualification。Dashboard 只是 read boundary：它读取服务器已经归一化并验证过的事实，不用 client `Date.now()` 猜健康，不按空列表猜 pass，也不触发 mutation。mutation boundary 留给 worker、watchdog、recovery command 和 break-glass 流程，而且每一步都要有 fence、epoch、attempt 或 lease 身份。break-glass 在 writer 不可用时可能只能先走 generic one-shot direct page；这时 ledger 和 Dashboard 可能 stale，恢复 writer 后必须重新对账 incident/action/outbox。

## 代码地图

- `src/polyarb/control_plane/postgres.py`：control-plane 读模型的 authority，负责把 controller、active tasks、incidents、recovery actions、outbox、data product freshness 和 qualification 组装成 `/perception/control-plane` payload。
- `dashboard/lib/control-plane.ts`：Dashboard strict decoder。字段缺失或 shape 错误时返回 unavailable，而不是让组件自行补默认健康。
- `dashboard/app/control-plane/page.tsx`：按 Runtime overview、Active tasks、Incident timeline、Rolling qualification 的顺序渲染新面板，并保留旧 cloud usage、immutable evidence 和 watchdog ledger。
- `dashboard/app/control-plane/RuntimeOverview.tsx`：显示 canonical controller、epoch/tick/lease，以及 Quote pointer 与 Structure manifest 的真实 published_at。
- `dashboard/app/control-plane/ActiveTasks.tsx`：显示 job/stage/recovery state/progress、server-provided heartbeat/progress ages 和 deadline/overdue。
- `dashboard/app/control-plane/IncidentTimeline.tsx`：显示 durable incident transition reason/impact，并独立列出所有 bounded recovery actions，避免 resolved 或 unlinked action 从视图里消失。
- `dashboard/app/control-plane/QualificationPanel.tsx`：只用 server eligible/required 算 Rolling qualification 进度，并锚定 certificate digest。
- `src/polyarb/control_plane/watchdog.py` 与 `src/polyarb/control_plane/alert_delivery.py`：把 runtime transition 写成统一 payload，再渲染 Telegram transition/reminder 文案。
- `Makefile`：`make smoke-control-plane-dashboard` 只读拉取已认证 `/control-plane` 正文，拒绝登录页 200，并验证四个真实 heading。

## 设计取舍

- 任务事实优先，watchdog 兜底：任务本身知道 stage、attempt、progress 和 terminal result，应该在同一个事务里写事实；watchdog 负责发现“任务没有继续说话”的异常，而不是替任务猜业务结果。
- durable incident 和 outbox 分离：incident 是审计事实，outbox 是投递事实。Telegram 失败不能抹掉 incident，投递成功也不证明用户已读。
- Dashboard 只读：read boundary 只允许展示 server facts；mutation boundary 需要明确 controller、job、action、epoch、attempt 和 lease fence。break-glass 是人工接管姿态，不是 Dashboard 普通读操作；writer 不可用时它可能先通过 generic one-shot direct page 发出，ledger/Dashboard 可能 stale，恢复后必须补做对账。
- Rolling qualification 用服务器进度：eligible/required、breaker、policy identity、last fact 和 certificate digest 都来自 API。客户端不能用本机时间或缺失字段自行推断资格。
- 登录页 200 不能算 smoke 通过：受保护 Dashboard 常见返回 Auth 页面，因此 smoke 必须检查 `Runtime overview`、`Active tasks`、`Incident timeline` 和 `Rolling qualification` 四个真实 heading。

## 操作者读法

Runtime overview 先判断 controller 是 healthy、critical 还是 unavailable。顶层 unavailable 或 nested missing-controller 都读作 not healthy or empty；不能把空 controller 当正常。Quote 和 Structure freshness 必须看 pointer/manifest 的 published_at，缺失就是 unavailable。

Active tasks 用来确认任务有没有自己留下 heartbeat/progress，以及哪个 deadline 已 overdue。一个 task 进入 recovery state 后，只代表自愈动作已被记录或启动，不代表结果已经 verified。

Incident timeline 用来追踪生命周期和动作结果。durable incident 解释影响和 reason_code；Recent recovery actions 解释 action type、raw/normalized state/result、target、requested/started/finished/next_allowed、worker/epoch 和 fence。即使当前没有 open incident，completed/unlinked action 也必须可见。

Rolling qualification 是上线资格视图，不是 UI 自检。它显示四态进度、last breaker、policy identity、last fact 和 certificate digest。certificate anchor 只是页面内定位证据，不虚构外部 endpoint。

## 自检题

1. 如果 `/control-plane` 返回 HTTP 200 但正文是 Vercel Authentication，为什么 smoke 必须失败？
2. 为什么 heartbeat age 和 progress age 要由 server 提供，而不是 Dashboard 用浏览器当前时间计算？
3. 一个 recovery action 已 completed，但 incident 已 resolved 或 action 没有关联 incident 时，为什么还要在 Recent recovery actions 中显示？
4. break-glass 为什么仍属于 mutation boundary，而不是 Dashboard 上的普通读操作？
5. Rolling qualification 为什么只能用 eligible/required 和 certificate digest，而不能用“看起来没有事故”推断通过？

## FAQ 增量

**Q: watchdog 已经每隔一段时间检查，为什么还要任务本身事件触发？**

A: watchdog 看到的是外部症状，比如 deadline 过期、lease stale、heartbeat 停止。任务本身知道的是业务语义，比如 fetch 已失败、persist 已提交、certificate 已生成。没有任务事实，watchdog 只能报警“卡住了”，不能可靠解释“卡在哪、影响什么、能否恢复”。

**Q: outbox delivered 是否等于操作者已经知道？**

A: 不是。outbox delivered 只证明 Telegram API delivery writer 成功，不能证明手机展示、用户已读或后续处置。操作者审计仍以 durable incident 和 Dashboard 读模型为准。

**Q: 为什么 smoke 不直接用 Authorization header 参数？**

A: make argv 容易进入 shell history、process list 或 CI 日志。需要 header 时用 `auth_header_file`，让 curl 从文件读取；默认推荐用预先保存的认证 cookie jar。
