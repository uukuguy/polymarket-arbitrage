# 增长证据不能放进每轮状态行

## 30 秒心智模型

状态行回答“现在是什么”，证据账本回答“历史发生过什么”。把全部历史 JSON 塞进状态行，会让
每次读取、锁定和更新都随运行时间变慢；`statement_timeout` 甚至管不到 SQL 完成后的结果传输。

正确形态是：每条 qualification fact 只 append 一行；epoch 只更新固定大小的状态、计数和 cursor。
进程重启按 ordinal 分页重放，终态只在内存中一次性 materialize 后生成证书；epoch 行仍不膨胀。

## 代码地图

- `alembic/versions/030_m1_normalized_qualification_facts.py`：append-only facts 与固定计数。
- `src/polyarb/control_plane/qualification_service.py`：500 行分页重放、version/cursor 双 CAS、终态 materialize。
- `src/polyarb/control_plane/qualification_store.py`：证书只核对固定大小 epoch projection。
- `src/polyarb/control_plane/postgres.py`：总览只读固定 qualification 列。
- `tests/m1-perception/test_control_plane_postgres.py`：501-fact 的 500+1 重启边界。

## 关键代码片段

活跃写入只追加一条事实，再更新 epoch 标量；两者在同一事务中：

```python
_append_epoch_fact_cursor(
    cursor,
    epoch_id=decision.epoch_id,
    ordinal=len(fact_records),
    fact_record=appended_record,
)
# epoch update: state/version/last_fact_at/counts；active arrays 保持 []
```

重启不执行一个无界 `SELECT *`，而是按可恢复 ordinal 分页：

```sql
SELECT ordinal, fact_record
FROM public.m1_qualification_epoch_facts
WHERE epoch_id = %s AND ordinal > %s
ORDER BY ordinal
LIMIT 500
```

## 设计取舍

### 为什么不把 status timeout 从 5 秒改成 30 秒

因为增长发生在结果形状和每轮 JSON 重写，不在某个固定慢查询。调大数字只会推迟同一个故障。

### 为什么终态也不再保存完整数组

证书需要完整 canonical evidence，但不需要把它重复写进 epoch 再 `SELECT *` 读回。服务在终态
从 append-only 行分页 materialize 一次，生成 evidence digest 和 certificate；数据库只核对固定标量。

### 为什么 restart replay 可以长，但每页必须短

重启一次做 O(n) 重放是合理成本；每 tick 做 O(n) 读写会累计成 O(n²)。分页让每条 SQL 有固定
结果上限，ordinal 是可恢复 checkpoint，进程中断后可以重新从持久化事实开始。

## 自检题

1. SQL 在 2 秒内执行完，但返回 20 MB JSON，为什么 5 秒 `statement_timeout` 仍可能救不了 CLI？
2. 3,000 个事实、每个 tick 重写全部历史，与 append 一行相比，总写入量的数量级分别是什么？
3. facts append 成功、epoch CAS 失败时，为什么同一事务必须整体回滚？
4. 为什么 `source_cursor` 相同但 epoch `version` 不同仍要拒绝当前进程继续写？
5. 哪两种终态会触发一次性内存 materialize？为什么 epoch 数组仍保持空？

## FAQ 增量

### generated status column 不是已经解决增长读取了吗？

只解决了一个 status consumer。总览仍可能 `SELECT *`，writer 仍可能每轮重读/重写原数组。设计审计
必须沿所有 consumer 和 writer 走完整 chain，不能因为一个入口变快就宣布问题消失。
