# 可达权限与无秘密拓扑审计

## 30 秒心智模型

权限不是一张平面表，而是一条可达链：

`能连接数据库 → 能进入 schema → 对象 ACL 允许操作`。

对象上写着 `PUBLIC SELECT`，不等于角色真的能读；如果缺少 schema
`USAGE`，路径在上一跳已经断了。相反，运维工具看到 provider JSON
也不等于应该把它打印出来：先在内存里缩成闭合字段，再输出。

这次两个问题其实是同一种设计：**只传播真正可达、明确允许的信息**。

## 关键代码片段

迁移先检查所有 schema：只有 `public USAGE` 可以成立，其他非系统
schema 的 `USAGE/CREATE` 都拒绝（`alembic/versions/026_m1_runtime_scoped_roles.py:330`）。
对象枚举随后加上可达条件（同文件 `:355`）：

```sql
AND pg_catalog.has_schema_privilege(
        '{role}', namespace.oid, 'USAGE'
    )
```

这不是“忽略 extensions 权限”，而是准确表达 PostgreSQL 的访问链。
如果未来角色真的得到 `extensions USAGE`，schema 总门会先拒绝；不会把
provider ACL 偷偷加入允许集。

Fly 审计的边界在 `src/polyarb/control_plane/fly_topology_audit.py:44`：

```python
child_env = os.environ.copy()
child_env["FLY_API_TOKEN"] = ""
return subprocess.run(
    command, capture_output=True, text=True, timeout=30, check=False, env=child_env
)
```

关键不是 `capture_output` 本身，而是 raw body 此后只能进入严格 parser；
provider 失败统一变成 reason code，stderr 和解析异常正文都不会传播。

## 设计取舍

### 为什么不硬编码 Supabase 的两个扩展视图？

硬编码 `pg_stat_statements*` 只是给今天的 provider 形态开洞。可达性规则
来自 PostgreSQL 语义，能覆盖未来任意不可达扩展对象，同时仍拒绝真正
可访问的额外权限。

### 为什么不直接撤销 PUBLIC ACL？

那会改变 Supabase 和四个既有应用共享的数据库环境，扩大生产变更面。
revision 026 的目标是隔离两个新进程，不是重写 provider 默认权限。

### 为什么 env key 也会触发拒绝？

只隐藏 value 仍可能让密码继续以普通 Machine env 存在。审计遇到
`DSN/PASSWORD/TOKEN/SECRET/...` 类普通 key 直接失败，迫使 credential
回到 Fly hidden secret；错误可以指出 key，但绝不打印 value。
