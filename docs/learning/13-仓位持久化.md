# 13 — 仓位持久化：让每个进程看见同一本账

← [12-套利引擎](12-套利引擎.md) | [00-INDEX](00-INDEX.md)

## 30 秒心智模型

Phase 2 的 `PositionTracker` 像一张放在某个 Python 进程桌上的草稿纸：`run` 写完，进程结束，另一个 `status` 看不到。Phase 3 把草稿纸换成了一本 SQLite 账簿：

```text
run/status/close（每次都是新进程）
              │
              ▼
      PositionTracker（PnL / 风控规则）
              │ transition(state)
              ▼
 PositionRepository（事务与幂等边界）
              │
              ├── m2_account_state       当前余额 + 累计已实现 PnL
              ├── m2_open_positions      当前未平仓投影
              └── m2_applied_operations  已经做过的操作及原返回值
```

一句话：**Tracker 决定“这笔账怎么算”，Repository 保证“这笔账只算一次，并且三张表一起成功或一起失败”。**

## 用户工作流

```bash
# 三个命令可以是三个完全独立的 shell 进程，只要 db= 相同
make run-arb db=data/m2-positions.db mid=0.40 stake=100 legs=1
make status-arb db=data/m2-positions.db
# 需要跨进程重试保证时，调用方生成并保留 immutable operation_id
make close-arb db=data/m2-positions.db market_id=cond-0 exit_price=0.50 operation_id=close-20260717-001
make status-arb db=data/m2-positions.db

# 重试同一次 synthetic run 时显式复用身份；新机会不要复用
make run-arb db=data/m2-positions.db signal_id=retry-20260717-001
```

也可用 `POLYARB_POSITION_DB_PATH` 设置默认路径；CLI 的 `--db-path` / Makefile 的 `db=` 优先。

## 一次状态变更到底发生什么

`PositionTracker.open_position()` 不再直接改自己的字段。它定义一个只负责领域计算的 closure，再交给 repository：

```python
# src/polyarb/routing/position_tracker.py:168
def transition(state: PositionState) -> bool:
    # 余额、敞口、重复市场检查都基于事务内读到的 state
    ...
    state.open_positions[market_id] = Position(...)
    state.balance -= stake
    return True

result = self.repository.apply(
    operation_id, "open", market_id, transition
)
```

SQLite 侧的顺序是固定的（`position_repository.py:176-228`）：

1. `BEGIN IMMEDIATE`，先拿写锁，避免两个 writer 都基于旧余额通过风控。
2. 查 `m2_applied_operations`。ID 已存在就直接返回原结果，不再执行 closure。
3. 读取唯一账户行和全部未平仓持仓，重建 `PositionState`。
4. 执行领域 closure。
5. 写回账户、替换持仓投影、记录 operation 及返回值。
6. 三者一起 `COMMIT`；任一步异常就 `ROLLBACK`。

这就是 crash consistency：进程在 commit 前死掉，旧账仍完整；commit 后死掉，下个进程读到新账。

## 为什么 operation ID 是正确性的组成部分

“市场已经有持仓，所以第二次 open 被拒绝”不等于幂等。它虽然没重复扣钱，却会新增一次失败操作，而且如果第一次已经 open+close，重试可能真的重新开仓。

执行引擎因此生成稳定身份（`execution/engine.py:267-320`）：

```text
open:{signal_id}:{leg_id}
close:{signal_id}:{leg_id}:paper-close
```

同一个 signal/leg 重试会命中 ledger，直接拿到第一次的 `True` 或 PnL；新的合法机会必须有新的 `signal_id`，所以市场平仓后仍能再次开仓。

真实 venue close 优先使用 `Fill.fill_id`：

```text
close:{signal_id}:{leg_id}:fill:{venue_fill_id}
```

旧 adapter 没给 `fill_id` 时仍暂用 fill 时间，系统会明确 warning：这条路径不具备 durable retry guarantee。未来真实 adapter 的边界必须把交易所不可变的 fill/trade ID 带进来；本地接收时间不是 venue truth。

## Durable receipt：投影消失不等于操作没发生

`m2_open_positions` 回答的是“**现在**哪些仓位还开着”。close commit 后，这一行理应消失。因此看到“没有持仓”无法区分两种完全不同的事实：

1. close 从未发生；
2. close 已经发生，只是进程在打印结果前崩了。

`m2_applied_operations` 和 `OperationReceipt` 回答第二个维度：“operation X 是否已 commit，原返回值是什么？”（`position_repository.py:85-96,184-198`）。operator close 的顺序因此是（`cli_arbitrage.py:367-418`）：

```text
caller-owned operation_id
          │
          ├─ receipt 已存在且 type/target 一致 → 返回原 PnL，replayed=true
          ├─ receipt 已存在但 type/target 冲突 → fail closed
          └─ receipt 不存在 → 检查 open position，再执行 close
```

read-before-write 不是并发正确性的最终防线。两个进程可能同时查到 `None`；真正串行化它们的仍是 `apply()` 内的 `BEGIN IMMEDIATE`、ledger 主键和事务内 replay check。receipt lookup 优化的是“恢复响应”，事务保证的是“钱只记一次”。

### `retry_safe` 为什么取决于谁生成 ID

- 调用方显式传 `operation_id=close-001` 并保留它：响应丢了仍能重放，所以 `retry_safe: true`。
- CLI 为兼容旧用法临时生成 ID：成功响应里会返回它，但如果这个响应本身丢了，调用方不知道该重放哪个 ID，所以必须诚实报告 `retry_safe: false`。

不能用 market + price + size + 当前时间推导“看起来稳定”的 ID：同一个市场 reopen 后可能以同价同量再次合法成交，而重试时生成的时间又会变化。身份必须来自调用方请求或 venue fill，而不是从交易内容猜。

## 三张表为什么不是一张 JSON blob

- `m2_account_state` 是 singleton，能明确检查“必须恰好一行”；多一行或少一行都 fail closed。
- `m2_open_positions.market_id` 是主键，数据库层也保证一个市场最多一个当前持仓。
- `m2_applied_operations.operation_id` 是主键，重放检查和审计不需要反序列化整本账。

一个 JSON blob 写起来更短，但难以做 cardinality/uniqueness 校验，也无法低成本回答“这个操作是否已经提交”。当前三表是最小的规范化投影，不是完整 event sourcing；历史平仓明细留给后续真实交易审计阶段。

## fail-closed：为什么坏库不能自动重置

首次启动没有 DB 时，系统会创建 schema 和初始 paper account。已有 DB 则以 durable state 为准，即使本次 `initial_balance` 配置不同也不会重置余额。

以下情况直接非零退出：

- schema 缺少必需列；
- account singleton 不是恰好一行；
- 文件不是合法 SQLite；
- 写锁超过 `POLYARB_POSITION_BUSY_TIMEOUT_MS`。

原因很直接：在交易系统里，“读不到旧账，于是假装余额又是 1000”比停机危险得多。

## 设计取舍

### 领域规则留在 Tracker，事务留在 Repository

如果 SQLite 类自己计算 BUY/SELL PnL，内存测试和 SQLite 生产会出现两套公式。现在同一个 transition 同时跑在 `InMemoryPositionRepository` 和 `SQLitePositionRepository` 上：前者让单元测试轻，后者让进程间状态可靠。

### `BEGIN IMMEDIATE` 而不是先读后写

余额与敞口检查必须和扣款属于同一串行化写事务。普通的“先 SELECT、算完、再 UPDATE”会让两个进程都看到余额 1000，各自认为能开 600，最后超额暴露。

### 当前是单 paper account

Phase 3 的目标是打通单机 paper 生命周期，不是多账户清算系统。singleton 检查反而让损坏更容易暴露；多账户需要先定义 account identity、隔离和迁移规则，不能靠悄悄多插几行扩展。

## 对手测试（实战决策题）

1. close 已 commit，但响应丢失。调用方必须保留哪个值，才能在新进程恢复原 PnL？
2. 为什么“open position 不存在”既不能证明 close 成功，也不能证明 close 从未发生？应该查哪张表？

5. 为什么本地 timestamp fallback 不是 venue truth？真实 adapter 应把哪个字段写进 `Fill`？

## FAQ 增量

### Q：SQLite WAL 是不是意味着多进程可以无限并发写？

不是。WAL 主要改善 reader 与 writer 并发，SQLite 同一时刻仍只有一个 writer。本项目用 bounded timeout 明确暴露竞争；如果实盘写入量证明单 writer 成为瓶颈，再用数据决定是否升级存储，而不是预先引入分布式数据库。

### Q：为什么 `load()` 返回/重建完整 state，而不是暴露可变对象？

因为可变引用会绕过 transaction boundary。内存仓储也做 deep copy；调用方修改副本不会悄悄污染已提交状态。真正发布新状态只能经过 `apply()`。

### Q：为什么拒绝开仓也记录 operation？

因为相同 operation 的重试应得到相同结论。否则余额后来变化后，同一个旧请求可能突然成功，破坏“一个 operation 只产生一次确定结果”的语义。新的尝试应使用新的 operation ID。

### Q：为什么 receipt replay 不再检查本次传入的 exit price？

因为 operation ID 标识的是已经提交的那一次 close；ledger 中的原 PnL 才是事实。本次 `exit_price` 只作为请求上下文回显，不能重算或覆盖已提交结果。如果调用方想执行新的 close，必须先有新的 open position，并使用新的 operation ID。

### Q：receipt lookup 会不会绕过 identity conflict？

不会。CLI 在返回回执前同时核对 `operation_type == "close"` 和 `target_id == market_id`；不一致直接非零退出。即便两个进程都在 lookup 阶段没看到 receipt，repository `apply()` 内仍会在同一写事务中核对 identity，后到者只能拿到原结果或 conflict。
