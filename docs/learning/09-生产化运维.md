## 30 秒心智模型

把 daemon 想成一艘 7×24 在大洋里跑的船。Phase 02 让船能跑 + 三种告警雷达（Sentry / Telegram / Better Stack）能响；Phase 02.1 修了三个船员痛点，让 ops 真能在岸上把船开回来：

**核心哲学**：监控告警语义（`/health` 503 = 告警信号正确）与平台路由探针语义（`/healthz` 永远 200 = 不让 Fly proxy 切流量）必须分离。一个 endpoint 同时承担两件事会让其中一个一定坏。同理 fail-soft 不等于 silent — 不抛 exception ≠ 不留 audit trail。

## 核心代码片段

### 块 1 — orchestrator step 7.5 三分支（D-01 修法）

**为什么这块重要**：Phase 02 chaos Inj 3 暴露的盲点 —— 在加这条 `else` 之前，撤了 Supabase secret 后 `supabase_mirror_enabled=False`，整段 mirror 路径直接掉到 if/elif 末尾，0 log + 0 breadcrumb + `/health` supabase 子 check 也消失。fail-soft 契约 D-12（不阻断 snapshot）在工程上变成了 fail-silent 反模式。

`src/polyarb/snapshot/orchestrator.py:549-567`：

```python
    else:
        # D-01 (Phase 02.1, BUG-7): audit log + breadcrumb for config-disabled skip.
        # Previously this branch was completely silent — daemon log had nothing,
        # Sentry events had no breadcrumb context. The 2026-05 chaos Inj 3
        # (撤 POLYARB_SUPABASE_SERVICE_KEY → pydantic flips mirror_enabled=False)
        # surfaced this as Bug #7: fail-soft path collapsed to a black hole.
        #
        # D-12 invariant: fail-soft contract unchanged — snapshot still completes.
        logger.info(
            f"step 7.5: mirror disabled — reason=config-disabled "
            f"(snapshot_id={snapshot_id}). "
            "Supabase dashboard will not update until mirror is re-enabled."
        )
        sentry_sdk.add_breadcrumb(
            category="mirror",
            level="info",
            message="mirror skipped: reason=config-disabled",
            data={"supabase_mirror_enabled": False, "snapshot_id": snapshot_id},
        )
```

**两个细节**：

1. **breadcrumb category="mirror"** 与既有 R2/Supabase 失败 breadcrumb 的 `category="storage"` 不同 —— 同 module，不同语义：mirror 是 *config 状态*（不是错误），storage 是 *运行时失败*。Sentry dashboard 用 category 分类，下次出事翻 breadcrumbs 不会混淆 "skip 是因为没配" 还是 "试了但 push 失败"。

2. **breadcrumb 不被 LoguruIntegration(level="ERROR") 过滤** — Sentry SDK 的 loguru 集成只把 ERROR+ 转 event，但 `sentry_sdk.add_breadcrumb()` 是手工 API 调用，永远进 breadcrumb 缓冲区。所以 level="info" 不影响下次 event 是否携带这条 breadcrumb（Phase 02 L7 自我欺骗教训：千万别用"测试时能看见 log"反推"prod 时 Sentry 也能看见" — 必须 chaos 实测）。

### 块 2 — control.py 的 HMAC 中间件独立设计（D-03）

**为什么这块重要**：Path guard 用 `startswith("/control")` 而不是 scan.py 那种 `!= "/scan"` —— 这是关键差别。前者把 `/health` / `/healthz` / 未来其它 public 路径自然 bypass；后者会拦截一切非 /scan 的路径（RESEARCH Pitfall 1 警示）。

`src/polyarb/http/control.py:73-100`：

```python
    if not request.url.path.startswith("/control"):
        return await call_next(request)

    received_sig = request.headers.get("X-Signature")
    if not received_sig:
        return JSONResponse(
            {"error": "missing X-Signature header"}, status_code=401
        )

    # Accept both `sha256=<hex>` (Stripe/GitHub) and bare `<hex>` (backward compat).
    if received_sig.startswith("sha256="):
        received_sig = received_sig[len("sha256=") :]

    body = await request.body()
    expected_sig = hmac.new(secret.encode("utf-8"), body, hashlib.sha256).hexdigest()

    # Constant-time compare — T-02.1-8-01 / T-02.1-8-03 mitigation.
    if not hmac.compare_digest(received_sig, expected_sig):
        return JSONResponse({"error": "invalid X-Signature"}, status_code=401)
```

unpause 处理 (control.py:121-147)：

```python
async def unpause(request: Request) -> JSONResponse:
    ...
    # Sync call — scheduler.unpause() is `def`, not `async def` (Pitfall 4).
    scheduler.unpause()
```

**两个细节**：

1. **sync call from async handler** — Pitfall 4：`scheduler.unpause()` 在 `src/polyarb/daemon/scheduler.py:192-198` 是 `def` 不是 `async def`（它只动内存 + SQLite 一次写）。从 async handler 里直接 `scheduler.unpause()` 不加 `await` 是正确的；如果手贱加了 `await` 会得到 `TypeError: object NoneType can't be used in 'await' expression`。这种"小函数同步 vs 异步"的判断要看 method 实现，不要看类型名猜。

2. **`pause` 和 `control_status` 是 501 stub**（control.py:165, control.py:175）—— Phase 02.1 D-07 严格 fix-up scope 只要求 unpause；但 D-03 允许 planner 顺手搭 future-proof router 框架。Phase 03+ 加 pause/status 实现时不动 app.py、不动 middleware、只填 handler body —— 这是"可演化设计"在文档纪律里的体现。

### 块 3 — health.py 抽 helper + 拆两 endpoint（D-05/D-06）

**为什么这块重要**：`/health` 和 `/healthz` 必须共享 4 个 check 的逻辑（D-06 锁定 — 不分叉），否则下次加新 check 时只改一处就漂移。helper 模式是这里的强制约束。

`src/polyarb/http/health.py:77-96`（helper 签名）：

```python
def _build_health_checks(
    store: Any,
    settings: Any,
    now_s: float,
) -> tuple[dict[str, list[dict[str, Any]]], str]:
    """Compute all health sub-checks and the overall status.

    Shared by /health (IETF strict — fail → 503) and /healthz (always 200).
    Both endpoints render the same JSON body shape; only the HTTP status code
    differs (per D-06 — full-mirror body schema, do NOT diverge check logic).
    ...
    Returns:
        (checks_dict, overall_status) where overall_status in {"pass","warn","fail"}.
    """
```

`src/polyarb/http/health.py:223-241`（/health handler，IETF strict）：

```python
async def health(request: Request) -> JSONResponse:
    ...
    checks, overall = _build_health_checks(store, settings, time.time())
    body = _build_health_body(overall, checks, settings)
    http_status = 200 if overall in ("pass", "warn") else 503  # IETF strict
    return JSONResponse(body, status_code=http_status, media_type=HEALTH_CONTENT_TYPE)
```

`src/polyarb/http/health.py:244-270`（/healthz handler，Fly-friendly）：

```python
async def healthz(request: Request) -> JSONResponse:
    """GET /healthz — Fly-friendly probe. ALWAYS HTTP 200.

    /healthz keeps the proxy happy so external administrative endpoints
    ...
    """
    checks, overall = _build_health_checks(store, settings, time.time())
    body = _build_health_body(overall, checks, settings)
    return JSONResponse(body, status_code=200, media_type=HEALTH_CONTENT_TYPE)
```

**两个细节**：

1. **handler 短到只剩 3 行业务** — `_build_health_checks` 决定 body 内容，`_build_health_body` 渲染 IETF schema，handler 只决定 HTTP status code。这是 "helper-first refactor" 模式：handler 是 thin wrapper，business logic 全在 private helper —— 测试时 helper 可单独 unit test、新加 endpoint（比如未来 `/health/r2-only`）只需要一个新 handler。

2. **fly.toml 配套 patch**（`fly.toml:34-38`）：
   ```toml
     [[http_service.checks]]
       path = "/healthz"
   ```
   只有 fly.toml 改了，Fly proxy 才会停止读 `/health` —— 这个 platform-level 变更是 D-05 修法的真正闭环点。chaos Inj #6-verification（02-SOAK-LOG.md 第 427 行起）正是 deploy 后 cross-inject 一次 /health=fail 看 Fly proxy 是否仍 keep traffic in，做最后实证。

## 设计取舍

### 取舍 1 — fail-soft visibility 选 audit-log 不选 settings 拆分（D-01 拒绝 option (a)）

候选方案：

- **(a)** 把 `supabase_mirror_enabled` 在 Settings 层拆成 `config_disabled` vs `invalid_creds` 两态，下游消费这两态做不同处理（~80 行改动）
- **(b)（选）** 不动 settings 语义，在 orchestrator step 7.5 入口加 audit log + Sentry breadcrumb（~30 行改动）
- **(c)** 在 `/health` 加一条 "config drift" 子 check 实时上报 mirror_enabled 状态

**为什么选 (b)**：

- (a) 过度工程 — 拆 settings 语义会引发对所有 Settings 字段的"是否也该拆"质疑，回归测试面积大；config_disabled 与 invalid_creds 在 ops 视角是"都跳过 mirror"的同一组动作
- (c) 与 #6 trade-off 决策耦合 — `/health` schema 在 Plan 02-05 已 frozen，加新子 check 会反过来要求重新决策 IETF 严格性。两个 bug 决策耦合在一起是 plan-code drift 的滋生地
- (b) 改动量最小（30 行）且语义清晰：fail-soft 不变（D-12），可见性补全（D-01）。RESEARCH/PATTERNS 已确认 sentry_sdk.add_breadcrumb 不会被 LoguruIntegration 过滤，所以 prod 行为可预测

### 取舍 2 — unpause endpoint 选独立 `/control/unpause` 不选 `/scan?action=unpause`（D-03 拒绝 option (a)）

候选方案：

- **(a)** 复载 `/scan` action 语义：POST /scan?action=unpause 让 scan endpoint 多带控制副作用
- **(b)（选）** 新建 `/control/unpause` 专语义 endpoint，配套 `/control/pause` + `/control/status` 501 stub
- **(c)** 在 Vercel dashboard 加 "Unpause Daemon" 按钮，绕开 endpoint 层

**为什么选 (b)**：

- (a) 让 /scan 语义脏 — /scan 是 P11 模板 "trigger 一次扫描"，加 action 复载会让 endpoint 既"触发扫描"又"控制 daemon"，URL semantics 走样
- (c) 超 fix-up scope（D-07 严格）— Vercel dashboard 增强是独立 plan，本 Phase 不蔓延
- (b) future-proof — Phase 03+ 加 /control/pause / /control/status 直接填 stub body，不动 router / 不动 middleware / 不动 app.py 注册。`scheduler.unpause()` 在 `scheduler.py:192` 已经存在但 codegraph_callers 显示 0 callers，这正是 BUG-8 的本质：method 实现了，但没接 HTTP entry —— 修法等价于"补一条线"

### 取舍 3 — `/health` 与 `/healthz` 拆 vs `/health` 降级总 200（D-05 选 option (c)）

候选方案：

- **(a)** `/health` 永远 200（status 在 body）—— 一个 endpoint 同时承担监控告警 + Fly probe
- **(b)** Fly 改用 TCP probe 替代 HTTP probe —— 只验证端口 listening，不验证 HTTP 服务真健康
- **(c)（选）** 拆两 endpoint：`/health` IETF strict 503 不让步，`/healthz` 永远 200 给 Fly proxy

**为什么选 (c)**：

- (a) 破坏 Better Stack 告警语义 — 外部探针总 200 等于失去 HTTP-layer 的告警信号（Better Stack 需要看到 503 才触发 alert）。这违反 "alert chain discipline" 第 1 条：监控告警语义必须正确，不能为了平台兼容性把告警通道废掉
- (b) TCP probe 不够强 — uvicorn 端口 open 不等于 application logic 健康（比如 SQLite 卷挂载失败但 socket 还 listening 的边缘场景）。Phase 02 L6 教训 "HTTP 200 ≠ user notified" 反向也成立："port open ≠ app healthy"
- (c) 关注点分离 — 监控告警与路由探针 endpoint 必须分离。`/health` 做 IETF strict（503 = 告警信号正确），`/healthz` 做 Fly proxy 探针（200 = 不切流量）。fly.toml 一行 patch 让 Fly probe 读 /healthz，Better Stack 继续读 /health

### 取舍 4 — HMAC middleware 独立（control.py）vs 复用 scan.py 中间件（planner discretion）

候选方案：

- **(a)** 改 `scan_auth_middleware` 的 path guard，从 `!= "/scan"` 改成 `not in ("/scan", "/control/unpause", ...)`
- **(b)（选）** 在 `control.py` 内独立写 `ControlAuthMiddleware`，HMAC 逻辑 inline 复制 scan.py pattern，但不 import scan.py

**为什么选 (b)**：

- (a) 改 scan.py 引入回归风险 — scan.py 是 Phase 02 P11 模板已 frozen，每次扩 path guard 都可能 break 既有 /scan 测试。"不要改稳定的东西" 是工程纪律
- (a) 关注点耦合 — scanner-trigger 与 scheduler-state-machine 是两个 subsystem。HMAC 逻辑相同 ≠ ownership 相同。未来某个 plan 可能给 /control/* 换不同 secret（更严格的 ops secret），那时 (b) 的独立 middleware 一行参数改完，(a) 则要重构 scan.py
- 代价：~20 行 HMAC 逻辑重复。这是接受的 — "复制 HMAC 逻辑" vs "复制 ownership 耦合" 选前者，因为 HMAC 逻辑稳定且小

## 自检题

1. **如果 prod 上 daemon 是 PAUSED 状态，但你忘了 secret 的本地副本，怎么 unpause？**

   *期望思路*：两条路 — (i) `flyctl ssh console -a polyarb-l1 -C 'cat /tmp/polyarb-state.json'` 或者直接 `sqlite3 /data/<db>` UPDATE state（最后的暴力路径，Phase 02 之前的全部 ops 流程）；(ii) `flyctl secrets list -a polyarb-l1` 看 POLYARB_SCAN_SHARED_SECRET 还在 → 用 `flyctl ssh console` 直接 printenv 拿一份本地写回 .env → `make unpause-prod`。option (ii) 才是 D-03 设计的"prod-friendly" 路径，但前提是 secret 在 Fly secrets store 还没被替换/旋转。

2. **如果 chaos Inj 3-v2（撤 mirror secret）跑完，daemon log 里看不到 "mirror disabled" 字串，三种最可能的故障原因是什么？**

   *期望思路*：(a) D-01 修法部署到 prod 时 deploy 失败回滚了（`flyctl status` 看 release 版本，对比 git log）；(b) `else` 分支位置写错了 — 比如加在了 F-05 guard 的 elif 内部而不是顶层 else（RESEARCH Pitfall 3），这种情况下 mirror_enabled=False 直接跳过整段 if/elif/else，根本 unreachable；(c) Sentry/log buffer 没等够 flush 时间 —— Fly logs 有 5-day retention 但流式 buffer 大约延迟 1-3 秒，chaos 跑完立刻 grep 可能空。`sleep 60` 后再 grep 是必备步骤。

3. **`/healthz` 永远返 200 会不会让外部探针误判系统总健康？**

   *期望思路*：不会。因为 Better Stack 外探针监控的 endpoint 是 `/health`（IETF strict 503 on fail），不是 `/healthz`。`/healthz` 只服务 Fly platform machine probe（让 proxy 不切流量）。监控告警语义（/health）与平台路由探针语义（/healthz）在 endpoint 层面分离 —— 这正是 D-05 的核心设计。如果用户把 Better Stack 误配到 `/healthz`，告警通道就废了，但这是配置错误，不是 D-05 设计的问题。

4. **`make unpause-prod` 的 HMAC body 是空字符串。如果攻击者抓到一次 unpause 的 HTTP 请求，能否 replay？**

   *期望思路*：能。unpause 是幂等操作（T-02.1-8-04 disposition=accept）—— 重放 N 次效果与 1 次一样（state 已经 RUNNING 时直接返 `already_running`）。Phase 02.1 没加 nonce 是有意决策，因为 unpause 无破坏性放大效应。如果 Phase 03+ 加破坏性操作（比如 `/control/wipe` 或 `/control/rotate-secret`）必须加 nonce 或时间窗（Stripe webhook style）。同时注意：constant-time `hmac.compare_digest` 防的是 timing oracle 推测 secret，不防 replay。

5. **Phase 02 LEARNINGS L7 "测试按钮不算 verified" 在 Phase 02.1 体现在哪？**

   *期望思路*：每个 bug 修法的 verification 凭证都不是 unit test，而是 prod chaos：BUG-7 的 Inj 3-v2（撤 prod secret）、BUG-8 的 Inj 4（让 daemon 真 PAUSED 再用 `make unpause-prod` 切 RUNNING）、BUG-6 的 Inj #6-verification（deploy 后 cross-inject /health=fail 看 Fly proxy 是否切流量）。三段都写进 `.planning/workstreams/m1-perception/phases/02-l1-production-grade/02-SOAK-LOG.md`（第 305 / 367 / 427 行起）—— 这正是 L7 教训"测试按钮（unit/local smoke）只证 happy path，prod chaos 才证 fail path 闭环"的执行落地。

## Cross-bug 互锁观察（Phase 02.1 元学习）

Inj 4 把 BUG-8 与 BUG-6 **同时摊开**，是本 Phase 最有教育意义的发现：

- BUG-8 修法（Plan 02.1-02）—— `/control/unpause` endpoint + `make unpause-prod` —— 在 *容器内 localhost:8080/control/unpause* 单 POST 完全 work
- 但 *prod proxy 路径* 阻塞 — 因为 daemon PAUSED 后 `/health` 返 503 → Fly proxy 看 503 切流量 → `make unpause-prod` 收到 "could not find a good candidate within 40 attempts at load balancing"
- 这意味着 **BUG-8 的 UX 闭环（一条 make 切 RUNNING）依赖 BUG-6 先修**。Plan 02.1-03 把 fly.toml probe 从 `/health` 切到 `/healthz` 上线后，BUG-8 的"一条 make unpause-prod"才在 prod 真闭环

**教训**：bug 不是孤立点，是依赖图。Phase 02.1 三个 bug 的修法顺序（Plan 01 / 02 / 03）在执行层并行（Wave 1: 01+02 并行，Wave 3: 03 收尾）—— 但 *verification 闭环顺序* 是 03 必须先 deploy，02 的 prod UX 才闭环。下次类似场景：先看依赖图（02-CONTEXT.md § Cross-bug interaction）再排 Wave，不要只看 file overlap。
