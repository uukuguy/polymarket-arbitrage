# 满批消费者不能固定休眠

## 30 秒心智模型

`batch_size=100` 只应限制一次事务处理多少事实，不能再和
`interval_seconds=30` 相乘成为每分钟 200 条的永久消费上限。一次读取正好满 100
条意味着“后面可能还有积压”；此时应结束当前事务、让出一次事件循环以便响应停止，
然后马上读下一页。只有读到不足 100 条，才说明游标暂时追上生产端，可以等待 30 秒。

```text
full page  -> commit cursor -> cancellable yield -> next bounded page
short page -> commit cursor -> idle poll interval -> next page
```

## 为什么不直接把 batch 调成 10,000

大 batch 会放大事务时间、内存峰值、锁持有时间和 SIGTERM 排空时间，而且只是把饥饿阈值
推高。正确边界是“事务大小有界、追赶轮数不设人为休眠、每页之间可停止”。这样突发积压
可以快速排空，稳定态仍保持低频轮询。

## 为什么仍然只有一个 writer

吞吐问题来自不必要的睡眠，不来自单写者。资格状态带 epoch version 与 source cursor CAS；
并发 writer 会增加冲突和重复工作，却不提高单条事实应用速度。连续的非重叠 tick 已足够，
并保持恢复模型简单。

## 低内存节点的观察纪律

256 MB Machine 只运行其 resident process。不要通过 SSH 再启动一个 Python CLI 来“只读状态”；
解释器、依赖和数据库连接足以触发 OOM，反而中断被观察者。使用公共 control API 或平台日志；
确需独立数据库诊断时，在隔离的 operator 环境执行。
