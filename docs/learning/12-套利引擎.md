## 30 秒心智模型

套利引擎是一条「信号 → 路由 → 执行 → 持仓 → 平仓 → 止损」的流水线。M1 扫出候选信号后，M2 负责决定"在哪做、怎么做、做完了怎么管"：

```
┌───────────────────────────────────────────────────────────────┐
│  Signal（T2）：滑点模型计算跨场成本                              │
│  → ArbitrageSignal 带着 max_arbitrage_pct 进入闸门              │
│  → SlippageCalculator 估算 PM vs CLOB 的净成本各多少 bps          │
│  Code: src/polyarb/models/signal.py:144                         │
│  Code: src/polyarb/models/slippage.py:94                        │
├───────────────────────────────────────────────────────────────┤
│  Route（T3）：选场 — 哪条腿走 PM，哪条腿走 CLOB                   │
│  → RoutingEngine 遍历每个 market，调用 _select_venue             │
│  → 比较 pm_net_cost_bps vs clob_net_cost_bps，选便宜的           │
│  → 产出 ExecutionPlan（含有序的 ExecutionLeg 列表）               │
│  Code: src/polyarb/routing/engine.py:28                          │
├───────────────────────────────────────────────────────────────┤
│  Execute（T4）：顺序执行，首腿失败中止（Atomic Invariant）          │
│  → ExecutionEngine 逐腿执行，每腿最多 retry_attempts 次           │
│  → 第一腿失败 → ABORTED（后续全跳过）                             │
│  → 后腿失败 → PARTIAL（不 abort，记录完整失败模式）              │
│  → 成功腿更新 PositionTracker；失败腿不碰 tracker                │
│  Code: src/polyarb/execution/engine.py:104                       │
├───────────────────────────────────────────────────────────────┤
│  Position（T5）：生命周期管理 — 开仓 / 平仓 / 止损                │
│  → open_position 扣减 balance，录入 open set                     │
│  → close_position_with_fill 结算 PnL，归还 balance               │
│  → check_stop_loss_event 只在 realized loss 超阈值时触发          │
│  Code: src/polyarb/routing/position_tracker.py:120               │
├───────────────────────────────────────────────────────────────┤
│  Stop-Loss（T5）：止损面 — 对外发信号                             │
│  → ExecutionResult.stop_loss != None → caller 停止新信号          │
│  → CLI status 命令自动展示止损状态                                │
│  Code: src/polyarb/routing/position_tracker.py:265               │
└───────────────────────────────────────────────────────────────┘
```

**一句话总结**：M2 的目标不是「找到哪儿有套利」，那是 M1 的事。M2 是「确定能不能做、在哪个场子做、做了之后怎么管钱」。

## 用户工作流（30 秒实操法）

```bash
# 1. 先看路由决策（不执行）—— 确认闸门和选场逻辑
make eval-arb                                   # mid=0.5 stake=1000 legs=2
make eval-arb mid=0.45 stake=500 legs=3 venue=clob

# 2. 满意后跑 paper-mode 执行（不连真实交易所）
make run-arb                                    # 开仓，不自动平仓
make run-arb paper_close=1                      # 开仓 + 立即按 estimate_price 平仓（零 PnL 闭环）

# 3. 查看持仓和组合状态
make status-arb

# 4. 手动平仓（operator-driven，诊断用）
make close-arb market_id=synth-m0 exit_price=0.55
```

## 关键模块与代码地图

### 1. Signal 模型层 — `src/polyarb/models/signal.py`

整个 M2 的数据契约定义在一个文件里。核心类：

| 类 | 行号 | 作用 |
|---|---|---|
| `SignalStatus` | 17 | 信号生命周期：DETECTED → ROUTING → PENDING_EXECUTION → FILLED / PARTIAL / REJECTED / ABORTED |
| `ArbitrageSignal` | 144 | 一条套利机会，携带 `max_arbitrage_pct`（闸门判断）和 `list[MarketSignal]`（候选市场） |
| `MarketSignal` | 74 | 单个市场的报价快照：`condition_id`, `venue`, `price`, `hedge_ratio` |
| `ExecutionLeg` | 208 | 一条已就绪的执行腿：`exchange`（PM/CLOB）, `action`（buy/sell）, `size`, `limit_price` |
| `ExecutionPlan` | 240 | 有序的腿列表 + 飞行前成本估算 |
| `RoutingDecision` | 309 | 路由引擎产出：`plan` + `is_profitable` + `expected_profit_pct` |
| `PipelineResult` | 266 | 一次管道执行的终端结果（T4 之前的老契约，ExecutionEngine 现在用 `ExecutionResult`） |

关键字段：
- `ArbitrageSignal.max_arbitrage_pct`（171 行）：这是 T2 滑点模型修正后的预期利润百分比。**这个值进 RoutingEngine 闸门，不是 raw price difference。**
- `ExecutionLeg.limit_price`（228 行）：PM 腿 = `None`（市价单），CLOB 腿 = `price * 1.001`（buy）或 `price * 0.999`（sell）。这是 0.1% 的 heuristic buffer。

### 2. 滑点模型 — `src/polyarb/models/slippage.py`

套利的敌人不是市场方向，是执行成本。滑点模型把成本拆成三层：

```
total_cost_bps = market_impact_bps + fee_bps + mid_price_delta_bps
```

| 类 | 行号 | 作用 |
|---|---|---|
| `SlippageParams` | 14 | 所有可调参数（bps），默认值经过对标打表 |
| `SlippageResult` | 56 | 一条腿的成本拆分结果 |
| `SlippageCalculator` | 94 | 核心计算器 |

**三笔成本分别是什么**：

1. **market_impact_bps**（129-136 行）：Kyle's lambda 近似。越大的单子对市场冲击越大。公式：`impact_coef * notional / sqrt(daily_volume)`。`impact_coef` 默认 0.001，`daily_volume_usd` 默认 10k（T4 传真实值）。

2. **fee_bps**（138-148 行）：各交易所的 maker（rebate = 负成本）和 taker（正成本）费率。PM maker rebate 30bps 是 Polymarket 的 maker 激励政策。

3. **mid_price_delta_bps**（150-156 行）：下单时 mid 价 vs 生成信号时 mid 价之间的漂移。只有传了 bid/ask 时才计算；否则为 0。

**`fee_diff_bps` 方法**（37-52 行）：计算跨场执行 vs 单场的费率差。这个值是选场的关键输入。

**`estimate_cross_execution_savings` 方法**（172-203 行）：对同一个信号分别算 PM-only 和 CLOB-only 的成本，输出 dict → `_select_venue` 用的就是这个。

### 3. 路由引擎 — `src/polyarb/routing/engine.py`

| 方法 | 行号 | 职责 |
|---|---|---|
| `RoutingEngine.__init__` | 31 | 注入 `RoutingConfig` + `SlippageCalculator` |
| `route` | 43 | 入口：过闸门 → 建腿 → 产出 `RoutingDecision` |
| `_passes_gate` | 95 | `max_arbitrage_pct >= min_profit_threshold_pct` |
| `_build_execution_legs` | 106 | 遍历 markets，对每个 market 调 `_select_venue` |

**闸门逻辑**（95-104 行）：
```python
def _passes_gate(self, signal: ArbitrageSignal) -> bool:
    if signal.max_arbitrage_pct < self.config.min_profit_threshold_pct:
        return False
    return True
```
默认阈值 1.0%（`RoutingConfig.min_profit_threshold_pct`, config.py:30）。闸不过的信号返回 `None`，不生成决策。

**选场逻辑**（178-233 行）：对每个 market，同时算 PM 和 CLOB 的成本 bps，选净成本更低的。平局选 PM。如果上游 caller 在 `MarketSignal.venue` 设了非默认值（不是 `polymarket/pm/""`），则按 caller 指定的走（override）。

| 方法 | 行号 | 职责 |
|---|---|---|

| `execute` | 133 | 主循环：逐腿执行 + 首腿 fail abort + 止损检查 |

**Abort vs Partial 语义**（execution/engine.py:133-214）：

| 失败位置 | 结果状态 | 后续腿 | 解释 |
|---|---|---|---|
| 第一腿失败 | `ABORTED` | 全部跳过 | 原子不变式：不允许多腿策略单边暴露 |
| 中间腿失败 | `PARTIAL` | 继续执行 | 记录完整失败模式，已成交的腿保留 |
| 所有腿成功 | `COMPLETED` | — | — |
| 所有腿失败 | `FAILED` | — | 无成功腿 |

**可插拔模式**（104-131 行）：
- `leg_executor`：异步 callable `(ExecutionLeg, attempt) -> (bool, str|None)`。测试注入模拟任何失败模式；生产注入 py-clob-client 适配器。
- `fill_provider`：异步 callable `(ExecutionLeg) -> Fill`。生产端从交易所拿到真实 fill。
- `paper_close`：当 `True` 且无 `fill_provider`，引擎合成 `Fill(exit_price=estimated_price)` → 零 PnL 闭环（用于纸面模式的全生命周期演练）。

默认 `_default_leg_executor`（92-101 行）是一个 10ms sleep + 永远返回 success 的 no-op stub。

**止损面**（execution/engine.py:204）：`execute()` 完成后调 `tracker.check_stop_loss_event()`，结果写进 `ExecutionResult.stop_loss`。caller（CLI / daemon）看到 `stop_loss != None` 即停止新信号。

## 设计取舍

### T3 Revision 4 → 6：fee-differential vs depth-curve

最早的 venue 选择是简单的「Polymarket-first 硬编码」，因为 PM 的 maker rebate 看起来更便宜。但 Revision 4 后发现一个盲点：PM 的 rebate 再高，如果 CLOB 的总流动性更厚、market impact 更低，CLOB 的实际净成本可能更低。

Revision 6（SESSION 36）换成了完整的滑点感知选场：对每个 leg 同时估算 PM 和 CLOB 的 `net_cost_after_rebate_bps`（含 impact + fee + mid delta），然后选便宜的。平局选 PM（少一个交互点）。

相关测试在 `tests/routing/test_engine.py` 有行为矩阵（locked behavior matrix）。

### paper-mode vs real venue

这是 M2 的**安全生产发现面**。`make run-arb` 默认走默认 no-op executor — 也就是说永远执行成功，但没有任何钱在链上动。它的意义是：

1. **让操作员先看系统"会怎么做"**，确认路由决策和闸门正确
2. **让开发者在没连真实交易所时就能测试**完整的 signal → route → execute → close 链路
3. **防止误操作**：一定要显式接了 `leg_executor` + `fill_provider` 才连真实交易所

`make eval-arb` 比 `make run-arb` 更轻 — 只跑路由不执行，用来确认闸门逻辑。

### abort-vs-partial：为什么第一腿和后续腿不同

在 Polymarket 多腿套利中，如果 Buad 第一腿失败（比如 Alice 的 YES token 没买到），而你继续执行第二腿（Bob 的 YES token 卖出），你就变成了**单边裸空头**——另一条腿没对冲上。

如果第三腿失败了，第一腿已经成交了 — 你已经有裸露风险，但至少有一条腿成了。Partially filled 也比 abort 好，因为你可以手动平掉露出的那条腿。

所以：**首腿失败 → ABORT（保命），后腿失败 → PARTIAL（记录全貌）**。

### pluggable leg_executor / fill_provider

两个 callable 注入点（execution/engine.py:87-89）让 ExecutionEngine 不依赖任何具体交易所 SDK。测试可以注入 mock 来模拟任意失败模式；生产可以注入 py-clob-client 适配器；未来 M3（Kalshi）可以直接复用同一个 engine，只换 executor。

这也是「paper-mode 安全的生态位」：默认 executor 是 no-op，不连真实交易所。要连就必须显式注入。

## 对手测试（答得上 = 你懂了）

**1. 为什么 RoutingEngine.route() 不接受一个"我指定 PM 走高、CLOB 走低"的子市场列表？—— 它是怎么自动选场的？如果 PM 和 CLOB 的净成本恰好相等会选哪个？**

<details>
<summary>点击展开答案</summary>

RoutingEngine 不接受用户手动指定选场。每个 market 的选场由 `_select_venue`（engine.py:178）自动决定：它调 `slippage_calc.estimate_cross_execution_savings` 对同一个信号同时估算 PM 和 CLOB 的 `net_cost_after_rebate_bps`，选更便宜的。平局选 PM（少一个交互点，更简单）。

上游 caller 如果想 override，可以在 `MarketSignal.venue` 设一个非默认值（不是 `polymarket/pm/""`），`_select_venue` 会识别这个 override（engine.py:192-193）并跳过错综比较。但这不是"选场"，这是"强制"。

</details>

**2. ExecutionEngine 在执行多腿时，第一腿失败了会做什么？第三腿失败了会做什么？为什么处理方式不一样？**

<details>
<summary>点击展开答案</summary>

第一腿失败：`aborted = True; first_leg_failed = True`（engine.py:177-178）。后续所有腿标记 `skipped=True`，不执行。结果是 `ExecutionStatus.ABORTED`。

第三腿失败：记录为 failed，继续执行后续腿（engine.py:198-199 的 PARTIAL 分支）。已成交的第一、第二腿保留在位置追踪器中。

区别原因：第一腿失败意味着对冲还没建立，继续执行会让策略单边暴露（没对冲风险）。第三腿失败时第一二腿已经建立了对冲，继续执行只是损失覆盖率，但不会让整个策略崩。

</details>

**3. `make run-arb paper_close=1` 和 `make run-arb`（不带 paper_close）执行后在 `make status-arb` 的输出中有什么不同？为什么 paper_close 下 realized_pnl 是 0？**

<details>
<summary>点击展开答案</summary>

不带 `paper_close`：`make status-arb` 看到 `open_positions > 0`，持仓仍然是 open 状态（只开不平）。balance 已扣减 stake。

带 `paper_close=1`：`make status-arb` 看到 `open_positions = 0`，因为每条腿执行成功后马上被 `_maybe_close_for_leg`（engine.py:302-308）用 `Fill(exit_price=estimated_price)` 平掉了。`realized_pnl = 0` 因为平仓价格 = 开仓价格，无价差收益。这是纸面模式的"全生命周期演练"——验证 open→close 路径通，但不产生真实 PnL。

</details>

**3. `make run-arb paper_close=1` 和 `make run-arb`（不带 paper_close）执行后在 `make status-arb` 的输出中有什么不同？为什么 paper_close 下 realized_pnl 是 0？**

<details>
<summary>点击展开答案</summary>

不带 `paper_close`：`make status-arb` 看到 `open_positions > 0`，持仓仍然是 open 状态（只开不平）。balance 已扣减 stake。

带 `paper_close=1`：`make status-arb` 看到 `open_positions = 0`，因为每条腿执行成功后马上被 `_maybe_close_for_leg`（engine.py:302-308）用 `Fill(exit_price=estimated_price)` 平掉了。`realized_pnl = 0` 因为平仓价格 = 开仓价格，无价差收益。这是纸面模式的"全生命周期演练"——验证 open→close 路径通，但不产生真实 PnL。

</details>

**4. PositionTracker.check_stop_loss_event 为什么只看 realized PnL 不看 unrealized？如果我的持仓浮亏 50% 但还没平，止损会触发吗？**

<details>
<summary>点击展开答案</summary>

`check_stop_loss_event`（position_tracker.py:265-293）明确只看 `_realized_pnl`（已经结算的盈亏），不用 `_unrealized_pnl`（未结算的浮赢浮亏）。代码逻辑：`if self._realized_pnl >= 0: return None` — 只要还没真正亏钱，止损就不触发。

所以如果持仓浮亏 50% 但还没平仓，止损**不会**触发。理由是：unrealized PnL 可能在下一个 tick 回正，提前平仓会把浮亏变成实亏。只有当你的一连串交易已经真正亏掉了一定比例的钱（默认 `stop_loss_pct=5%`），系统才会喊停。

</details>

**5. 为什么 `close_position_with_fill` 要求 `fill.filled_size == position.stake`？如果 fill 是部分成交（比如只成交了 70%），会发生什么？这是 bug 还是 feature？**

`close_position_with_fill`（position_tracker.py:241-244）明确检查 `filled_size != pos.stake` 时抛出 `ValueError`——「partial fill not supported (T5 scope)」。这是 **feature**（设计阶段 scope 限制），不是 bug。

原因：T5 阶段没有实现部分成交的聚合逻辑。如果让一笔 70% 大小的 fill 悄悄结算，PnL 计算会错误（用的是总 stake，但只成交了一部分）。抛出 `ValueError` 确保"不对也比算错好"。部分成交聚合（一腿多个 fill 拼成满 stake）是 T5+1 的 scope。

生产环境下，operator 可以先 accum 多个 partial fill 再调 `close_position`（低层 primitive，不检查 size），或者等 T5+1 的聚合实现。
