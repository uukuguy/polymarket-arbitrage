## 30 秒心智模型

Phase 1 把 2 万个 Polymarket 市场落成了 SQLite + Parquet。Phase 1.1 在上面盖了 6 层抽象，让你不用写 SQL 也能"看"市场：

```
┌───────────────────────────────────────────────────────┐
│  Layer 1: Recipe（配方）                                │
│  → 一条 SQL where 子句 + 描述 + 输出，就是一个"配方"    │
│  → Code: src/polyarb/observation/recipes.py:30          │
├───────────────────────────────────────────────────────┤
│  Layer 2: scan-*（扫描）                                │
│  → 6 条内置配方，每条回答一个具体问题                    │
│  → `make scan-thick-but-slippery` = "哪些市场流动性      │
│     很大但价差也大？"                                    │
├───────────────────────────────────────────────────────┤
│  Layer 3: show-market（单市场详情）                      │
│  → 中英对照 + 时间维度 + neg-risk 兄弟 + 5 次历史        │
│  → Code: src/polyarb/observation/show.py:102             │
├───────────────────────────────────────────────────────┤
│  Layer 4: compare-snapshots / track-market（时序）       │
│  → 两个 snapshot 之间谁动了、某个市场的历史轨迹           │
│  → Code: src/polyarb/observation/diff.py:46              │
│  → Code: src/polyarb/observation/tracker.py:33           │
├───────────────────────────────────────────────────────┤
│  Layer 5: watchlist（自选）                              │
│  → yaml 管理关注列表 + 受限表达式告警                     │
│  → Code: src/polyarb/observation/watchlist.py:140        │
├───────────────────────────────────────────────────────┤
│  Layer 6: translation（翻译）                            │
│  → OpenAI 兼容 API 批量翻译 question，独立缓存表           │
│  → Code: src/polyarb/translation/client.py:127           │
└───────────────────────────────────────────────────────┘
```

**核心设计原则**：每一层都是只读 SQLite（`mode=ro`）+ 参数化查询。整个 observation toolkit 不会写一行数据。

## 用户工作流（30 秒决策法）

典型一天的使用节奏：

```bash
# 1. 早上：拿到当天数据（自动拉 Gamma + CLOB，含翻译）
make snapshot-markets-v

# 2. 横切扫描：从 2 万市场筛几十个候选
make scan-near-end              # 72h 内结算
make scan-neg-risk-incomplete   # 组合不全 = 套利候选
make scan-thick-but-slippery    # 避开陷阱

# 3. 深看候选：中英对照 + 历史轨迹
make show-market slug=<从 scan 输出挑的 slug>

# 4. 加入自选（编辑 watchlist.yaml）
#   - slug: <挑中的 slug>
#     reason: near-end neg-risk group 偏离大
#     alert_when: spread < 0.02

# 5. 第二天或下次 snapshot 后：查告警
make watchlist-alerts
make track-market slug=<关注的 slug>

# 6. 隔天对比：哪些市场漂了
make compare-snapshots
```

## 6 个 Batch 1 配方分别看什么

每个配方 = 一条参数化 SQL + 终端表格 + 自动 parquet 落盘。落盘路径：`data/scans/<name>/<timestamp>.parquet`。

### scan-thick-but-slippery — 流动性虚高陷阱

```
Where: liquidity_usd > 100000 AND (best_ask_price - best_bid_price) > 0.10
Code:  src/polyarb/observation/recipes.py:81
```

**为什么这是陷阱**：spread > $0.10 意味着 bid 和 ask 之间隔了至少 10 分钱。mid 价（bid+ask 的中位）看起来正常，但你的第一笔成交就已经差了 $0.05+，加上后续滑点，任何套利毛利都会被吃光。这类市场在 MM rebate 模式下才有机会（M4 阶段才讨论）。

**什么时候有用**：新人进市场先跑这个 —— 知道哪些市场**不能碰**比知道哪些能碰更重要。

### scan-near-end — 套利窗口最密区

```
Where: end_time_ms > <now> AND end_time_ms < <now + 72h>
Code:  src/polyarb/observation/recipes.py:87
```

**为什么这里是套利窗口最密的**：临近结算时，oracle 解析的概率分布坍缩，但订单簿可能滞后调整。这产生两种机会：（1）neg-risk 组内部失衡（一条腿更新了另一条没动）；（2）市场价格与现实概率的差距拉大。72h 是经验值 —— 更短没有流动性，更长机会还没到密集期。

**什么时候有用**：每天跑，筛出候选后再用 show-market 逐个看 neg-risk 兄弟和 spread。

### scan-ghost-suspicious — CLOB 幽灵报价

```
Where: JOIN validation_issues ON category='ghost_book'
Code:  src/polyarb/observation/recipes.py:97
```

**为什么这跟 incomplete=1 不一样**：这是 Phase 1.1 执行过程中暴露的关键纠正。CONTEXT.md 初稿写 `incomplete=1` 是笔误 —— `incomplete=1` 是 Layer 2 字段缺失（zombie / resolving / unknown），而 ghost_book 是 Layer 4 cross-source 检查：CLOB 返回了 token_id 但订单簿实际上是空的（bid=0.01, ask=0.99 这种假价）。两者表示不同问题，混用会找错可疑市场。

**什么时候有用**：如果你关心某个市场的 CLOB 流动性是否真实存在，跑这个。注意 72% 的 subset 市场都有 ghost_book 问题 —— 这是 Polymarket 的设计前提，不是 bug。

### scan-coin-flip — 高不确定性 50/50

```
Where: mid_price BETWEEN 0.45 AND 0.55
       AND end_time_ms BETWEEN <now> AND <now + 7d>
Code:  src/polyarb/observation/recipes.py:111
```

**这是套利候选还是赌博**：mid 在 0.45-0.55 意味着市场认为概率 ≈ 50/50 —— 不确定性最高。这类市场对新闻最敏感，可能在结算前大幅波动。如果你有信息优势（M4 阶段），这是信号源；如果没有，这就是噪音。

**什么时候有用**：配合近端筛选（near-end），排除掉那些"离结算还早"的 50/50 噪音。

### scan-neg-risk-incomplete — M2 套利直接信号

```
Where: neg_risk_market_id IS NOT NULL
Group: neg_risk_market_id
Having: ABS(SUM(mid_price) - 1.0) > 0.02
Code:   src/polyarb/observation/recipes.py:121
```

**为什么这是 M2 的直接信号**：neg-risk 市场是一个事件的所有互斥结果组成的集合，理论上所有 leg 的 mid 价加起来应该正好等于 1.0。偏离超过 ±0.02 意味着存在组合套利空间：买低的一条腿同时卖高的一条腿，锁定无风险利润。

**什么时候有用**：这是 6 个配方里离"套利执行"最近的一个。结果列表里的每一组都是候选。

### scan-by-tag — 赛道全景

```
Group: event_tags.tag_label
Code:  src/polyarb/observation/recipes.py:131
```

**看什么**：按 Polymarket 的事件标签（"Finance" / "Crypto" / "AL West" 等）聚合 —— 每个标签下有多少市场、总流动性、平均价差。1773 个标签，top 50 输出到终端。理解 Polymarket 的内容分布结构。

**什么时候有用**：找你的知识优势领域。如果你懂 Crypto 但不懂 Sports，就盯着 Crypto 赛道的市场。

## 三个新技术点的取舍

### 1. 翻译为什么用独立缓存表（不在 markets 加 question_zh 列）

Phase 1 的 markets 表是全量覆盖式写入（D-C1 决策）：每次 snapshot 先 `DELETE FROM markets` 再 INSERT 所有行。如果 question_zh 直接存在 markets 里，每次 snapshot 都会丢掉所有翻译缓存，下次必须重新翻译全部 2 万条。

所以用了独立 `question_translations` 表（Code: `src/polyarb/storage/schemas.py:140`），hash question_en 做主键，append-only。scan 时 `LEFT JOIN question_translations ON question_en`（Code: `src/polyarb/observation/scanner.py:148`），零额外查询成本，跨 snapshot 复用。

### 2. 为什么 SQL where 用字符黑名单 + read-only URI，不引 sqlglot

真实威胁模型：用户从论坛 / AI 生成的 yaml 复制陌生配方，不是防本人恶意。4 层防御：

| 层 | 机制 | 防什么 | Code |
|---|---|---|---|
| 1 | `sqlite3.connect("file:...?mode=ro")` | 引擎层拒绝任何 DDL/DML | scanner.py:142 |
| 2 | 正则黑名单（`; -- /* DROP DELETE UPDATE INSERT SELECT UNION...`） | 多语句 / 注释注入 / 子查询 | scanner.py:53 |
| 3 | WHERE 字符白名单（只允许 `a-zA-Z0-9_()., '=<>!+-*/%`） | 函数调用 / 算术注入 | scanner.py:65 |
| 4 | 参数化 limit（int 强转） | DoS（`LIMIT 99999999`） | scanner.py:114 |

为什么不用 sqlglot（SQL parser）？它 5MB 依赖，收益不匹配 —— 我们只是执行一条参数化 SQL，不是 parse 任意 SQL。trust split（builtin 配方 trusted=True 走 expressiveness 路径，yaml 配方 trusted=False 走全量检查）已经满足需求。

### 3. 为什么 watchlist alert_when 用受限 AST walker，不用 Python 内置任意代码求值器

Python 内置的表达式求值函数能跑任意代码 —— 包括动态导入 + 系统调用。本项目运行时 load 的 `watchlist.yaml` 可能来自 git 同步的其它机器或 AI 生成，交给那个内置函数等于把代码执行权外包出去。

我们的方案：`ast.parse(expression, mode="eval")` → 遍历 AST 节点 → 只允许白名单节点类型（Code: `src/polyarb/observation/watchlist.py:29`）：
- `Expression`, `Constant`（仅数字）, `Name`（仅在 ALLOWED_VARS）
- `UnaryOp`（Not / USub）, `BinOp`（+ - * /）
- `Compare`（< <= > >= == !=）, `BoolOp`（And / Or）
- **禁止**：`Call`, `Attribute`, `Subscript`, `Lambda`，以及任何不在白名单的节点类型

效果：把"能执行的语言"限定到算术 + 比较 + 白名单变量 = 11 个已知字段。把"配置文件"和"代码文件"重新分开。

### 4. DuckDB 为什么用 union_by_name=true

Phase 1.1 给 markets 加了 category/tags（Phase 1 的 parquet 没有这些列）。跨 parquet 查询时 `read_parquet(glob, union_by_name=true)` 自动为老 parquet 缺失的列填 NULL，不报错。

**不变量**（RESEARCH §3.5）：parquet schema **只能加列，不能改列类型**。如果未来某 phase 要把 `liquidity_usd` 从 float64 改成 int64，必须写迁移脚本重写所有历史 parquet —— DuckDB 的 `union_by_name` 只对齐列名，不对齐类型。

### 1. Recipe 定义

def _eval_node(node: ast.AST, env: dict[str, float]) -> float | bool:
    t = type(node)
    if t not in _ALLOWED_AST_NODES:       # ← 白名单外的任何节点 → ValueError
        raise ValueError(f"AST node {t.__name__} not allowed")
    if t is ast.Constant:
        if not isinstance(node.value, (int, float)):  # 只允许数字常量
            raise ValueError("only numeric constants allowed")
    if t is ast.Name:
        if node.id not in ALLOWED_VARS:   # 只允许 11 个预注册变量名
            raise ValueError(f"unknown variable: {node.id!r}")

## 自定义配方（config/scan_recipes.yaml）

内置 6 条配方是起点。你自己的观察逻辑写进 `config/scan_recipes.yaml`：

```yaml
# config/scan_recipes.yaml
- name: my-watchtower
  description: 高流动性 + 低 spread + 近端 = 最优候选
  where: liquidity_usd > 50000
         AND (best_ask_price - best_bid_price) < 0.03
         AND end_time_ms > <now>
         AND end_time_ms < <now + 7d
  order_by: liquidity_usd DESC
  limit: 30
```

```bash
make scan name=my-watchtower   # 跟 builtin 一样的体验
```

⚠️ yaml 配方的 where 走严格 4 层防御 —— SELECT 子查询、算术表达式等都不允许。要复杂逻辑就写成 builtin 配方提 PR。

**1. scan-thick-but-slippery 找出来的市场为什么不能直接套？**

<details>
<summary>点击展开答案</summary>

spread > $0.10 意味着 bid 和 ask 之间隔了至少 10 分钱。mid 价是用 (bid+ask)/2 算的"虚假中位"——真实成交时第一笔 fill 已经差 $0.05+，加上后续滑点，任何套利毛利都会被吃光。这类市场只在 MM rebate 模式下有戏（M4 智能策略阶段才讨论）。

换句话说：这个配方不是用来"找机会"的，是用来"排除雷区"的。新人进市场先跑这个，知道哪些不能碰比知道哪些能碰更重要。

</details>

**2. near-end 市场为什么是套利窗口最密的？**

<details>
<summary>点击展开答案</summary>

临近结算时，oracle 解析的概率分布坍缩（结果的真实概率越来越确定），但订单簿可能滞后调整。这产生两种机会：
1. neg-risk 组内部失衡 —— 一条腿更新了（因为有人知道结果），另一条腿没动
2. 市场价格与现实概率差距拉大 —— 信息不对称的钱

72h 是经验值：更短（<24h）流动性基本枯竭，更长（>7d）概率坍缩还没开始，机会密度低。这个窗口是 M2 组合套利和 M4 信息套利的最密集区。

</details>

**3. scan-ghost-suspicious 为什么 JOIN validation_issues 表而不是 markets.incomplete=1？**

<details>
<summary>点击展开答案</summary>

这是 CONTEXT.md 初稿的笔误，在执行中被发现并纠正。两者表示完全不同的问题：

- `incomplete=1`：Layer 2 字段缺失 — 市场缺少必要字段（zombie / resolving / unknown），Validation 阶段打的标记
- `ghost_book`：Layer 4 cross-source 检查 — CLOB 返回了 token_id（声称有订单簿），但实际拉到的订单簿是空的（bid=0.01, ask=0.99 假价）

`incomplete=1` 存于 markets 表直列；`ghost_book` 存在 validation_issues 表（category='ghost_book'）。用 `incomplete=1` 筛 ghost_book 会把所有字段缺失的市场混进来，而真正的幽灵报价（如果 incomplete=0）会漏掉。

</details>

**4. watchlist 的 alert_when 走 AST 白名单而不是 Python 内置任意代码求值器，为什么这个区别在生产环境很重要？**

<details>
<summary>点击展开答案</summary>

Python 内置的表达式求值函数能执行任意代码 — 包括 `__import__('os').system('rm -rf /')`、动态导入、系统调用。本项目运行时 load 的 `watchlist.yaml` 可能来自：
- git 同步的其它机器
- AI 生成的配置
- 论坛 / 社区复制的模板

交给那个内置函数等于把代码执行权外包给任何能写 yaml 的人。

AST walker 方案（`ast.parse` + 节点白名单）把"能执行的语言"限定到：算术（+ - * /）+ 比较（< <= > >= == !=）+ 布尔（and or not）+ 11 个白名单变量名。没有函数调用、属性访问、字符串、下标、lambda。这是把"配置文件"和"代码文件"重新分开 —— yaml 是配置，不是代码。

</details>

**5. 如果未来某 phase 想给 markets 表改列类型（INTEGER → BIGINT），为什么必须重写所有历史 parquet？**

<details>
<summary>点击展开答案</summary>

DuckDB 的 `read_parquet(glob, union_by_name=true)` 只对齐**列名**，不对齐**列类型**。老 parquet 的 INTEGER 列 + 新 parquet 的 BIGINT 列在 DuckDB UNION 时类型不匹配，直接报错。

所以 RESEARCH §3.5 立了不变量：**parquet schema 只能加列，不能改类型**。如果非改不可，必须写迁移脚本：
1. `read_parquet(glob)` 读全部历史 parquet
2. `CAST(liquidity_usd AS BIGINT)` 转类型
3. 逐文件重写（`tmp + os.replace` 原子替换）

这个成本不低 —— 100 个 snapshot × 20k 行 = 2M 行重写。所以设计时要把列类型选择看作不可逆决策。

</details>
