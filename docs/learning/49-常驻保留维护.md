# 常驻保留维护：证据不会因为“有清理命令”就自动变小

## 30 秒心智模型

M1 的 Structure 数据分三类：authority evidence 证明哪一代可信；replayable payload
承载可重放的大体量行；operational runtime 说明后台维护现在是 idle、running、backoff
还是 blocked。清理只能删除超过 current + rollback 两代之外的 payload，必须保留 publication、
comparison receipt 和 cleanup receipt 这条证明骨架。

因此生产级维护不是偶尔手跑命令，而是 daemon 内唯一、低优先级、可重启的 owner：每次最多删
500 行，先后两次检查 Quote 是否活跃/到期，持有共享 producer lock 完成一个事务后释放。失败写入
持久 backoff/blocked 状态，health 和 Polywatch 读取同一事实；成功继续收敛到两代保留底线。

## 三条容易混淆的边界

### Checkpoint 为什么能清零 streak，却不能宣告恢复？

连续失败的定义是“中间没有真实前进”。一个经过认证且写入 durable cursor 的非 defer chunk 已经
证明系统还在向前，所以后续一次失败应从 1 重新计数。但 `RECOVERING → RUNNING` 需要完整、认证、
可服务的新真值；checkpoint 只证明进度，不证明终点。

### 为什么 Quote 同时拥有 snapshot retention 和 producer-lock 优先级？

Quote run 是 snapshot 的真实外部 owner；只看旧的辅助引用表会误删仍被报价使用的快照。运行时上，
机会新鲜度也比历史 housekeeping 更接近用户价值，所以 cleanup 在拿锁前和拿锁后都检查 Quote。
已经开始的 500 行事务不会被粗暴中断；Quote 最多等待当前一个有界事务，然后在下一事务前抢占。

### 为什么失败不应“长期静默降级”？

runtime 表记录连续失败、下一次尝试、错误类型和 checkpoint。低于阈值的 backoff 是 warn；达到阈值、
authenticated block，或仍有 reclaimable pressure 时 runtime 长期不前进，均为 fail。Polywatch 对同一
component 首次报警、周期提醒，并在状态恢复后发 recovery，而不是让降级永久存在。

## 设计取舍

- 保留两代是回滚能力，不是可调成 0/1 的磁盘旋钮。
- 每事务 500 行换取 Quote 公平性和取消边界；常驻循环提供吞吐，而非扩大单事务。
- writer busy 是资源竞争，不增加 failure streak；unexpected error 才指数退避。
- `make structure-generation-cleanup` 是人工诊断/推进一块，不是生产调度器。
- 约 30 万行真实 SQLite 验收要求 `<240s`、单事务 `<=500`、最终 retained `<=2`、
  reclaimable `=0`，并验证部分进度重启与 Quote 抢占。

## FAQ 增量

### 为什么不让 health 只看 retained/reclaimable？

pressure 说明“有多少工作”，不说明“worker 是否活着”。runtime 说明 owner 是否持续尝试、退避或阻断；
两者必须一起看，才能区分正常收敛、短暂竞争和永久停摆。
