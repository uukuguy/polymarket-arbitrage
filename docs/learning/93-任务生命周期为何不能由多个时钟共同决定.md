# 任务生命周期为何不能由多个时钟共同决定

## 30 秒心智模型

一个任务只能有一个“生死裁判”：数据库中的 fenced attempt。lease 说明谁能写，heartbeat
说明进程还活着，progress 说明工作还在推进，attempt deadline 限制总生命周期；调度器只负责
何时再看一眼，不能再套一个更短的 timeout。

停止服务时也不是“等多久就算失败”。先停止新 claim，再请求当前 worker 到安全边界；若在统一
terminal grace 内没有结束，就保留 lease、checkpoint 和 runtime event 作为下一任可 reclaim 的
事实。晚到的旧线程会被 lease epoch 拒绝，不能偷偷提交终态。

## 关键代码片段

policy 不是一组互不相干的秒数，而是一组必须同时成立的不变量：

```python
# src/polyarb/control_plane/runtime_deadlines.py:122
bounded_lease = max(3, int(lease_seconds))
heartbeat = max(1, min(30, bounded_lease // 3))
progress = max(bounded_lease, heartbeat * 3)
attempt = max(progress, bounded_lease * spec.attempt_multiplier)
terminal_grace = max(3, min(30, bounded_lease // 2))
io_timeout = max(1, min(90, progress - 1, terminal_grace - 1))
```

因此始终有 `io_timeout < terminal_grace`、`io_timeout < progress <= attempt`。worker 不得在
自己的模块里复制另一套 profile，scheduler 也没有 claim 后的 turn timeout。

停止时，同步调用不能被 Python 安全杀死，所以只能把“进程能返回”和“旧调用还能提交”分开：

```python
# src/polyarb/control_plane/service_lifecycle.py:68
request_stop()
task.cancel()  # 第一次：允许 worker 进入安全终态路径
done, _ = await asyncio.wait((task,), timeout=terminal_grace_seconds(...))
if not done:
    task.cancel()  # 第二次：grace 已耗尽，bridge 必须 detach
    # durable lease/checkpoint 保留；下一 epoch 用 fencing 接管
```

daemon thread 使 `asyncio.run()` 不会在默认 executor shutdown 时无限 join；真正的数据安全仍由
client I/O bound、checkpoint 和 lease epoch 提供，而不是 daemon 本身。

## 设计取舍

### 为什么不能简单把 105 秒改成 1,200 秒

因为第二个计时器仍然拥有错误的终止权。工作量再次变大时，同一故障只会晚一点复发；而且
scheduler cancel 若绕过 worker terminal path，数据库仍会留下 `running` 孤儿。

### 为什么 open circuit 要先于 expired lease 判断

open circuit 的 runtime row 本来就是最后一次失败 attempt，heartbeat/lease 过期是正常历史。
若先判断它，会生成 `reclaim-job`，但 action target 却是 `circuit`，executor 必然拒绝并永久卡住。
正确顺序是 cooldown 到期后只由 controller 释放一次 `probe-circuit`。

### 为什么 checkpoint 需要数字序列

时间戳可能相同，字符串 cursor 也不保证业务顺序。`checkpoint_sequence` 在 job row 锁内单调分配，
takeover 只按它恢复；generation、digest、policy 任一不匹配都拒绝复用。

### qualification 为什么不是每次首次启动都跳到 high-water

系统的第一条 qualification 身份必须消费当前已有 breaker，否则启动前刚发生的 terminal failure
会被漏掉。只有数据库已存在 predecessor identity 时，新 release 才从当前 ledger high-water 建立
baseline，旧历史不会伪装成新版本的连续在线证据。

## FAQ 增量

### terminal grace 耗尽后立刻把 job 写成 retryable，不是更清楚吗？

不一定。此时旧同步线程可能仍持有连接；由没有 attempt fence 的 scheduler 强写终态，会和 worker
的 terminal transaction 竞争。更安全的权威路径是保留当前 lease，等待过期后由 claim/recovery
事务原子关闭旧 attempt、写失败事件，再开启新 epoch。

### 只读 status 有 statement timeout，为什么仍可能挂很久？

`statement_timeout` 只限制 PostgreSQL 执行 SQL 的时间，不限制服务端执行完成后客户端接收巨大结果的
时间。qualification epoch 把完整 `fact_records` / `fact_digests` 保存在 append-only 证据中；operator
status 若 `SELECT *`，结果大小会随运行时间增长，数据库已显示 idle，客户端仍可能在收 JSON 并占着
事务。仅把 `fact_records -> -1` 留在查询里也不够：传输虽小，数据库仍需处理增长值。Revision 029
把最后 fact、recovery 总数和最近 20 条摘要做成写入时更新的 `STORED GENERATED` 列；status 只读这些
固定投影，前一 epoch breaker 只读原因和时间两个标量。证书验证路径才读取完整证据。这里的“可中断”
首先来自有界数据合同，不是再给 CLI 外套一个秒数。

### 第一次取消后的 cleanup 可以无限等吗？

不可以。第一次取消只获得一个统一 terminal grace，用来完成已经开始的 fenced terminal transaction。
第二次取消就是 grace 到期：blocking bridge 必须 detach，异步 reader 必须停止排空，而且 cancellation
handler 不得再启动一条新 DB/R2 调用。否则所谓“可停止”仍会被 cleanup 路径反向绑架。
