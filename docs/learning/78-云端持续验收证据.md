# 云端持续验收证据

## 30 秒心智模型

“系统在运行”与“系统能证明自己连续健康运行了 24 小时”是两件事。前者可以由某台电脑上的脚本声称；后者必须由云端独立角色，把每次观察写入不可变账本，并由同一套 fail-closed 规则复核。

这套机制观察五台正式采集 Worker，而第六台 `soak_sampler` 不采集市场、不写 R2、不领取 job。它只做三件事：读控制面、读 Fly Machine 状态、每五分钟把签名快照追加到 Postgres。

## 代码地图

- [cli_control_plane.py](../../src/polyarb/cli_control_plane.py:305)：通过 Fly Machines HTTPS API 读取精确 Machine 状态；生产镜像不依赖 `flyctl`。
- [cli_control_plane.py](../../src/polyarb/cli_control_plane.py:347)：将控制面和 Machine 状态封装为 canonical observation，基线与普通样本走不同写入方法。
- [cli_control_plane.py](../../src/polyarb/cli_control_plane.py:372)：sampler 固定节奏运行；任一次读/写失败即退出，让缺口成为可审计的失败证据。
- [soak_evidence.py](../../src/polyarb/control_plane/soak_evidence.py:92)：24 小时验收规则：样本时序、900 秒最大缺口、五机持续 started、控制面 available、计数不倒退。
- [postgres.py](../../src/polyarb/control_plane/postgres.py:120)：基线和普通 observation 进入独立的 append-only 云端账本。

## 关键取舍

`soak_sampler` 不做“失败后在本地补一条样本”。那会把证据系统变成掩盖故障的系统。它退出后，下一次验收会因时间缺口失败；这是故意的 fail-closed 设计。

Fly API token 采用只读组织 token：它只能读取 Machine 状态，不能发布、重启或修改任何 Machine。数据库凭据仍只用于追加账本。
