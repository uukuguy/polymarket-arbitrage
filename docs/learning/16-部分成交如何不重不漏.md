# 部分成交如何不重不漏：每个 fill 都是一笔不可重复的状态迁移

> Phase 7 / H-005。读完后你应该能解释：为什么“累计成交 30 shares”不是一个
> 安全的重试身份，以及为什么最后一笔成交必须吃掉剩余 cost basis。

## 30 秒心智模型

把开放仓位看成一张还没有撕完的票：

- `quantity` 是还剩多少格；
- `cost_basis` 是这些剩余格仍锁着多少现金；
- 每个 venue `fill_id` 是一次只能撕一次的防伪编号；
- partial fill 撕掉一部分 quantity，并按比例释放对应 cost basis；
- final fill 把最后的 quantity 和所有现金余数一起拿走。

```text
BUY 100 @ .40                          remaining authority
q=100, cost=40, balance=960
        │ fill-1: 30 @ .45
        ▼
q=70, cost=28, balance=973.5, realized=1.5
        │ retry fill-1 → receipt replay, no mutation
        │ fill-2: 70 @ .50
        ▼
q=0, cost=0, balance=1008.5, realized=8.5
```

## 为什么仓位字段表示“剩余权力”

partial fill 之后，原始 quantity=100 已经不能继续授权下一次成交；下一次最多只能消费 70。
因此仓位不另存一套“初始值 + 累计成交”再在每个调用点临时相减，而是直接把
`Position.quantity_value` 和 `cost_basis_money` 更新为剩余值。

核心迁移在 `position_tracker.py:478-500`：

```python
allocated_cost = Money.allocate(
    pos.cost_basis_money,
    fill.filled_quantity_value,
    pos.quantity_value,
)
state.balance_money += allocated_cost + pnl_money
if is_partial:
    pos.quantity_value -= fill.filled_quantity_value
    pos.cost_basis_money -= allocated_cost
else:
    del state.open_positions[fill.market_id]
```

这样 overfill 的判断只需比较 fill quantity 与当前 remaining quantity；数据库重启后读到的也
是同一个 authority，而不是需要重新拼装的事件缓存。

## 为什么最后一笔不能继续普通比例舍入

Money 和 Quantity 都只有六位小数。多次比例分配时，HALF_EVEN 会让每一笔最多产生微小的
量化差；如果 final fill 仍重新乘比例，可能留下 `1 micro-pUSD` 没有归属。

`Money.allocate` 的规则是：当 numerator 等于 denominator，直接返回全部 remaining Money。
所以中间 fill 可以量化，最后一笔一定清空 residual，账户守恒不靠“误差够小”。

## 为什么 fill ID 比 operation ID 更权威

调用者可能因为超时用另一个 request/operation ID 重试，但交易所的同一笔成交事实没有变。
如果 caller ID 能覆盖 fill ID，同一 fill 就可能以两个 operation 写入两次。

因此 tracker 无条件使用：

```text
fill_id=abc123  →  operation_id=venue-fill:abc123
```

SQLite 先查这个 receipt：存在就返回原来的精确 PnL，不重新执行 transition。即使第一次进程已经
提交但 stdout 丢失，第二个进程也只能观察同一结果。

## Fail-closed 边界

- `filled_quantity <= 0`：没有有效状态变化，拒绝；
- `filled_quantity > remaining`：会制造负仓位，拒绝；
- anonymous partial fill：无法证明重试是不是同一成交，拒绝；
- 同一 fill ID 指向另一 market：operation target conflict，拒绝；
- anonymous full operator/paper close：保留旧兼容路径，因为一次就删除整个仓位。

这些校验都在 repository transition 内完成。异常意味着 transaction rollback，不会留下
“quantity 已扣、receipt 没写”或相反的半状态。

## 设计取舍

1. **复用 applied operations 表，不新增 fill ledger**：当前需求是 exactly-once mutation 与
   receipt replay，已有事务边界已经满足；订单审计明细留给 live adapter。
2. **保留 `--operation-id`**：人工 full close 仍可安全重试；venue partial fill 使用更强的
   `--fill-id`。
3. **PnL 仍由 paper 价格公式计算**：H-005 只解决数量、残余与幂等；实际 proceeds/fees
   属于 H-006 reconciliation。
4. **Engine 可多次收到同一 fill**：不在易丢失的进程内存里去重，而让 SQLite receipt 成为
   唯一裁决者。
