# 外部告警监督器

## 30 秒心智模型

Telegram 和 Dashboard 只有在**有人发现故障**时才有意义。原有 Fly
watchdog 能监控采集、API、evidence 和 writer，但它自己若停止，便失去
发现者。外部监督器把这一个监控节点放到 Cloudflare Cron：每分钟只读取
精确的 Fly alert Machine；停止、API 异常或 start 事件增加时，直接向
Telegram 和 Dashboard 账本写入同一个 `detected` 事实，恢复后写入
`recovered`。

这不是第二套采集器，也不读取市场或数据库。它只守护“谁来守护看门狗”
这个最小的独立失败域。

## 关键代码

- `monitoring/watchdog-supervisor/src/index.js:12`：只读取指定 alert
  Machine；机器 ID 不匹配、响应无法解析、非 `started` 都变成有界故障码。
- `monitoring/watchdog-supervisor/src/index.js:42`：由来源、事件类型、Cron
  时刻和故障集合计算 SHA-256 幂等键，重复触发不会在账本留下重复 receipt。
- `monitoring/watchdog-supervisor/src/index.js:56`：同一次状态转换并行投递
  writer 与 Telegram；其中一端失败会让 Cron 重试，不能静默吞掉。
- `src/polyarb/control_plane/runtime_event_writer.py:31`：`source` 可选但严格
  校验，Dashboard 事件会显示 `cloudflare-watchdog-supervisor`，不会误归因为
  Fly 内 watchdog。

## 设计取舍

KV 只保存上一轮健康状态和 start 计数，以便做到“只在转换时报警”；它不是
业务事实的权威库。真正可审计的事实仍在 Postgres incident ledger。Worker
只有 Fly 只读 token、Telegram 与 writer token：没有 Supabase、R2、行情、
调度或钱包凭据，即使它出错也不能影响采集。

首次健康观测不发送“恢复”，因为它没有可关闭的故障。首次不健康必发
`detected`；从不健康回到健康必发 `recovered`。因此 Dashboard 能解释
异常的来源、时间、节点和闭环，而不是只有一条手机消息。

## 自检题

1. 为什么独立监督器只检查 alert Machine，而不重复查询所有采集 worker？
2. 为什么 KV 不能作为 Dashboard 的权威故障历史？
3. Fly Machine 是 `started` 时，哪类事件仍能证明它刚刚发生了进程级故障？

## FAQ 增量

- **Cloudflare Cron 重投会不会写两次？** writer 使用确定性 64 位幂等键；
  同一 scheduled transition 的重投返回同一 receipt。Telegram 采用
  at-least-once 语义，宁可极少数重复提醒，也绝不遗漏故障。
