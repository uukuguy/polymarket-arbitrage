# 低内存控制器的单进程恢复事务

## 30 秒心智模型

256MB runtime controller 只能容纳一个 Python 运行时。通过 SSH 再启动一个
Python，不是“临时诊断”，而是在同一 Machine 里创建第二个资源所有者，会触发
OOM 并把恢复控制器本身打掉。

安全恢复是一笔可回滚的进程替换事务：保存 fresh Machine 基线，通过
`current_version` 乐观锁把常驻 observe-only daemon 替换为一个 exact target/action
维护进程；维护进程只在 worker lane 忙时有界等待，执行一次后停止；验证数据库中
出现新的 `completed/succeeded` action，最后恢复保存的完整基线并验证新版本。

```text
fresh baseline -> process replacement -> bounded lane wait -> exact action
      |                                                    |
      +---------------- exact restore <--- outcome proof <-+
```

## 关键代码

- `src/polyarb/control_plane/fly_machine_update.py`：渲染 maintenance/restore payload，
  保留 VM shape、镜像、权限和 stop contract；拒绝 Machine ID、region、version 或
  config 漂移。
- `src/polyarb/cli_control_plane.py`：`runtime-reconcile-until` 只重试
  `deferred + worker-lane-busy`，默认每秒一次、最多 45 秒；其他状态立即失败。
- `Makefile`：统一暴露 render、outcome verify、restore 三个入口。

维护进程的成功条件不是“进程退出”或“Machine stopped”。这两种现象也可能来自
唯一约束冲突、DB 失败或 lane 一直繁忙。后置验证会比较维护前后的 action ID，要求
恰好出现一个新的、目标与动作完全匹配的 `completed/succeeded` 记录。

## 为什么 lane busy 只能有界等待

circuit probe 使用原任务的 worker lane。生产 backlog 非空时，该 lane 可能正在执行
普通作业；恢复器必须等待空档，不能与它并发写同一任务事实。另一方面，无限等待会
把维护 Machine 变成新的常驻单点，因此等待预算固定为 45 秒，controller lease 必须
比预算更长。

probe release 自身还有领取窗口。正确顺序是：worker 已运行且健康，释放一个 probe，
在窗口内观察 successor attempt，关闭后才处理下一个 circuit。批量释放、之后再启动
worker 会让窗口过期；同时释放多个 probe 会违反 singleton lane 防惊群约束。

## 设计取舍

- 不增大 controller 内存掩盖 SSH 双进程：资源形状不是进程所有权协议。
- 不复用固定 maintenance owner：`controller_id` 与 `owner_id` 都必须逐次唯一，避免
  `(owner_id, lease_epoch)` 冲突。
- 不缓存一整个批次的 Fly token：每次云变更前重新取得短期凭证；403 后只重放带
  `current_version` 的当前步骤。
- 不把 worker-lane-busy 计作失败 action：它在预算、action 和业务 mutation 之前
  defer，等待空档后才执行一次。

## FAQ 增量

### 能否直接让常驻 controller 接收恢复请求？

可以，这是下一步更低中断的形态；但必须有持久化、鉴权、exact selector 和审计入口。
在该入口落地前，乐观锁保护的单进程替换事务比 SSH 第二进程更安全，也能在任一步骤
失败后从保存的基线恢复。
