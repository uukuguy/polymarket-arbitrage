# 四类证据时间线：不要在 Dashboard 拼两个不同快照

## 30 秒心智模型

一个套利组的运维事实来自四条链：成员修订、报价批次、机会状态转换、异常事件。它们不是四张“当前状态卡片”，而是一条按时间倒序排列的证据流。

关键约束有三个：

1. 四类数据必须在同一个 SQLite 读事务中取得。
2. 每个来源最多返回 `limit + 1`，合并后再截成一页。
3. 历史被压缩时必须明确报告 floor，不能把“已删除”说成“从未发生”。

因此 group 页面只请求一次：

```text
GET /perception/groups/{group_id}/timeline?limit=100&before=<opaque>
```

## 为什么 opportunity 只记录“转换”

Candidate watcher 可能连续多次得到同一个结果。若每次轮询都渲染，时间线会被重复的 `watching` 淹没。这里比较归一化状态：

```text
(last_result, opportunity)
```

只有二元组改变才产生 `opportunity_transition`。`watching/edge → no-edge/no edge` 是转换；连续两个 `watching/edge` 不是。

## compaction floor 上为什么需要 per-group seed

Candidate 历史压缩使用全局高水位。假设 g-b 写入了全局最后一行，g-a 的旧 fact 可能全部被删除。之后 g-a 再写一行时，仅看物理 suffix 会误以为它是第一条事实。

checkpoint 因此在认证的 `seeds_json` 中保存每个 group 在压缩点的归一化状态。首条 suffix 用这个 seed 作 predecessor：

```text
checkpoint seed (g-a: watching/edge)
             ↓
first suffix (g-a: no-edge/no edge)
             ↓
render one transition, not “initial”
```

旧 checkpoint 若没有 per-group seed，代码不会虚构 predecessor；在已有压缩前缀的情况下，它宁可不渲染无法证明的首条转换。

## 游标为何必须绑定 group identity

游标承载：

```text
version, group_id, occurred_at_ms, class_order, stable_id
```

同毫秒时先按固定 class order 排列，再按 stable ID 倒序。解码后必须重新 canonical encode 并与输入完全相等，因此 padding、替代 JSON 表达和跨 group 重放都会被拒绝。

## 设计取舍

- Candidate 的 membership/quote/fact floor 是全局、保守的。现有 checkpoint 没有每组删除计数，所以不能伪造精确数字。
- Incident floor 是 `candidate:<group_id>` exact-scope，因为 incident authority 本来就维护 scope floor。
- `history_complete=false` 只说明 prefix 曾被压缩；当前页是否还有下一页只看 `next_before`。
- Dashboard 仍复核服务端顺序，但不再自行判断 incident 属于哪个 group。
