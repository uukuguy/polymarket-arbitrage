## 30 秒心智模型

Phase 02 把 L1 从「我电脑上能跑」变成了「云上 7×24 不靠我管」。核心变化是三件事：

```
┌───────────────────────────────────────────────────────────────┐
│  1. 云原生 Daemon（Fly.io）                                     │
│     → HTTP server (uvicorn) + 调度器（asyncio）并行跑           │
│     → asyncio.gather — 不是线程，不是进程，是协程               │
│     → 单 1GB VM，SQLite 卷挂载（/data），两次/天自动快照         │
│     Code: src/polyarb/daemon/main.py:38                        │
├───────────────────────────────────────────────────────────────┤
│  2. 自愈状态机（SnapshotScheduler）                             │
│     → RUNNING → 3 次连续 FAILED → PAUSED + Telegram 告警       │
│     → DEGRADED 不算失败（mirror/R2 挂了，数据还在 SQLite）       │
│     → PAUSED 之后 /scan 或 SSH 手动恢复                         │
│     Code: src/polyarb/daemon/scheduler.py:35                   │
├───────────────────────────────────────────────────────────────┤
│  3. 三条告警路径（全 E2E 验证）                                  │
│     → Sentry（错误聚合）→ Better Stack（SLA uptime）             │
│     → Telegram（直达手机）                                      │
│     Code: src/polyarb/daemon/alerts.py                         │
│     Dashboard: Vercel Next.js → Supabase 镜像数据               │
└───────────────────────────────────────────────────────────────┘
```

**核心设计哲学**：SQLite 是主库，Supabase/R2 是可选镜像。镜像挂了 = DEGRADED（数据安全），Gamma API 不通 = FAILED（数据缺失）。两类故障的处理方式完全不同。

## 用户工作流（日常运维）

```bash
# ── 早上 30 秒健康检查 ──────────────────────────────────────────
# 1. 查看 /health 三态（pass/warn/fail + 4 子检查）
curl https://polyarb-l1.fly.dev/health | python -m json.tool

# 2. 查看 Vercel dashboard（最近快照数据 + movers）
# → https://polymarket-arbitrage-ppf6exo78-jiangwen-su-s-projects.vercel.app/status

# ── 出问题时 ────────────────────────────────────────────────────
# 3. 查看调度器实时状态（需要 flyctl）
flyctl ssh console -a polyarb-l1 -C "cat /tmp/polyarb-state.json"

# 4. 查看 SQLite 磁盘用量（7 天 soak 目标 ≤ 4GB）
flyctl ssh console -a polyarb-l1 -C "df -h /data"

```

## 关键代码片段

### 1. asyncio.gather：HTTP + 调度器并行启动

`src/polyarb/daemon/main.py:76–89`

```python
server_task = asyncio.create_task(server.serve())

# Gate: wait for uvicorn to bind port before starting scheduler
# Without this, first tick monopolizes event loop → Fly health check fails
for _ in range(100):
    if server.started:
        break
    await asyncio.sleep(0.1)
logger.info(f"daemon running: http server on :{settings.http_port}, starting scheduler")

scheduler_task = asyncio.create_task(scheduler.run(stop_event))
```

**为什么有 100 次轮询？** uvicorn 绑端口是异步的。调度器第一次 tick 会发 Gamma HTTP 请求，可能占用事件循环几分钟，导致 Fly 的 health check 一直看不到端口，误判 VM 死了。

### 2. SnapshotStatus 三态枚举

`src/polyarb/validator/category.py:26–37`

```python
class SnapshotStatus(str, Enum):
    """
    OK:       No Layer 1 issues. Count matches within tolerance.
    DEGRADED: Minor count discrepancy (≤ 1%). Data is usable, API was reachable.
    FAILED:   API_UNREACHABLE at Layer 1, or count discrepancy > 1%.
    """
    OK = "ok"
    DEGRADED = "degraded"
    FAILED = "failed"
```

**关键约束（D-12 amendment）**：DEGRADED 不触发 failure_counter 递增。只有 FAILED 才会。

### 3. 调度器状态机：3 次 FAILED → PAUSED

`src/polyarb/daemon/scheduler.py:35–51, 186–197`

```python
class SchedulerState(str, Enum):
    RUNNING = "RUNNING"
    PAUSED = "PAUSED"

FAILURE_THRESHOLD = 3  # 3x consecutive FAILED → PAUSED

# Inside _tick():
if self._failure_counter >= self.FAILURE_THRESHOLD:
    self.state = SchedulerState.PAUSED
    self._persist_counter()
    await self._on_paused()   # → send_paused_alert (Sentry + BS + Telegram)

# On OK/DEGRADED:
self.state = SchedulerState.RUNNING   # reset if was PAUSED via unpause
self._failure_counter = 0
```

**状态持久化到 SQLite**：重启后 `_failure_counter` 和 `state` 从 `scheduler_state` 表恢复。PAUSED 跨重启保持，不会因为 Fly VM 重启自动恢复（避免掩盖真实故障）。

### 4. /health 三态响应结构

`src/polyarb/http/health.py:5–19, 41–42`

```
三态: pass | warn | fail
- pass  → 所有检查绿灯（HTTP 200）
- warn  → 至少一项降级，无失败（HTTP 200）
- fail  → 至少一项失败（HTTP 503）

子检查 1 — 快照时效（snapshot:last_success_age_seconds）:
  pass  < 14h（subset cron 12h + 2h 缓冲）
  warn  14-25h
  fail  > 25h 或从未有快照

子检查 2 — 最近状态（snapshot:last_status）:
  SnapshotStatus.OK      → pass
  SnapshotStatus.DEGRADED → warn
  SnapshotStatus.FAILED   → fail
```

**Better Stack 用 503 判断 DOWN**：HTTP 503 = fail = 触发 Better Stack incident → Telegram 推送。

### 5. /scan HMAC 鉴权中间件

`src/polyarb/http/scan.py:1–13`

```
D-22 amendment: /scan 公网可达（非 Flycast 内部），但 HMAC-SHA256 保护。
- X-Signature 请求头：HMAC-SHA256(body_bytes, SCAN_SHARED_SECRET)
- hmac.compare_digest — 常数时间比较，防 timing oracle
- recipe_name: isinstance(str) + len ≤ 64（防 SQL 注入第一道）
- SQL 路径：run_recipe / run_recipe_grouped（Phase 01.1 P1 trust-split）
```

**Vercel dashboard 的 /scan 怎么拿 secret？** 环境变量 `SCAN_SHARED_SECRET`（Vercel 端） vs `POLYARB_SCAN_SHARED_SECRET`（Fly 端）— 名字不同是故意的（防止直接 copy-paste 混淆哪一端）。

### 6. SQLite WAL 模式：并发安全

`src/polyarb/storage/sqlite_store.py:102–114, 181–183`

```python
def init_schema(self) -> None:
    """Create tables, indexes, set WAL mode. Idempotent — safe to re-run."""
    # ...
    # WAL 模式必须在首次 init_schema 时设置
    con.execute("PRAGMA journal_mode=WAL")
```

**为什么需要 WAL？** daemon 里 HTTP handler（asyncio 协程）读 SQLite，调度器写 SQLite，两者并发。WAL 模式允许读写同时进行，不会互相锁住。默认 DELETE journal 模式会导致 reader 等待 writer 完成，/health 响应延迟数秒。

### 7. 故障自愈后的 PAUSED 告警

`src/polyarb/daemon/scheduler.py:104–127`

```python
async def _on_paused(self) -> None:
    """Alert hook called when scheduler transitions to PAUSED state."""
    msg = (
        "SCHEDULER_PAUSED: consecutive failure threshold reached "
        f"({self.FAILURE_THRESHOLD}x FAILED). "
        "Run /scan or SSH to unpause."
    )
    try:
        # 用 module-level reference（非 from-import）让测试可以 monkeypatch
        await _alerts.send_paused_alert(...)
    except Exception as e:
        logger.warning(f"send_paused_alert failed: {e!r}")
        # 告警失败不能影响 PAUSED 状态转换
```

**为什么用 `_alerts.send_paused_alert` 而非 `from ... import send_paused_alert`？** 后者在 import 时绑定到函数对象，monkeypatch 无法替换。前者通过模块引用动态查找，测试可以用 `patch("polyarb.daemon.alerts.send_paused_alert")` 替换。

## 设计取舍

### 取舍 1：SQLite 主库 vs. PostgreSQL 主库

选 SQLite 的理由：Fly.io 持久化卷便宜且低延迟；单进程 daemon 不需要多连接并发写；1GB RAM 不够装 PostgreSQL。代价：不能多 VM 水平扩展写路径。Phase 02 单 VM 是设计约束，不是妥协。

### 取舍 2：asyncio 协程 vs. 线程 vs. 多进程

协程的 HTTP + 调度器共享同一个 event loop。HTTP 请求（快，ms 级）不会被调度器 tick（慢，分钟级）阻塞，因为 tick 内的 I/O 有 `await` 让出控制。代价：CPU-bound 操作（目前没有）会阻塞全部协程，需要 `run_in_executor` 卸载到线程池。

### 取舍 3：DEGRADED 不触发 failure_counter（D-12 amendment）

Supabase/R2 是「可选镜像层」，它们挂掉不影响 SQLite 数据质量。如果 DEGRADED 也计失败，Supabase 短暂 500 会误触 PAUSED，停止所有数据采集——损失远大于收益。代价：R2 持续 DEGRADED 时，用户可能没注意到，需要靠 Sentry + /health warn 发现。

### 取舍 4：Better Stack 云端探针 vs. 本地 7×24 监控

Better Stack 从 30+ 个全球节点每 30s ping /health，比本地脚本更真实（模拟用户体验，不是 localhost）。代价：需要 `BETTERSTACK_API_TOKEN` + `BETTERSTACK_MONITOR_ID` 两个环境变量，7 天 soak 依赖外部服务的 SLA。`make soak-status` / `make soak-export` 是事后审计工具，不是监控本体。

### 取舍 5：Vercel + Supabase Dashboard vs. 纯 CLI 监控

Vercel dashboard 让用户在手机上就能看 /movers、/status，不需要开电脑。代价：多了一个信任边界（Vercel 通过 magic-link 鉴权调用 /scan，secret 存在 Vercel env vars 里），也多了一个「Supabase 镜像延迟」的观察盲区（dashboard 看的是镜像数据，镜像可能落后几分钟）。

## 自检题

**Q1：daemon 启动时，为什么要等 `server.started` 才启动调度器？如果去掉这个 gate 会发生什么？**

答：调度器第一次 tick 会立刻向 Gamma 发 HTTP 请求，可能占用 asyncio event loop 数分钟（等待大量市场数据分页返回）。这段时间内，uvicorn 虽然已在 `serve()` 里但实际还没绑端口（或绑了但 event loop 被占满不处理新连接）。Fly.io 在部署时会 HTTP 探测 /health，如果探测超时就认为 VM 启动失败，自动回滚。去掉这个 gate 会导致第一次部署大概率失败。

**Q2：PAUSED 状态持久化到 SQLite 有什么意义？VM 重启后会怎样？**

答：PAUSED 跨重启保持。如果 3 次 FAILED 是真实故障（如 Gamma API 永久不通），重启不应该让 daemon 自动恢复并重新采集垃圾数据。用户必须主动 `/scan resume` 或 SSH 进去确认故障已修复后才恢复。这是「fail-safe」设计：宁可停着，不要带病运行。

**Q3：/scan 的 `recipe_name` 长度限制（≤ 64 chars）和 P1 trust-split 各自防什么攻击？**

答：长度限制防止超长字符串把解析路径变成攻击面（但更根本的防护是后面这个）；P1 trust-split 是 Phase 01.1 建立的约定：所有 SQL 只能通过 `run_recipe`/`run_recipe_grouped` 执行，这两个函数只接受白名单 Recipe 对象（不接受原始 SQL 字符串）。就算 recipe_name 参数绕过了长度检查，KeyError 查 recipes dict 也只返回 404，不会执行任意 SQL。

**Q4：SnapshotStatus.DEGRADED 具体在什么情况下出现？它和 FAILED 对 /health 的影响有什么不同？**

答：DEGRADED 有两个来源：(1) Supabase mirror push 抛异常（step 7.5）——数据写进 SQLite 了，但镜像没推上去；(2) R2 Parquet 上传失败（step 7.6）——Parquet 文件没存到 Cloudflare，但 SQLite 热数据完整。这两个都是「可选镜像层」故障，核心数据安全。对 /health 影响：DEGRADED → `warn`（HTTP 200，Better Stack 不触发 DOWN）；FAILED → `fail`（HTTP 503，Better Stack 触发 DOWN + Telegram 推送）。

**Q5：Better Stack 的 `soak-status` 命令返回 exit code 1 代表什么？什么情况下 Phase 02 的 soak gate 判 FAIL？**

答：exit code 1 = uptime < 99.0%。Phase 02 soak gate（RESEARCH §11 生产级判定标准）要求 7 天内 uptime ≥ 99%（即最多 ~1.68 小时宕机）。触发 FAIL 的场景：Fly VM crash 没有自动恢复、/health 持续返回 503（scheduler PAUSED）、网络问题导致 Better Stack 探针连续失败。Soak gate 是 Phase 02 进入 Phase 03 的必要条件之一。
