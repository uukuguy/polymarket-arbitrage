# 24 — L3 连续性事务：先证据，后切换

← [23-生产机会流](23-生产机会流.md) | [00-INDEX](00-INDEX.md) | [M1 使用手册](../M1-市场感知平台使用手册.md)

## 30 秒心智模型

L3 轮换不是“先把新名单公布出去，再等数据慢慢补齐”，而是：

```text
准备 5 市场 / 10 token
        ↓
同一 WS generation 收齐 10 个 durable book-level 写入
        ↓
make-before-break 控制 + 一次性发布 10/10/10
        ↓
采样器读取完整的新 mapping
```

旧的完整 mapping 在准备期间继续对外成立。采样器和 promoter 共享一把
`transition_lock`；真实 reconnect 时，采样器还会等待 membership 恢复
`desired=committed=evidenced`。因此落库样本只可能是“旧的完整状态”或“新的完整
状态”，不能是 8/10、9/10。发出 subscribe 消息本身不算新鲜度；只有
`l2_book_levels` 持久化成功才算证据。

## 为什么要修：2026-07-26 的两个真实故障

- `06:03:31Z`，promoter run 450 轮换两个 token，却以
  `evidenced_count=8` 写成 success。
- `06:03:36Z`，sample 4500 看到 desired/committed 为 10、evidenced 为 9，
  因 `membership_convergence_failed` 失败；到 `06:04:02Z` 才恢复 10/10/10。
- `06:12:00Z`，只有 2/5 市场的持久化输入仍低于 120 秒，strict health 失败；
  `06:13:02Z` 恢复 5/5。
- 首版修复 release 73 在 `08:04:13Z` 对未变化的 target 强制重刷，差 4 个
  book dump 后关闭健康 generation；随后两个 durable sample 都是 8/10。
  `08:08:01Z` 普通 quiet refresh 又因差 2 个再次关闭连接。这一版被永久拒绝。

常驻 Polywatch 正确发现并发送了故障与恢复消息，这证明监控有效，也证明数据链本身
确实存在连续性缺口。修复目标不是隐藏 503，而是消灭不完整状态的发布边界。

## 关键代码地图

| 责任 | 代码位置 | 不变式 |
|---|---|---|
| 准备目标 | `src/polyarb/daemon/ws_consumer.py:718` | target 未变化时复用本 generation exact evidence；变化时先准备、不发布 membership |
| evidence barrier | `src/polyarb/daemon/ws_consumer.py:759` | failed depth write、旧 generation 和 timeout 都不能满足 barrier |
| 原子提交 | `src/polyarb/daemon/ws_consumer.py:940` | subscribe-before-unsubscribe；最后只 publish 一次 |
| 超时恢复 | `src/polyarb/daemon/ws_consumer.py:918` | 记录 bounded failure；已确认 control 的业务证据超时不关闭 socket |
| promoter 成功门 | `src/polyarb/observation/l3_promote.py:1144` | desired = committed = evidenced = target，且数量严格为 10 |
| 采样隔离 | `src/polyarb/observation/l3_sampler.py:351` | mapping transition 与 reconnect 收敛期间都不持久化半状态 |

`PreparedL3Target` 是跨模块的不可变凭证：它带着 generation、目标 token 集合和每个
token 的持久化时间。旧连接的凭证不能在新连接上提交。

## 三种失败分别怎么处理

### 1. 准备阶段收不齐 10 个证据

promoter 写 `target_evidence_failed`，保留旧的完整 mapping，不调用 commit。若最终
subscribe 已在同一 generation 明确成功，consumer 记录
`subscription_control_failed/evidence_timeout` 和剩余数量，但保留 socket，在下个
周期只重试缺失身份。只有 control send 失败、取消或 generation identity 漂移才属于
歧义，需要补偿捕获的 socket。

target 与当前 10/10/10 完全相同时，promoter 直接复用 current-generation durable
evidence，不再每五分钟 unsubscribe/subscribe 十个 token。

### 2. 控制消息部分成功

提交采用 make-before-break：先确保新增 token 已订阅，再移除退出 token。任一步
失败都不发布新 membership，并补偿捕获的 generation。因为服务端实际状态可能已改，
继续使用同一 socket 比重连更危险。

### 3. membership 已提交，但终态账本没有 ACK

promoter 在释放 transition lock 前恢复旧 reconnect intent、补偿当前 generation，
并回滚 Dashboard mirror。采样器仍没有机会把新 mapping 当成成功样本。

### 4. 真实 reconnect 正在收 initial dump

strict `/health` 仍立即显示 membership mismatch，Polywatch 可以及时报警；durable
sampler 则等待 exact 10/10/10。若 75 秒内仍不收敛，失败表现为 sample-age 超限，
而不是写一条会永久污染连续窗口的 8/10 中间样本。

## 为什么不加 grace period，也不把 120 秒改成 180 秒

grace period 会把真实的 8/10、9/10 伪装成 pass；提高阈值只是延迟报警。二者都会让
“24 小时连续证据”失去含义。当前方案保留 `<120s`、首故障立即报警和 exact
10/10/10 三个合同，把修复放在产生错误状态的边界上。

## 运维判断

- `l3:membership_convergence=fail`：mapping 身份、WS membership 或 durable
  evidence 不一致；不是单纯“市场安静”。
- `l3:worst_market_freshness=fail`：至少一个已映射市场的持久化 book/OHLC 输入越过
  120 秒；全局还有新帧也不能覆盖它。
- `WAITING_FOR_EVENT`：只是连接处于安静窗口。只有上述 strict evidence 仍 pass 时
  才能单独视为非故障。

先运行 `make smoke-l2-health-strict-prod` 保存失败 body，再用
`make polywatch-resident-status`、`make fly-l2-logs` 和
`make l3-evidence-status` 沿监控、进程日志、持久证据三层定位。不要先重启。

## 对手测试

1. 新 target 已有 9 个 token 写入成功，第 10 个只有 top-of-book 写入成功。能提交吗？
2. 准备完成后 WS generation 从 7 变成 8。generation 7 的 prepared target 能否复用？
3. subscribe 成功、unsubscribe 超时。为什么不能保留 socket 并直接重试一次？

<details><summary>答案</summary>

1. 不能；barrier 只认 10 个 durable book-level 成功。
2. 不能；prepared evidence 与 generation 绑定，必须在新 generation 重新准备。
3. 服务端状态已经歧义，继续用它可能发布或采样错误成员关系；必须关闭捕获的
   generation，让 reconnect 重建完整真相。

</details>
