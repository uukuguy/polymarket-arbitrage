> 这一章盖的是 m1-perception 三层金字塔的**塔尖**——L1 全市场快照 → L2 候选集 WS 跟踪 → L3 单市场显微镜。

## 30 秒心智模型

L1 / L2 / L3 是 m1-perception 的三层金字塔，每层数据频率递增、覆盖范围递减：

```
┌──────────────────────────────────────────────────────────────────┐
│ L1 — 全市场快照 (polyarb-l1)                                      │
│   频率: 每 6h                                                    │
│   覆盖: ~20,000 市场 (Gamma + CLOB)                               │
│   表: markets_latest, l2_candidates                              │
├──────────────────────────────────────────────────────────────────┤
│ L2 — 候选集 WS 流 (polyarb-l2)                                    │
│   频率: 秒级 (WS push)                                           │
│   覆盖: ~500 个候选 market (candidate_refresh 选出)                │
│   表: l2_top_of_book, l2_trades, l2_book_levels, l2_signals      │
├──────────────────────────────────────────────────────────────────┤
│ L3 — 单市场显微镜 (polyarb-l2 内置 L3 promoter)                    │
│   频率: 秒级 book event (push) + 5min promote (pull)              │
│   覆盖: 5 个市场 × 2 tokens = 10 tokens (D-13, 硬锁)              │
│   数据: OHLC 视图 (1m/5m/1h) + book_levels top-10              │
│   面: 仪表盘 /l3/[asset_id] (K 线图 + 深度滑梯)                  │
└──────────────────────────────────────────────────────────────────┘
```

**L3 做了什么**：每 5 分钟从 `l2_top_of_book` 表里选 5 个 `depth_yes_usd > $500` + `spread < 0.02` 的市场 → 扩展成 10 个 token（Yes/No 各一个） → 订阅这些 token 的 WS book event → book 事件到齐时写入 `l2_book_levels`（买卖各 top-10 档位） → Supabase 上 `l2_ohlc_1m/5m/1h` 三个正则视图自动聚合成 K 线 → 仪表盘 `/l3/[asset_id]` 拿 OHLC 画蜡烛图 + 拿最新 book_levels 画深度滑梯。

**L3 不用 TimescaleDB**，只用 Postgres 原生 `date_trunc` + `floor(epoch/300)` → 后面"设计取舍"详谈。

## 关键模块

### 1. 候选选择：怎么选出 5 个市场（l3-promote.yaml）

选市场的 SQL 写在文件里，不是代码常量：

**`src/polyarb/scan_recipes/l3-promote.yaml:19-24`** — D-13 阈值：

```yaml
where: |
  spread < 0.02
  AND depth_yes_usd > 500
  AND ts > (strftime('%s', 'now', '-1 hour') * 1000)
order_by: depth_yes_usd DESC
limit: 5
```

三个条件：
- **spread 紧**：`best_ask - best_bid < 0.02`（排除假流动性）
- **yes 边够深**：`depth_yes_usd > 500`（这是 10 档价格×数量的总和，Phase 05 Plan 03 的 `_sum_depth_usd` 函数在 `src/polyarb/daemon/l2_main.py:132` 算出）
- **最近活跃**：`ts > 1 小时前`（Blocker #2 epoch-ms 谓词）

**信任层级**：l3-promote.yaml 是第 3 级 recipe trust tier（`src/polyarb/observation/l3_promote.py:35-39`），用 `Recipe(..., _is_trusted=True)` 直接构造。文件在 repo 里，修改走 PR review。第 1 级（SQLite 只读 URI）和第 4 级（LIMIT）防御仍然生效。

**环境变量覆写**：`POLYARB_L3_DEPTH_MIN_USD` 可以在不碰 yaml 文件时调阈值（`src/polyarb/observation/l3_promote.py:316-354`）。无效值 → 退回 yaml baseline 500，不会静默禁用 promoter。

### 2. L3 promoter：5 分钟 cron 的 promote/demote 逻辑

promoter 的核心函数是 `promote_run`，每 5 分钟被 `run_periodic` 调用一次：

**`src/polyarb/observation/l3_promote.py:657-699`** — 原始 asyncio cron loop：

```python
async def run_periodic(
    *, stop_event, settings, ws_consumer, recipe_yaml_path,
    interval_s: float = 300.0,
) -> None:
    # Initial run — no cold-start delay for /health
    await promote_run(...)
    while not stop_event.is_set():
        await asyncio.wait_for(stop_event.wait(), timeout=interval_s)
        await promote_run(...)
```

不是用 APScheduler，而是 `asyncio.wait_for(stop_event.wait(), timeout=300)` —— cross-pattern decision #4（和 ws_consumer 的 idle-wait 一样）。

**`src/polyarb/observation/l3_promote.py:438-654`** — `promote_run` 的 9 步流水线：

```
1. Resolve Supabase creds      → 缺失则 freeze _l3_active_set
2. Build client                → 失败则 freeze
3. Fetch l2_top_of_book (1h)   → 失败则用 last-known rows
4. Recipe + temp-DB + scanner  → 失败则 freeze
5. Fetch yes/no token ids      → 5 markets → 10 tokens (D-05)
6. Diff token set              → 比对新旧，算 MARKET-level diff
7. WS subscribe/unsubscribe    → fail-soft，失败后仍继续
8. Write-through mirror        → l2_candidates.l3_promoted_at_ts
9. Mutate state anchor         → _l3_active_set + _last_promote_at_s
```

这里的第 3 步不是把最近 1000 条时序行原样交给 scanner。PostgREST 先按
`ts DESC` 返回有界结果，promoter 再按 `asset_id` 保留每个资产的第一条（即
最新一条）。否则同一热门资产的多个 snapshot 会重复占用 recipe 的
`limit: 5`，表面选中 5 行，实际却不足 5 个市场。

去重后还要在 LIMIT **之前**做 outcome identity 过滤。L3 会同时订阅 Yes/No，
所以几分钟后 `l2_top_of_book` 里两侧都有数据；若把高 depth 的 No token 当成
候选 Yes row，它会占掉一个名额，直到 pair expansion 才被拒绝，造成下一 tick
从 10/10 掉到 8/10。promoter 现在先用 `markets_latest.yes_token_id` 确认
Yes-side universe，再跑 recipe；真实但不完整的 Yes/No pair 仍保持 fail-closed。

**Supabase 断连策略**（Open Question #5 — `src/polyarb/observation/l3_promote.py:41-46`）：任何 Supabase 操作失败 → **freeze** `_l3_active_set`（保留 last-known-good），不清零。因为清零会让 WS 退订所有 L3 token，比用过期数据更糟。staleness 通过 `/health` 的 `l3:last_promote_at_s` 暴露。

**Pitfall 5 修复**：`ws_consumer._l3_active_set` 和 `ws_consumer._candidate_set` 是两个独立的 set，**互不覆盖**（`src/polyarb/daemon/ws_consumer.py:125-137`）。`add_subscriptions` 只改 `_l3_active_set`；candidate refresh 只改 `_candidate_set`。`subscribed_assets` property 返回两者的**并集**（`src/polyarb/daemon/ws_consumer.py:209-216`）。

### 3. Book levels writer：买/卖各 top-10 档位

当 WS 收到 `event_type == "book"` 的帧且 asset_id 在 L3 active set 里时，触发 book levels 写入：

**`src/polyarb/daemon/l2_main.py:409-423`** — gate 逻辑：

```python
if event_type in ("price_change", "best_bid_ask", "book"):
    row = _tob_row_from_frame(frame)           # 无条件写 top_of_book
    if row is not None:
        l2_mirror.push_top_of_book([row])
    if event_type == "book":                    # 只有 L3 token 才写 levels
        from polyarb.observation import l3_promote
        if asset_id_raw and asset_id_raw in l3_promote.get_l3_active_set():
            book_rows = _book_levels_rows_from_frame(frame, max_levels=10)
            if book_rows:
                l2_mirror.push_book_levels(book_rows)
```

**`src/polyarb/daemon/l2_main.py:255-309`** — `_book_levels_rows_from_frame`：
- 接收 WS `book` 帧，逐 `bids`/`asks` 数组展开 → 每个有效 level 一行 `{asset_id, ts, side, level, price, size}`
- 每边最多 10 档 → 最多 20 行/event
- 完全不处理 price_change/best_bid_ask 帧（那不是 book depth）

#### 生产教训：数组第 1 项不一定是最优价

2026-07-20 的生产对照发现，同一个 token 的 CLOB `/book` 响应中，bids
是价格升序（最差 → 最优），asks 是价格降序（最差 → 最优）。如果直接取
`bids[0]` / `asks[0]`，真实 `0.369 / 0.377` 的盘口会被投影成
`0.001 / 0.999`，spread 从 `0.008` 失真成 `0.998`，继而让 L3 的
`spread < 0.02` 筛选全军覆没。

当前投影先过滤非法或非正 size 的档位，再统一按可执行距离排序：BUY 价格
降序、SELL 价格升序。`best_bid` / `best_ask`、top-10 depth 和
`l2_book_levels.level=1..10` 共用这条排序规则。因此 **level=1 表示最优
可执行价，而不是上游数组位置 0**。自检时应把存储结果与同 token 的实时
CLOB book 对照，不能只检查“字段非空”。

**`src/polyarb/storage/l2_supabase_mirror.py:216-267`** — `push_book_levels`：
- 成功路径：写 Supabase `l2_book_levels` → 更新 `l3_promote._last_book_levels_write_at_s`（chain-truth 锚点）
- 失败路径：log warning + Sentry breadcrumb，**不**更新锚点（只进不退）

l2_book_levels 表结构（`alembic/versions/005_l2_book_levels_and_ohlc.py:80-101`）：
```
asset_id TEXT, ts TIMESTAMPTZ, side VARCHAR(8) BUY|SELL,
level SMALLINT 1..10, price NUMERIC(10,6), size NUMERIC(14,4)
UNIQUE(asset_id, ts, side, level)
INDEX: BRIN(ts) — 比 btree 小 10×
```

### 4. OHLC 视图：从 l2_top_of_book 生成 K 线

三个**非物化正则视图**在 Supabase 上实时聚合 `l2_top_of_book` 的 `mid_price`：

**`alembic/versions/005_l2_book_levels_and_ohlc.py:137-198`** — 三种粒度：

| 视图 | 桶策略 | 粒度 |
|------|--------|------|
| `l2_ohlc_1m` | `date_trunc('minute', ts)` | 1 分钟 |
| `l2_ohlc_5m` | `floor(epoch/300) * 300` | 5 分钟 |
| `l2_ohlc_1h` | `date_trunc('hour', ts)` | 1 小时 |

每个视图的输出形状：
```
asset_id, bucket_ts, open, high, low, close, sample_count
```

**open/close 语义**：`array_agg(mid_price ORDER BY ts ASC)[1]` = 桶内按时间升序的头一个 mid_price（open）；`DESC [1]` = 末尾（close）。用 `array_agg` 而不是 `FIRST_VALUE/LAST_VALUE` 窗口函数 —— 因为 `GROUP BY` 聚合更便宜，等价于等权价格分桶。

**5m 为什么用 `floor(epoch/300)`？** `date_trunc` 不支持任意分钟倍数的 bucket（只支持 minute/hour/day 等固定单位）。5 分钟桶的 canonical PG 做法是把 epoch 秒除以 300 后取整再乘回来（`alembic/versions/005_l2_book_levels_and_ohlc.py:161-163`）。

**RLS/Grant 纪律**（`alembic/versions/005_l2_book_levels_and_ohlc.py:194-198`）：视图不继承基表 RLS，显式 `GRANT SELECT ON l2_ohlc_* TO anon` 保持读路径白名单。

### 5. /health L3 子检查（chain-truth 三锚点）

l2_health.py 的 `_compute_l3_health_checks` 从三个 getter 读值，无 config-flag gate：

**`src/polyarb/http/l2_health.py:423-523`** — 三个子检查：

| 子检查 | 数据源 | warn 阈值 | fail 阈值 | 影响 overall？ |
|--------|--------|-----------|-----------|----------------|
| `l3:active_count` | `l3_promote.get_l3_active_count()` | < 10 tokens | N/A | **否** (informational) |
| `l3:last_promote_at_s` | `l3_promote.get_last_promote_at_s()` | ≥ 600s (10min) | ≥ 1800s (30min) | **是** |
| `l3:last_book_levels_write_at_s` | `l3_promote.get_last_book_levels_write_at_s()` | ≥ 120s (2min) | ≥ 600s (10min) | **是** |

**chain-truth 纪律**：每个 getter 读取的字段，写入侧真实 mutate（`src/polyarb/observation/l3_promote.py:17-26`）。`None` sentinel 表示 "cold-start: never run" → warn。

- `_last_promote_at_s` ← `promote_run` 成功路径第 9 步（`src/polyarb/observation/l3_promote.py:628`）
- `_last_book_levels_write_at_s` ← `L2SupabaseMirror.push_book_levels` 成功路径（`src/polyarb/storage/l2_supabase_mirror.py:250`）
- `_l3_active_set` ← `promote_run` 成功路径 diff 后的最终 set（`src/polyarb/observation/l3_promote.py:627`）

**冷启动陷阱**：两个 timestamp 锚点的初始值是 `None`（不是 `0.0`）。`0.0` 会让 /health 的 age 计算以为是 1970 年，触发 "很久没跑" 的假阳性（`src/polyarb/observation/l3_promote.py:28-32`）。

## 设计取舍

### 1. 为什么不用 TimescaleDB？为什么不用物化视图？

- **TimescaleDB 在 Supabase PG 17 已被废弃**（`alembic/versions/005_l2_book_levels_and_ohlc.py:23-36` 已文档化）。`date_trunc` + `floor(epoch/300)` 是纯 Postgres 原生方案，不依赖任何 extension。
- **不用物化视图**：因为 `l2_top_of_book` 的 OHLC 查询过滤了 `WHERE mid_price IS NOT NULL AND asset_id = ?`，数据量有限（最多 500 个候选的 mid_price）。非物化视图的查询开销 ≈ `INDEX scan l2_top_of_book` → `GROUP BY date_trunc`，每次请求延迟 ~数十毫秒。物化视图会增加定时刷新复杂度，且 Supabase Free tier 可能不支持 `pg_cron`。
- **关键教训**：从 TimescaleDB → date_trunc 的 pivot 是在 CONTEXT D-03 的 RESEARCH 阶段做的（不是实现阶段），避免了上线后才发现 `function does not exist` 的严重 bug。参考 https://github.com/orgs/supabase/discussions/23365。

### 2. 为什么是 5 个市场（D-12 strict）？

- **WS subscription 上限安全面**：Polymarket WS 一台 connection 能稳定支撑的订阅数没有公开文档保证。保守取 10 tokens（5 个市场 × 2 个 Yes/No token）是够用又安全的边界。
- **book_levels 写入量控制**：10 个 token 的 book event ≈ 每 token 秒级频率，加上每个 book frame 最多 20 行 book_levels → 可能达到每秒几百行写入。5 个市场把写入爆炸控制在已知安全范围内。
- **promote 逻辑不可加 `> 5`**：不是 "最多 5 个" —— recipe 的 `limit: 5` 是硬约束。加不到 5 个是因为不够 5 个市场满足 `depth_yes_usd > $500` 阈值。想加更多？改 yaml depth 阈值，不改 LIMIT。

### 3. 为什么 chicken-and-egg（冷启动时 depth 怎么选）？

promoter 的 5-min cron 需要已有的 `l2_top_of_book` 数据来选候选。但如果 L3 promoter 刚启动，还没有任何市场被 subscribed，就没有 book event → 没有 top_of_book 数据 → promoter 选不了市场。

**Phase 05.3 修正**：启动期 bootstrap 只能证明 wiring，不能保证长期输入有代表性。
现在 `l3-seed` 从每次 L1 snapshot 中选择最多 100 个液态中间价 Yes token，经过
既有 candidate reconciliation 进入 WS；详见
[21-L3-候选与双 Token](21-L3-候选与双Token.md)。

这个 seed 也会被 `candidate_refresh` 的 diff 逻辑持续重算（不会永久存在）。不是
code bug——而是**市场感知层必须面对的物理现实**：你不先观察代表性资产，就无法
用真实盘口判断哪些值得升级。Bootstrap 仍可作冷启动 wiring 保险，但不再是唯一或
主要的长期覆盖机制。

## 会让你卡住的细节

### 1. 为什么 promoter 先拉 l2_top_of_book 到本地 SQLite 再跑 scanner？

**`src/polyarb/observation/l3_promote.py:215-304`** — `_build_tob_temp_db` docstring 已解释：

- `scanner.run_recipe` 打开自己的 `sqlite3.connect(f"file:{db_path}?mode=ro", uri=True)` 连接。
- 两个 `:memory:` 连接是**两个独立的空数据库**，无法共享数据。
- **必须用 named temp file**（`tempfile.NamedTemporaryFile(delete=False)`）让多个连接读同一份数据。

这是 Phase 04 Plan 02 Pitfall 1 的教训复用。

### 2. ts 为什么必须是 INTEGER epoch ms？

**`src/polyarb/observation/l3_promote.py:235-239`** — Blocker #2：

Supabase 返回的 `ts` 是 ISO 8601 TIMESTAMPTZ。`_iso_to_epoch_ms`（`src/polyarb/observation/l3_promote.py:189-212`）转为 INTEGER epoch ms。原因：

- Recipe SQL 写的是 `ts > (strftime('%s','now','-1 hour') * 1000)` —— 纯数值比较。
- 如果用 ISO 文本比较 → `"2026-06-07T01:00:00+00:00" < "2026-06-07T02:00:00Z"` 的 lex 大小关系依赖 TZ offset 格式，会**静默错序**。

### 3. promoter 的 temp DB 表名叫 markets 而不是 l2_top_of_book？

**`src/polyarb/observation/l3_promote.py:226-233`** — 叫 `markets` 是 `scanner.run_recipe` 的硬编码要求：

```python
# scanner.py 固定 SQL:
SELECT m.*, qt.question_zh FROM markets m
LEFT JOIN question_translations qt ON qt.question_en = m.question
```

所以 temp DB 必须有一个 `markets` 表和一个空的 `question_translations` 表（LEFT JOIN 不失败就行）。字段名必须匹配 recipe 的 WHERE 列名（asset_id, ts, spread, depth_yes_usd 等）。

### 4. L3 active set 和 candidate set 为什么会打架？

**Pitfall 5 修复前**（Phase 05 Plan 02）：candidate refresh 调用 `ws_consumer.set_subscriptions(new_list)` → 把 `_l3_active_set` 当候选集清空了。修复分两步：

1. 加了专用 `add_subscriptions`/`remove_subscriptions` 方法（`src/polyarb/daemon/ws_consumer.py:258-335`），只改 `_l3_active_set`。
2. candidate refresh 用 `set_candidate_set` 只改 `_candidate_set`（`src/polyarb/daemon/ws_consumer.py:225-254`），附 DeprecationWarning 保护。

测试验证：`test_candidate_refresh_l3_protection`（`src/polyarb/observation/l2_candidate_refresh.py:411-426` 已文档化）。

### 5. K 线图为什么用动态 import？

`lightweight-charts` 在模块加载时调用 `document`/`window`/`ResizeObserver`（`dashboard/app/l3/[asset_id]/KlineChart.tsx:4-14` Warning #14）。Next.js 15 Server Component 构建阶段没有浏览器 API → top-level `import` 会直接炸。解法是 `"use client"` + `await import("lightweight-charts")` 放在 `useEffect` 里 → SSR 阶段完全不执行这个 import。

### 6. book_levels 写成功和失败时 _last_book_levels_write_at_s 怎么处理？

- **成功**：`l2_supabase_mirror.py:250` 直接 `l3_promote._last_book_levels_write_at_s = time.time()`。
- **失败**：锚点**不动**。只成功路径才更新时间。失败路径不动时间是为了 chain-truth：如果上次写入是 8 分钟前失败，锚点仍然显示 8 分钟 —— 正确反映 "真实最近的写入是 8 分钟前"。如果失败也更新时间，锚点会谎报 "刚刚写完"（Phase 02 L1 教训：fail-soft 路径不能污染 freshness 锚点）。

## 5 道对手测试题

> 答得上 = 这一节过；答不上 = 重新看上面代码地图找到证据。

**Q1**. 你是 Polymarket 的 L3 promoter。凌晨 3:15 时 Supabase 出现了持续 8 分钟的短时断连。断连期间 promoter 的 5-min cron tick 到了。会怎样？当前订阅的 10 个 token：
  (a) 全被退订 —— promoter freeze 了 `_l3_active_set` 为空
  (b) 保持不动 —— promoter freeze 了 `_l3_active_set` 保留 last-known-good
  (c) 被新选的 10 个 token 替换 —— promoter fallback 到 `POLYARB_BOOTSTRAP_ASSET_IDS`

<details><summary>答案</summary>

(b) 保持不动。Open Question #5 的 freeze 策略（`src/polyarb/observation/l3_promote.py:41-46`）：Supabase 断连 → promoter 返回 `{"added": [], "removed": [], "skipped": "..."}` → `_l3_active_set` 不变。清零比用过期数据更糟，因为清零意味着退订所有 L3 token，丢失的关键数据无法恢复。

`l3:last_promote_at_s` 的 age 会逐渐升高，`/health` 最终触发 fail（≥1800s）。WS 数据流继续收，仪表盘 `/l3/[asset_id]` 的 K 线和深度滑梯仍然工作（只是 promote 不刷新候选集而已）。
</details>

**Q2**. 仪表盘 `/l3/abc123` 的 K 线图显示了 1 分钟蜡烛图。数据是 `l2_ohlc_1m` 视图返回的 open/high/low/close。问题：这个 `open` 值来源于哪个原始数据？是 book_levels 还是 top_of_book？

<details><summary>答案</summary>

来源于 `l2_top_of_book.mid_price`，不是 `l2_book_levels`。三个 OHLC 视图（`l2_ohlc_1m/5m/1h`）全部是基于 `l2_top_of_book` 的正则视图（`alembic/versions/005_l2_book_levels_and_ohlc.py:137-198`）。`mid_price = (best_bid + best_ask) / 2` （`src/polyarb/daemon/l2_main.py:204`），是 best_bid_ask/book 帧的投影。

`l2_book_levels` 被深度滑梯（DepthLadder 组件）单独消费，不参与 K 线的聚合逻辑。
</details>

**Q3**. `l3:active_count` 子检查（`src/polyarb/http/l2_health.py:442-463`）返回 warn 而不是 fail，也不影响 overall status。为什么故意这么设计？什么场景下 active_count < 10 是合法的？

<details><summary>答案</summary>

`active_count` 不 bump overall 的原因是它被标记为 `informational only`（`l2_health.py:461`），和 `ws:subscribed_count` 一样。活跃 token 不满额有两种合法场景：
1. **冷启动**：promoter 还没跑过第一次，`_l3_active_set` 为空。
2. **市场不足**：当前不够 5 个市场满足 `depth_yes_usd > $500 AND spread < 0.02` 的阈值。这不是 bug —— 是市场没满足选择标准。

如果 active_count < 10 就告警 fail，每次冷启动或市场萧条时都会触发无意义的告警。staleness 由另外两个更可靠的锚点（`last_promote_at_s` 和 `last_book_levels_write_at_s`）来覆盖。
</details>

**Q4**. promoter 在 `promote_run` 的第 8 步调用 `_mirror_l3_promoted_at_ts`，把 `l2_candidates.l3_promoted_at_ts` 写回 Supabase。这一步如果失败，对 /health 和 /candidates 页面有什么影响？

<details><summary>答案</summary>

- **对 /health**：不影响。`l3_promoted_at_ts` mirror 只是写回 Supabase 的表面字段，不影响 `_last_promote_at_s`、`_last_book_levels_write_at_s`、`_l3_active_set` 这些内存锚点（`src/polyarb/observation/l3_promote.py:373-376` 的 docstring：`_l3_active_set` is the source of truth）。
- **对 /candidates 页面**：`★ L3` badge 不会出现（`dashboard/app/candidates/page.tsx:100` 取决于 `l3_promoted_at_ts IS NOT NULL`）。但 `/l3/[asset_id]` 仪表盘不受影响，因为 OHLC 和 book_levels 的读路径不依赖 `l2_candidates` 表。

mirror 失败 = Sentry breadcrumb `category="l2-mirror" level="warning"`；daemon 继续运行。
</details>

**Q5**. 你想把 L3 限定的 5 个市场改成 10 个。改哪个文件、改哪个值？为什么不能只改 yaml 的 limit？

<details><summary>答案</summary>

需要改**三个地方**：
1. `src/polyarb/scan_recipes/l3-promote.yaml:24` — `limit: 5` → `10`
2. `src/polyarb/http/l2_health.py:443` — `L3_EXPECTED_TOKEN_COUNT = 10` → `20`（10 markets × 2 tokens）
3. 重新评估 D-12 strict boundary：WS 最大订阅数是否仍然在安全范围内？book_levels 写入量是否在 Supabase Free tier 范围内？

不能只改 yaml 的 limit，因为 `/health` 的 `L3_EXPECTED_TOKEN_COUNT` 硬编码了 10。如果只改 yaml 不改 health check → promoter 成功选 20 个 token，但 /health 永远报告 "20/10 (under-filled)" warn，误报率 100%。
</details>
