# 长事务任务的恢复与吞吐预算

## 30 秒心智模型

一个 materializer 不是“一次 HTTP 请求”，而是可能要把 208 个事件页拆成 52 个
R2 分片批次的长事务任务。它每做完四页就先把不可变 artifact 和 Postgres checkpoint
写稳；这意味着进程即使此刻消失，下一次租约也只会从下一批继续。

所以，**checkpoint 是真实恢复，不是半成品假成功**：它已经让系统向前移动且不会丢失
已认证事实。对于这种长任务，若仍等到全部 52 批结束才关闭旧 incident，健康面会把一个
持续前进的 worker 误报成故障。反过来，checkpoint 只能在同一个 lease epoch 下作为
恢复证据，不能让旧 worker 冒充新 owner。

吞吐预算同样不是“多开线程”。scheduler 在一轮基线 worker 后，额外串行执行指定数量
的 `run_once()`；每次仍须从 Postgres 领取 lease。因此它提高的是已验证瓶颈的服务率，
不是绕过 fence 的本地并发。

## 关键取舍

### 为什么不直接把 materializer 并发数调大？

materializer 从 R2 读、归一化、再写 R2；无节制并发会把内存、对象存储和 Postgres
lease 竞争一起放大。现在的预算只串行重复已有 worker，且默认 `0`，所以既保留原行为，
也能在 staging 用具体 checkpoint 时间校准容量。

### 为什么 checkpoint 能关闭 incident，却不能发布 generation？

checkpoint 证明一个批次可恢复，但不证明 52 批已经齐全。只有 materializer finalization
产生完整 manifest，随后所有 Structure range receipt 齐全并由 certifier 认证，才能进入
Quote；只有 Quote 全部 batch 认证后才会移动 `quote:current`。恢复健康与发布真值是两条
不同的状态机。
