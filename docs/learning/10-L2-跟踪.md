## 30 秒心智模型

`polyarb-l2` 是一个**独立 Fly 进程**（不是 polyarb-l1 里加 task）。
两条数据流方向相反：

```
┌─ polyarb-l1（已存在的 cron daemon）──┐         ┌─ polyarb-l2（Phase 03 新）──────────┐
│ APScheduler 每 6h:                  │         │ asyncio 长期事件循环                  │
│   Gamma + CLOB snapshot             │         │   ├─ uvicorn server (/healthz)        │
│   → SQLite + Supabase mirror + R2   │         │   ├─ EventListener (asyncpg LISTEN)   │
│   → pg_notify('snapshot_complete')  │────────►│   │    ↓ on_snapshot_complete         │
│       (opt-in: B1 默认 FALSE)        │ NOTIFY  │   │    compute_candidates             │
│                                      │         │   │    diff_candidate_sets            │
│                                      │         │   │    ws_consumer 更新订阅           │
│                                      │         │   │    mirror.upsert_candidates       │
│                                      │         │   ├─ WsConsumer (async iter)          │
│                                      │         │   │    ↓ async for event              │
│                                      │         │   │    L2SupabaseMirror.push_*        │
│                                      │         │   └─ WsWatchdog (30s 心跳)            │
└──────────────────────────────────────┘         │     ↓ event 流冻结 → reconnect        │
                                                 └────────────────────────────────────────┘
                                                       ↓ 4 张 l2_* 表（Supabase）
                                                 ┌─ Vercel dashboard 4 页 (D-07) ────────┐
                                                 │   /candidates  /asset/[id]/tob        │
                                                 │   /asset/[id]/trades  /signals        │
                                                 └────────────────────────────────────────┘
```

**控制流**（图里的 NOTIFY 箭头）是稀疏事件，**数据流**（WS event 自下而上）是高频流。
两者解耦：L1 cron 决定**看哪些**（候选集），L2 WS 决定**看到什么**（成交 / 报价更新）。

**故障路径**：WS event 流 30 秒不动 → `WsWatchdog` 触发重连（退避 1/2/4/8/16/30s）；
1 小时内 ≥10 次重连 → 进入 `DEGRADED_REST_POLLING`（R5，防 Polymarket IP-ban）。
Mirror 写失败：`add_breadcrumb(category='l2-mirror', level='warning')` + 返回 False，
**daemon 不 crash**（D-12 fail-soft，Phase 02 L1 教训：失败路径和成功路径**双锚点**才可见）。

async def on_snapshot_complete(payload, *, ws_consumer, settings, mirror):
    now = time.monotonic()
    if now - _last_refresh_at_s < REFRESH_DEBOUNCE_S:
        return False                        # debounce 跳过
    new_rows = compute_candidates(settings, ...)
    removed, added = diff_candidate_sets(set(ws_consumer.subscribed_assets), new_rows)
    ws_consumer._subscribed_assets = [r.asset_id for r in new_rows]   # 见 Plan 04 ↔ Plan 05 契约

        mirror.mark_candidates_removed(list(removed))
        mirror.upsert_candidates([r.as_dict() for r in added])

recipe 按 `ranking_score.liquidity` 截断。

## 设计取舍

### 1. 为什么独立 daemon（D-06）而不是 polyarb-l1 里加 task？

- **Crash 隔离**：WS reconnect 风暴不会拖累 L1 cron；L1 cron 长时间 GC 不会冻结 L2 实时流。
- **Chaos 可独立**：Phase 03 Wave 6 chaos 只对 polyarb-l2 注入（kill connection / 撤 mirror secret），
  polyarb-l1 完全不受影响——攻击面是隔离的。
- **资源配额独立**：L2 用 `1024MB` Fly machine（事件循环 + asyncpg pool），L1 用 `256MB`（cron tick），
  互不挤压。
- **单 binary 双部署**：同一个 Dockerfile，两套 `fly.toml`（`fly.toml` + `fly-l2.toml`），
  polyarb-l2 的 `[processes]` 不带 cron 组——构建一次部署两次。

### 2. 30s watchdog 而不是依赖 Polymarket PING？

Polymarket 服务端 PING 是 TCP 层 keepalive（`ping_interval=10` 是 client 侧主动 ping），
**Issue #292 实证**：TCP socket 没断、PONG 正常回，但业务 event 流冻结（服务端推送队列阻塞）。
唯一可信的活体信号 = **"业务 event 最近发生时间"**。

30s 是 RESEARCH 建议值——平衡误报（流动性差的市场可能真没成交 30s）和延迟（实时性要求秒级）。
误报对策：`WsWatchdog` 触发时仅 emit Sentry breadcrumb（**not** alert），7 天 soak 观察误报率，
真高了 Phase 04 改 60s 或 per-asset 而不是 per-connection。

### 3. Postgres NOTIFY 而不是 Redis Pub/Sub？

**D-05 决策**：Phase 03 不引新基础设施，复用已有 Supabase Pro 投资（90 连接池够用）。
NOTIFY 的硬约束：

- payload ≤ 8000 bytes（实际 ~80 bytes，安全）
- L2 daemon 离线期间的 NOTIFY 会**丢**（asyncpg LISTEN 必须在线）
- 解决"丢 NOTIFY"：`l2_event_cursor` 表 + `catchup_from_cursor()` 启动时回放

Phase 04+ 如果 daemon 数量 ≥ 3（M2 m2-combinatorial + M3 跨平台 + M4 strategies），
再评估是否换 Redis Pub/Sub。

### 4. 候选集 500 cap 是怎么来的？

R9：Polymarket WS 的 `initial_dump=true` 给**每个**订阅 asset 推一份完整 orderbook snapshot。
500 asset 的 initial_dump 总 payload ~2-3 MiB，单帧打在 `max_size=2**22 = 4 MiB` 的上限内。
1000 asset 会撞上限——要么 frame 被 websockets 库截断报错，要么超时断连进重连循环。

策略上：watchlist YAML（用户钉住的，**优先级最高**）永远保留；recipe 按 `ranking_score.liquidity`
降序截断到剩下的额度。极端情况 watchlist > 500 时直接报错（用户问题，不该 silent drop）。

### 5. fail-soft 双锚点 — 为什么成功路径也要 emit breadcrumb？

**Phase 02.1 L1 教训**：L1 secret 撤掉时 `mirror.push_markets()` 默默 return False，
daemon 不 crash → Sentry SDK 的 breadcrumb buffer **永远不 flush** → 在 Sentry UI 里
撤 secret 这段时间永远 invisible（"design-unreachable" bug）。

修法：

```python
# ✗ 之前
try:
    push_to_supabase(...)
    return True
except Exception:
    sentry_sdk.add_breadcrumb(category='mirror', level='warning', ...)  # 永远 invisible
    return False

# ✓ 现在
try:
    push_to_supabase(...)
    sentry_sdk.add_breadcrumb(category='l2-mirror', level='info', ...)   # 双锚点
    return True
except Exception:
    sentry_sdk.add_breadcrumb(category='l2-mirror', level='warning', ...)  # 至少一条会被 buffer 留住
    return False
```

成功路径 breadcrumb 的代价：噪声 +1（但 level='info' 不会触发 alert）；收益：失败 breadcrumb
在偶尔出现的真 exception 触发 buffer flush 时也能 visible。

### 6. Event Bus 默认 OFF（B1 安全门）

`POLYARB_EVENT_BUS_ENABLED` 在 `settings` 里默认 **FALSE**。
plan-checker iter 1 提出的安全门：**新出站 NOTIFY 路径**生产默认关，opt-in 才打开。

理由：L1 是 production-grade（Phase 02 已经 soak 14 天），加新副作用要保守。
万一 `publish_snapshot_complete` 在 prod 里有边角 bug（asyncpg dependency 安装失败 /
DSN 错 / NOTIFY 卡死），L1 cron 不该因为这条 L2 优化路径出事。

opt-in 路径：`flyctl secrets set POLYARB_EVENT_BUS_ENABLED=1 -a polyarb-l1` → cold restart →
事件正式打开。Phase 03 chaos Inj L2-3a/L2-3b 两个子注入分别验证 "默认 OFF L2 不疯" 和
"opt-in 后 NOTIFY 正确投递"。

### 7. 启动期 hybrid catchup + bootstrap（Wave 5 deploy 实战修法）

最初设计：L2 启动只调用 `catchup_from_cursor`（从 `l2_event_cursor` 回放漏掉的 NOTIFY）。
**deploy 时发现的 bug**：第一次部署时 `l2_event_cursor` 表为空，回放返回 0 行，
`ws_consumer.subscribed_assets` 一直为空，daemon 跑但什么 WS 都不订阅。

修法：catchup 之后 + LISTEN 之前，**主动从 SQLite 读 L1 最近一次 snapshot 的候选列表**
作为 bootstrap asset_ids，先订上再说。这条路径在 `src/polyarb/daemon/l2_main.py` 的
main() 后段（catchup_from_cursor 之后那段 if-else）。

教训：纯事件驱动架构必须有 "我也能从 cold storage 拉一遍" 的兜底，不然 fresh DB 第一次跑
永远什么都看不见。这是 Phase 03 Wave 5 修的 catchup replay loop bug（commit `060b98e`）。

## 自检题

读完本章你应该能不看代码答出：

**Q1**. 描述 L2 daemon 启动的 init order（≥6 步），并解释 P9 server-started gate 不存在时 prod 会发生什么。

  <details><summary>答案</summary>

  顺序：`init_logging()` → `load_settings()` → `init_sentry(settings)` →
  `sentry_sdk.set_tag("service", "polyarb-l2")` → `SQLiteStore(...).init_schema()` →
  `create_l2_app(...)` → `uvicorn.Server(...)` → **P9 gate**（`for _ in range(100): if server.started: break; await asyncio.sleep(0.1)`）
  → `asyncio.create_task(watchdog.watch / consumer.run / listener.listen)`。

  没有 P9 gate：watchdog / consumer 抢在 server 绑端口之前启动 → Fly platform probe 永远拿不到 `/healthz=200`
  → 120s grace 一到判 unhealthy → machine restart → 无限循环。Phase 02 L5 实证。
  </details>

**Q2**. L2 daemon 重启过程中漏了 L1 的 3 个 NOTIFY，怎么恢复？如果 `l2_event_cursor` 表都不存在（fresh DB）怎么办？

  <details><summary>答案</summary>

  恢复：启动时 `catchup_from_cursor(dsn, consumer='l2-candidate-refresh')` 读
  `l2_event_cursor.last_snapshot_id`，从 `snapshots WHERE id > last_seen` 回放每条 snapshot。

  Fresh DB 情况：`listener.py:113-135` 的三档 fail-soft 之一会触发——表不存在 → `logger.warning` +
  `return 0`，daemon **继续**启动；然后由 hybrid bootstrap（main() 后段）从 SQLite 读 L1 最近 snapshot
  的候选列表作为初始订阅。Wave 5 修的 bug。
  </details>

**Q3**. 30s WS watchdog 在低流动性市场（一晚上没成交）会误报吗？误报了 prod 会发生什么？我们怎么决定要不要调大阈值？

  <details><summary>答案</summary>

  会误报——低流动性 asset 真可能 30s 没 event。
  误报后果：仅 `add_breadcrumb(category='l2-ws', level='warning')`，**不**触发 Sentry alert / Telegram。
  daemon 进入 `_on_stale()` → 退避重连，重连成功后 `consecutive_stales` reset。
  数据上没损失（重连后 initial_dump 把 book 重新同步）。

  调阈值的判据：7 天 soak（Phase 03 Sign-Off 还有 "7-day window 观察 acceptance criteria"）观察
  误报率；如果误报 > 真触发 5×，Phase 04 改 60s 或重构为 per-asset watchdog 而不是 per-connection。
  </details>

**Q4**. 候选集在某次 L1 snapshot 后从 500 个变成 480 个（churn 掉 20 个），离开的那 20 个 asset 的历史 trades 数据怎么处理？为什么不直接 DELETE？

  <details><summary>答案</summary>

  D-08 **hard-cut at refresh**：`diff_candidate_sets` 算出 `removed=20 asset_ids` →
  `ws_consumer._subscribed_assets` 立即去掉这 20 个（下一次 WS 重连不再订阅）→
  `mirror.mark_candidates_removed(removed)` 把 `l2_candidates.removed_at_ts` 写成 now()。

  **但 `l2_trades` 里这 20 个 asset 历史成交行 NOT delete**——M4 backtest 必须能看到
  "这个候选还在的时段成交什么样"。软删除（`removed_at_ts IS NOT NULL`）让 dashboard 知道
  "现在不订了"，但数据可观察性保留。
  </details>

**Q5**. Mirror 写 Supabase 失败时（撤 SUPABASE_SERVICE_KEY 或 Free tier paused），daemon 会 crash 吗？错误怎么暴露给 ops？

  <details><summary>答案</summary>

  daemon **不 crash**——D-12 fail-soft：`L2SupabaseMirror.push_*` 的 try/except 接住所有 Exception，
  `logger.warning(...)` + `add_breadcrumb(category='l2-mirror', level='warning')` + 返回 False。

  ops 可见性双锚点：
  - 成功路径也 emit `add_breadcrumb(category='l2-mirror', level='info', ...)`（Phase 02.2 preemptive）→
    某次真 exception 触发 Sentry buffer flush 时，failure breadcrumb 顺带 visible。
  - 外部探针：Better Stack 监控 `/healthz` body 里的 `mirror:l2_tob_age_seconds` 子检查
    （**注**：Phase 03 Wave 6 chaos Inj L2-2 发现这条**链尚未完整接通**——`settings.l2_mirror_enabled`
    flag 在 Plan 03-06 里漏加，`/health` 的 mirror 子检查从未触发。Phase 03.1 GAP-1 待修。）
  </details>
