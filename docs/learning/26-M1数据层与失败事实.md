# M1 数据层与失败事实

> 对应：M1 continuity repair（2026-07-27）
> 先看操作：[M1 市场感知平台使用手册](../M1-市场感知平台使用手册.md)

## 30 秒心智模型

市场数据和“这次采集是否失败”不是同一种事实。

- **已发布市场事实**：最近一版完整、可供 M2 判断 event membership 的市场结构；它回答“现在还能安全读取哪一版”。
- **调度尝试事实**：L1 刚刚是否启动、成功、失败或取消；它回答“系统此刻是否正在变坏”。

一次 OOM 可以同时为真：昨天完整快照仍可读，刚才新快照已失败。前者不能覆盖后者。
因此 M1 的 strict health 同时报 `snapshot:last_success_age_seconds`、
`snapshot:latest_attempt`、`snapshot:failure_counter`。M2 在未得到新 Structure revision 前可以
继续识别旧版的边界，但不能把“旧版仍可读”误判为“感知层运行正常”。

## 关键代码

快照子进程启动前，父调度器先追加一条 `running` 尝试；这使 SIGKILL/OOM 不会只留在易失日志中。

```python
# src/polyarb/daemon/scheduler.py:306
attempt_id = await asyncio.to_thread(
    self._sqlite_store.begin_snapshot_attempt,
    started_at_ms=int(time.time() * 1000),
)
```

终态只允许把同一条 `running` 记录关一次，避免“后来成功”篡改已经观察到的失败。

```python
# src/polyarb/storage/sqlite_store.py:893
UPDATE snapshot_attempts
SET finished_at_ms=?, outcome=?, snapshot_id=?, failure_kind=?
WHERE id=? AND outcome='running'
```

健康检查把最新尝试和市场事实年龄合并：新失败但旧市场事实尚新鲜是 `warn`；市场事实也不新鲜时才是 `fail`。

```python
# src/polyarb/http/health.py:288
if attempt_value in {"failed", "cancelled"}:
    attempt_status = "warn" if truth_age_status == "pass" else "fail"
```

本机只读入口是：

```bash
make snapshot-attempt-status
```

它输出 volume-local SQLite 的最新记录，适合核对本机 daemon；生产判断仍以生产 `/health` 和
Polywatch 事件为准。

## 设计取舍

| 选择 | 为什么 |
|---|---|
| 追加式 `snapshot_attempts`，不用覆盖一个“最后状态”字段 | 失败是需要审计的历史；覆盖会使 OOM 在下次成功后消失。 |
| `never-started` 兼容为 pass | 老数据库已有正常快照但没有新表记录，不能凭空宣布故障；它也绝不等同于成功尝试。 |
| 快照失败但旧市场事实仍新鲜时先 warn | 让操作者保留“当前可读版本”和“系统需要修”的两个信息，不用二选一。 |
| Polywatch 按组件保存 incident | L2 持续故障时，L1 仍应独立发 recovery；否则 Telegram 会制造“L1 从未恢复”的假象。 |
| archive 不进入交易关键路径 | 历史研究/审计重要，但不能因归档失败阻塞 Structure、Quote 或 L2/L3。 |

这不是把旧的 all-in-one snapshot 变成生产 Structure 服务，也不是新的 24 小时验收已经开始。
它只补齐“故障可见且可区分”的基础能力。

## FAQ 增量

### 为什么不直接把 latest attempt 失败视为 HTTP 503？

因为两件事要同时保真：最近完整市场版本仍可被读取，与新的采集尝试已经失败。先以 `warn`
暴露新失败，等已发布事实过期或连续失败达到保护阈值后再升级为 `fail`，操作者能更准确地判断
是“停止使用新输入”还是“当前整个输入不可用”。

### 为什么新 Structure 与新 Quote 之间不是立即 `fail`？

新的 Structure 一发布，上一版 Quote 的成员关系就不能再供 M2 使用；但 Quote worker 正在为
新 Structure 重算时，十几秒到数十秒的短窗口并不表示采集器坏了。health 因此显示有界的
`source-snapshot-refreshing` warning：接口仍拒绝旧输入，Polywatch 也不会制造告警。300 秒内
没有匹配 Quote，或者 worker 失败/停止，才升级为真实 fail 和报警。

### “显示 running 就说明运行正常吗？”

不一定。`running` 只说明父调度器已开始一轮并尚未得到终态；超过 240 秒仍为 `running`，
它就是明确故障：`snapshot:latest_attempt` 变为 fail，父进程终止 Structure 子进程并把
`snapshot-subprocess-timeout` 写为持久失败事实。这样不会让一次 Gamma 上游异常或 CPU 死循环
无限占住之后的 5 分钟周期；下一轮会重新尝试，连续 5 次才进入暂停保护。

### 为什么 `snapshot:last_status` 不能从 `notes` 猜？

`notes` 只保存有界的 API 不可达原因；一个完整但有字段质量降级的 Structure 可以没有 notes。
因此 status 现在随快照原子写入 `snapshot_status`。`DEGRADED` 仍可让完整 Structure 和 Quote
继续工作，但 health 会如实显示 warn，而不是把“没有失败原因文本”偷换成 OK。
