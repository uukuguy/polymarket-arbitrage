# 生产故障控制边界

## 30 秒心智模型

生产故障实验不是一个“能制造异常”的脚本，而是一条四角色、两阶段的证据链：

```text
source/export（双 HMAC + SOURCE private）
  → 原始 response bytes + SOURCE 签名的 RECOVERED source facts
candidate evaluator（SOURCE public + VERDICT private）
  → signed candidate PASS
finalizer（双 HMAC + VERDICT public）
  → 在当前 SQLite 事务中重算 source facts，追加 VERIFIED
final evaluator（SOURCE public + VERDICT public）
  → 重读 VERIFIED source，给出 final PASS
```

运行期的 fault control 出问题时必须 **fail-open**：真实 Gamma/CLOB/Telegram
调用继续，不能让控制基础设施成为生产故障源。资格证据出问题时必须
**fail-closed**：缺一条链、签名不对、过期或恢复 writer 不匹配，都不能宣布
PASS。这两个方向并不矛盾：前者保护业务可用性，后者保护资格结论真实性。

## 为什么隔离 producer 必须在边界 claim

Candidate、Discovery、Reconciliation 可能运行在独立子进程。控制 API
写入 intent 的时刻，不等于目标 producer 已经拥有它；若 client hot path
每次查 SQLite，会把控制库锁和延迟带进真实请求。

因此 supervisor 为每次 child attempt 生成新的 `producer_boot_id`，worker
注册 exact `(component, release, machine, boot, supervisor run, attempt)`。
producer 只在下一次安全 cycle/batch 边界事务性 claim 一条 intent，随后把
不可变 `ActiveFault` 留在本进程内。client hot path 只读内存。进程重启后
boot ID 改变，旧的 armed/injected intent 不会被新进程重放。

## 为什么 Candidate 用 group ID，Telegram 用 outbox ID

Candidate 的业务正确性边界是一个完整 neg-risk group。一次 books 调用要为
同一个 `group_id` 拉齐全部 leg；用 URL、token 或“下一次请求”定位会误伤别组，
也无法把恢复绑定到该组的 complete quote batch。因此 CLOB fault 的
`target_key` 必须是 durable `group_id`。

Telegram 的恢复事实不是“某条消息后来发成功”，而是同一个 durable outbox
row 的 failed attempt 后出现 delivered attempt。因此其 `target_key` 是十进制
notification ID；用文案、chat ID 或任意下一条成功消息都会造成跨卡片假恢复。

## 清理、恢复与验证的严格顺序

```text
INJECTED → DETECTED → CONTAINED
  → memory clear
  → CLEANED commit
  → cleanup-confirmed
  → exact business writer row
  → RECOVERED
  → candidate PASS
  → VERIFIED
  → re-export + final PASS
```

远端 `cleanup-requested` 只是请求，不是 producer 内存已清的证据。producer
必须先 clear memory，再由专用状态 writer 写清理 receipt；receipt 写失败会令
runtime degraded/frozen。随后恢复也不能靠日志或 sleep：必须由相同 component、
target、runtime 的 Discovery batch、Reconciliation checkpoint、Candidate
success receipt 或 Telegram delivered attempt 提供真实 row。

## 不可变 source facts 与时间门

SOURCE 签名保护完整导出 envelope；`source_facts_digest` 则专门绑定可重算的
SQLite source facts，不把导出当下的 freshness 布尔值混进去。candidate artifact
同时携带持久化 writer 时间推导出的 `source_valid_until_ms`。

finalizer 在一个 `BEGIN IMMEDIATE` 事务中重新生成完整 source facts：

- 数据变了，digest 不同，报 `verdict-source-mismatch`；
- 数据没变但当前 authority clock 已越过 deadline，报
  `verdict-source-stale`；
- 两者都通过，才可追加绑定 `verdict_id` 与 `verdict_digest` 的 `VERIFIED`。

这样“仅仅时间流逝”有稳定、可追溯的 stale 结论，不会伪装成随机 source
mismatch；导出时刻本身也不能制造不同的 immutable digest。

## 设计取舍

1. **控制面 fail-open，证据面 fail-closed**：宁可本次实验不生效，也不能影响
   正常 upstream；宁可资格 FAIL，也不能用缺失证据补零。
2. **两套 Ed25519 权限**：SOURCE 证明“这确实来自 authority snapshot”，
   VERDICT 证明“独立 evaluator 判过”；任一私钥不能替代另一角色。
3. **四进程而非一个万能 CLI**：source、candidate evaluator、finalizer、final
   evaluator 各自持有最小能力，降低自写、自签、自盖章的可能性。
4. **原始 response bytes 优先**：磁盘上的 `evidence.json` 就是被认证传输的
   精确字节，避免 parse→serialize 改写产生另一份“看起来相同”的证据。
5. **一 fault 一次消费**：one-active、TTL、exact runtime/target、single-use
   一起把爆炸半径限制到一个确定调用；cleanup 失败立即冻结 matrix。

## 对手测试

1. SOURCE facts 没变，但 candidate artifact 在 finalizer 前刚好越过
   `source_valid_until_ms`。应该是 mismatch、stale，还是仍可 VERIFIED？
2. Candidate `group-A` fault 清理后，`group-B` 写出成功 quote batch。能否作为
   recovery writer？为什么？
3. arm 的 HTTP 响应丢失，operator 不知道 intent 是否 accepted。为什么不能
   直接重发同 nonce？下一步的安全动作是什么？
4. cleanup endpoint 返回 200，但没有 `cleanup-confirmed`。是否能继续下一行
   matrix？
5. final evaluator 持有 SOURCE/VERDICT 两个公钥，但没有任何私钥和 HMAC。
   它能伪造哪一步？它又能验证哪些绑定？
