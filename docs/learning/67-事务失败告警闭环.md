# 事务失败告警闭环

## 30 秒心智模型

`retryable` 不是“已经处理过的失败”，而是一次尚未恢复的运行事实。若 worker
先把 job 标为 retryable、稍后再写告警，进程可能正好死在两者之间：系统会继续
重试，但操作员完全不知道。现在的提交边界把三件事合在同一笔 Postgres 事务中：

```text
lease fenced retry → immutable failed attempt → incident event + dashboard outbox
```

因此只要失败对下一位 worker 可见，它对控制面也必定可见。

## 为什么要用 lease epoch 当事件幂等键

同一个 job 可以失败多次，但同一次 lease 只能有一个失败事件：

```python
idempotency_key = f"job-retry:{lease.job_key}:{lease.lease_epoch}"
```

这样网络重放或 worker 在提交响应丢失后再试，不会重复创建 outbox；而真正被接管
的下一次运行拥有新的 epoch，会留下新的失败证据。incident 的 `dedupe_key` 则只按
job 区分，所以连续失败仍归入一个开放 incident，不会制造无数相同告警卡片。

## 设计取舍

- 当前 channel 是 `dashboard`：先保证 durable operator 可见性；实际 webhook /
  Telegram 投递仍由独立 alert worker 消费 outbox，绝不让通知网络阻塞采集。
- retry 的 severity 是 `warning`：旧的 certified truth 仍可读时，单个 shard
  重试不是全局 P1；具体升级门由在线 SLA 和 incident policy 决定。
- 不在 worker 内直接发送消息：发送失败本身也需要可重试的持久证据，不能与数据
  获取绑成一个同步 RPC。
