# 事务型云端采集工作池

## 30 秒心智模型

“多开几个 worker”本身不会提升正确性；正确性来自每个 worker 都必须先在
Postgres 取得带 epoch 的 lease，只有持有当前 lease 的 worker 才能写回收据。
工作池只提高吞吐：协调器负责准入、物化和认证，Structure range 与 Quote batch
各自独占可扩展的循环。它们即使同时看见同一任务，也只能有一个成功领取。

如果队列已积压，高水位会让协调器停止生成新的 source window。此时少采一次比继续
采过期数据更好：先把可用容量用于降低已有工作的年龄，恢复新鲜度后再准入。

## 代码地图

- [worker_loop.py](../../src/polyarb/control_plane/worker_loop.py:15)：一个角色只运行自己的有界 turns；
  本地 lock 防止单进程重叠，但跨机器所有权仍由 Postgres lease 决定。
- [scheduler.py](../../src/polyarb/control_plane/scheduler.py:43)：协调器构造时排除两个独占池；
  coordinator 带 range budget 会被拒绝，不能暗中抢回 range 工作。
- [cli_control_plane.py](../../src/polyarb/cli_control_plane.py:149)：`serve --worker-role` 是唯一角色选择入口；
  `all` 仅为旧单机命令的兼容模式。
- [postgres.py](../../src/polyarb/control_plane/postgres.py:242)：源窗口准入在同一 advisory-lock
  事务里检查 Structure/Quote 未完成量，再决定 admitted、busy 或 backpressured。
- [postgres.py](../../src/polyarb/control_plane/postgres.py:3517)：独立 API 返回的 `queue_health`
  只含数量、最老年龄和 next job hint。

## 设计取舍

`next_job_key` 不是预约，也不是授权。它只是给操作者和扩容脚本的无敏感提示；真正执行
仍必须调用 `claim_job`，因为另一台机器可能先领取。把它当成 lease 会造成重复写入的错觉。

高水位计入 `runnable/retryable/leased/checkpointed`，而不是只看 runnable。否则正在执行或
等待收据的工作不被计数，多个协调器仍会持续灌入队列。
