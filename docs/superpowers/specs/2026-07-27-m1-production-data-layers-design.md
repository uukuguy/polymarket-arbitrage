# M1 生产数据层与快照策略设计

**日期：** 2026-07-27

**状态：** 已获方向批准；等待书面规格审阅后进入实施计划

**目标：** 让 M1 作为持续、可证明的市场感知层为 M2 提供事实，而不是让一个全量快照进程偶尔跑完。

## 1. 问题重述

当前 L1 的“snapshot”在一次作业中混合了四类职责：全市场结构枚举、
neg-risk 候选资格、CLOB 价格采集和历史归档。它在当前生产规模下运行约
31 分钟后再次被内核 OOM 杀死；同时与 HTTP 服务和两分钟报价采集器共用
同一 1 GB cgroup。旧快照仍较新时，`/health` 不能直接表达这次失败，报价也
可能被连带推过 300 秒的 fail-closed 边界。

这不是“把同一个作业升到更大内存”就能定义完成的缺陷：不同消费者需要的
事实、时效和失败语义不同。M1 尚未达到生产上线门槛；M2 当前只能使用真实
数据做机会巡检和 paper，不能使用这些数据自动真实下单。

## 2. 生产目标与非目标

### 生产目标

1. M1 持续发布一个可验证的市场结构版本：市场、事件、结果腿、状态和
   neg-risk 关系完整且带版本身份。
2. M2 只消费“认证的结构版本 + 绑定该版本的新鲜报价”；缺少其中任何一个
   都必须拒绝机会结果，不能输出伪零机会。
3. 实时盘口独立于结构归档。正式套利的下单判断来自短时盘口与成交风险规则，
   不等待全市场快照。
4. 每次失败均可在健康、告警和持久记录中看到；任一层恢复应独立通知，不能
   被其他组件的持续故障遮蔽。
5. 历史快照仍可用于研究、审计和回测，但它的失败不得拖垮在线结构、报价或
   盘口链。

### 非目标

- 本阶段不接入钱包、签名、下单或真实资金。
- 不把历史全量价格快照伪装成实时交易数据。
- 不立即把 SQLite 当作跨机器共享数据库；跨机器前必须先有明确的发布边界。
- 不因一次 OOM 直接承诺某个固定内存值。内存是每一数据层容量测量的结果，
  不是架构目标。

## 3. 四种数据产品

| 数据产品 | 内容与时效 | 消费者 | 失败语义 |
|---|---|---|---|
| **结构同步（Structure）** | Gamma 市场/事件/结果腿/状态/neg-risk 关系；5 分钟增量同步，30 分钟内必须有已认证结构版本；每日一次全量对账 | M1 候选筛选、M2 组合合法性 | 新版本失败时保留旧认证版本；超过 30 分钟不再允许新的 M2 候选进入在线机会链 |
| **报价事实（Quote）** | 对已认证候选集合的 CLOB 顶档、数量、拒绝原因；当前巡检/paper 每 120 秒，超过 300 秒即失效 | M2 机会发现 | 任何 run 不完整、版本不匹配或过期都返回不可用，而不是零机会 |
| **实时盘口（L2/L3）** | 被选候选、paper 仓位和未来实盘 watchlist 的 WS 深度/成交证据 | M1 盘口感知、未来执行风控 | 对应市场停流或不新鲜时禁止该市场的实时决策；不由其他市场流量掩盖 |
| **历史归档（Archive）** | 完整市场结构与可选全量价格横截面；低频批处理、不可变 Parquet/R2 | 研究、回测、审计、长期变化发现 | 作业失败独立告警、保留上次归档；不阻塞 Structure/Quote/L2/L3 在线链 |

### 关键判断

“全量 CLOB 价格快照”属于 Archive，不是 M2 的价格输入。M2 需要的是对一个
已认证结构版本的 Quote；正式套利需要 L2/L3 的更短时事实。结构同步与报价
可以共享版本身份，不能共享“必须一次抓全、一次写完”的生命周期。

## 4. 分阶段架构

### 阶段 A：M1 初期生产感知

保留单一 L1 应用和本地 SQLite 作为当前部署边界，但把职责拆开：

1. Structure 生成与发布独立于 Archive。每次结构更新先写入 staging，完成
   完整性校验后原子发布 `structure_revision`；Quote run 必须记录并验证这个
   revision/hash。
2. Quote worker 继续只读 CLOB、写本地 SQLite，但其调度、内存和健康不再依赖
   Archive 的成功。它只使用已发布的 Structure。
3. Archive 改成低优先级、可取消、带独立资源预算的批任务。它只写归档和结果
   记录，不覆盖在线 `structure_revision`。
4. 所有 Structure/Archive 尝试在启动、运行、完成、失败、SIGKILL/possible-OOM
   时持久化 attempt 事实。健康同时显示“最后成功”和“最近一次尝试”，旧成功
   不能掩盖新失败。
5. 当前同机过渡期按实测峰值配置足够容量；容量变更只是在拆分完成前避免把
   在线链拖垮的护栏。上线门槛是各层 SLO 与失败可见性，不是 VM 内存数字。

阶段 A 的在线验收：连续一段观察内，Structure 不超过 30 分钟、Quote 不超过
300 秒、Archive 失败不影响前两者、每一失败和恢复可由健康与 Telegram 单独
定位。

### 阶段 B：M1 → M2 集成

当 M2 需要稳定消费而不是本机读取时，建立跨机器发布边界：

1. Structure publisher 生成不可变 revision manifest（revision id、内容 hash、
   完整性结果、生成/发布时刻、来源版本）。
2. 共享的权威元数据放入适合多消费者读取的数据库/对象存储发布面；本地
   SQLite 降为 L1 热缓存和采集状态，绝不被两个机器并发写入。
3. M2 订阅或轮询“已发布 revision”，并将 Quote run、机会结果和后续 paper
   receipt 都绑定到 revision/hash。未完整发布、版本漂移、结构过期均 fail closed。
4. Archive worker 可以独立机器/资源运行，完成后只追加归档索引，不改变当前
   已发布在线 revision。

这一步的结果是：Archive 的 CPU、内存或失败域不再与在线服务共享；M2 可重放
“当时看见的结构 + 报价”，而不是依赖某一台机器的文件系统状态。

### 阶段 C：正式套利运行

正式资金运行前拆为三个故障域：

- **感知域：** Structure、Quote、L2/L3 和完整的来源/时效证明；
- **策略域：** 组合计算、费用/滑点、资金占用、候选排序与 paper/live 决策；
- **执行域：** 认证、allowance、限额、下单、成交回报、对账和 kill switch。

执行域只接受带有效结构 revision、报价时效和实时盘口证据的策略请求。全量
Archive 永远不在执行关键路径；任何一个关键输入过期时，系统拒绝新单而不是
继续使用“看起来最近”的旧快照。

## 5. 故障、告警与恢复契约

### Structure / Archive attempt truth

新增持久 attempt 记录而不是只保存成功快照：开始时间、结束时间、数据产品、
输入 revision、结果、失败分类、退出信号、OOM 指示、产物/发布 revision。

- Structure attempt 失败：`/health` 立即 warn/fail（取决于最后认证 revision 的
  年龄），Telegram 报告具体失败；旧 revision 仅在 30 分钟有效期内可继续供
  已有读者读取。
- Archive attempt 失败：`/health` warn，Telegram 报告；在线 Structure/Quote
  仍可为 pass。
- Quote attempt 失败或 age >300 秒：M2 opportunity fail closed，独立告警。
- L2/L3 不新鲜：该市场的实时决策 fail closed，不能由全局 WS 活跃掩盖。

### 独立通知

Polywatch 不再用一个全局 `active_keys` 决定恢复。每个组件拥有自己的 incident
状态、首次通知、提醒、恢复通知和失败重试；L2 持续故障时仍必须发送 L1 的恢复。

## 6. 存储与资源策略

1. **在线热状态：** 阶段 A 为单机 SQLite；只允许一个写入进程族。阶段 B 起，
   权威发布元数据迁往共享服务，本地 SQLite 不跨机器共享。
2. **冷归档：** Parquet/R2 作为不可变历史；本地卷只保留有明确恢复用途的有限
   热窗口。保留长度和对象存储成本在实施前根据实际文件量测算，并通过归档
   manifest 可追溯，不由静默 purge 决定。
3. **计算：** 在线 Structure/Quote/L2/L3 的容量以峰值 RSS、cgroup 使用量和
   时效 SLO 验证。Archive 使用独立资源预算；4 GB 或 8 GB 仅在证明归档频率和
   数据价值后分配，不作为掩盖在线架构耦合的永久补丁。

## 7. 迁移顺序

1. **可见性止血：** 持久化最新 Structure/Archive attempt，健康/Telegram
   直接暴露 OOM、失败计数和组件独立恢复；为当前数据产品建立明确名称。
2. **在线契约分离：** 从现有单体 snapshot 中抽出 Structure revision 发布和
   Quote 的 revision 绑定；禁止 Archive 覆盖在线 truth。
3. **容量与调度验证：** 依据分层后的真实峰值设置过渡期资源，证明 Archive
   与 Quote 不再互相突破时效 SLO。
4. **共享发布面：** M2 接入前完成 manifest/共享权威元数据，删除跨机器共享
   SQLite 的假设。
5. **资格观察：** 只有 1–4 均通过后，启动新的 24 小时观测。它验证在线数据层，
   不把 Archive 成功次数当作交易就绪证明。

## 8. M1 上线门槛与 M2 边界

M1 初期生产可用必须同时满足：

1. 有不超过 30 分钟的认证 Structure revision，且完整性/来源 hash 可查询；
2. Quote 对该 revision 完整并在 300 秒内；
3. L2/L3 对受监控市场保持各自既有严格健康合同；
4. 任一层失败、恢复和最近一次尝试可从 `/health`、持久数据和 Telegram 对齐；
5. Archive 不会使 1–4 失效。

这允许 M2 做可靠的真实数据巡检和 paper。M2 真实下单还额外需要策略的费用、
滑点、多腿成交、资金、认证、限额、对账和 kill switch 门槛；本设计不把 M1
数据可用误报为套利可实盘。

## 9. 验证策略

- 单元/集成：每种 attempt 结果、revision 原子发布、旧 revision 过期、Quote
  版本漂移、Archive 失败隔离、独立 incident recovery。
- 容量：在真实或等比例市场规模下采集各数据产品峰值 RSS/cgroup，验证 Quote
  p99 age 与 Structure 发布时效；不使用“进程没有崩溃”作为容量通过标准。
- 生产：先验证一个 Structure 发布、连续 Quote、Archive 成功/故障隔离和
  Telegram 逐组件告警；随后启动新的 24 小时在线链资格观察。

## 10. 取舍

- **不选择立即双机拆分。** 当前卷绑定 SQLite，先拆机器会制造不可见的双写或
  旧数据读取风险；先形成 revision 发布合同，再拆分。
- **不选择永久单体加内存。** 它可以作为过渡护栏，但不能提供 M2 所需的数据
  版本语义，也不能隔离 Archive 故障。
- **不选择放弃历史归档。** 它对研究、审计和模型反馈有价值，但必须以非在线
  的频率、资源和失败语义运行。
