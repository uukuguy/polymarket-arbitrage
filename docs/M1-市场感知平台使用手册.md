# M1 市场感知平台使用手册

> 最后核验：2026-08-10
> 动态状态：以 [`.planning/CURRENT.md`](../.planning/CURRENT.md) 和生产 L1/L2 `/health` 为准。
> 定位：产品说明 + 日常运维；设计学习请进入 [`docs/learning/`](learning/00-INDEX.md)。

## 1. 30 秒心智模型

市场发现 → L1 Structure（5 分钟）→ Quote（2 分钟）→ 候选集 → L2 实时订单簿 → L3 观察证据 → 人工/paper 决策。
M1 的职责是看清市场和暴露数据质量，不构成真实资金下单授权。

三种事实必须分开：本地运行只证明当前 checkout 和本地数据；“候选”是 L1 筛出并送往 L2 的市场候选集，其收敛证据只证明数据链跟上；生产事实必须由当前生产实例的 strict `/health`、读模型和可审计时间戳共同证明。任何一层的绿灯都不会自动升格成下单许可。

## 3. 五分钟日常巡检

### 自动报警与本机临时检查

生产主监控部署在 Fly `polyarb-l1` 的独立 `cron` 机器上，每 2 分钟检查
L1、机会 feed、L2/L3 和 Dashboard。故障通知进入 Telegram 与
[@polyarb_l1_bot](https://t.me/polyarb_l1_bot) 的私人聊天：首次或变化后的故障
立即通知，同一故障持续 30 分钟提醒一次，恢复后通知一次；全绿时不发送例行消息。
GitHub Actions 是异地兜底，不作为准点时钟。

四个监控面（L1、机会 feed、L2/L3、Dashboard）各自拥有独立的故障与恢复状态：
同一轮可以合并发送多个新故障，但 L1 恢复不会再等待仍故障的 L2 一起恢复。Telegram
中的 Structure 阈值告警明确标为 `RECOVERING`，表示 strict health 已失败、短延迟
有界重试仍在运行；它不再使用会误导为永久停产的 `PAUSED` 文案。
投递失败时，只保留投递失败的那个组件，下一轮继续补发，不会把其他组件重新标为故障。
Opportunity outbox 每轮最多发送 20 条、相邻 Telegram 请求至少间隔 1.1 秒；HTTP
失败仍按持久化指数退避重试。因此机会状态突变形成积压时会持续排空，不会用无界突发
把 Telegram 限流变成长期故障。

每次新的 Structure 发布后，匹配的新 Quote 在同一个 300 秒 SLA 窗口内重算。
新轮完成认证和机会投影前，机会接口继续服务上一个完整认证版本，并以
`refreshing=true`、`latest_structure_snapshot_id` 和 `source_snapshot_id` 明示新事实与当前服务
事实的边界；它不会把新旧腿混成一个 run。旧 feed 自身超过 300 秒、采集失败且
无法在时限内恢复，或 collector 停止，才是必须处理的故障与 Telegram 告警。

新的 `quote_feed:collection_phase` 子检查持久化显示 `universe`、`admission`、
`fetch`、`transform`、`persist`、`certify` 和 `projection` 阶段。当前 checkpoint
45 秒未推进为 warn，120 秒未推进为 fail；这是新轮的卡点证据，不是把仍在
SLA 内的旧认证 feed 清空的指令。CLOB fetch 有 100 秒 stage timeout，整个 child
从 attempt start 起有 120 秒 absolute hard limit；到线会在预留的 shutdown 窗口内
terminate→kill→reap，停止续租、把 run/attempt 标成 failed 并重试，不会已知 fail 后
继续运行到 180 秒。
配置加载会拒绝任何无法证明 SLA 的 timing 组合：`interval + child hard limit + 30s`
发布余量必须严格小于 300 秒，`fetch timeout + shutdown reserve` 必须严格小于 child
hard limit。边界等于 SLA 也会启动失败，不能通过把 interval 调到 240 秒制造“合法但长期
陈旧”的生产配置。默认值为 120s cadence、100s fetch、120s child hard limit、2s shutdown
reserve。

每次新 Quote feed 先完成认证发布，再有界清理最多 20 个旧终态 Quote run。最近
10 个 complete、最近 10 个 failed 和全部 collecting 都受保护；清理失败不撤销新
feed，下一轮继续。SQLite 通过 freelist 复用已删除页，生产禁止为了让文件尺寸立即
变小而在线执行 `VACUUM`。磁盘排障应联合看可用空间、`page_count`、`freelist_count`
和旧 run 数，不能只看 `state.db` 的显示大小。

启用容量治理后，`perception:capacity_controller` 是容量故障的主事实面：`pressure`
为 warn，`critical`/`exhaustion-imminent`、运行态缺失或三个巡检周期未更新为 strict
fail。Dashboard 的 P1 storage capacity card 显示剩余空间、已执行的自动回收、下次
处置、重试与回执；它只有在压力后的正向回收回执和 normal 测量同时成立时才关闭，
绝不能因重试启动或短暂降级而关闭。

同机 Structure 与全市场 Quote 子进程不会再同时抢 CPU/SQLite：两者共享一个
producer slot。Structure 每次最多推进 80 个已原子提交的 Gamma 页面便主动 checkpoint
并释放 slot；这不是失败或降级，health 显示 `checkpointed/pass`，调度器立即续排下一片。
已经到期的 Quote 可在切片边界取得 slot 并保持 300 秒新鲜度 SLA；Structure 随后从同一
opaque cursor 继续，完整认证后 Quote 再绑定新版本重算。等待 slot 的时间不消耗
Structure 子进程 timeout，也不停止父进程 HTTP、health 或 Polywatch。
Structure 认证发布会立即唤醒 Quote 单 worker；从新版本可见到 worker 标记
`collecting` 之间的调度竞态也归入同一个 300 秒 `source-snapshot-refreshing/warn`
窗口，不制造故障报警。匹配 Quote 未提交前机会接口仍 fail closed，不返回旧报价。

在本机临时检查，直接复制：

```bash
make polywatch-healthz-dry
make polywatch-resident-status
make polywatch-resident-repair
```

若你在本机运行过 L1 daemon，想看该 SQLite 中**最新一次快照尝试**的原始结果，运行：

```bash
make snapshot-attempt-status
```

它只读本地数据库，输出 `latest` JSON；`failed` 的 `failure_kind` 可直接区分可能 OOM、
子进程失败或取消。它不连接 Fly、不发送 Telegram、不创建表，也不能替代生产 strict
`/health`。生产问题仍先跑 `make smoke-health-prod`，再用 Fly/Telegram 证据定位。

- `make polywatch-healthz-dry`：立即用正式监控的同一套规则读取四个生产面，但
  **不会发送 Telegram**、不会 unpause 或修改生产。`noop` 表示该面正常；
  `push` 表示正式巡检会报警；Structure stale 会报告 `RECOVERING` 和 durable
  页进度，不会由巡检器盲目调用 unpause。
- `make polywatch-resident-status`：读取 Fly 上最近的自动巡检和状态文件，需本机
  `flyctl` 已登录。`active_keys` 为 `[]` 表示当前没有未恢复故障；
  `last_seen_at_s` 应约每 2 分钟推进。状态文件固定在容器内
  `/app/logs/polywatch-healthz-state.json`：该目录在镜像构建时属于运行用户
  `polyarb`，避免历史 root 所有的 `/tmp` 文件让监控循环静默失去去重与恢复状态。
- `make polywatch-resident-repair`：这是**监控监控者**的恢复入口。它从 Fly
  control plane 要求“恰好一个、且为 `started` 的 cron”机器；发现 stopped 时会
  自动 start、复查，再发送一条 L1 Critical Telegram。机器缺失、重复、权限失败、
  拉起未验证或 Telegram 未送达都会非零退出，不能被误报为健康。

Fly cron 是两分钟主告警链，但它被停止时无法报告自身失联。因此 GitHub Actions 还会
每五分钟在 Fly 外部运行同一 watchdog：检测到 cron 被停止会先尝试恢复并立即通知。
GitHub schedule 仍可能抖动，不能当作五分钟硬 SLA；它的职责是独立故障域兜底。每次
L1 部署也会在 HTTP smoke 之前执行这项检查，部署成功不再能掩盖一个 stopped cron。

当 `/perception` 的 Open incidents 出现 `quote-collection-timeout` 时，不要把
机会列表为空理解为“没有机会”。卡片中的 `Impact`、`Automatic action`、`Next action`
来自同一条 durable incident：它会显示 120 秒子进程期限、连续失败次数和最后一次
认证成功的年龄。`retry immediately` 仅表示自动恢复已启动；只有后续认证 Quote
成功并在历史中出现 `verified` 才表示行情盯盘恢复。处置顺序是：先保留 incident ID
与 `/healthz`，再检查 CLOB 可达性、子进程 I/O/日志和容量；在 `feed unavailable`
期间不得据机会 API 作交易或 M2 输入判断。

`quote-collection-failure` 则覆盖非 timeout 的子进程退出（例如 Structure/源真相
读取不可用）。Dashboard 会显示 `retry at next cadence`、`inspect child stderr` 和
经过 API 脱敏的 failure reason；父进程日志只保留最多 1KB 的 stderr 尾部以便定位，
不将它混入机器可读 stdout 协议。它同样必须等待后续完整认证 Quote 转为 `verified`，
不能因一次重试启动或旧 feed 尚可读取而自动关闭。

机会 API 的 `source_truth_status=last-known-authenticated` 表示实时的 SQLite
diagnostic read 暂时超时，但本次返回仍严格绑定在尚未过期的认证 Quote 的
`source_snapshot_id + universe_hash` 上。此时 `/health` 为 HTTP 200 且
`quote_feed:source_truth_read=warn`：可以继续把候选作为 M2 的**只读评估输入**，
同时应查看 `consecutive_failures` 与容量告警；不得把它误读为实时 source truth 已恢复。
只有认证绑定失效，或 Quote/universe 自身超过 SLA 时，API 与 strict health 才 fail-closed。

Structure 发布后的 snapshot/staging retention 是低优先级 SQLite 写操作：只要 Quote
pipeline 已 active 或到期，scheduler 会记录 `snapshot retention deferred` 并跳过本轮
清理，等待下一次成功 Structure tick。它不能为了回收旧数据而与 Quote `persist` 争抢
写锁、把当前报价拖到 120 秒 hard timeout；这是一项自动恢复保护，而非清理失败。

不要用 `make polywatch-healthz` 做普通临时检查：它是正式模式，可能真实发送
Telegram，并在 L1 snapshot stale 时执行受控 unpause。

当前 release 75 的修复后 L3 连续性窗口还多一层**本机证据定时器**。它不是故障
报警器，而是每 5 分钟判断 T+6/T+12/T+18/T+24 是否到点；到点后调用既有
`make l3-soak-checkpoint`，只提交 PASS 报告。查看它：

```bash
launchctl print "gui/$(id -u)/com.polyarb.l3-soak-autocheckpoint" \
  | grep -E "state =|runs =|last exit code|run interval"
tail -50 "$HOME/Library/Logs/polyarb-l3-soak-autocheckpoint.log"
```

正常的未到点输出形如
`idle next=T+6@2026-07-26T14:51:13.206077Z`；`last exit code = 0`
表示最近一次预检成功。Mac 睡眠期间不会丢市场证据：生产数据库仍每 30 秒记账，
唤醒后定时器补生成累计报告；但如果 Mac 一直关机，报告会延后生成。实时故障仍看
Telegram/Fly Polywatch，不要把这个本机定时器当告警主链。

1. 先读 [`.planning/CURRENT.md`](../.planning/CURRENT.md)，确认当前已关闭和未关闭的质量门。CURRENT 是仓库当前结论，不是生产实例的实时心跳。
2. 跑 `make smoke-health-prod`，再跑 `make smoke-market-truth-prod`。两者都只读 L1 strict `/health`，不调用 flyctl。除整体 `pass` 外，还必须看 `market_truth:coverage=complete/pass`；它回答最新一次 snapshot 尝试是否完整发布。再联合看 `snapshot:latest_attempt`、`snapshot:failure_counter` 和 `snapshot:structure_sync`：前者专门报告调度器最近一次尝试（即使旧完整快照仍新鲜，也会暴露新的 OOM、子进程失败或取消）；`checkpointed/pass` 表示 Structure 达到 **45 秒协作墙钟预算或 40 页上限**后主动让 Quote 使用 producer slot，不是失败，也不增加 failure counter。`snapshot:schedule` 暴露 adaptive `effective_timeout_s`、当前 `producer_slot_budget_s`、`attempt_timeout_s`，以及三个不可混用的边界：`generation_checkpoint_budget_s=45` 是 Gamma/generation 的协作 checkpoint；`generation_child_hard_limit_s=75` 是 Gamma 获取、generation chunk 写入或认证 child 的硬上限；只有 publication 已是 `ready` 时才使用 `pointer_switch_hard_deadline_s=15` 完成原子指针切换。旧的 180 秒 finalizer slot 已移除；一个 child 不能从 75 秒阶段静默跨入 15 秒阶段。即使切片刚提交最后一页，也必须先 checkpoint，让下一次独立调度进入或恢复 bounded generation publication worker。该 worker 逐块归一化、认证并持久化 checkpoint，达到 ready 的调用不切换，后续调用才原子发布；`running` 超过本次入场阶段的真实 `attempt_timeout_s` 就会终止子进程，不能让 Structure 长期饿死 Quote。Quote pipeline 对共享 producer slot 有优先权：Structure 在初检及拿锁后都会重查 Quote active/due；命中时写入 `snapshot:producer_defer=warn` 的有界 queued receipt，释放 slot，5 秒后重试。defer 不创建 `running` attempt、不增加 failure counter，锁等待也不计入 `started_at_ms` 或 attempt duration；因此只能把 prolonged defer 诊断成排队/饥饿，不能误报 child timeout。上述边界必须与 Quote 的 300 秒严格 SLA 联合验收，任何 Quote age 达到 300 秒都算失败。无论协作 checkpoint 或异常终止，Structure 已提交的 Gamma 页面和 opaque cursor 都会保留；前者立即续排，后者按恢复退避从同一窗口继续，而不是退回第一页。`structure_sync` 的 `open/events_complete/complete/published` 分别表示 events、markets、认证发布和已绑定快照，output 给出两类已提交页数。连续失败计数 `0` 为正常、`1–4` 为预警、`5+` 为严格失败，但新版本保持 `RECOVERING` 主动重试，不再进入永久 `PAUSED`；历史数据库中的 `PAUSED` 会在加载时迁移为 `RECOVERING`。`storage:volume_free_percent` 在可用空间低于 20% 时 warn/Polywatch 报警、低于 10% 时 strict fail。重启时会先从 SQLite 的完整认证 Quote 重建紧凑机会 feed，再采集新 Quote；若重启中断 Quote 子进程，已确认退出后会把唯一 `collecting` run 标成 `collector-cancelled`，不留下阻塞新实例的租约；Structure 在 Quote 采集途中换代时，旧 Quote 会被拒绝并立即重试，不必等待完整 120 秒周期。`never-started` 仅表示实例尚未写入新尝试记录，兼容已有旧快照，不能当作一次成功。`market_truth:last_complete_age_seconds` 只回答最近一次完整发布有多旧，不能替较新的失败尝试开绿灯。
3. 跑 `make smoke-l2-health-prod` 先确认 L2 Fly 路由可达，再跑 `make smoke-l2-health-strict-prod` 读 strict `/health`。前者只检查 always-200 `/healthz`；后者打印 HTTP 与 body，非 200 退出非零。不得用 `/healthz` 代替 strict 结论。
4. 在 L2 strict body 中联合看 `event_bus:cursor_lag`、`ws:last_event_age_seconds`、`mirror:l2_tob_age_seconds` 和 `l3:active_count`。冷启动的 `null`、`WAITING_FOR_EVENT` 或 L3 低于 10 都是“证据不足”，不是已验证的稳定性。
5. 若要检查本地 quote-run 合同，先确认已有最新 snapshot，再跑 `make collect-neg-risk-quotes db=data/state.db`；它对 CLOB 只读、但会写本地 SQLite，既不是生产 cron，也没有部署或下单。随后跑 `make scan-arb-quotes db=data/state.db`。只有 quote 与 universe 两个时钟都在 SLA 内，它才输出完整 run 的 gross-before-fees 候选；缺 run 或任一 stale 均非零退出。该 known-universe 覆盖不含下一次 membership snapshot 前新挂出的组。历史积压追赶使用 `make cleanup-neg-risk-quotes db=data/state.db max_runs=20`：每个 run 单独短事务，始终各保留最近 10 个 complete/failed，绝不删除 collecting；市场数据为公开数据，清理连接关闭 SQLite secure overwrite，让释放页进入 freelist 供后续 Quote 复用。它不会缩小主 DB 文件，禁止在在线卷上用 `VACUUM` 冒充恢复空间。
6. 最后跑 `make diagnose-arb-feed-prod`（实战加 `min_edge_bps=0`），并在 L1 strict `/health` 联合查看 `market_truth:*`、`quote_feed:last_complete_age_seconds` 与 `quote_feed:collector_state`。诊断输出只有在 success payload 明确包含 `coverage=verified-standard-neg-risk`、合法 snapshot/universe/run 身份和逐候选 provenance 时才 exit=0。`available-zero` 才是合法零机会；HTTP 503 或 invalid response 不是零机会。旧的 1,278/1,278 报价容量证据建立在被截断的 market universe 上，已撤销其 M2 readiness 含义；即使历史采集跨周期稳定，仍不代表机会 feed 已准备就绪。

## 4. 三种使用方式：生产巡检、本地验证、Dashboard

### 生产巡检（只读）

- `make smoke-health-prod`：纯 GET L1 strict `/health`，失败时不要继续将 L1 当新鲜输入。
- `make smoke-market-truth-prod`：在同一只读 health body 中强制验证最新 snapshot 尝试已完整发布，并打印 release、覆盖计数和最近完整发布年龄。
- `make smoke-l2-health-prod` 只证明 L2 `/healthz` 可达；`make smoke-l2-health-strict-prod` 才以只读 GET 给出 strict `/health` 的 HTTP/body 和业务健康结论。
- `make diagnose-arb-feed-prod min_edge_bps=0`：一次只读 GET 后分类 M1→M2 机会 feed。成功还会验证 `verified-standard-neg-risk`、source snapshot、universe hash、quote run 与逐候选身份；任何缺失都是 `invalid-response`，不能把 feed 升格为 ready。

2026-07-31 的生产验收入口就是以上四条命令，不需要手工启动 worker。L1 app
自动运行 Structure 与 Quote，独立 cron 每两分钟运行 Polywatch；操作者日常只读
巡检、查看机会 feed 和处理报警。不要在 SSH 中手工常驻 `structure-sync` 或
`collect-neg-risk-quotes`，它们会绕开生产单写者编排。

L1 的 `/data/state.db` 是单写者 SQLite authority：一次只能有一台运行中的 `app`
machine 挂载权威卷。部署必须通过 `make deploy` 或受同等约束的 CI 入口；它以
`--ha=false --max-concurrent=1` 串行更新并收敛为 `app=1 cron=1`。不要为单卷 SQLite
让 Fly 临时创建未播种的 app 备用实例：否则 HTTP、Structure、Quote 和机会 feed 会在两份
数据库事实之间分叉。若 Fly 控制台显示多台 app，先按 volume 确认既有权威
`/data/state.db`，停止未播种副本，再检查 `/healthz` 的 `machineId`、
`snapshot:structure_sync`、`quote_feed:*` 和 `/perception/incidents`；机器数收敛本身
不是恢复证明。

### L1→L2 市场候选链（只读观察）

**候选不是独立 staging 部署**；在本项目中，它指 L1 根据最新市场快照筛出、写入 Supabase，再由 durable cursor + NOTIFY/poll 驱动 L2 订阅的市场集合。

前置条件：L1 `make smoke-health-prod` 不是 fail；L2 `make smoke-l2-health-prod` 证明 `/healthz` 可达；操作者有读取生产 health 和 Supabase read model 的权限；要跑 L3 dry-run 时，本地 `.env` 需有现有 Supabase 读取配置。

1. 跑 `make smoke-health-prod` 确认 L1 快照链的 strict 状态，再跑 `make smoke-l2-health-prod` 确认 L2 路由可达；后者不是 strict 通过证明。
2. 跑 `make smoke-l2-health-strict-prod` 读 L2 strict `/health`，确认 `event_bus:cursor_lag=0`、`event_bus:last_reconciliation_age_seconds` 在阈值内，以及 `candidates:supabase_fetch_age_seconds` 为 pass。这三项分别证明账本追平、轮询仍在工作、候选源数据取得成功。
3. 查看 `ws:subscribed_count` 与当前 candidate 数；要观察哪些市场符合 L3 推广条件时，跑 `make l3-promote-dry-run`。该 target 可读生产 Supabase 并计算 `proposed_active`，但显式禁用 WS add/remove、`l3_promoted_at_ts`、LKG、module active state 与 freshness anchor 的全部 mutation；输出是提案，不是“运行后 active state”。

停止条件：L1 或 L2 strict health 为 fail；cursor lag 超过 grace 后仍不归零；reconciliation 或 candidate fetch stale/fail；候选数与 WS 订阅持续不收敛。命中任一条都停止将候选链当作新鲜输入，先按第 7–8 节诊断。

### 本地验证

- `make sync-structure-local` 会从 Gamma 写入一版完整 Structure；这是本地 mutation，但**不**请求 CLOB、不写 Parquet/R2，也不产生可交易价格。它是本地验证 M1→M2 市场成员关系的最短路径。
- `make archive-markets-local` 才会做完整 CLOB/Parquet 历史归档；这是明确的研究/审计 mutation，可能耗时和占用磁盘。无论成功或失败，都不会替换当前 Structure 的 `markets` 视图。
- 旧的 `make snapshot-markets-v` 保留给历史兼容工具；它产出的 `legacy_combined` 不能作为切换后的 M2 输入证据。
- `make overview` 读最近一次本地 SQLite；零行时先检查本地快照而不是猜测生产异常。
- `make scan-l3-seed` 只读当前本地 snapshot，按 non-null Yes token、mid 0.1–0.9、liquidity ≥500、liquidity 降序/market ID 升序列出最多 100 个代表性 L3 seed；它不等于 promotion，也不改变生产候选或订阅。
- `make daemon-run-local` 在本地启动 L1，`make daemon-l2-run-local` 在本地启动 L2；它们都会持续运行并可写本地状态，Ctrl-C 停止。

### 本地 known-universe quote 首次路径

```bash
# CLOB 只读；仅写本地 data/state.db，不是 cron 或生产任务
make collect-neg-risk-quotes db=data/state.db

# 仅扫描同一 complete run；任一时钟 stale/unavailable 都非零退出
make scan-arb-quotes db=data/state.db min_edge_bps=0 \
  max_quote_age_s=300 max_universe_age_s=50400
```

`collect-neg-risk-quotes` 的 universe 必须来自最新 complete、published snapshot，
并且只收入 exact event membership 已匹配的 standard neg-risk 组。故新上市的
neg-risk 组要等下一次 snapshot 才会进入下一轮收集；它不会补读或混用别的 run。`scan-arb-quotes`
只报告 gross-before-fees，不是 order instruction。HTTP 入口若返回 503，表示 run、quote 或
universe 不可用/过期，绝不是“0 条机会”。2026-07-26 的 1,278/1,278 报价运行
只证明对当时本地子集的采集能力；后来证实旧 offset 分页在第 2,100 行 HTTP 422
后把截断误认成结束，因此这组历史证据不再证明 M2 可用性。

旧链路的问题不是“少几行无所谓”：Michigan 事件 `111080` 在截断视图中只剩两条腿，
实际事件结构有 33 个成员且属于 augmented neg-risk。新链路使用 markets/events
keyset 的终止 cursor 证明全集，再以 event 内嵌成员生成 exact membership hash；
augmented 组保留在拒绝统计中，原因
`augmented-neg-risk-not-supported`，绝不进入 standard buy-all 候选。

生产 feed 的每个候选必须同时带：

- `event_id` 与 `membership_hash`：证明属于哪个完整事件结构；
- `source_snapshot_id` 与 `universe_hash`：证明来自哪次完整发布和哪套腿；
- `quote_run_id`：证明各腿报价属于同一原子 run。

缺少任一身份，或顶层 coverage 不是 `verified-standard-neg-risk`，诊断命令都拒绝。

### Opportunity-first 按组盯盘（Slice B，尚未生产启用）

仓库现已具备按一个完整 neg-risk 组采集 top books 的 Candidate Watcher。它在请求前后
读取同一组的 `membership_hash`，只有成员未变化、全部有序 Yes token 都返回可执行
ask/size 时，才发布一个原子 `quote_batch_id`。成员变化或缺腿只影响该组，不再要求
一次十分钟级的全市场采集成为在线机会的统一闸门。

该能力由 `POLYARB_OPPORTUNITY_FIRST_WATCHER_ENABLED` 控制，默认是 `false`。
当前没有新增 operator 命令，也不得仅因代码存在就把它打开或描述为已经生产切换。
后续还需要滚动 Discovery、checkpoint Reconciliation、incident/资源隔离、公开 API、
Dashboard 和故障资格门。旧 `/arbitrage/opportunities` 与 known-universe Quote 路径
在这些门完成前保持不变。

Candidate 的初始控制输入是
`POLYARB_CANDIDATE_HIGH_INTERVAL_S`、`POLYARB_CANDIDATE_NORMAL_INTERVAL_S`、
`POLYARB_CANDIDATE_EXPLORE_INTERVAL_S` 和
`POLYARB_CANDIDATE_QUOTE_HARD_STALE_S`。每轮工作上限、lower-lane 保留槽、
per-group timeout 和 supervisor retry 分别由
`POLYARB_CANDIDATE_CYCLE_MAX_GROUPS`、
`POLYARB_CANDIDATE_RESERVED_NON_HIGH_SLOTS`、
`POLYARB_CANDIDATE_GROUP_TIMEOUT_S`、
`POLYARB_CANDIDATE_HIGH_BURST_GROUPS` 和
`POLYARB_CANDIDATE_LOWER_LANE_MAX_WAIT_S`，以及
`POLYARB_CANDIDATE_SUPERVISOR_RETRY_S` 控制；scheduler 空转轮询由
`POLYARB_CANDIDATE_SCHEDULER_POLL_S` 控制。所有时间值必须是正有限数，high interval
不能大于 hard-stale。默认每轮 12 组中保留 3 槽，且始终要求至少
`ceil(cycle_max_groups * 20%)` 给 normal/explore。顺序确定为“首段 high（默认 1 组）
→ 保留 lower lanes → 其余已选工作”，所以 hot 至少先服务一组，排队 high 不能先耗光
lower 的时间预算。`high_burst * group_timeout` 必须严格小于 lower 最大等待；该等待可
调严但不能高于生产验收的 120 秒。high burst 还不能超过 high CLOB worker 数。
normal/explore 基准周期可以高于 high hard-stale，它们不代表 high freshness SLA。

同步 CLOB SDK 的资源隔离由 `POLYARB_CANDIDATE_HIGH_CLOB_WORKERS`（默认 2）和
`POLYARB_CANDIDATE_LOWER_CLOB_WORKERS`（默认 1）控制。high 与 normal/explore 使用
不同的有限线程池，不占用 SQLite/Structure 的默认 executor。per-group timeout 会让
scheduler 继续，但不能强杀已经运行的同步 SDK 调用；关闭时只取消未开始的 future，
运行中调用仍受 CLOB HTTP timeout 约束。

有效间隔、原因和下一次到期时间会随每次终态写入 SQLite；它们是后续 API/Dashboard
的事实源，不是仅存在内存里的日志。source/cycle supervisor 与 per-group degraded
状态分开统计：单组只有在同组下一次成功时才记 recovery，其他组成功不会清除它。

### Bounded Discovery（Slice C，尚未生产启用）

滚动 Discovery 每次只读取一个最多 100 events 的 Gamma keyset 页面。它复用现有
event/market normalizer；只有完整 standard neg-risk membership 同时具备每腿
market ID、condition ID、Yes token 和标题时，才在同一事务发布 certified revision、
priority schedule、promotion、coverage sample 和 opaque next cursor。身份不完整或
unsupported 的组会留下有界拒绝原因但不 promotion；传输、normalization 或写入失败时
整个页面回滚，cursor 不前进。

`POLYARB_OPPORTUNITY_DISCOVERY_ENABLED` 默认 `false`；页面大小和周期分别由
`POLYARB_DISCOVERY_PAGE_LIMIT`（1-100）与 `POLYARB_DISCOVERY_INTERVAL_S` 控制。
首次 Candidate 启动承诺由 `POLYARB_DISCOVERY_CANDIDATE_MAX_WAIT_S` 控制，默认且最大
均为 60 秒。complete-supported 组先认证并进入 durable queue；只有满足
`poll + bounded selection + capacity × attempt-start SQLite write + (high burst + prior
admitted slots) × (group timeout + terminal-write busy budget) ≤ 60s` 的 factless
集合才 admission/promotion。所有预算按毫秒向上取整；默认 effective capacity 为 1、
effective start bound 为 47 秒。超量组保持 unpromoted，
按 queue deadline、score、group ID 等待，前一组写入终态事实时同事务 admit 下一组。
attempt-start 不是 scheduler 的前置推测：它是 watcher 入口第一条取消安全事务，
绑定 event/membership/promotion/deadline；若已超时则同事务写 unavailable、释放槽位并
跳过 Structure 与 books。
每次真实 admission 会同步追加 audit（身份、promotion/deadline、完整 capacity proof）；
状态页只接受能 exact join audit 且 revision 在 promotion 前已认证的 attempt。
首次 incomplete/unsupported sample 合法地没有 revision，状态校验不会误报；只有
complete-supported sample 必须提供 batch 时点前的精确 revision。
所有 sample 同时写 append-only schedule evidence；状态按 batch/time/identity/
quality/reason/promotion exact join，因此历史拒绝样本即使字段表面合法也不能改成 ghost。
promotion 使用 normal/explore 保留容量且排在 genuine high burst 之后，不会被重标为
global high。degraded 探针周期由
`POLYARB_DISCOVERY_DEGRADED_PROBE_EVERY_CYCLES` 控制：N-1 轮 yield 后最多放行一个
有界页面，phase/streak/modulus 持久化，重启不能重置。即使打开，也只会
对“独立 bootstrap authority + 已有 durable Candidate fact 的 current certified
authority + admitted promotion”
的 matching complete Quote 做一次 durable p95/missing snapshot；尚未 watch/admission
的认证排队组不制造 missing-Quote degradation，unavailable fact 不刷新 Quote age。
缺 Quote 或 p95 接近 hard-stale 时先 yield。Discovery
promotion 与 legacy active masters 组成去重并集，接入不会丢掉旧 hot candidates；
首次 Candidate 终态前按持久化 Decimal score 排序，之后由 durable due time 接管。

本地只读巡检：

```bash
make perception-discovery-status db_path=/path/to/state.db
```

输出完整 cursor/sweep receipt chain、最近 batch、promotion queue、effective
admission capacity/60 秒启动上界、attempt-start receipt/deadline breach readiness、
degraded streak/modulus/decision、最老 visit，
以及 15/30/60 分钟 raw 和 liquidity-weighted active-known coverage。低覆盖是有效
业务事实，命令仍返回 0；
数据库不可读、schema 无效或 cursor/promotion/Decimal/coverage 语义链损坏才非零。
所有字段来自一个 SQLite read transaction，不混合并发提交前后的事实。该覆盖是滚动
统计，不是“任何新套利组都不漏”。
Discovery receipt 超过 8,000 行后会先完整验证，再在同一事务将已完成前缀压成
版本化 checkpoint，保留约 1,000 行后缀。checkpoint 绑定完成 batch、逐组
sample/schedule evidence、coverage seed、累计计数和 prefix digest；后续 status
只重放 checkpoint 后缀。checkpoint 篡改、前缀重新注入或 prune 失败均 fail closed，
旧库迁移只接受可验证历史且可重复执行。
通用 `init_schema()` 只做 additive/idempotent schema 与 receipt sequence migration，
不会在 active Settings 生效前擅自设 capacity 或 demote。只有启用的 Discovery/
Candidate wiring 调用显式 admission configure transaction，才按真实配置持久化 proof
并确定性 reconcile legacy factless promotions。
### Checkpointed Full Reconciliation（Slice D，尚未生产启用）

Full Reconciliation 是低优先级校准作业，不是在线发布门。每次 batch 最多读取一个
Gamma event 页面，并在一个事务写 staging groups、batch receipt、window counts 和
opaque next cursor。只有 upstream terminal 空页才把 window 标为 `complete`；随后在
一个 `BEGIN IMMEDIATE` 事务发布 added/changed/closed/unchanged/rejected diff。
`open` 窗口永不修改在线 group revision。进程在 terminal receipt 后死亡会留下可恢复的
`complete`，重启先幂等 apply，不重新从第一页抓取。
窗口开始事务会保存 exact current-certified baseline；change/closure 都要求 apply 时
current 仍精确匹配该 baseline，不依赖可能同毫秒或回拨的 observed timestamp。
baseline 另有带 domain/version/count 的 canonical digest；等行数替换也会 fail
closed，旧无 digest 窗口新建重扫而不猜测回填。terminal receipt 还要求
event/candidate/sample 与 observed/unique/update/duplicate/rejected 全部为零。跨页
重复 group 写 append-only samples：相同事实 de-dup，变化 latest-wins；receipt 保留
observed/unique/update/duplicate/rejected 计数。cursor 指回当前或历史位置时窗口持久化
为 `failed/cursor-loop` 且绝不 apply，下一轮从新窗口第一页恢复，不会永久卡在同一
checkpoint。

```bash
# 本地 mutation：推进一个 bounded page
make reconcile-market-map

# 只读 checkpoint/window/counts
make reconciliation-status db_path=/path/to/state.db
```

`POLYARB_OPPORTUNITY_RECONCILIATION_ENABLED` 默认 `false`。旧 universe-sized
Structure loop 由独立的
`POLYARB_LEGACY_STRUCTURE_RECONCILIATION_ENABLED=false` 控制；其历史尝试和自适应
时长证据保留，但默认不再运行。health 的
`perception:reconciliation_progress` 与
`perception:reconciliation_checkpoint_age_seconds` 直接读取 checkpoint 和最后一条
receipt；它们不改变 Candidate/整体 availability。并发 Discovery 发布了更晚 revision
时，reconciliation 计 unchanged 而不覆盖；closure 只作用于 baseline 中、完整窗口
未观察且 current 仍 exact-match 的 certified group。incomplete/unsupported identity
记 rejected；只有 group/event 能绑定 baseline 才能保守抑制 closure，attacker event
不能用相同 group ID 掩盖真实缺失。apply 同事务写逐组
added/changed/closed/unchanged/rejected evidence，绑定 baseline、最终 staging 和实际
result revision；validator 从 evidence 重算五项计数。applied rejected 表示最终
rejected group 数，不是跨页历史 rejected observation 总数。
每个成功 reconciliation page 还会推进 authority checkpoint，绑定 exact window、
staging digest/count、最新 receipt、seen cursors 和累计 page metrics，再原子删除被
替代的 page receipt/sample。status 因而验证 checkpoint 加有界 suffix，而不是运行越久
扫描越多；apply、cursor-loop 和 legacy migration 仍保留上述 baseline/diff 语义，任何
checkpoint/staging/prefix 不一致都 fail closed。

## 5. L1/L2/L3 数据与新鲜度契约

L1 是广覆盖、低频的市场事实切片。`snapshot:last_success_age_seconds` 表示最后一次
成功发布快照的年龄；“请求成功”或“有行”都不等于市场全集。它与
`snapshot:latest_attempt` 必须一起看：前者说明市场事实多久未更新，后者说明最新一次
调度尝试的结果；因此新 OOM 不会被旧的成功快照掩盖。`snapshot:failure_counter` 显示
连续失败趋势，达到 5 时 strict health 失败且调度器进入可见的 `RECOVERING`；
producer 仍按短延迟主动续跑，不会永久停产。`snapshot:structure_sync` 显示当前 durable
窗口处于 events、markets 还是 publish，以及两类已原子提交的页数。`market_truth:coverage`
读取最新尝试，分页失败、membership 不完整或未发布都会 fail；即便
`market_truth:last_complete_age_seconds` 仍能指出一个较旧的完整版本，最新失败也不会
被它掩盖。`snapshot:schedule` 显示 Structure 当前真正使用的 timeout/cadence、
成功样本数、p95 和调整原因，并分别公开 45 秒协作 generation checkpoint、75 秒
Gamma/generation child 硬上限与 ready publication 的 15 秒 pointer-switch 硬期限；不再有
180 秒 finalizer 预算。health 对 running attempt 的超时判断读取入场阶段对应的真实
attempt timeout，而不是静态默认值。Quote-priority defer 另记为 warn receipt，拿锁前后的
排队时间都不伪装成 running attempt 或 child runtime。Supabase 镜像和 R2 归档是独立故障域。
Task 8 起，`/health` 与 `/healthz` 还返回同一进程稳定的 `releaseId`、
`machineId`、UUID `bootId` 和 release-bound `qualificationPolicy`；任何一项在采集
窗口中改变都会拒绝整段证据，不能把 rolling deploy 两侧样本拼成一次资格判定。
Candidate 的 CLOB 缺腿、HTTP 429、有界组超时和 SQLite `BUSY/LOCKED` 会分别持久化为
`clob-missing-leg`、`clob-429`、`clob-latency`、`sqlite-busy`，scope 固定为
`candidate:<group_id>`。它们会出现在 Incident Dashboard/API，而不是只留在日志；
只有同一 group、同一当前 membership 的新原子 Quote success receipt 才能 verified。
Candidate 先原子提交本组终态事实，再在本轮 reserved lane 服务结束后统一推进 Incident，
避免 Incident SQLite 写入抢占 normal/explore 的连续性预算。
Resource controller 每轮还把数据库所在文件系统的 free bytes 和
`1m load / cpu_count` 写入同一 authenticated sample/decision history。低于
`POLYARB_RESOURCE_MIN_DISK_FREE_MB`（默认 128）时产生
`resource-disk-pressure`；达到 `POLYARB_RESOURCE_MAX_LOAD_PER_CPU`（默认 2.0）
时产生 `resource-contention`。两者先进入 `protect-hot-path`，只允许更新的
`mode=normal + health_claimed=true` Resource decision verified；Dashboard 的
Resource history 是传感器事实，Incident 面板是处置 lifecycle，两者不能互相替代。

只有标记为 **Structure** 的完整发布版本才会被 strict health、报价运行和 M2 输入认可。
它只读取 Gamma 并保留最终 event/member reconciliation；CLOB 价格必须由独立 Quote run 提供。
此前的 `legacy_combined` 快照仍可用于历史研究，但不能证明当前市场结构。`archive` 是显式的
Parquet/R2 研究产品；它失败时 health 会显示 `archive:*` warning，但不会阻断 Structure、Quote
或 M2。生产尚未部署这次切换，所以生产状态仍以 CURRENT 和生产 health 为准，不能把本地
Structure 测试说成已迁移的生产版本。

L1→L2 有两个互补机制：**NOTIFY 是门铃**，只告诉 L2 “可能有新快照，来看一眼”；**durable cursor 是账本**，记录已处理到哪个 snapshot。门铃丢了可以靠 poll/reconciliation 补读，但 cursor lag 持续增长意味着账本没跟上，不能因为 listener 还连着就忽略。

L2 还要分开两种“活着”：WS transport liveness 是 TCP/PING/PONG 和连接状态；business frame freshness 是最近一个真实市场业务帧的年龄。前者可以在后者冻结时仍显得正常，因此必须同看 `ws:connection_state` 和 `ws:last_event_age_seconds`。`mirror:l2_tob_age_seconds` 再证明业务帧确实写到了镜像，而不是只被接收。

L3 是覆盖最小、频率最高的深度证据层。`l3:active_count` 的严格目标是 5 个市场×2 tokens = 10；`0/10` 是 under-filled/证据不足，不能用 OHLC 页面外观代替 active set 和 book-level freshness 的闭环。更深设计见 [10-L2 跟踪](learning/10-L2-跟踪.md) 和 [11-L3 K 线](learning/11-L3-K线.md)。

### L3 24h R08 精确门

R08 不是“五个检查点都看起来绿”，而是对同一个 manifest 和同一个 boot 的完整区间判定：

- `sample interval = 30s`，实际相邻/边界 `sample gap ≤ 75s`；
- `promoter interval = 300s`，每次 `promoter start gap ≤ 360s`，且 tick 连续、结果均为 success；
- 每市场 `book / OHLC age < 120s`；
- 固定 `5 markets / 10 tokens`，每个过程样本必须保持 `10/10/10 desired/committed/evidenced`；
- 精确窗口覆盖 `all 10 book tokens` 和 `all 5 Yes OHLC`；
- 同一 boot、release、machine/version、image digest、mapping 和 `AcceptanceConfig`；`schema revision 007`、recipe/code identity 不得漂移；
- 默认拒绝 `watchdog_stale`、`reconnect_failed`、`subscription_control_failed`、`evidence_writer_failed`，判定只看 event kind，不受可变 severity 影响；
- 最终窗口必须恰好 24 小时，五张证据表的 `recorded_at` 和原始行 hash 都要能重查；`retention ≥ 30 days`。

L2 release 37 只证明旧实现曾达到 10/10 和真实深度写入。由于当时的六小时人工检查无法覆盖中间的 promoter、membership、writer 和五市场 freshness，release 37 已明确降级为 `diagnostic-only`，不能绑定新 manifest，也不能作为 R08 strict PASS。

当前 production 已是 Alembic 007，runtime/retention 使用两个隔离角色。最终
release 72 / boot `9eeab4d5…` 的 A7 精确窗口已经完成 T0/T6/T12/T18/T24：
2,880 个 health row、14,400 个 market row、288/288 promoter tick 均通过，
final verifier 重新查询原始行并复现相同 hash。

随后 release 73 在真实 promoter 边界暴露了重连期间的部分证据采样问题，因此不能
用旧 A7 替代当前代码的连续性证明。修复后 release 75 / boot `d029c2ea…` 已通过
真实 promoter、quiet refresh 和新窗口 T0；其 T+6/T+12/T+18/T+24 由上述
`launchd` 定时器自动收集。最终边界是
`2026-07-27T08:51:13.206077Z`，此前不得宣称修复后的 24 小时窗口完成。

## 6. 如何解读结果与实战边界

一条 neg-risk 机会记录只是当时可观察的 gross-before-fees 输入。从“有 edge”到“可部署策略”至少还有六个缺口：

- **fee**：交易费、gas/转账和其他成本尚未从 gross edge 中完整扣除。
- **slippage**：显示的 best ask 不代表整个仓位都能以该价成交。
- **fill**：多腿不保证同时成交，部分成交会留下方向性暴露。
- **oracle**：结算规则、数据源和争议可以使“数学闭环”不等于“可兑付闭环”。
- **risk/capital approval**：认证、allowance、单市场/单日限额、kill switch 和人工资金批准都尚未成为 live gate。
- **sustainable return**：一次或少量命中不能证明机会频率、容量、存活时间和回撤后的可持续收益。

因此，本手册中的 M1 输出、健康绿灯、Dashboard 结果和 paper 证据均**不构成真实资金下单授权**。详细验收步骤链接到 [端到端验收指南](E2E_ACCEPTANCE_GUIDE.md)，不在这里复制一份会漂移的流程。

| `diagnose-arb-feed-prod` → `available-opportunities` | exit=0、`count>0`、payload 可解析 | 只表示观察到 gross-before-fees 输入；仍需费用、滑点、成交、oracle 和资金门控。 |
| `diagnose-arb-feed-prod` → `stale-snapshot` | HTTP 503 body 的快照年龄 | 上游快照超过 SLA；停止依赖该 feed，保存证据并排查 producer cadence。 |
| `diagnose-arb-feed-prod` → `feed-unavailable` | HTTP 503 非快照错误或其他非 200 | endpoint 不可用，不是 0 条；保留 body 后按 H-008 只读 chain-truth 诊断。 |
| `diagnose-arb-feed-prod` → `invalid-response` | HTTP 200 但 JSON/schema 不合法 | 不把意外 200 降格成零机会；保存 body，排查 endpoint 合同。 |
| `diagnose-arb-feed-prod` → `transport-error` | curl 本身失败、固定 JSON、exit=2 | 网络/DNS/TLS 等传输失败；没有 HTTP 语义，不能推断机会数量。 |
| `scan-arb-quotes` 非零退出 | `quote run unavailable`、quote age 或 universe age | 不回退到 snapshot best ask，也不输出零机会；先检查本地 snapshot、complete run 和两个时钟。 |
| Dashboard 显示登录页/401 | Vercel Auth 会话与白名单 | 这是受保护产品页的预期访问控制，不替代事故入口；直接打开 Fly `/perception/console`。若 console 非 200，Polywatch 才按 operator-visibility 故障报警。 |
| Polywatch opportunity 报警 | L1 `market_truth:*`、`quote_feed:*` 和 `/arbitrage/opportunities?min_edge_bps=0` | market truth 不完整、endpoint 不可达或 verified coverage/response 合同错误会报警；只有完整 verified payload 的空列表才不会报警。 |
| Polywatch L3 报警 | `l3:active_count` 与四个 strict evidence 子检查 | 必须 10 tokens 且 evidence、ledger、membership、worst freshness 全 pass；单独 `WAITING_FOR_EVENT` 且数据新鲜不会报警。 |
| Polywatch Dashboard 报警 | Vercel 产品路由与 Fly console 两个首个响应 | Vercel 302/307 是受保护产品页可达；Vercel `DEPLOYMENT_NOT_FOUND`、5xx 或传输失败仍报警。Fly `/perception/console` 只有 200 健康，其他状态或传输失败是直接的 operator-visibility 故障。 |
| Polywatch 没有按 GitHub `*/5` 准点 | `make polywatch-resident-status`，必要时 `make polywatch-resident-repair` | Fly cron 每 2 分钟是生产主监控；GitHub 每 5 分钟只作异地兜底且可能抖动。先确认 cron 状态；stopped 会由外部 watchdog 自动 start 并 Telegram 通知，缺失/重复/未验证恢复必须升级处理。 |
| R2 warning | L1 `r2:upload_recent_success` | 归档路径降级不自动否定 SQLite 快照，但必须记录并恢复冷存储保护。 |

## 8. 运维与恢复

**永远从只读诊断开始**：保存 strict `/health` body、release/instance 识别、首次异常时间，再读日志和上游新鲜度。先确定是本地路径、候选版本、还是当前生产实例；先定位故障域，再选恢复动作。

Structure generation 上线固定门禁是 **schema deploy → bounded backfill → compare PASS → 显式设为
`generation` mode → natural publication**。行复制完成不是发布；只有带认证 receipt 的 atomic
**pointer switch** 才是新代可见的发布事件。回滚只把 read mode 恢复为 `legacy`，不删证据、
不修改指针；任何操作命令都不会自动切模式。

- `make structure-generation-status`：只读 pointer、publication stage/cursor/checkpoint age、comparison 与保留压力。
- `make structure-generation-backfill max_rows=500 max_chunks=100 max_elapsed_seconds=60`：生产恢复批处理示例；一个进程只初始化
  一次 store/schema，然后最多推进 100 个 durable 有界块。默认 `max_chunks=1`、
  `max_elapsed_seconds=30`；单 chunk `max_rows<=500`、批次总行数不超过 50,000、最多 100 chunks/
  60 秒，重复到聚合 JSON 的 `final_progress.complete=true`。该 operator 命令使用独立 250ms writer admission；SQLite writer busy 时在
  约 1 秒内 exit 0，输出 `deferred=true,defer_reason=writer-busy,copied_rows=0`，表示可重试
  且本次未创建 attempt/failure/partial progress，不能解读为 complete。释放 writer 后重跑同一
  `make` 命令；这里只按 SQLite `SQLITE_BUSY` / `SQLITE_LOCKED` primary result code（含扩展码）
  判定竞争，其他 OperationalError 必须失败透传。若 bootstrap 已提交 blocked progress 后旋转
  successor 再遇竞争，命令会 exit 1 并明确输出 `mutated=true,blocked=true,rotation_pending=true`，
  绝不会谎报 zero-write deferred；正常 scheduler 的 busy timeout/rollback 语义不变。若升级前的 complete Structure
  window 尚缺 event→market 关系，命令先输出
  `phase=event-market-bootstrap`、`window_id`、`event_cursor`、`member_offset` 和 `blocked`；
  每个 chunk 同时限制 event 数和关系写入数，默认 500、硬上限 500。63,919 个 legacy event 在
  `max_rows=500,max_chunks=100` 下至少 2 个进程批次；若嵌套关系超过 event 数，还需按关系预算继续，单个巨大
  event 也会由 `member_offset` 跨调用续跑。fresh 事件页只持久 raw event，不在采集事务内
  展开关系；最终 market 页原子绑定 complete-window identity 后，fresh/legacy 才走同一
  bounded bootstrap。无效 JSON/member 或单 event raw payload 超过 1,000,000 bytes 会在
  `json.loads` 前持久 `blocked=true`；每次调用还以 metadata cursor 流式取数，raw decode
  总量硬封顶 16,000,000 bytes，不会因批处理预取数 GB payload。scheduler/命令
  以 CAS 保留旧窗口
  为 failed evidence 并新建 open successor 重采；持久 recovery-root 让 successor 再因 cursor restart
  时仍属同一恢复 lineage。append-only rotation observation 在旧 staging/window 清理后仍独立
  保留并每次重算 digest；最终 lineage successor 完成时在同一事务封存独立
  append-only recovery receipt，因此后续 retention 清理该 successor 也不会复活历史故障。
  bootstrap 完成前持续让 strict health fail，恢复后保留历史但不污染 current health。
  禁止直接清空 blocked evidence。fresh bootstrap 是 warn，blocked/recovering 或 checkpoint 超
  Structure SLA 是 fail。
- `make structure-generation-compare`：只读 authenticated receipt；仅 `matches=true` / exit 0 是 PASS。
- `make structure-generation-drift-compare`：只读当前 exact 或 sealed drift-safe receipt；仅
  `authorized=true` 且 `authorization_mode=exact|drift-safe-sealed` / exit 0 是 PASS。该命令不创建或推进
  drift comparison、不切换 pointer/read mode；incomplete、stale、class conflict、unclassified、digest 或
  当前身份不一致均 exit nonzero。
  新 drift 证据固定使用 `hash_algorithm=row-chain-sha256-v2`。升级发现 active v1 progress 时，会原子记录
  `phase=stale, terminal_reason=drift-hash-algorithm-superseded` 并从 v2 cursor zero 重启；旧 sealed v1
  receipt 仍可审计但不能授权 v2。这个 stale 只描述比较证据，不表示 legacy serving plane 长期降级。
  exact receipt 授权路径保持独立。v2 receipt 同时认证 generation-domain audit roots 与
  projection/source-domain comparison mirror roots/counts；两侧 canonical rows 的严格相等只比较同 domain
  commitment，任一 audit/mirror/progress/receipt 替换都 fail closed。schema 初始化会幂等补齐 receipt
  comparison 列和 `(snapshot_id,market_id,...)` scan indexes；初始化失败时停止验收并修复，禁止绕过。
  写侧默认关闭；受控启用后仍只由 scheduler 在 Quote 双检和共享 producer lock 内启动隔离 child。每个
  child chunk 最多 500 行并独立 CAS，单 slice 最多 100 chunks / 45 秒；parent 75 秒 hard timeout，
  TERM 后 15 秒仍未退出才 KILL。writer busy 保留已提交 cursor 且不增加 Structure failure counter。
  其中 `source-events` 因每行还会展开 embedded markets/group truth，先取最多 100 events，再按累计 member
  workload ≤500、payload ≤512 KiB 选稳定前缀；正常单 event 至少推进1条，单 event 自身超限则
  `source-event-workload-oversized` fail closed、0 progress 并由 health 报警。global 500 上限和其它 phase 不变。parent timeout 后以最后一条 post-CAS marker 记录已提交 chunks/rows，
  不得把已推进的 cursor 伪记为 `0/0`。
  parent 必须先写专用 `structure_drift_attempts` ownership 才能 spawn；每个 checkpoint、成功、defer、timeout、
  SIGKILL、cancel 或 invalid JSON 都由 parent 终结并保留安全诊断，启动时回收 orphan，terminal 历史封顶 100 条。
  该账本不进入普通 `snapshot_attempts` 或 adaptive schedule；strict health 会引用最新 drift attempt。
  分类合同固定为 `structure-drift-classifier-v2`：v1 active progress 会原子变为
  `drift-classifier-contract-superseded`，v2 从 cursor zero 重启；历史 terminal evidence 不删除。
  同一 frozen identity 的 v2 stale terminal 不重试，等待下一 natural window/pointer identity，避免 deterministic
  retry storm。complete fresh projection 覆盖 market staging 与 event-only anti-join union；global relation conflict
  优先于 duplicate/quarantine/group-ineligible。`fresh-group-ineligible` 只解释仍 active 的 legacy sibling，且必须
  绑定 `complete-unsupported / standard-neg-risk-has-non-tradable-members` source truth。stale 状态只有 terminal
  receipt digest、diagnostic count/root、每 code 最多三条 sample 全部认证后才对 operator 暴露。
  Polywatch 将 authenticated terminal identity 作为 incident key：首次 push、相同 identity 去重/提醒；只有同一
  current identity 出现 sealed PASS 才发送 recovery，旧 comparison 的 PASS 不能关闭新 incident。
  生产 rollout 分两次 mutation：先在 Quote disabled 下切 generation read 并验证 natural publication/legacy
  rollback；稳定后才单独 enable Quote 并复验 freshness/candidate lifecycle。classifier PASS 本身不授权任一步。
- `make structure-generation-cleanup max_rows=500 retain_generations=2`：每次只在一个 component 删最多
  `max_rows` 行，durable progress 保证崩溃可续跑。当前代、rollback floor、active publication/comparison
  和 authenticated legacy proof skeleton 保留；证明不完整或身份变化时 fail closed，不得改用 generic purge。

`snapshot:structure_generation` 超 publication SLA 是 strict fail；正常 Quote-priority defer 是 warn，但 queued age
超同一 Structure SLA 必须升为 fail。
`snapshot:structure_generation_comparison` 把 bounded repair 中的 missing receipt 报为 recoverable warn；
`snapshot:structure_generation_evidence` 在超容量或 cleanup blocked 时 fail 并报警。

restart、deploy、修改 secrets 和 chaos 注入都是**生产 mutation**，需明确的目标 app/instance、授权、当前证据保存、回滚/清理路径和事后 strict `/health` 复验。不要因为 `/healthz` 仍为 200 就跳过这些门。

受控恢复顺序是：固化证据 → 确定单一故障域 → 选最小 mutation → 记录操作者/时间/对象 → 等待数据新鲜度窗口 → 同一 strict 检查复验 → 记录结果。仅路由恢复但 cursor/mirror 仍 stale 不算恢复完成。

## 9. 命令安全分级索引

### 日常只读

- `make structure-generation-status`、`make structure-generation-compare`、`make structure-generation-drift-compare`：前者仅用 SQLite read-only/query-only
  connection 读有界压力下界、pointer、active publication/comparison 与认证状态；后者只读 sealed
  comparison receipt；drift 命令只认证当前 exact 或 sealed drift-safe full identity。三者都不跑 schema
  init/repair、不推进比较、不切 read mode、不写 SQLite。
- `make perception-status`、`make perception-opportunities limit=100`、`make perception-groups limit=100`、`make perception-incidents limit=100`、`make perception-resources limit=100`：从云端机会优先读模型读取稳定 JSON。每次读取最多 500 项、HTTP 最长 10 秒；`opportunities.status=available,count=0,reason=no-certified-edge` 才是有效零机会，HTTP 503 / `unavailable` 表示 worker 或历史证据链不可用，不能解释成零机会。`perception-opportunities` 返回认证的当前机会行及 keyset cursor；`perception-resources` 返回当前资源决策、最近有界 sample/decision pairs 和 history floor。两者都不扫描无界完整历史。这些命令不读取 HMAC secret，也不调用生产者。
- `make status`：前置为仓库 checkout；成功表示读到当前文档与 checkout，不表示云服务健康。
- `make snapshot-status`、`make snapshot-attempt-status` 和 `make overview`：前置为本地快照 DB；成功只解读本地事实。`snapshot-attempt-status` 是 JSON 格式的最新一次调度尝试，`latest: null` 表示无记录，不表示成功。
- `make collect-neg-risk-quotes db=data/state.db`：CLOB 请求只读、但会把一个 complete-or-failed run 写进本地 SQLite；不是 production cron、部署或订单命令。`make scan-arb-quotes` 只读该本地 run；两者都不证明生产容量或 readiness。
- `make smoke-health-prod`、`make smoke-market-truth-prod`、`make smoke-l2-health-prod`、`make smoke-l2-health-strict-prod`、`make diagnose-arb-feed-prod min_edge_bps=0`：前置为网络可达；分别解读 L1 strict health、L1 最新市场全集发布、L2 `/healthz` 可达性、L2 strict health 和 verified 机会 feed。最后一个只有完整 verified payload 的 `available-zero`/`available-opportunities` 才 exit=0；其余状态均不是零机会。
- `make fly-l2-status` 和 `make fly-l2-logs`：前置为 flyctl keychain auth；是诊断性读取，日志可能含运维元数据，不对外粘贴。
- `make polywatch-resident-status`：前置为 flyctl keychain auth；只读主监控 cron machine、最近日志和告警/恢复状态。生产主监控每 2 分钟运行，GitHub 定时器不是准点 SLA。
- `make smoke-perception-dashboard`：前置为网络；只读探测 Vercel `/perception` 产品路由，HTTP 200 或 302/307 受保护重定向都表示路由可达；404、5xx 和传输失败都失败。`make smoke-operator-console` 只读探测 Fly `/perception/console`，只有 HTTP 200 才证明 on-call 可直接进入事故详情；它是 Polywatch 的 operator-visibility gate。两者都不证明 perception JSON 可用、数据新鲜或零机会。
- `https://polyarb-l1.fly.dev/perception/console`：Fly 同域的只读事故控制台，不依赖 Vercel 登录。它每 30 秒读取有界 `/perception/incidents?limit=100`，并联合读取 Quote/容量两类近 24 小时的已恢复事故及其 exact-ID lifecycle；因此恢复不会从操作者记录中“消失”。当前与最近恢复卡片均显示 severity、影响、自动动作、人工下一步、失败尝试号、重试与恢复证据，完整生命周期 JSON 可直达。Structure 的 `structure-producer-failure` 也以 P1 卡直接显示 `market-map-stale` 影响、`retry-bounded-structure-child` 自动动作、失败 stage/elapsed，以及 `inspect-stage-checkpoint-and-child-budget` 的处置路径；只有故障发生之后的持久化 `snapshot_attempts` 成功记录与同一 snapshot ID 才能把它验证关闭。Quote 超时时的失败尝试号来自刚刚终结的 durable attempt；尚未安全投影到 `quote_run_id` 时明确留空，绝不把上一轮成功 run 归因给这次故障。Quote supervisor 的 `child-*` 失败同样以 P1 显示：恢复中为 `retry-supervised-producer`，升级后为 `automatic-retries-exhausted`。新 supervisor 接管升级事件后，只有**接管之后**落库的 complete Quote run（run ID、完成时间、报价时间及成功计数全部一致）才会把 P1 自动转为 verified；旧成功 run 或单纯重启绝不能关闭它。此时先查看同卡的有界 producer receipt / recovery evidence，再按受控恢复顺序重启对应 producer，不能把遗留 open row 当作普通历史。daemon 自身会监督 supervisor：后者返回或异常后按有界退避重新创建，只有 daemon 停机才允许 Quote producer 消失。Vercel `/perception` 也把 `quote` 与 `quote-collection` 一并置顶为 P1 卡。任一 `read-model-unavailable` / `read-model-saturated` 必须按**操作者可见性故障**处置，绝不能解读为零事故。此页面没有任何控制按钮，不会重试生产者、删除数据或修改运行状态。
- `https://polyarb-l2.fly.dev/console`：L2 同域只读运维视图，实时渲染 strict `/health` 的每个 warn/fail。每张卡片给出 health check 名、影响、观测值、自动恢复状态、下一步人工处置和 raw evidence；例如 `ws:last_event_age_seconds` 指向 websocket/quiet-refresh 证据路径，`l3:evidence_sample_age_seconds` 明确要求检查 `evidence_timeout` 与 runtime-event queue，`l3:membership_convergence` 要求以 5 markets / 10 tokens 的新收据证明恢复。页面可达绝不等于 L2 健康；health 读取失败本身是 operator-visibility 故障。L1 incident console 提供直达该页面的链接；两页均没有控制按钮，不会重试生产者、删除数据或修改运行状态。
- Fly L1 已启用容量维护控制器：每 30 秒记录一次容量事实，活跃或即将执行的 Quote 优先并使维护 defer；仅在 pressure/critical/exhaustion 水位时才运行一次有界、FK-safe 的历史回收。incident 只有在**正回收 receipt**之后经过 hold 窗口得到 normal measurement 才能 verified；扩容、重启或零行回收都不能静默关闭容量事故。
- `make smoke-l2-dashboard`：前置为网络；200 只表示 candidates、asset TOB/trades 和 signals 路由或 Auth 页可达。L3 生产检查显式跑 `make smoke-l3-dashboard asset_id=<known-id> URL=https://polymarket-arbitrage-jiangwen-su-s-projects.vercel.app`，再用已认证浏览器验证内容并手工检查 `/status`。
- `make l3-evidence-status`：只读最新 boot、身份、membership 和证据连续性锚点；缺证据或不一致必须按 NOT-CLOSED 处理。
- `make l3-soak-checkpoint manifest=<path> start=<ISO> end=<ISO> output=<unique-path>`：只读精确 `[start,end)` 数据并以 O_EXCL 新建一个 canonical checkpoint；不会覆盖报告，也不会绑定 manifest。
- `make l3-soak-verify manifest=<path> start=<ISO> end=<ISO>`：只读重载 manifest 声明的 T+0/T+6/T+12/T+18/T+24 五份报告，逐份重查 raw rows/hash，最后要求精确 24h PASS。
- `make l3-evidence-retention-check`：只读五张证据表的 server `recorded_at` 范围与行数，验证配置和已成熟历史没有早于 30 天被删除。
- `make l3-runtime-credential-check expected_ref=<ref>`、`make l3-retention-operator-check expected_ref=<ref>` 和 `make supabase-prod-revision expected_ref=<ref> expected_revision=<rev>`：对应 DSN 必须显式带唯一的 `sslmode=require|verify-ca|verify-full`；检查还会用当前 PostgreSQL session 证明 TLS 已实际启用。runtime/retention 检查枚举递归角色成员关系、public 全部表/视图/序列有效权限和相关函数显式 ACL，任何额外 capability（包括 `pg_read_all_data`）、额外 public 对象权限、RLS 关闭或 restrictive cursor policy 都返回 NOT-CLOSED。输出只含目标、角色、布尔 TLS 证明和 sslmode，不含 DSN、cipher 或 secret。

### 本地 mutation

- `make structure-generation-backfill max_rows=500 max_chunks=100 max_elapsed_seconds=60`、`make structure-generation-cleanup max_rows=500
  retain_generations=2`：都会写本地 SQLite；backfill 单进程最多推进 100 个 durable bounded chunks，cleanup 每次只推进一个。backfill 不切换
  read mode；cleanup 只能删除 rollback floor 之外、已完整认证的旧 generation bulk rows，保留
